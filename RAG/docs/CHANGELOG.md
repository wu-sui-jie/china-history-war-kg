### 阶段内发现并修复的系统问题

RAGv4（6 项，均有复现与修复证据）：

1. **F02 朝代筛选机制缺陷**——问句朝代原为"字典别名子串匹配 + 硬过滤"，把被问到的朝代连同事件一起剔除，4 道题因此误拒答。终态改为**软偏置**：自动识别的朝代写入 `F02Output.dynasty_bias`，只在 F03/F04 排序前置、不剔除结果；只有 F01 下拉的显式筛选才是硬过滤。主套件由 ok 24/28 恢复到 28/28。
2. **F04 长改写问题纯 AND 必然 0 命中**——召回完全依赖 OR 兜底；已量化，策略优化留 v5（v5 由 hybrid 融合解决）。
3. **拒答缺口**——实体命中但"问题属性不存在"的越界问题不会被拒答；v5 补规则。
4. **F03 证据 ID 跨表重复**——`source_row_id` 只在各 legacy 表内唯一（实测 6,437 个行号跨表重复），证据 ID 改为 `graph_{legacy表名}_{行号}`，17,700 行 ID 全局唯一。
5. **跨进程非确定性**——`sorted(set(...), key=len, reverse=True)` 等长并列受 `PYTHONHASHSEED` 影响，两次 run 的证据顺序不一致，破坏"可重复运行"验收；并列改按词序，两次独立进程 run 内容级 0 差异。
6. **筛选损耗**——`filters-on` 时文本 top-k 召回 100%→0%（元数据缺失），已量化并留 v5 处理。

RAGv5（8 项）：

1. `np.save()` 会给非 `.npy` 文件名自动补后缀，导致全量向量构建中断、955 批白跑一半——修临时文件名并抢救已付费批次续传。
2. 评测报告用白名单过滤配置，跑了 112 条只列 2 个配置——未知配置改为追加在后，不再静默丢弃。
3. `--suites` 参数被逐字符迭代，v4 文档里的 `run --suites main` 从未真正跑通。
4. 离线回答的 SSE 增量丢换行（切分正则吃掉空白），流式拼出的答案与缓存回放不一致——重写切分，保证"拼接严格等于原文"。
5. 推理模型 `max_tokens` 被 reasoning 吃满 → 正文为空但 `finish_reason=normal`，演示可能得到空白回答——空正文一律降级离线回答器。
6. F02 兜底 `max_tokens=256` 同样被 reasoning 吃满，解析出空实体、兜底形同虚设——提到 1024。
7. 同上三处"静默"行为（参数/报告/构建）——均已修复并加守护用例。
8. **跨朝代同名事件答错对象**——问"西汉的井陉之战"仍选中战国那条；`_resolve_ambiguity` 增加问句朝代**偏好**（同名候选中朝代相符者前置、候选集合不变，不重蹈 v4"硬过滤整题清空"的坑），并新增 `dynasty_disambiguated` 可观测字段。

### 两处观测口径（记录在案，避免误读报告）

- `trace.finish_reason` 只有 `normal`/`degraded`/`refused`，**不反映截断**（截断仅日志告警）。
- `ok/n` 是"回答里出现标注词"的机械口径，真实 LLM 用自然语言作答会漏词（v4 是"28/28 ok 但 0 correct"，v5 是"24–26/28 ok 但回答更完整"）。**正确性以评分表为准。**

## 二、六轮审核整改主线（2026-09-15 ~ 09-16）

六轮都是**只读复核 + 整改**的形式：复核方读代码与文档、列出问题与工作单，实施方按单整改并附验证证据。逐轮结论：

| --- | --- | --- | --- |
| 第 1 轮 | 全项目审核（11 个模块） | 22 条问题（P0 4 / P1 10 / P2 8），9 个模块属实、2 个有缺口 | 22/22 处置完毕（代码 5 项、文档 17 项） |
| 第 2 轮 | 复查裁定 | — | 22/22 处置属实，无强制修改项 |

| 第 5 轮 | 独立复核 + 增量审核 | 13 项重裁定 + R5-1…R5-7 新增问题 | 已修 17 项；真实 demo 制品待付费评测 |
| 第 6 轮 | 独立复核（对象为第 5 轮的修改说明） | B1–B8 修复缺陷 + G1 高优先增量 + Z/D 级清查项 | 已修 19 项；余项为外部动作 |

### 第 1 轮的处置原则（后续各轮沿用）

当文档描述的是更早的设计意图、而现有代码行为已经过评测验证或已冻结为数据产物时，
**以代码现状为准回写文档**，而不是为对齐文档去改动已验证的行为或重建数据产物——
后者会造成新的版本错位。22 条里 17 条按此原则改文档。

### 第 4 轮的发布阻断（P0，均已修）

- `RAG_REQUIRE_ACTIVE_VERSION` 检查写在扫描分支之后，未指定版本时不可达——强制检查前移，生产模式下不存在"自动选最新目录"的路径。
- 整体 deadline 用心跳当等待上限，心跳为 0 时永久等待、心跳大于剩余时间时晚一个周期——改用 `time.monotonic()` 算剩余时间，每次等待取 `min(心跳, 剩余)`；超时按"是否已送出正文"区分 `interrupted`/`failed`，错误码独立为 `timeout`。
- `Runtime.shutdown()` 是同步方法，在运行中的事件循环里 `asyncio.run()` 必然抛错且被吞，异步客户端从未真正关闭——改为 `async def shutdown()` 并由 lifespan `await`。
- `health` 只报告 HEAD，脏工作区下无法定位源码——新增 `source_dirty`/`release_id`/`config_fingerprint`/`artifact_manifest_sha256`/`version_selection`/`demo_ready`。

### 第 5/6 轮遗留的外部动作（非代码问题）

- **P2-1 真实 demo 制品**：需要一次付费模型评测；由维护者在正式交付前执行（已于 2026-09-17 完成重建，见 current-status.md 第四节）。
- **远端 CI / release 绿色 run、干净 commit 上的发布演练**：需提交并推送后触发。
- 明确不处理项：前端 ESLint、SSE 同步 CPU 调用下沉、本机临时文件清理。

## 三、反复踩到、值得固化的约定

1. **版本必须显式固定**：`RAG_ACTIVE_VERSION` 由 `--version` 写入，health 用 `version_selection` 区分 `cli_explicit`/`env_pinned`/`latest_scan`。生产档（`RAG_REQUIRE_ACTIVE_VERSION=true`）下不再有"自动选最新目录"的路径。
2. **拒答口径要写在一处**：`server/generate/refusal.py` 是拒答判定与文案的归属地，在线（`server/sse.py`）与评测（`evaluation/chain.py`）共用，避免"评测拒答、线上不拒答"。
3. **评测绕过缓存**：缓存键已含文本检索模式与数据/模型版本，但跨配置共享仍会污染对比结论，故评测一律绕过。
4. **依赖声明与锁定分四个文件**：`requirements.txt`（人工，回答"要什么"）、`requirements-dev.txt`（人工，含测试依赖）、`requirements.lock` / `requirements-dev.lock`（工具生成，每条带多个 sha256，CI 与发布用 `--require-hashes` 安装）。锁文件体积大属正常。
5. **文档数字只有一处**：版本、测试数、数据计数只在 `docs/current-status.md` 维护，`scripts/check_docs.py --strict` 机械核对，避免同一数字在多份文档里各写一版。
6. **改字段先改契约**：涉及 `data-contract.md` 的字段调整，必须先更新该文件与 `contracts/`，再同步受影响的功能文档。
7. **GitHub Actions 全绿不等于发布就绪**：release 链路还要求干净 commit、数据制品 URL 与哈希、SBOM 与血缘一致。
