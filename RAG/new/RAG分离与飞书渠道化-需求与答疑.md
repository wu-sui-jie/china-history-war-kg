## 一、需求背景与目标

### 原始想法

1. 把 `RAG/` 从整个项目中**分离**出来，作为可独立部署的问答能力。
2. 普通用户不会在电脑上打开网页程序，而是用**手机 / 微信小程序 / IM** 这类入口，
   希望改成 **Hermes + 飞书**的方式，降低使用门槛。
3. 需要一套**触发机制**：例如用户预约时间发生变更后，由 Hermes 修改时间（提醒/日程）。

### 要达成的目标（可验收表述）

| 编号 | 目标 | 验收口径 |
| --- | --- | --- |
| R1 | RAG 可独立部署，不再依赖旧项目目录结构 | 拷贝 RAG 代码 + 数据制品到独立机器即可启动问答 |
| R2 | 用户通过飞书对话即可提问并获得带引用的回答 | 单聊/群聊 @机器人 提问，收到回答卡片 |
| R3 | 回答中的引用与知识面板在飞书内可用 | 引用可查看、实体/时间线有呈现、图谱有图片或文字降级，无空白 |
| R4 | 具备触发机制：预约时间变更后自动改期/重排提醒 | 改期事件（对话或 webhook）触发后，提醒按新时间生效 |
| R5 | 现有 Web 问答页保留，作为运营/演示通道 | Web 通道功能不回退 |

## 二、现状盘点

整个工程实际是「一条知识生产流水线 + 面向不同人群的三个产品面」：

| 模块 | 角色 | 使用者 | 形态 |
| --- | --- | --- | --- |
| `entity-event-relation/` | 数据生产：LLM 三轮抽取，产出图谱数据 | 开发者（离线） | Python 批处理 + 缓存 + P/R/F1 评测 |
| `backend/`、`frontend/` | 旧知识库系统：SQLite + Neo4j 双库，图谱可视化、节点 CRUD、质量工作台、旧问答 | 管理员/编辑 | Flask + Vue3 Web 后台 |
| `RAG/` | 新一代智能问答引擎：图谱 + 文本双通道 RAG，自包含 | 最终用户 | FastAPI + SSE + Vue3 SPA |

数据流：`entity-event-relation` 产出原文数据 → 旧库 →（F09 导出）→ `RAG/data/snapshot/` +
`RAG/data/index/` → 在线问答。

### RAG 的分离度评估（结论：天生可拆）

- RAG 为**独立仓库**，运行时不依赖旧后端、旧前端、Neo4j 是否启动，只读取自身目录下的治理快照与索引。
- 唯一耦合点是**离线导出**：`scripts/export_snapshot.py` 通过 `.env` 的
  `LEGACY_SQLITE_PATH` / `LEGACY_RAW_TEXTS` 一次性只读旧 SQLite 与原文。导出完成后，
  在线服务不再访问旧项目。
- 因此本需求不需要"解耦重构"，主要是**接口形态、鉴权会话、输出适配、部署打包**四件事。

### 在线面现状（决定改造范围）

对外接口只有 4 个：`POST /api/query`（SSE 流式问答）、`GET /api/health`、`GET /api/dicts`、
`GET /api/demo/examples`（F08 示例题）。

单次回答产出三类数据（统一定义见 `docs/data-contract.md` 与 `contracts/`）：

1. `answer`：Markdown 正文（带引用编号）
2. `citations`：引用列表（来源、原文片段、冲突标记）
3. `panel`：结构化知识面板 JSON —— 实体卡、图谱子图、时间线、地图点（无坐标自动降级为地点列表）

> 关键判断：**回答本质是「Markdown 文本 + 结构化 panel 数据」，没有任何浏览器独占能力**，
> 天生适合平移为 IM 卡片消息。改造难点不在算法链路，而在把 SSE 流与 panel 富展示翻译成聊天消息。

## 四、目标形态：拆成三层边界

原始想法里混在一起的三件事（拆 RAG、用户走手机、Hermes+飞书+触发）实际是三个不同边界：

```text
┌─────────────────────────────────────────────────────────────┐
│ 业务层（预约/提醒/日历等结构化业务数据）                        │
│ 预约系统 ──改期事件──▶ Hermes 触发器（webhook / 定时 / 意图）    │
└───────────────┬─────────────────────────────────────────────┘
                │ 按意图分流
┌───────────────▼─────────────────────────────────────────────┐
│ 渠道编排层 = Hermes（飞书机器人网关 + 会话 + 技能路由）          │
│  • 接收飞书消息（im.message.receive_v1 / @机器人）             │
│  • 触发机制：定时任务 / 业务变更 webhook / 消息事件             │
│  • 调用技能：改期、发提醒、写日历、查知识                        │
└───────┬───────────────────────────────┬─────────────────────┘
        │ 知识类问题走 RAG                │ 结构化动作直接调业务系统
┌───────▼───────────────────────────────┘
│ 引擎层 = RAG（保持现状，HTTP 化）                               │
│ 纯知识问答：Markdown 回答 + 引用 + panel                        │
└────────────────────────────────────────────────────────────────┘
```

**边界原则**：引擎层（RAG）只回答知识问题、无状态、不接触写操作；编排层（Hermes）是用户与引擎
之间的翻译官，也是所有"动作"与"触发"的归属地；业务层（预约系统）数据归谁管谁负责，通过事件通知 Hermes。

> 「用户预约时间改变后 Hermes 修改时间」——改的是**结构化预约/提醒数据，不是知识库**，
> 因此天然属于编排层 + 业务层。把它做进 RAG 是职责错位；让 RAG 专注只读知识问答，
> Hermes 专注动作与触发，这个边界本身就是最好的架构。

## 五、改造点清单（映射到代码）

### 5.1 引擎层：只新增一个非流式接口（小改动）

`POST /api/query` 是给浏览器流式消费的。Hermes/飞书需要"一次调用取完整结果"。
建议新增非流式 JSON 接口（如 `POST /api/query/json`，或给现有接口加 `stream=false` 参数），
内部复用 `server/sse.py` 的生成器在服务端聚合，**不改 F02–F06 任何链路**：

```json
{
  "answer_md": "……",
  "citations": [ /* 引用列表 */ ],
  "panel": { /* 实体卡/子图/时间线/地图点 */ },
  "finish_reason": "normal",
  "model_used": "……"
}
```

飞书侧先做整包回复；需要流式体验再走卡片增量更新（真 token 流另议）。

### 5.2 会话与身份（必须补，工作量中等）

现状：`session_id` 为调用方任意字符串、无鉴权、限流按 IP、`CORS` 全开。对外服务需要：

| 项 | 现状 | 目标 |
| --- | --- | --- |
| 会话标识 | 调用方任意传 | 由 Hermes 生成 = `open_id` + 群/单聊维度 |
| 多轮上下文 | 服务端按 `history_max_turns` 裁剪 | 群聊多用户共存时注意上下文隔离 |
| 鉴权 | 无 | RAG 与 Hermes 之间共享密钥/内网；飞书消息验签在 Hermes 层 |
| 限流 | 按 IP（进程内滑窗） | 按用户/会话维度，可通过请求头透传 |

### 5.3 输出翻译（把 Web 渲染换成消息可承载的形态）

| RAG 输出 | Web（现状） | 飞书对话对应 |
| --- | --- | --- |
| `answer` Markdown | MarkdownContent 渲染 | 卡片文本（飞书 md 子集，需白名单收敛） |
| `citations` | 右侧证据卡，可展开原文/跳转 | 回答末尾引用列表；片段放折叠卡片 |
| `panel` 实体卡/证据 | 标签页 + 折叠区 | 折叠卡片 / 交互按钮（"查看详情"再推一条） |
| `panel` 子图（echarts） | 前端绘图、节点可点击追问 | **服务端渲染成图片**（echarts SSR）或降级为分组文字列表 |
| `panel` 时间线 | TimelineView | 文字化时间轴 |
| `panel` 地图点 | 地图/列表降级 | 飞书地图卡片，或复用"无坐标→文字列表"降级 |

要点：子图/地图是 Web 独占最多的部分，**服务端出图为通用解法**；Web 版不删，与飞书通道共存，引擎只有一份。

### 5.4 部署与数据更新（决定"分离"是否彻底）

- 部署的关键不是代码而是**数据**：`data/snapshot`、`data/index` 被 `.gitignore` 忽略，原文有版权不进仓。
  正确姿势：内部机跑离线链路（F09 导出治理 + F11 建索引）→ 打包数据制品 → 拷贝/上传到服务器
  → 服务启动加载最新一致版本（版本校验 `server/runtime.py` 已具备）。
- 知识库更新 = 离线重建 + 换版本重启；这是**运维任务**，与用户触发的业务触发器无关，不可混淆。
  历史战争知识基本不变，无需实时数据同步。

### 5.5 不需要改动

F02 实体识别/消歧、F03 图谱检索、F04 文本检索、F05 融合/冲突/panel 装配、F06 生成与缓存、
F09/F11 离线链路、RAGv4 评测闭环均无需改动。接口适配完成后，可用 `evaluation/` 与
`data/eval/` 题库跑回归，防止适配过程破坏链路。

## 六、渠道选型：飞书 vs 微信小程序

| | 微信小程序 | 飞书（企业自建应用） |
| --- | --- | --- |
| 适合用户 | 外部**公众消费者** | 企业内员工、场馆工作人员、合作方/教育团体 |
| 资质与审核 | 需企业主体认证、服务类目、**每次发版走微信审核** | 企业内部应用免应用市场审核，迭代快 |
| 网络要求 | 服务器**必须公网 HTTPS + 备案域名** | 机器人支持**长连接模式，可不需要公网回调地址**，内网可跑 |
| 聊天式问答 | 需自建聊天 UI，并接内容安全合规 | **消息即交互**：卡片、@机器人、事件订阅、日程都是现成的 |
| 与预约/提醒结合 | 需自建推送（订阅消息） | 飞书自带日程、提醒、卡片回调 |

**工程结论**：用户是普通公众 → 微信小程序是终态，但重（备案、审核、合规）；用户是场馆导览 /
内部运营 / 受邀团体 → 飞书几乎零成本。推荐路径：**先飞书 + Hermes 打通"问答 + 触发"闭环，
未来若要面向公众，同一 RAG 引擎再挂小程序通道**（届时补 HTTPS/域名/审核），引擎层无需二次改动。

## 七、触发机制设计（以"预约改期"为例）

| 触发类型 | 例子 | 事件来源 |
| --- | --- | --- |
| 消息事件 | 用户说"把周三的讲解改到周六 10 点" | 飞书 `im.message.receive_v1`，Hermes 意图识别 |
| 定时任务 | 预约前 1 天 / 2 小时发提醒 | Hermes 定时器，提醒任务持久化（SQLite）防重启丢失 |
| 业务变更 webhook | 后台/小程序改了预约，系统主动推"改期事件" | 业务系统回调 → Hermes 接收、验签 |

```text
① 用户对话改期 / 业务系统改期 webhook
        ↓
② Hermes 触发服务收到事件（预约单号 + 旧时间 + 新时间）
        ↓
③ Hermes 调用预约系统确认改期（幂等：同一事件重复投递只生效一次）
        ↓
④ Hermes 重算后续提醒任务：
     旧提醒删除或改期 + 新提醒按新时间重排（落库、统一时区、失败重试）
        ↓
⑤ 飞书卡片回执用户："已改到周六 10 点，提前 2 小时提醒你"
        ↓
⑥（可选）用户接着问"周六这场战争是哪一场？"
     → Hermes 按意图把问题路由给 RAG → RAG 回答 → Hermes 转卡片
```

实现要点：提醒/预约任务**持久化**（不能只放内存，服务重启即丢）；改期回调**幂等**；
**审计日志**（谁在何时改了什么）。以上均属 Hermes 侧独立模块，与 RAG 无关。

## 八、答疑结论（11 问）

| # | 问题 | 结论 |
| --- | --- | --- |
| Q1 | RAG 与旧前后端分离、启动路径不同怎么办 | 分离不是缺陷而是**要固化的边界**；要解决的是三个副作用（双问答并存、入口分散、数据靠人工同步）。**不建议合并代码** |
| Q2 | 只把 RAG 接入飞书，功能是否过于单一 | 对外只有 4 个接口，能力边界就是知识问答，确实单一；但**补齐能力所需的接口大部分旧后端已具备**，收编为 Agent 工具即可 |
| Q3 | 无向量库、本地存储，大规模文本处理会不会出问题 | 风险在「全量重建 + 单文件矩阵 + 暴力检索」的实现方式，而非"本地 vs 向量库"；1 万级 chunk 规模本地存储够用。（⚠️ 此问的"无向量库"前提已在 RAGv5 变化） |
| Q4 | 接入飞书要等 Agent 建好，会有影响吗 | "RAG + 大模型 API"做问答机器人够用，做"能改预约时间的助手"不够用；飞书接入与 Agent 成熟度**不构成串行依赖**，可并行。真正的上线阻塞项是 LLM 密钥配置与会话/任务持久化 |
| Q5 | 旧知识库系统里的智能问答页面要不要删 | **不必立刻删**：先取消它的用户入口身份（摘路由/菜单），保留作答案质量对照基线，新入口稳定后再删。删除范围仅限"问答页 + 问答入口"，不含实体识别/规则推理模块 |
| Q6 | "旧系统降级为管理后台"是什么意思，运行环境不同怎么办 | 改的是**服务对象，不是系统形态**：旧前端建议保留（管理动作需要图谱可视化与表单交互）。两套运行时靠「进程隔离 + HTTP 通信 + 数据单向离线流动」共存，在线只跑 RAG，旧系统连同 Neo4j 按需启动 |
| Q7 | "收编旧后端只读接口为工具"是拿旧页面模块来用吗 | **复用接口与数据、不复用页面**：页面间的关联性由 Agent 会话上下文接替。真正的工作量是把"页面友好"的响应适配成"模型友好"的工具签名，前提是所选模型支持 tool calling |
| Q8 | 页面数据已收敛为只返回 200 个节点，模块化后如何保证模型思考时间 | 200 是**"看图护栏"不是"工具上限"**：200 条关系三元组对 ECharts 刚好，对模型是灾难级体量。工具必须另设收敛策略（聚合摘要 + top-K + 字段裁剪 + 可追问） |
| Q9 | 这些页面功能会在飞书上体现吗，旧系统的价值在哪 | "页面功能是否在飞书体现"**不该是目标**：飞书要的是"结论 + 依据 + 可追问"。读类可对话化、图谱/地图降级体现、写与批量类留在旧系统；旧系统的价值是 RAG 的数据源头与质量保障 |
| Q10 | 整体理解确认：旧库留 Web、RAG 在飞书、agent 去旧库找答案 | 三条成立，但需修正三点——飞书出现的是"**数据**"而非"页面"；agent 调用的是"**数据/接口**"而非"页面模块"；**RAG 是工具而非 agent** |
| Q11 | 旧知识库是 agent 的"离线构建"、agent 使用时是"在线构建"吗 | 旧知识库是**源头与治理面**（不是构建产物）；RAG 的快照 + 索引才是**离线构建产物**；答问走的是**在线服务（检索 + 生成）**而非"在线构建"——构建一次、服务多次 |

## 十一、待决项（需拍板）

1. **Hermes 的定义与能力边界**：是否已有飞书自建应用？消息收发、定时、日程、卡片是现成还是需自建？
2. **最终用户是谁**：公众消费者（终态为微信小程序）还是企业内部/场馆/团体（飞书即可）。
3. **"预约"业务的落点**：改期事件来自用户对话还是业务系统 webhook。
4. **部署网络**：Hermes 与 RAG 是否同内网即可；RAG 是否允许 Hermes 之外访问。
5. **Web 问答页保留策略**（建议保留，作为运营/演示通道）。
6. **是否需要卡片流式"打字机"体验**（相对整包回复属二期优化）。
7. **管理台形态选择**：保留旧前端（推荐）还是只保留后端 API。
8. **模型能力确认**：拟接入 Hermes 的模型是否支持 tool calling，决定工具层的实现方式。
9. **对话通道延迟目标**：整链路 SLO（如 P95 ≤ N 秒），据此确定 LLM 超时/重试取值与降级阈值。
10. **是否采用"先发卡片后更新"的进度交互**：影响飞书侧的首响体验与实现复杂度。
11. **只读工具的数据来源**：建在 RAG 快照上（推荐，旧服务不必常驻）还是在线调旧后端接口
    （要求 Neo4j 常驻）。

## 十二、风险与注意事项

1. **Hermes 定义未定**：若 Hermes 不具备消息收发/定时/卡片能力，P2、P3 的工作量会显著上升（需自建网关与调度）。
2. **飞书 Markdown 子集**：飞书卡片不支持完整 Markdown，F06 输出需做白名单收敛，避免渲染错乱。
3. **图谱/地图可达性**：IM 内无法交互式画图，必须走"服务端出图 + 文字降级"双路径，不能直接搬运 panel。
4. **多用户并发**：内存图谱 + FTS5/Chroma 单实例可服务；多 worker 会各自加载一份数据，需评估内存，
   建议限流 + 单实例起步。
5. **数据制品与代码版本对齐**：快照/索引与代码必须同版本发布，`manifest.json` 版本校验已有，
   发布流程要固定。
6. **版权约束**：原文文本受版权限制，公开渠道仅发布治理后的知识快照，不可暴露原文全量。
7. **写操作边界**：预约/提醒等写操作不要混入 RAG，避免知识引擎被业务状态污染。
