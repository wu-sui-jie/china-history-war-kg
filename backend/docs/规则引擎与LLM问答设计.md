# 旧版智能问答：规则引擎与大模型推理设计

> 本文档讲**设计口径**（为什么这么做、边界在哪），不讲代码逐行实现——实现见
> `inference/rule_llm_integration.py`、`entity_extract/extractor.py` 与 `rules/rule_base.json`。
> 逐行细节（大段代码引用与提示词全文）不再单独维护，需要时用
> `git log --diff-filter=D -- backend/规则引擎与大模型推理技术文档.md` 取回。

## 一、整体链路

```text
用户问题
  ↓ ① 实体抽取（规则快速命中，不足则 Ollama 兜底）      entity_extract/extractor.py
  ↓ ② 问题类型判定（枚举题 / 详情题 / 参与者题 / 通用题） inference/rule_llm_integration.py
  ↓ ③ 图谱查询（精确 → 朝代别名 → 模糊 三段回退）+ 实体间路径搜索
  ↓ ④ 规则推理（20 条规则生成隐含关系）                 rules/rule_base.json
  ↓ ⑤ 按问题类型选提示词 → Ollama 生成回答
  ↓ 回答 + 知识图谱参考信息（图谱数据另供前端可视化）
```

## 二、规则库（`rules/rule_base.json`，20 条）

每条规则由 `condition` 与 `inference` 两部分组成，`inference.direction` 决定是否反转关系方向：

```json
{
  "rule_id": "war_001",
  "name": "主战场反向推理规则",
  "condition": { "relation": "主战场" },
  "inference": { "relation": "发生于", "direction": "reverse" },
  "description": "如果事件--[主战场]-->地点，则地点发生于该事件"
}
```

### 2.1 细分规则（17 条，均为反向推理）

| 条件关系 | 推出关系 | 规则 | | 条件关系 | 推出关系 | 规则 |
| --- | --- | --- | --- | --- | --- | --- |
| 主战场 | 发生于 | war_001 | | 统帅 | 统帅作战 | war_009 |
| 出发地 | 出征起点 | war_002 | | 将领 | 率军参战 | war_010 |
| 目的地 | 作战目标地 | war_003 | | 谋士 | 军事策划 | war_011 |
| 指挥所 | 指挥中心 | war_004 | | 阵亡 | 战死于 | war_012 |
| 补给地 | 承担补给 | war_005 | | 投降 | 向其投降 | war_013 |
| 发起方 | 发起战争 | war_006 | | 包含关系 | 隶属于战役 | war_016 |
| 防守方 | 防御战争 | war_007 | | 战略要地 | 战略核心 | war_017 |
| 同盟方 | 结盟参战 | war_008 | | 议和地点 | 议和发生地 | war_018 |
| | | | | 议和方 | 参与议和 | war_019 |

**为什么细分规则都是反向**：图谱里的关系是"事件 → 地点/组织/人物"的方向，
而用户的问法多是"某地点/某人参与了什么"——反向推理把图谱方向翻过来，正好对上提问方向。

### 2.2 复合规则（3 条，多跳推理）

| 规则 | 条件 | 路径长度 | 推出 |
| --- | --- | --- | --- |
| war_014 | 因果关系 | 2 | 间接因果 |
| war_015 | 顺承关系 | 2 | 连续演进 |
| war_020 | 包含关系 | 3 | 战争阶段 |

### 2.3 加载与索引

启动时按 `condition.relation` 建立"关系类型 → 规则列表"索引（`_build_rule_indices`），
推理时用 `_find_applicable_rules` 按索引查、按 `priority` 排序，
**不要改成每次遍历全表**——规则数虽小，但推理是逐关系调用的，全表扫描是 O(关系数 × 规则数)。

## 三、实体抽取（`entity_extract/extractor.py`）

两级策略，先便宜后昂贵：

1. **规则匹配**（`_extract_by_rules`）：用后缀词表（战争事件后缀 / 人物称号 / 政权威权词 / 地点关键词）
   与历史地名词典（`historical_places.txt`，同时作为 jieba 自定义词典）快速命中。
   **命中 ≥ 2 个实体就直接返回**，不调用模型。
2. **大模型兜底**：规则不足时调 Ollama（`deepseek-r1:7b`）抽取，解析后做后处理。

后处理包含：去重、`_should_filter` 噪声过滤（停用词、占位值、过短/过长串）、按相关性排序、
结果缓存（按文本内容，LRU 128）。抽取缓存与问答生成缓存共用 `common_utils.lru_get/lru_set`。

## 四、问题理解与实体过滤

**问题类型判定**驱动后面选哪套提示词（见第五节），共四类：

| question_type | 触发场景 | 图谱侧准备 |
| --- | --- | --- |
| `dynasty_event_list` | "唐朝有哪些战争" | 按朝代取事件清单 |
| `event_detail` | "赤壁之战的经过" | 取单个事件的完整字段 |
| `participant_event_list` | "曹操参与了哪些战争" | 按人物/组织取事件清单 |
| 其他（通用） | 其余 | 实体信息 + 关系 + 路径 |

**实体相关性过滤**（`_filter_relevant_entities`）避免把无关实体塞进提示词：实体在图中存在 +10 分、
名称越长分越高（更具体者优先）、与问题关键词匹配加分、直接出现在问题中额外加分，**最多保留 4 个**。

**图谱查询三段回退**（`query_single_entity`）：精确匹配 → 朝代别名归一后匹配 → 模糊匹配。
回退是必要的，因为抽取出的实体名可能是别名或带朝代前缀。

## 五、提示词与生成

按问题类型选 `user_prompt` 与 `system_prompt` 成对分支：

| 类型 | system_prompt 的核心约束 |
| --- | --- |
| `dynasty_event_list` / `participant_event_list`（枚举题） | 必须完整覆盖清单中每一条事件；不得自行删减、合并、补充清单外事件；不得把枚举题答成单个"最准确答案" |
| `event_detail`（详情题） | 只能用记录中的字段作答；字段缺失时说明图谱未提供；不得补充图谱外史实 |
| 通用题 | 只回答原始问题、不复述指令；不说"根据提供的信息"之类的引导语；不编造关系 |

三者共同的立场是**把"事实来源"钉在图谱上**：枚举题不许漏、详情题不许补、通用题不许编。

> **维护提醒**：这三段 system_prompt 只由 `generate_response_with_llm` 提供一处，
> 不要在调用方（如 SSE 分支）里再复制一份——两份提示词一旦漂移不会报错，
> 只会让同一类问题走出不同的答案。

**回答缓存**：键 = `(模型, 问题类型, 问题/实体/关系/路径/metadata/prompt 的稳定哈希)`，
命中直接回放，避免重复付费与重复等待。

## 六、返回给前端的两类数据

1. **回答文本**：SSE 流式输出（`/api/ai/inference/stream`），前端逐块渲染。
2. **知识图谱参考信息**（`_format_relations_for_context`）：按
   `【涉及实体】/【直接关系】/【推理关系】` 分节的文本，直接关系最多 15 条、推理关系最多 10 条，
   带 `→【关系】→` 的结构化标记。前端 `renderFormattedKgContext` 解析这个格式并渲染。

## 七、边界与已知限制

1. **`max_depth` 只能有一处初始化**：路径搜索深度由 `RuleLLMIntegration` 实例参数决定，
   而"先到请求决定全局配置"意味着多个兜底初始化点会各自用不同取值（如 `3` 与 `30`）
   互相覆盖。现在只在 `before_request` 初始化一处；新增兜底分支前先确认不会改变全局取值。
2. **依赖 Ollama 常驻**：模型不可用时问答直接失败（与 RAG 不同——RAG 无密钥时会降级到离线摘要回答器）。
   生成回答前会清理模型输出里的 markdown 代码块围栏。
3. **规则库用相对路径读取**（`rules/rule_base.json`），必须从 `backend/` 目录启动服务。
4. **Cypher 拼接面**：`model_search.py` 里**标签与属性名**仍是内联拼接（查询值已全部参数化），
   标签走 `common_utils.safe_identifier()` 的白名单校验。**不要用"手工 `replace` 转义字符串"**：
   那样处理不了反斜杠。新增查询请一律用参数化写法。
5. **朝代词表只有一份出处**：`backend/dynasty_data.py`（显示顺序、别名、校正、合法值都在这里），
   并带口径差异自检。多份词表会出现"汉朝"与"汉"这类不一致，漏改一处就让某条链路悄悄查不到数据。
   **改动朝代相关逻辑时以该文件为准**，不要再新增第二份词表。
6. **旧问答与 RAG 的边界**：本模块已被菜单下线入口（由 RAG 问答承接），接口保留给
   「文本实体识别」等内部链路，并按 `editor` 及以上限权（见 [../README.md](../README.md) 的角色职责表）。
