## 三、未采纳建议条目的裁定（本轮核心）

### 裁定 1：P1-9「不执行 apply_audit 真实回填，以文档口径收口」——**不修改**（接受）

第一轮推荐的是方案 A（真实回填），整改方选择方案 B（文档降级），并给出三条理由。
经核实，**三条理由全部成立**，故裁定维持方案 B，不强制执行回填：

1. **主体性冲突成立**：F09 审核闭环的设计前提是「人工审核」，本次整改执行主体是 AI。
   由 AI 从 1,215 组重名中挑选并执行合并，产出的 `audit_applied` 不构成人工审核记录，
   反而会制造一条形式上「已完成人工审核」的虚假记录——这与第一轮审核「报告结果必须如实」
   的原则相悖。第一轮报告原文对方案 A 的措辞是「让**人工**审核记录从待审清单变成已执行记录」，
   AI 代跑并不满足该语义。题库审核用 AI 代理已在 P2-22 中如实标注口径，同理 apply_audit
   也应留给真实人工执行。
2. **影响面判断成立**：回填产出新快照后必须重建 9,544 条向量索引、更新数据版本并回归——
   这是数据版本切换与部署决策，超出「文档-代码一致性整改」的范畴。第一轮报告本就注明
   「工作量较大，执行方评估后再做」。
3. **成本与不可逆性成立**：全量重建消耗百炼 API 配额（约 25 分钟串行），出错需回滚。

**处置**：P1-9 以方案 B 收口，09 文档三处口径一致（功能作用:9、人工审核要求:68-73、
验收第 5 条:101），如实反映「工具就绪、未执行」。转为**遗留事项**（非缺陷）：
正式答辩或对外交付前，由真实人工按 F09 文档执行一次 apply_audit 小批量回填并重建索引，
届时同步更新 09 文档与数据版本。

### 裁定 2：P0-3「fusion 事件改文档而非改代码」——**无分歧**（与第一轮建议一致）

第一轮推荐即方案 A（改文档）。整改方补充的技术依据经核实**成立且比其声称的更强**：
`frontend/src/stores/session.ts:306-364` 的事件 switch 根本没有 fusion 分支（落入
default 被整体忽略，连 evidence_count 都未读取）；`evaluation/chain.py` 完全不走 SSE。
fusion 事件当前无任何证据数组消费方，改文档是正确选择。

### 裁定 3：P1-5「关系路径降级为子图承载」——**无分歧**（与第一轮建议一致）

第一轮推荐即方案 B（改文档，推荐）。事实依据已核实：`contracts/panel.py` 全量 82 行中
PanelData 仅 4 字段（entity_cards/subgraph/timeline/map_points），全部子模型无任何
path/route 字段；补代码需动契约 + F05 + 前端三层，收益低于回归风险。改文档正确。

### 裁定 4：P1-8「治理前后对比选方案 B」——**接受**（在第一轮给定的选项内）

第一轮给的是「方案 A 或 B」二选一。整改方选 B 的理由（治理报告是已冻结的历史产物，
只改 `_before_after()` 不重跑治理会造成代码与产物不一致）成立。接受。
