## 二、RAGv4：F10 问答效果评测（质量闭环）

目标：建立可重复运行的评测闭环，持续验证检索与回答效果，输出量化证据与错误归因，
支撑「图谱+文本双通道 vs 纯文本 RAG」的对比结论（F10 验收标准第 3 条）。

> 状态更新（2026-09-04）：本规划中的 RAGv4 任务已执行完成首轮——`evaluation/` 评测包、
> 题库 reviewed-2（39 条）、基线报告与评分均已完成，并量化出 F02 朝代子串误判、
> F04 长改写 AND 失效、event_type 筛选原文损耗与应拒答缺口等质量问题。
> 实现细节与结果见 [RAGv4-开发说明.md](RAGv4-开发说明.md)；本小节保留为任务清单与
> 验收对照参考。

### 任务与要做的模块

1. **黄金问答集（30~50 条）**
   - 覆盖实体介绍、关系、因果、时间线、背景等类型；由人工审核，确保答案可依据现有数据回答；
   - 与 F08 共用同一题库：F08 恢复后的示例问题从已审核通过的评测题中挑选（F10「题库统一说明」）。
2. **召回标注**
   - 每条问题预先标注"应召回的相关文档/实体"，用于计算 recall@5、图谱命中率等客观指标；
   - 标注由人工完成，评测报告记录**标注版本**（F10「检索召回标注」）。
3. **人工评分体系**
   - 先定评分说明，避免多审核人标准不一致；
   - 答案正确性：correct / partial / incorrect / unknown_answer（应拒答时正确拒答）；
   - 引用正确性：supported / unrelated / unsupported；
   - 每条记录：问题、系统答案、人工评分、备注、对应证据；可导出逐条复核（F10 验收第 4 条）。
4. **评测脚本与报告**
   - 一条命令可重复运行（F10 验收第 1 条）；
   - 报告能区分四类失败：**答案错 / 引用错 / 检索失败 / 无证据**（F10 验收第 2 条）；
   - 同一问题可跑不同检索配置并保存对比结果（如关键词 AND/OR、图谱 top-k、向量开关、单文本通道）；
   - 输出"双通道 vs 纯文本"对比结论 + 失败样例，便于下一步优化。
5. **专项评测口径（长改写问题）**
   - RAGv2 复核已暴露：长改写问题（如"长平之战的主要经过和结果是什么？"）F04 的 AND 优先
     常命中 0、OR 兜底排序噪音明显；
   - 评测口径定为**"相关文本是否进入回答/引用"**，不能只看 `text_results` 非空；
   - 归因四类：text_result 为空 / 相关文本被排序挤出 / 融合名额裁剪 / 回答未引用相关文本；
     保留 graph_results/text_results/fusion 现场供归因与 F10 对照。
6. **筛选召回专项（事件类型筛选的原文损耗）**
   - F04 `_pass_meta`：带 event_type 筛选时，缺少 event_type 元数据的 raw/evidence 片段会被
     整批剔除，只有事件卡片片段参与召回（已记录为 RAGv2 边界）；
   - 该损耗是筛选场景下的实际召回损耗，F10 应作为专项口径验证：
     “开 event_type 筛选时相关原文证据是否仍能进入回答/引用”，必要时给 raw/evidence
     补元数据或放宽该筛选项。

### 验收对照（来自 F10 功能文档）

1. 评测可一条命令重复运行；
2. 报告区分答案错误 / 引用错误 / 检索失败 / 无证据；
3. 输出双通道 vs 纯文本对比结论；
4. 人工评分结果可导出并逐条复核。

### 前置与边界

- 前置：RAGv3 收口（Git 固化）完成；RAG 后端可重复启动、真数据（`20260904_v2` 及以上）就位。
- 边界：答案正确性/引用正确性采用**人工评分**，不默认用模型评分；评测脚本只自动化
  客观指标（召回/命中/耗时）与报告生成；本阶段不引入账号/权限体系。
- 不在本阶段：F08 页面（示例问题选型依赖 RAGv4 已审核题库）、真实 LLM key 的效果调参。

### 技术选型口径（决策留痕：向量库与 RAG 框架取舍）

> 本节回答评审/执行中高频追问的两个选型问题，作为决策记录固化，供 RAGv5 开发说明引用。

> **2026-09-13 修订（重要）**：RAGv5 开工前，用户决定改用 **Chroma 向量库**
> （本地嵌入式 `PersistentClient`，落 `data/index/<v>/vectors/chroma/`，`hnsw:space=cosine`），
> 取代下方第 1 条"暂不引入向量库、用 `ids.json + embeddings.npy` 内存检索"的暂定结论；
> embedding 模型同时确定为 **阿里云百炼 `text-embedding-v4`（1024 维）**。
> 第 1 条的原始分析（数据量级、升级触发条件、契约稳定性）**保留为历史判断依据**，
> 不再作为实施口径。现行口径见 [RAGv5-规划说明.md](RAGv5-规划说明.md) §4.1（D1–D3）
> 与 [RAGv5-开发说明.md](RAGv5-开发说明.md) §四.3。

1. **为什么现在不用独立向量数据库（Qdrant/Milvus/FAISS 等），后面在什么条件下用？**
   （*历史分析，2026-09-13 已被上述修订取代；仍适用于解释"为什么当时这么判断"*）
   - 数据量级小：原文约 30 万字 + 事件约 1050 + 关系约 1.77 万（见 architecture.md），
     切分后片段在数千量级，`data/index/vectors.py` 产出的 `ids.json + embeddings.npy`
     由 F04 加载进内存算相似度即可毫秒级返回，无需额外起服务；
   - 演示环境要求轻量、可本地跑、不依赖重型服务，且"无任何模型 key 也要能用"
     （FTS5 关键词兜底）是硬约束，强外部依赖与离线兜底设计冲突；
   - 检索模式"不提前定死、以 F10 评测数据为准"是 F04 已确认口径，向量检索属于待评测的
     半条腿，评测前不急于搭建服务；
   - **升级触发条件（满足其一再评估引入独立向量库）**：片段规模上到约 5 万以上或单库
     向量超过数百 MB 内存压力明显；需要索引增量 upsert/删除或低延迟并发查询（当前演示为
     只读快照、一次性全量重建，不需要）；需要向量+元数据混合过滤/分片/高可用；
   - 当前接入点已抽象（`embed_fn` 注入 + 加载侧 `len(ids)==embeddings.shape[0]` 校验 +
     F04 自动降级关键词），将来真迁独立向量库只动 F04 读取层，`data-contract.md` 契约不变。
2. **为什么不用 LangChain / LangGraph，什么条件下重新评估？**
   - 主线是图谱+文本双通道（F03 内存图谱检索 + F04 文本检索），LangChain 是文本中心的
     抽象，图谱通道帮不上；请求流是 F02→F03/F04→F05→F06 线性链加可选 LLM 兜底，
     LangGraph 的状态机/agent 编排无的放矢；
   - 全链路以 `data-contract.md` 强契约为枢纽（证据字段/SSE 协议/分数 min-max 归一化/
     引用编号），F05 融合重排、F06 离线摘要回答器均按契约自研，LangChain 的
     Retriever/QA Chain 抽象会反向要求突破封装适配自定义字段；
   - 无 key 可跑 + F10 评测可复现是刚需（确定性离线回答器、一条命令重复运行），
     LangChain 生态默认"接模型"的思路与"模型可有可无、规则兜底"设计相抵触；
   - 依赖刻意最小化（requirements.txt 仅 8 行），为两处 OpenAI 兼容调用引入框架和
     整棵依赖树不划算；
   - **重新评估条件**：未来出现真正需要 agent 化多轮工具编排、同时接入多家模型/工具
     链、或团队要复用 LangChain 生态现成评估器时，再评估 LangGraph 编排层；当前不引入。
3. **模型口径备忘**：文本切分用规则（段落→句子边界 + 字符聚合/重叠，无分割模型，见
   data/index/chunking.py）；关键词检索用 SQLite FTS5(BM25)；向量化用云端中文文本向量
   模型（OpenAI 兼容，模型名与 dim 未定，RAGv5 开工时确认后填 `EMBEDDING_BASE_URL /
   EMBEDDING_API_KEY / EMBEDDING_MODEL / EMBEDDING_DIM`，.env.example 预留
   `EMBEDDING_DIM=1024` 示例）；回答生成/实体识别兜底用 deepseek-v4-flash（OpenAI 兼容）。
   文档不臆造"已接入的向量模型名"，具体模型在 RAGv5 接入时以实际配置为准并回填本节。
