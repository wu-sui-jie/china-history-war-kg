## 二、依据（都是实测，不是推断）

### 2.1 为什么删 `秦始皇` / `吴起`

`EntityClassifier.is_valid_person_name()` 会把这两个名字整条丢掉，而它**全仓库只有一处调用**
（`main.py:113`，在建最终 `entities.persons` 列表时）。实测：

| 事实 | 出处 |
| --- | --- |
| 人工标注 persons 里 `秦始皇` 1 条、`吴起` 1 条 | `data/annotations/sample_entities.json`（506 条 persons） |
| 预测 `entities.persons` 里两者各 **0** 条 | `output/中国历代战争简史/9_final_all.json`（2492 条 persons） |
| 实体评估**只比对 `PersonName`** | `optimal_evaluator.py:365`（gold 集合）、`:410`（匹配） |

所以这两条**必然**是漏抽（各贡献 1 个 FN）。而模型其实是抽出来的，只是散在别处：

| 名字 | 出现在 | 取值 |
| --- | --- | --- |
| `吴起` | `relations.event_person_relations[].PersonName`（关系类型「统帅」） | `'吴起'` × 2 |
| `吴起` | `events[].Commanders` | `'吴起'`（魏攻秦河西之战、魏灭中山国） |
| `秦始皇` | `relations.event_person_relations[].PersonName`（关系类型「君主」） | `'秦始皇'` × 2 |
| `秦始皇` | `events[].KeyPersons` | `'秦始皇、扶苏'`、`'秦始皇'` |

顺带暴露一处内部不一致：关系数据里写着"吴起是统帅""秦始皇是君主"，但 `entities.persons`
里没有这两个人——一个关系指向了实体列表里不存在的人物。

**判定**：这两个名字在产物里以「统帅」「君主」这类**合法角色**出现，把它们整条丢弃看不出收益；
当初为何加进名单，代码与提交信息里都查不到依据。故删除。

### 2.2 为什么统一为宽口径

`split_multi_value()` 原先挂两套"什么算没有值"的集合，`main.py` 用窄的（只排 `不详/null`）、
`relation_extractor` 用宽的（还排 `未知/无/None`）。差别就是同一段 `"甲、未知、乙"` 的拆分结果：

| 排除集 | 结果 |
| --- | --- |
| 宽（抽取器用） | `["甲", "乙"]` |
| 窄（`main.py` 用） | `["甲", "未知", "乙"]` ← "未知"被当成真名字留下 |

下游 `Normalizer.is_placeholder_value()`（`normalizer.py:220`）的词表虽然也覆盖这些词，
但它是不是在**所有**同路径上都生效，此前没实测过。统一成宽口径方向明确（少留垃圾名字），
窄集留着则是死代码。

### 2.3 为什么删 `AlignmentTool`

零引用实测：`grep -rn "AlignmentTool"` 只在它自己的定义处命中；`utils/__init__.py` 的
`__all__` 只导出 `EntityClassifier` 与 `Normalizer`，所以它连包 API 都不算。
它是第 10 轮删掉的那套"严格对齐、阈值 0.85"评估器（`evaluator.py`）的对齐引擎——
那套评估器一删，它就没人调用了（EER-10 的连带）。**留着它的危害与 EER-10 本身同类**：
一份看起来像官方对齐逻辑的死代码，读者无从判断该用哪个。

### 3.2 关键论断：当前产物的评估结果不受影响

这三项都在**抽取阶段**生效（产物已经生成），所以评估数字本不该变。实测证据——
改前/改后对**同一份产物**各跑一次完整评估：

```bash
cd entity-event-relation
python evaluate.py --output evaluation/run_before_decision   # 改代码之前
# …… 实施三项改动 ……
python evaluate.py --output evaluation/run_after_decision    # 改代码之后
# 然后递归对比三份输出文件
```

| 文件 | 差异 |
| --- | --- |
| `results.json` | **1 处**：`metadata.evaluated_at`（时间戳，每次运行都会变） |
| `error_analysis.json` | **0 处** |
| `field_report.json` | **0 处** |

指标值：关系 TP/FP/FN = 714/174/385、关系 F1 71.87%、宏观平均 F1 44.68%（与第 11 轮 C-6
口径变更后的记录一致）。两个临时输出目录跑完即删。

> **如实说明**：`backend/tests/test_extract_replay.py` 的录制回放**没有**因这次改动变红。
> 原因不必猜——那份夹具用的是 58 字的合成短文本，既不含 `秦始皇`/`吴起`，也不含占位词，
> 所以两条路径都没被它走到。它的定位（兜序列化/字段归一/后处理）没变，但**证不了**这次改动的效果。
> 同理，`snapshot_responses.py` 也看不到（它刻意跳过抽取端点）。

## 四、这次改动何时可见效果

**只在下一次真实抽取的产物里可见**——而这正好是「一次整本重跑」那件事
（见[项目现状与后续计划](项目现状与后续计划.md) 阶段 2.5）。三项改动合起来意味着：下一次重跑时

1. `秦始皇` / `吴起` 会作为人物实体进入 `entities.persons`（有望把这 2 个 FN 变成命中）；
2. `main.py` 链路上的多值字段会多滤掉 `未知` / `无` / `None`；
3. 模块少了一份死代码（与产物无关）。

**不要**把这次改动当成"指标会变好"的承诺：第 1 条有可能带来新的误报（当初加名单的意图无从考证），
第 2 条会把某些字段变短。重跑后应固定产物指纹、与本文的 714/174/385 对照，并逐条看差异从哪来。
