## 三、W3-1 EER-12 地理编码健壮化

`war_extraction/geocoding/geocode_amap.py` 原来：单次请求，`except Exception` 一网打尽、不重试；
只有批次末尾 `save_results` 才落盘；配额/频率超限与"地址查不到"用同一条提示。
修前实测（探针）：超时后 `request_count` 仍是 0（**修前失败的那次请求根本没计数**）、无重试、
`batch_geocode` 不产生任何进度文件。

改法：

| 项 | 改法 |
| --- | --- |
| 失败分类 | 新增 `_request_once` 返回判定：`ok` / `transient`（网络异常、5xx、429、响应非 JSON）/ `quota`（infocode 10003/10004/10021/10044）/ `deterministic`（其它 API 错误） |
| 重试 | **只对瞬时故障**退避重试：默认 3 次（含首次），等待 `backoff_base * 2^(n-1)` 即 1s、2s，可配；配额类与确定性失败**一次都不重试** |
| 配额处理 | 配额与频率受限单独提示；其中**日配额类（10003/10044）提前结束整批**（当天不会再成功，继续跑只是把剩余地点全刷失败），频率类（10004/10021）只跳过当前条、继续整批 |
| 落盘 | 每处理完一条就追加一行 JSONL（`geocoding_progress.jsonl`，带 `run_id`/`status`/`reason`）并 `fsync`；中途被杀最多丢当前一条 |
| 计数口径 | 「总请求数」改为按实际请求次数计（含重试），并单列重试次数 |

用例 `tests/test_geocode_amap.py`（11 例，全部注入假 session：不联网、不耗额度、不真等待——
`sleep_func` 注入）。覆盖：超时退避后成功且等待为 1s/2s、5xx 重试、重试耗尽放弃、
配额不重试且标记 `quota_exhausted`、确定性错误不重试、逐条落盘内容、日配额中断后部分结果保留、
频率受限不中断整批、`progress_path=None` 关闭落盘、默认路径固定。

> **证据口径说明（不夸大）**：这条改动的"修前对照"用的是**探针脚本跑旧代码**，不是这 11 例用例——
> 用例文件 import 了 `PROGRESS_FILENAME`/`default_progress_path` 这些新符号，拿旧模块跑会直接
> collection error，不能当成"修前 N 例失败"。旧代码的实测行为见本节开头那三句。
> 真正带"修前失败"证据的是 W3-4（输出不变，前后 diff）与 W3-2 的提示词回归（修前 2 例失败）。

## 六、W3-2 EER-7：修了一个真 bug，编排合并没做（附原因与迁移方案）

### 6.1 已做：backend 的提示词漂移（真 bug，静默降级）

核对两份编排时发现"平行演化易漂移"**不是风险预警，是已经发生了**：

```python
# backend/llm_pipeline.py（修前）
chunk_event_result = event_extractor.extract(chunk_text, chunk_entities)   # 第 2 个实参是对象
# war_extraction/extractors/event_extractor.py
def extract(self, text: str, place_list: str = "", org_list: str = "", person_list: str = "") -> ...
```

`place_list` 会被直接渲染进第 3 阶段提示词，于是模型拿到的是 Python repr。实测两边渲染结果：

| | 第 3 阶段提示词里的地点行 |
| --- | --- |
| 修前 | `- 地点：places=[PlaceEntity(geo_name='牧野', modern_name=None, DynastyName=None, Province=None, ...)]` |
| 修后 | `- 地点：牧野、朝歌` |

**这个 bug 不报错、不改变 HTTP 状态码、接口照常 200**，只是让模型拿着一串 repr 去抽事件——
典型静默降级。`snapshot_responses.py` 覆盖不到它（该工具刻意跳过会调大模型的
`/api/extract/entities-events`），所以必须在提示词层面钉住。

改法：backend 复用已经算好的 `chunk_place_names`/`chunk_org_names`/`chunk_person_names`
（原本就是给关系阶段用的），传字符串列表，与离线链路同口径。
用例 `backend/tests/test_extract_prompt.py`（3 例，桩 LLM、不联网）：**修前 2 例失败**
（`assert 'places=[Plac...e_text=None)]' == '牧野、朝歌'`）。

### 6.2 已做：主库路径配置化

`export_unmapped_places.py` 三处 + `import_coordinates.py` 一处，各自写了一遍"往上四层再拼
`backend/database`"。收进 `war_extraction/geocoding/db_path.py`，解析顺序为
显式参数 → `EER_DB_PATH` 环境变量 → 默认路径，**默认值与旧的四层 `dirname` 公式逐字符相同**

### 6.3 没做：把两份编排合成一个入口——为什么，以及怎么做

**没做的理由**（不是工期问题）：

1. **两份编排的差异不止调用口径，后处理管线本来就不同**。backend 逐字段做
   `_to_str`/`_normalize_dynasty`/`_normalize_role`/`_normalize_event_name`（朝代修正表在
   `backend/dynasty_data.py`，是 backend 自己的资产）；离线链路做
   `enrich_entities_from_events` / `cleanup_entity_conflicts` / `cleanup_events` /
   `finalize_outputs`。合成一个入口必然要选一套语义，**会改变至少一边的产出**——
   这就是行为变更，不是重构。
2. **两边的验收方式不同**：backend 是 HTTP 接口（有 67 请求快照兜底，但恰恰跳过了抽取端点），
   离线链路产出 `9_final_all.json`（下游 evaluation / 导入 SQLite / 同步 Neo4j 全依赖它）。
   合并后要验"两边结果一致"，**必须真跑大模型**（花钱、耗额度、不可在 CI 复现）。
3. 离线链路的编排里还嵌着**分段缓存**（按 chunk + prompt 版本缓存，`cache/` 已 22MB）。
   共享函数要么接受缓存回调，要么放弃缓存——前者接口复杂，后者直接改变缓存命中与产物。

**建议的迁移方案**（下一轮或专门一轮做）：

- 共享边界取"**分段循环 + 三阶段调用 + 去重收集 + 失败诊断**"，后处理各自保留
  （backend 的字段归一、离线链路的 cleanup 都留在各自一侧，靠共享函数的
  `on_chunk_*` 钩子挂进去）；
- 共享函数签名大致为
  `run_extraction(llm, text, splitter, *, per_chunk_hook=None, cache=None) -> (entities, events, relations, diagnostics)`；
- **验证闭环**：桩 LLM 驱动两边、逐字段 diff（本轮已用这个手法验证提示词，可复用），
  再加上 backend 的 67 请求快照与离线链路一次真实评估；两者都过才算完成。

在没做这个合并之前，**本轮那个提示词 bug 正好说明了风险是真的**——两份编排只要并存，
就还会再漂。建议这条优先于 EER 其余工程债。
