## 二、P0-1：数据重导不再删除账号

**问题**：`import_json_to_sqlite.py` 的 `run()` 里 `db.drop_all()` + `create_all()`，而
`UserInfo` 与知识表共用同一个 SQLAlchemy metadata——换一份抽取数据集重导，会把全部账号、
口令哈希与角色一起删掉。管理员账号消失后只能重新注册 viewer 再手工改库。

| 项 | 改法 |
| --- | --- |
| 不再重建全库 | 删掉 `db.drop_all()`，只保留 `db.create_all()`（对已存在的表是空操作，正好"补齐新表、不动老表"） |
| 清理范围显式化 | `clear_migration_tables()` 只清 4 类实体 + 4 类关系表，函数 docstring 写明"不动 UserInfo 等非知识表" |
| 删除顺序 | 改为**先关系、后实体**（原先相反，靠一句 `PRAGMA foreign_keys = OFF` 兜着——而那个 PRAGMA 在 SQLAlchemy 已开启的事务里是**静默无效**的，SQLite 明确要求它在事务外执行） |
| 事后核对 | 导入前后各取一次"账号数 + {账号: 角色}"快照，**不一致直接退出码 1**，并提示从备份恢复 |
| 中止提示 | 不带 `--yes` 时的提示改为"会清空全部知识数据"，并说明账号不在清理范围、导入前后会核对 |

**为什么要加那道事后核对**：它本该不可达——但"账号数量对不上"是 P0 级事故，让人事后才
发现登录不了，比当场失败糟得多。

**验收**：`backend/tests/test_import_preserves_users.py` 4 例。其中"不再调用 drop_all"用
打桩把 `db.drop_all` 换成"一被调用就 `pytest.fail`"，而不是读源码断言；另外三例分别验
账号与角色逐条不变、不带 `--yes` 时拒绝执行且零改动、旧知识数据确实被替换（防止"什么都
没干"也算通过）。

## 四、P1-1：RAG 服务端身份校验

**问题**：`/api/query`（SSE）没有任何鉴权；`/api/query/json` 只有一个**可选**共享密钥；
nginx 的 `auth_basic` 是注释掉的。知道 `/rag/` 地址就能调用问答接口，不受旧系统角色控制，
消耗模型配额；浏览器侧那个 uid 只用来拼 localStorage key，不是服务端身份。

### 4.1 服务端：用旧后端同一把密钥验签

新增 `RAG/server/auth.py`：

| 安全口径 | 做法 |
| --- | --- |
| 算法白名单 | `header.alg` 必须严格等于 `HS256`——同时挡住 `alg=none`（跳过验签）与 `RS256`（算法混淆，诱导服务端拿公钥当 HMAC 密钥） |
| 常量时间比较 | 签名用 `hmac.compare_digest`，不是 `==` |
| 严格 base64 | `b64decode(..., altchars=b'-_', validate=True)`；宽松解码会放过非法字符，让同一个 token 存在多种可接受拼写 |
| 强制 `exp` | 缺 `exp` 的 token 是永久凭证，泄露后无法作废；旧后端签发的一定带 `exp`，要求它不误伤正常流程 |
| 时钟容忍 | 默认 30s leeway，避免两端时钟有秒级差异时"刚签发就过期" |

**为什么用标准库自己实现而不是引入 JWT 库**：RAG 的依赖由带哈希的锁文件管理、CI 用
`--require-hashes` 安装，环境里既没有 PyJWT 也没在 `requirements.txt` 里声明；为这一处引入
新依赖要重新生成锁文件并补一次供应链审计，而 HS256 验签只用 `hmac`+`hashlib`+`base64`
就写得完整。权衡后选"少一个未审计依赖"，代价是 40 行可读代码 + 逐条拒绝分支的用例。

### 4.2 两条通道的准入

| 通道 | 口径 |
| --- | --- |
| `/api/query`（SSE） | `RAG_REQUIRE_AUTH=true` 时要求请求头 `Token`（也接受 `Authorization: Bearer`）为有效 JWT，否则 401。**校验放在限流之前**：未认证请求不该消耗配额，否则成了免费的配额打击手段 |
| `/api/query/json` | **JWT 或 `X-Bot-Key` 满足其一即放行**。飞书机器人没有用户身份、旧后端也不会给它签 token，要求 JWT 等于把这条调用方堵死 |

身份进入 `request.state.identity`（服务端验签后的事实），不再依赖浏览器 postMessage 自述的
uid。旧后端 `jwt_util.encode` 增加可选 `role` 声明并在登录/注册处写入，RAG 侧因此能一并拿到
角色（老 token 无该声明时取空串——**不猜、不兜底成 viewer**）。

### 4.3 启动门禁：只拦"说的与配的不一致"

- `RAG_REQUIRE_AUTH=true` 但没有密钥 → **拒绝启动**。否则服务起来后每个问答都 401，
  与其等用户反馈"全挂了"，不如启动即失败。
- 未开启校验 → 只告警（写日志 + 进 `health.warnings`），**不阻断**。
  理由：`nginx auth_basic + 只监听回环` 是合法且已被文档记录的内网部署方式
  （审查报告自己也把这条列为可接受的替代），一刀切成启动失败会把可用部署判成坏配置。
- `/api/health` 增加 `auth` 子对象（`required` / `jwt_configured` / `bot_key_configured`），
  让运维一眼看出"这个部署到底验不验身份"，不必去翻环境变量文件；密钥本身从不出现在响应里。

### 4.4 前端与部署

| 位置 | 改动 |
| --- | --- |
| `frontend/.../RagAssistant.vue` | postMessage 载荷增加 `token`。**用 postMessage 而不是拼进 iframe URL**：URL 会进浏览器历史与各级访问日志，而 token 是登录凭证 |
| `RAG/frontend/src/api/authToken.ts` | 新增：内存保管（**不放 localStorage**——主应用会在 iframe 每次 load 后重发，不需要它跨会话存活）+ 严格清洗（含空白/换行的值一律归零：进 HTTP 头会被 fetch 拒绝，甚至有注入额外头的空间） |
| `RAG/frontend/src/api/http.ts` / `sse.ts` | 两类请求都带身份头。`http.ts` 原注释写"不携带登录态"，开启校验后首屏词典与健康检查会直接 401，一并改掉 |
| `deploy/nginx/china-war.conf` | 第 3 节重写为"二选一"：方案 A 服务端验签（推荐，注明**直接打开 `/rag/` 将无法问答**是预期效果）、方案 B 反代层 `auth_basic` |
| `deploy/env/rag.env`、`RAG/.env.example` | 补 `RAG_REQUIRE_AUTH` / `RAG_JWT_SECRET` 及其"两处必须同值"的提醒 |

**验收**：`RAG/tests/test_rag_auth.py` 34 例——纯函数 21 例（alg=none、RS256、签名篡改、
换密钥签名、改 payload 沿用旧签名、过期、容忍窗口、缺 exp、尚未生效、缺 user_id、5 种畸形
token、空密钥 fail-closed、Bearer 与 `Token` 优先级），路由 13 例（两条通道的 401 与放行、
伪造凭证仍 401、校验先于限流、未开启校验时行为不变、开启校验后 Bot Key 仍可用、
**只配密钥未开开关时不阻断**、**配了 Bot Key 时头值不对仍 401**、health 的 `auth` 段与两类
告警、启动判定）。前端 `tests/unit/auth-token.test.ts` 4 例**断言真实发出的 Request**（拦
fetch），而不是"某函数被调用过"。

> 路由层最后两条是本轮**自己查出并修掉的一个缺陷**。第一版 `_resolve_identity` 一上来就看
> `RAG_REQUIRE_AUTH`，于是"只配了密钥、忘了开开关"（正是配置校验会提示的那种疏忽）会让它

> 正确的切分是：**开关只决定"验不过时拦不拦"，与"要不要尝试验签"是两件事**。前者由开关控制，
> 后者只看有没有配密钥；两条分别有用例钉住，避免以后再退化成"配一半就全挂"。

## 五、P1-2：外键打开 + 删除节点的关系级联

**问题**：`models.py` 声明了外键，但 `PRAGMA foreign_keys` 默认是**关**的，声明因此只是一句
注释；删掉一个已被关系引用的事件，关系表会留下指向不存在 id 的孤儿行（本机库实测
`PRAGMA foreign_keys = 0`）。

两条独立的事，**只修一条都不够**：只开外键 → 删除直接报 `FOREIGN KEY constraint failed`
（从"留脏数据"变成"删不掉"）；只做业务层删除 → 绕过接口的写入仍能造出孤儿行。

| 层次 | 改法 |
| --- | --- |
| 数据库层 | 连接钩子里 `PRAGMA foreign_keys=ON`（必须逐连接、且在事务外——PRAGMA 在事务内静默无效，连接钩子正是事务外） |
| 表定义 | 四张关系表的外键补 `ondelete='CASCADE'`。**只对新建的表生效**（`create_all()` 不会改已建好的表），存量库靠下面这条业务层路径 |
| 业务层 | `DbUtil.delete_node` 先删引用方关系行、再删实体行，与实体同一次提交（中途失败整体回滚，不会出现半删状态）。删除范围由 `_relation_models_for` 的显式映射给出——不拼表名，拼错了会静默变成"什么都没删" |
| 可观测 | 响应里带 `removed_relations`：删除是级联的，操作者要知道这一下删掉的不止一个节点 |

**验收**：`backend/tests/test_node_delete_cascade.py` 5 例——外键确实是开的（`PRAGMA` 查值）、
删事件连带删四类关系且计数归零、删地点/人物/组织各自连带自己的关系且不牵连事件、
只删引用被删节点的那几条（不误删指向其他事件的关系）、**绕过业务层直接插孤儿关系行会被
数据库拒绝**（这条同时是"外键真开着"的证据）。

## 六、P1-3：SQLite → Neo4j 双写的补偿队列

**问题**：写节点/属性都是"先提交 SQLite，再调 Neo4j"，失败时只在响应里带一句
`sync_status=failed`——没有记录、没有重试、没有补偿。管理台列表与图谱从此长期不一致，
而且**没人知道差在哪一条**（`consistency_check.py` 只能发现数量差）。

新增 `backend/sync_compensation.py` + `Neo4jSyncJob` 表：

| 设计选择 | 理由 |
| --- | --- |
| 落在 SQLite 而不是内存队列 | 进程重启（部署、崩溃）不该丢掉待补偿的写入 |
| 记录**属性快照**而不是只记 id | 重放要复原的是"当时那次写"；改成重放时重读当前行会把之后的修改一起写过去，把"这次差了什么"掩盖掉 |
| 重放是 upsert | `MERGE` 节点 + `SET` 属性，天然幂等，重复重放不产生重复节点 |
| 同一节点连续失败合并成一条 | 否则一次网络抖动留下几十条指向同一节点的任务，重放时对同一节点反复写，而我们要的只是"它还没同步上"这一个事实 |
| 有尝试上限（5 次）转 `abandoned` | 一个持续失败的节点（如同名节点多于一个）重试一万次也不会成功，只会把日志与队列塞满。转人工后**留在表里**，不是删掉 |
| 记账自身绝不抛异常 | 它跑在主流程**已经失败**的路径上，再冒泡一个异常只会盖住原始的 Neo4j 错误 |

**入口**：管理员/编辑可访问的 `GET /api/sync/pending`（列表 + 各状态计数）与
`POST /api/sync/retry`（批量重放，受 `require_write_role`——它只影响图谱侧可见性，与 editor
已有的写节点权限同类）；另给 `backend/retry_sync.py` 命令行入口（`--list` / 重放，退出码
可用于 cron：有失败或已放弃即 1）。两者调用同一个 `retry_pending`，不存在两套逻辑。

**边界（如实说）**：只补偿**节点属性**这一路；关系的双写仍由 `sync_sqlite_to_neo4j.py` 的
全量/增量同步承担。**删除失败不进队列**——SQLite 已经删了，按名重放删除需要"同名同类型
唯一"这类判断，有歧义的动作不自动做（与 `_delete_neo4j_by_name` 的"宁可不动"口径一致）。

**验收**：`backend/tests/test_sync_compensation.py` 10 例，含"记账失败不抛异常"、
"一条失败不堵住后面的"（逐条独立）、以及端到端一例——`DbUtil.create_node` 的 Neo4j 失败
路径必须落下待办，且主存储照常写入。

## 七、P1-4：旧前端登录页资源路径

**问题**：vite 的 base 是 `/static/`，而 `public/` 下的资源原样拷贝、不改名、**也不会被构建器
补上前缀**。于是三处引用写错，构建与组件测试都不报错：

| 形态 | 位置 | 生产表现 |
| --- | --- | --- |
| 漏前缀 | `views/login/index.vue` 的 `<img src="/login.jpg">` | nginx 按 `location /` 转给旧后端 Flask → 404 |
| 相对路径 | 同文件 CSS 的 `url(background.jpg)` | 相对 `dist/assets/*.css` 解析成 `/static/assets/background.jpg`；**更糟的是 vite 解析不到时会把整条 `background` 声明从产物里删掉**（实测修复前 dist 的 `.login-wrap` 规则里完全没有 background-image，页面上背景直接消失） |
| 同第一形态 | `layouts/BasicLayout.vue` 的 `<img src="/icon/logout.svg">` | 退出按钮图标 404（审查报告没提，属同类缺陷，一并修） |

**改法**：三处都改用 `import.meta.env.BASE_URL` 前缀（`loginImage` / `wrapStyle` 绑定，
`logoutIcon`）。用 BASE_URL 而不是写死 `/static/`：写死会在改 base 或换部署前缀时再犯同一次错。

**新增门禁** `frontend/scripts/check-dist-assets.mjs`，接进 `build:check`（CI 会跑）：

- **源码规则**：`src/` 下所有绝对根路径资源引用必须带 base；**裸文件名 + 资源扩展名**判错
  （vite 会相对当前文件解析不到并删掉声明）。判据刻意收窄，`url(../../assets/x.png)`、
  `@/assets/...`、完整 URL、`data:` 都不误伤；扫源码前**先剥注释**——注释里写示例路径不该
  被判成缺陷，也不该靠"别在注释里写"来维持门禁。
- **产物规则**：dist 里 `/static/...` 的每条引用都要真有其文件。
- **两条都要求"解析必须命中引用"**：一条都没命中说明检查已与产物脱节，此时"零失败"是假通过。

**验收**：拿 `git show HEAD:` 取修复前的三个文件到临时目录跑源码规则 → **三处缺陷全被命中**；
修复后的源码与产物 → 通过。另加组件用例 `asset-paths.test.ts` 2 例断言渲染出的 `src` 与
内联 style 确实带 `/static/` 前缀（`vitest.config.ts` 同步设 `base: '/static/'`，否则测试环境
拿到 `BASE_URL='/'`，断言与生产路径脱节等于没测）。

## 八、P1-5：空角色启动迁移改为 viewer

**问题**：`ensure_user_table_schema()` 对 `role IS NULL OR role=''` 的历史账号执行
`role='admin'`，而这条迁移**每次启动都跑**。任何来源的空角色行（导入、手工写库、旧版本
遗漏）都会在下一次重启时静默提权；它与 `DbUtil.get_role` 的最小权限兜底正好相反——同一个
空值，读接口按 viewer 放行，启动迁移却把人写成了 admin。

**改法**：回填 `viewer`，并在注释里写明"首个管理员不再靠这条迁移产生"。配合 P2-6 的显式
引导命令，形成"迁移只做最小权限回填、提权一律走显式动作"的口径。

**验收**：`backend/tests/test_role_backfill.py` 5 例——空值（NULL 与空串两种）回填 viewer、
已有角色不被覆盖、回填结果与 `get_role`/`to_dict` 口径一致（否则界面显示与实际权限对不上）、
迁移幂等（每次启动都跑，必须连跑两次无变化）、以及端到端一例：回填后的账号调写接口确实
拿到 403（而不是只改了显示值）。

### 9.3 P2-3：并入模式体积门禁假通过

`/rag/assets/...` → 一条都匹配不上，打出"入口 0.0 kB / vendor 0.0 kB / 首屏合计 0.0 kB，

| --- | --- |

### 9.4 P2-2：向量可用状态的假阳性

**问题**：`vector_available=True` 只说明"制品能加载 + 客户端已装配"，但查询侧 embedding 是
**网络调用**——密钥失效/端点不可达时制品与客户端依然完好，查询静默降级成关键词，health 却
报"向量可用"。审查当次 RAG 349 例里唯一失败的 1 例就是这么来的。

| 改法 | 说明 |
| --- | --- |
| 状态拆解 | `vector_artifact_ready` / `embedding_client_configured` / `embedding_probe_ok`（None=尚未探测）/ `last_vector_error` / `effective_text_mode` / `vector_error_count`，由 `TextSearcher.vector_status()` 统一产出 |
| 诚实报告模式 | 向量通道**报错**时 `mode` 如实报 `keyword`——不能因为关键词兜底出了结果就继续报 `vector`/`hybrid`。判据是"本次调用里错误计数是否增加"，与"返回空结果"（可能是真的没有近邻，不算故障）分开 |
| health | 增加 `vector` 子对象；`embedding_probe_ok is False` 时进 `warnings`（"声明可用但查询期失败"必须显式告警，而不是静默降级） |
| 不做启动期网络探测 | 那会把服务可用性绑到外部端点超时上（启动慢、离线起不来）；运行期是否真的能用由探针如实记录 |
| 测试离线化 | `tests/conftest.py` 提供确定性桩向量客户端（文本哈希派生、单位长度）。`test_chain_smoke` 的 runtime 夹具换上它——这些用例考的是"模式是否透传到检索"与"有没有结果"，不是检索质量；跑真端点会让断言依赖网络与密钥，那 1 例长期失败正是如此 |

**验收**：`RAG/tests/test_vector_health.py` 6 例（三字段各自独立、缺客户端不声称可用、
查询期失败留下原因且模式如实降级、hybrid 下向量半边故障同样降级、向量返回空不算故障、
health 子对象与告警），加上原先失败的 `test_text_mode_passthrough_and_autodowngrade` 转绿。

### 9.5 P2-5：飞书机器人的白名单与并发边界

| 项 | 改法 |
| --- | --- |
| 白名单 | `FEISHU_ALLOWED_CHAT_IDS` / `FEISHU_ALLOWED_OPEN_IDS`，逗号分隔；**命中任一即放行**，两个都空 = 不限（内网默认行为逐字不变）。判定在服务端，卡片回调同样过闸（否则被移出名单的群仍能点旧按钮继续提问）。不在名单内**不回执**：回一句"无权使用"等于对外暴露机器人存在，而白名单的用意本就是不想让这些人用 |
| 队列上限 | `queue.Queue(maxsize=QUEUE_MAX_SIZE)`（默认 200）。**非阻塞 `put_nowait`**：本方法跑在飞书 SDK 的 ws 事件循环线程里，`put()` 阻塞会把 ping/重连一起卡住，触发飞书判定"未应答"而重投——比丢消息更糟。满时计数 + 记日志 + 可选提示 |
| 忙时提示 | 用独立后台线程发送（发消息是几百毫秒的 HTTP 调用，在回调线程里做会拖住心跳），按会话冷却（默认 30s，避免提示本身变成新的消息风暴），失败只记日志 |
| 配置校验 | `QUEUE_MAX_SIZE<=0` 直接拒绝：`queue.Queue(maxsize<=0)` 表示**无界**，正是本项要修的问题，不能让人以为填 0 是"关闭限制" |

**未做**：分片 worker（按 `session_key` 分片串行 + 全局并发上限）与监控。审查报告把这条放在
第三批，本轮按它的优先级执行；单 worker 的现状已在配置与日志里写明为起步期上限。

**验收**：飞书用例从 279 增至 289，新增 10 例覆盖两份名单的或关系、白名单外消息与卡片回调
都不入队不回执、队列满时快速拒绝、忙时提示被发出、提示按会话冷却、提示可关闭。

## 十二、给部署方的动作清单（代码之外）

1. **轮换判断**：确认 `deploy/env/*.env` 里曾经出现过的口令与 JWT 密钥是否在真实环境用过；
   用过就轮换 Neo4j 口令与 `JWT_SECRET`（模板现在只有占位符）。
2. **RAG 对外部署**：二选一——`RAG_REQUIRE_AUTH=true` + `RAG_JWT_SECRET`（与 backend 的
   `JWT_SECRET` 同值），或 nginx 给 `/rag/` 开 `auth_basic`。两者都没做时
   `/api/health` 的 `warnings` 会一直提示。注意方案 A 下直接打开 `/rag/` 无法问答。
3. **首次管理员**：用 `python create_admin.py --account <账号>`，不要再手写 `UPDATE`。
4. **飞书白名单**：机器人若不再只是自己人用，先配 `FEISHU_ALLOWED_CHAT_IDS` /
   `FEISHU_ALLOWED_OPEN_IDS`。
5. **双写补偿**：出现 `sync_status=failed` 后，先 `python retry_sync.py --list` 看清单，
   再决定重放或人工核对；`abandoned` 的条目通常意味着 Neo4j 侧有同名同类型节点。
