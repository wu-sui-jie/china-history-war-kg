## 二、飞书机器人：停机死锁与消息永久丢失

对应文档第七节。

### 修了什么

| 缺陷 | 原实现 | 现实现 |
| --- | --- | --- |
| **停机死锁** | `stop()` 用 `queue.put(None)` 唤醒 worker；队列满时永久阻塞，`main.py` 的停机流程走不到 `close()` | worker 改为 `get(timeout=0.5)` 轮询 `_stop`，停机只依赖一个 Event；`stop()` 只置位 + join，超时记 WARNING 并说明队列剩余条数 |
| **消息永久丢失** | 先写 `processed_events` 认领、再入队；队列满被拒后事件已标记处理，飞书重投被自己的去重记录挡掉 | 认领 → 入队 → **入队成功才 call 实**。失败时 `release()` 把状态改成 `rejected_busy`（可重投）；无 `event_id` 的卡片回调则删掉内存窗口键 |
| **假承诺** | 卡片回调队列满也回 `正在查询…` | 队列满回 `warning` toast + 真实的繁忙文案 |
| **无监控** | 只在拒绝时打一行日志 | 新增 `queue_snapshot()` 与每 60 秒一条的队列观测（有积压或拒绝时 WARNING，否则 DEBUG） |

### 事件状态机

`received` → `accepted` → `processing` → `done`，另有 `rejected_busy` / `failed`。
`processed_events` 新增 `status` 列（老库由 `bot/db.py` 的加列迁移补上，默认 `accepted`
以保持既有去重行为）。`failed` **刻意不参与重投重试**：异常很可能发生在"回答已经发出去"
之后，重投会给用户发第二条回答，比静默丢掉一条更难解释。

### 关键取舍

- **不用哨兵消息唤醒**：哨兵路径的问题就是"队列满是阻塞点"，换成轮询后停机不再依赖队列状态；
  代价是停机最多慢 0.5 秒。
- **IP/账号等维度的"入队失败"痕迹保留在库里**（`rejected_busy`）而不是删除：删除会让
  "被拒了多少次"这件事在事后完全查不到。

### 验证

- `feishu-bot/tests/test_dispatcher.py` 新增 8 例：队列满时 `stop()` 不阻塞（不放行则用例挂死）、
  被拒事件可被重投、已坐实的认领仍去重、worker 状态推进到 `done`/`failed`、卡片回调繁忙 toast、
  退化窗口释放、老库补列迁移。
- 全量：**297 passed**（原 289 + 8），`ruff check .` 通过。

## 三、RAG 鉴权：模式分档 + 生产拒绝 disabled

对应文档第三节。

### 修了什么

1. **`RAG_AUTH_MODE` 三档**（`jwt` / `nginx` / `disabled`）。原先只有一个布尔
   `RAG_REQUIRE_AUTH`，于是"nginx 在把关"与"根本没人在把关"在配置里长得一模一样。
   旧开关仍被接受（`true` ≡ `jwt`、`false` ≡ `disabled`），老配置行为一字不变。
2. **显式生产档下 `disabled` 拒绝启动**。文档的原话是"应拒绝启动，而不是只输出警告"——
   原先这条只打 WARNING，而 WARNING 会被忽略，漏配的人根本不会去看日志。
3. **`nginx` 档 + 非回环监听 → 拒绝启动**（在 `scripts/run_server.py`，因为只有那里知道真实监听地址）。
   否则同网段可以直连后端端口绕过 nginx，"配了 nginx 认证"是一句假话。
4. **JWT 补 `iss` / `aud`**（文档第三节第 4 条）：验签只证明"这把密钥签的"，`iss`/`aud`
   才证明"是谁为谁签的"。同一把 HS256 密钥被多个服务共用时，缺这两项等于谁签的都收。
5. **`sub` 与 `user_id` 都认**：标准声明与既有契约指向同一事实，签发端将来只发 `sub` 时
   两端不必同时上线。
6. `/api/health` 的 `auth` 增加 `mode` 字段——`required=false` 区分不了"nginx 在把关"
   与"没人在把关"，只有模式能。

### 验证

- `RAG/tests/test_rag_auth.py` 现有 **46 例**（`pytest --collect-only` 实测；第 12 轮记录的全套为 389，
  本轮改动后全套 401，净增 12）。新增覆盖生产档拒绝 `disabled`、开发档只告警、
  `nginx` 档放行、模式拼错（`none`/`off`/`false`/`basic`）拒绝、大小写容忍、
  新旧配置优先级、`iss`/`aud` 不符与缺失拒绝、纯函数层不传期望值时不拦、`sub` 兜底、
  identity 形状稳定。
- 全量：**401 passed**（原 389 + 12），RAG CI 的 ruff 门禁通过。

## 四、登录限流、注册开关与 token 撤销

对应文档第五节与第十一节。

| 项 | 实现 |
| --- | --- |
| 限流两把尺子 | `login_guard.py`：同 IP **每次尝试**计数（默认 10 次/分钟，60 秒窗口）、同账号**连续失败**计数（默认 5 次锁 15 分钟） |
| 超限响应 | **HTTP 429** + `retry_after` + `Retry-After` 头（复用登录失败那套 `200 + code 403` 会丢掉"等多久"的信息） |
| `token_version` | `UserInfo` 新增 `token_version` / `disabled` 列；`app.before_request` 每次回库校验，改密码/停用/删号后旧 JWT 立刻失效 |
| 改密码接口 | 新增 `POST /api/user/password`，校验旧口令 + 新口令策略（10–64 位），成功后 `token_version +1` |
| 停用接口 | 新增 `POST /api/admin/users/<id>/status`，停用时同时 `+1`（纵深防御），**不允许停用自己**（否则最后一个管理员能把系统锁死） |
| 注册开关 | `ALLOW_SELF_REGISTRATION`，默认 `true`（不改变既有行为），公网部署必须设 `false` |
| 注册限流 | 注册成功也算一次 IP 尝试——被滥用的正是"成功建号"这个动作 |

### 关键取舍

- **X-Forwarded-For 默认不采信**：那是客户端自己能写的头，采信等于把限流交给攻击者决定
  （伪造一堆 IP 就绕过了）。只有显式 `LOGIN_TRUST_FORWARDED_FOR=true`（本项目部署形态是
  nginx 在前面）才按 XFF 第一段计数。
- **IP 维度不清零**：清 IP 会让"用自己的合法账号登录一次"变成重置配额的手段。
- **IP 维度不写 `locked_until`**：按来源地址"锁一段时间"会连带挡住同一出口 NAT 后面的所有人。
- **口令下限提到 10 位，但只在"设置口令"的路径生效**（注册、改密码）。登录路径**不校验长度**——
  策略提高前建的老账号口令可能只有 6~9 位，服务端本来就接受，前端照搬策略会把他们锁在门外。
  （这条是本轮自己踩到的坑：第一版把校验也加到了登录表单上，已纠正并加了用例钉住。）
- **7 天有效期没有直接改短**：本系统只有访问 token、没有 refresh token，调短等于部署后所有人
  立刻被登出、之后每半小时再登出一次。文档建议的 15–30 分钟必须与刷新流程一起做；
  当前用的撤销路径是 `token_version`，它覆盖了实际的安全需求（改密码/封号后旧凭证立刻失效）。

### 验证

- 后端新增 `tests/test_login_guard.py`（10 例）与 `test_admin_users.py` 的 5 例：
  IP 限流 429、账号锁定、成功清零、停用账号不能登录、注册开关、注册限流、
  XFF 不采信与显式信任、口令强度、改密码后旧 token 失效、停用/启用语义、管理员不能停用自己。
- 前端新增 `tests/component/login-failure.test.ts`（5 例）：429 与 403 的文案要显示出来、
  网络错误回落兜底、**登录不校验口令长度**、注册校验下限。

## 五、旧后端统一错误响应

对应文档第九节。**这是本轮唯一"部分完成"的项**，先说什么做了、什么没做。

### 做了：框架层统一（`backend/api_errors.py`）

改造前，框架层的错误返回的是 **Flask 的 HTML 页面**：未捕获异常 → 500 HTML（调试模式还带
完整堆栈与本地变量），路径/方法不对 → 404/405 的 HTML。前端只有 `apiErrorMessage` 一处会读
`error.response.data.msg`，拿到 HTML 时读不到任何文案，界面只能显示通用的"操作失败"——
服务端明明知道原因，用户看不到。

现在统一成 `{code, msg, message, data, request_id}` + 对应 HTTP 状态，并保证三件事：

1. **内部异常不外发**：500 只回安全文案，真实原因（含堆栈）进日志并带同一个 `request_id`；
   不回 `str(e)`（那会把文件路径、SQL、库名一起送出去）。
2. **已有响应不覆盖**：路由自己返回的 `{code, msg}` 一字不变（登录失败仍是 `200 + code 403`）。
3. **可追踪**：`request_id` 优先取上游 nginx 传来的 `X-Request-Id`（做 ASCII/可打印校验后才沿用），
   否则生成，并写进响应头。

同时给写路由加了 `json_body()`：请求体**必须是 JSON 对象**。原先 `data = request.json` 后直接
`data.get(...)`，请求体是数组/字符串时抛 AttributeError → 被兜底 `except` 收成 **500 +
`str(e)`**，于是一次参数错误在响应里表现为"服务器内部错误"。node.py 的 5 个写/查路由已改用它。

### 没做：per-route 业务码迁移

文档给的 `code` 是**字符串**（`"NODE_NOT_FOUND"`），而前端所有页面都按数值 `code == 200` 分支，
`frontend/src/utils/apiError.ts` 也读 `msg`。把 code 换成字符串是一次**跨端迁移**（前端、快照用例、
文档同时改），不是修缺陷；本轮先把"框架层错误没有 JSON 形状"这个真实缺口补上，并**同时给出
`message`**（文档用的字段名），让将来迁移时前端有现成字段可读。

同理，其余路由里仍有多处 `{"code": 500, "msg": str(e)}`（现为 HTTP 200 + 泄漏异常文本），
本轮只改了 `blueprints/node.py` 的写路径。**逐路由收敛是下一步**，改动面大但机械。

### 验证

后端新增 `tests/test_api_errors.py`（9 例）：404/405 是 JSON、未捕获异常返回 500 且不外发
内部信息、`request_id` 生成与采信上游、非法追踪号被丢弃、路由自己的响应不被改写、
未带 token 仍是 401、非法请求体不产生 500。

## 六、Neo4j outbox：事务性与稳定图谱键

对应文档第六节。**这是本轮最深的改动**，因为文档第一节阶段一把它排在第一。

### 修了什么（对照文档列的 A~F 六个问题）

| 文档问题 | 修法 |
| --- | --- |
| **A. 不是事务 Outbox** | 业务修改与待办在**同一次 SQLite 提交**里落库（`flush` → `stage_job` → `commit`），提交后再尝试立即写 Neo4j。崩溃窗口只剩"写完 Neo4j 没标 done"，而那一侧是幂等的 |
| **B. 重放成功不回写 `neo4j_id`** | `apply_job()` 成功后回写（只在原值为空时补，不覆盖已有的非空 id——那是主存储里可能正确、且重建前的值） |
| **C. 更新可能变成新建** | 任务里保存 `operation` 与 `from_name`。改名重放后清理"**没有 graph_key** 的同名历史节点"——只动旧体系的节点，不误伤新体系里同名的其他对象 |
| **D. 删除和关系不补偿** | 删除**已纳入**（`node_delete`）：有了稳定图谱键，"按名重放删除有歧义"这个原理由不再成立。**关系（四类）仍未纳入**，见下 |
| **E. 没有自动重试** | `next_retry_at` 退避落库（30 秒 → 2 分钟 → 10 分钟 → 1 小时 → `abandoned`），新增 systemd timer 每分钟跑 `retry_sync.py --due-only`；进程重启不会让退避归零 |
| **F. 重导后旧任务可能失效** | 新增 `app_meta` 表存"数据重导代数"，`import_json_to_sqlite.clear_migration_tables()` 重导时 `bump_dataset_version()`，**作废所有 pending 任务**（否则会把上一批数据重新写进图谱，且没有任何报错） |

### 稳定图谱键

`graph_key = "<NodeType>:<SQLite 主键>"`（`backend/graph_key.py`）。按名字 MERGE 会把同名节点
合成一个（"赤壁之战"在不同来源里确实有多个），改名又会被当成新建；按 `id(n)` 定位则不抗重建
（全量重导、恢复备份后 id 全变）。`graph_key` 由主存储决定，重放/重建/改名都不影响定位。
`neo4j_id` 保留并回写，但降级为**观测信息**，不再是任何写入路径的定位依据。

**迁移**：改造前建的无键节点会在第一次 upsert 时被**认领**（`MATCH (n:Label {name}) WHERE n.graph_key IS NULL` → `SET n.graph_key`），
因此升级后不会凭空多出一份重复节点。管理台写入路径（`db_utils`）与全量同步脚本
（`sync_sqlite_to_neo4j._create_node`）已统一到同一套语义。

### 一并删掉的旧机制

`DbUtil._find_neo4j_by_name` / `_delete_neo4j_by_name` / `_update_neo4j_by_name` 三个"按名回退"
辅助函数已删除：它们正是"同名多于一个时改错对象"的来源。历史遗留节点改由 upsert 的认领步骤接管。

### 没做：关系类进 outbox

关系的双写仍由 `sync_sqlite_to_neo4j.py` 的全量/增量同步承担。纳入 outbox 需要先给关系行
一个稳定键——关系没有主键可对标，要用"两端 graph_key + 关系类型"拼，那是一次独立重构
（还要处理关系删除、关系属性变更两类动作）。当前的组合是"节点级 outbox + 关系靠全量同步兜底"，
`backend/README.md` 已写明这个边界。

### 没做：py2neo → 官方 driver

文档第十三节建议加 `backend/neo4j_client.py` 适配层换成 `neo4j.GraphDatabase`。这是文档
**第十四节迁移阶段 3** 的工作，且依赖"阶段 2 先跑通纯测试"。本轮保留 py2neo，理由：
它是"统一到 3.11 就够、不要跳到 3.12"的主因（py2neo 最后一版 2021.2.4，未声明支持新版），
换驱动需要新增依赖 + 重走一次供应链审计 + 真实 Neo4j 集成回归，不该和 outbox 改动混在一次里。

## 七、Python 3.11 统一环境

对应文档第十四节。**建立了声明，没有做版本迁移实测。**

新增根 [`pyproject.toml`](../pyproject.toml)，按 `backend` / `extract` / `rag` / `bot` / `dev` / `all`
分组声明依赖，统一 `requires-python = ">=3.11,<3.13"`、SQLAlchemy 2、Pydantic 2、pytest/ruff 版本。

**如实说明三件事**（文件头也写了同样的内容，避免被误读成"迁移已完成"）：

1. **它还不是锁文件**。文档阶段 5 要求的可复现 lock 必须在六套测试全绿之后生成，
   否则锁的是"还没验证过的组合"。本轮没生成。
2. **backend 在 3.11 上能否全绿未经实测**。本机现状是 backend 跑在 Python 3.8 + SQLAlchemy 1.4
   （`place-name-KG` 环境，110 passed），RAG 与 feishu-bot 跑在 Python 3.11（`AI_Agent` 环境）。
   3.11 环境里缺 `flask_sqlalchemy` / `py2neo` / `PyJWT`，装上之后的行为差异（尤其
   SQLAlchemy 1.4 → 2.0 的 `Query.get()` 这类已废弃用法）需要逐条跑过才算数。
3. **CI 没有加 3.11 的 backend job**。文档阶段 6 说"先增加 3.11 job、保留 3.8"，但那要建立在
   "3.11 上确实全绿"的前提上；加一个必然失败的 job 只会让 CI 长期变红。
   因此本轮只做到阶段 1（声明目标）。

`pyproject.toml` 的合法性已用 pip 实测：
`pip install --dry-run -e ".[all]"` 能正确解析自引用 extra 并列出缺口依赖（`Flask-SQLAlchemy`、
`py2neo`、`PyJWT` 等），退出码 0。

## 九、刻意没有做的事（含原因）

| 项 | 为什么不做 |
| --- | --- |
| 关系（四类）纳入 outbox | 需要先给关系行拼稳定键（两端 graph_key + 关系类型），是独立重构；当前由全量/增量同步兜底，边界已在 README 写明 |
| py2neo → Neo4j 官方 driver | 文档迁移阶段 3 的工作，需新增依赖 + 供应链审计 + 真实集成回归；是本轮 outbox 之外的一次独立改动 |
| Python 3.11 上 backend 实测与 CI job | 见第七节：要先确认全绿，否则 CI 长期变红 |
| 生成全仓 lock | 必须等六套测试全绿之后（文档阶段 5） |
| per-route 业务码迁移（字符串 `code`） | 跨端迁移而非缺陷修复；本轮先补"框架层没有 JSON 形状"这个真实缺口 |
| 访问 token 缩短到 15–30 分钟 | 没有 refresh token，直接调短等于把所有人在部署后立刻登出；撤销需求已由 `token_version` 覆盖 |
| 服务端问答历史、多租户、多实例限流 | 文档第三阶段事项（用户规模扩大后） |
| 关系在线 CRUD | 文档明确的**产品决策**项，不是技术债；待产品确认是否需要在线维护关系 |
| 飞书会话分片 worker | 文档第七节第 3 条属于扩容阶段；P0 单 worker 是已记录的起始并发上限 |

   人为制造一次 Neo4j 失败（停 Neo4j → 管理台改一条节点 → 起 Neo4j → 等一分钟），
   确认待办被自动补齐——这是本轮新增机制唯一还没在真实部署里走过一遍的路径；
