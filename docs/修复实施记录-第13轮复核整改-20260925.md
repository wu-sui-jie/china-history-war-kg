## 二、登录限流：落库时间从 monotonic 改为 UTC epoch

对应复核清单第三节。

### 问题回顾

`login_guard.py` 把 `time.monotonic()`（开机以来的秒数）写进 SQLite 的
`window_start` / `locked_until` / `updated_at`。这个数只在**同一次开机**内可比：

```text
开机 5 天后   monotonic = 432000 → 写下的锁定截止 = 432900
机器重启后    monotonic = 30
比较          30 < 432900 → 判定"还要锁 432870 秒"
```

反向同样成立：老机器读到一个刚重启过的旧值，会把有效锁定当成早已过期，限流直接失效。

### 改了什么

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 落库时间 | `time.monotonic()` | `time.time()`（UTC epoch 秒） |
| 列名 | `window_start` / `locked_until` / `updated_at` | `window_start_epoch` / `locked_until_epoch` / `updated_at_epoch` |
| 旧数据迁移 | 无（两种时间基准混在一列） | 检测到旧列名 → **整表 `DROP`** 再按新结构重建 |
| 异常时间戳 | 无防护 | 比 `now + 锁定秒数 + 300s` 更远的"未来"值被判为异常并丢弃该行 |

### 关键取舍

- **列名带 `_epoch` 后缀**（复核清单只要求"改注释或改列名"）：注释会被后来者忽略，
  列名不会。把"这个数是绝对时刻还是开机以来的秒数"写进结构里，才挡得住 `monotonic()` 被写回来。
- **旧表整表作废而不是逐行换算**：monotonic 与 epoch 的换算需要知道"当时那次开机的时间原点"，
  而库里没有任何字段记录它。限流数据是**临时安全状态**不是业务数据，清空的最坏后果是
  锁定提前放行一次；相比之下混着两种基准的错误会随机出现且只能靠读代码解释。
- **异常时间戳按"未失败"处理而不是"继续锁"**：方向选择是有意的——最坏是少拦几次，
  而不是让人无端等几十万秒。
- 进程内缓存（RAG 那边的撤销查询缓存）仍然用 `time.monotonic()`：那个值**不落库、不跨重启**，
  单调时钟正是它的正确用法。两处的口径差异写进了两份模块文档。

### 验证

`backend/tests/test_login_guard.py` 新增 7 例，逐条对应复核清单第 3.5 节的验收项：

| 复核清单验收项 | 对应用例 |
| --- | --- |
| 写入值接近当前 epoch | `test_落库时间接近当前_epoch` |
| 模拟机器重启后时间基准变化 | `test_机器重启换掉_monotonic_基准后锁定仍按配置时长生效`（把 `monotonic` 打桩成 30，剩余锁定必须仍是 ~900 秒） |
| 旧 monotonic 数据不会造成超长锁定 | `test_旧_monotonic_数据不会造成超长锁定` |
| 过期锁定自动放行 | `test_锁定到期后自动放行` |
| ——（异常方向） | `test_远期异常时间戳被丢弃` |
| IP 窗口和账号窗口分别正确 | `test_IP_窗口与账号窗口各按自己的口径` |
| 迁移策略 | `test_旧口径表在升级时整表作废` |

第一条用例本身就是"写回 monotonic"的哨兵：monotonic 与 epoch 相差好几个数量级
（开机几天是十万量级，epoch 是十亿量级），`abs(值 - time.time()) < 5` 足以判红。

## 三、RAG token 撤销：从"验签通过就一直放行"到"会问后端"

对应复核清单第四节。选的是**方案 B（Backend Token Introspection）**。

### 为什么不是方案 A（缩短 token 有效期）

复核清单第 4.3 节把方案 A 列为第一步，理由是"结构简单"。但方案 A 需要 refresh token
与前端刷新流程，而**当前前端没有**（`jwt_util.py` 里对此已有记录：直接缩短默认有效期
等于让所有人在部署后立刻被登出、之后每半小时登出一次）。方案 B 不动用户的登录体验，
只加一次带缓存的服务间查询，并直接满足第 4.4 节全部验收项。方案 C（共享 Redis）
在多实例部署时再考虑（当前单机，为一次查询引入新中间件不划算）。

### 改了什么

**后端**：新增 `backend/blueprints/internal.py`，一个接口：

```text
POST /api/internal/token/introspect
请求头：X-Internal-Service-Key: <INTERNAL_SERVICE_KEY>
请求体：{"token": "<旧后端签发的 JWT>"}
响应：  {"code": 200, "data": {"active": true, "user_id": 3, "role": "viewer",
                              "token_version": 2, "disabled": false}}
```

三条安全边界（都由用例钉住）：

1. **未配置密钥 = 接口 503**，不是"不校验"。一个匿名的 introspection 接口不只是信息泄露，
   还等于给攻击者第二条探测手段（"这张凭证失效没有"）。
2. **失败原因不回给调用方**（响应字段走白名单 `_PUBLIC_FIELDS`），只写服务端日志。
   "改过密码"与"被停用"的区别对排障有价值、对调用方没有，泄露出去等于把账号状态
   变成任何持有旧 token 的人都能查的事实。
3. **公网不可达**：服务只监听回环，且 nginx 对 `/api/internal/` 前缀直接 404（见第四节）。

判定规则**复用 `DbUtil.token_status`**（`check_token_usable` 也改为调它）：RAG 的撤销判定
必须与旧后端自己的守卫逐条一致，否则会出现"旧后端拒绝、RAG 却放行"的裂缝，
而那种裂缝只在改密码/封号之后才显形。

**RAG 侧**：新增 `RAG/server/introspection.py`（查询器 + 缓存），并在两条问答通道的
验签之后插入检查（`server/api.py` 的 `_revocation_rejection`）：

| 设计点 | 取值与理由 |
| --- | --- |
| 缓存 | 按 token 的 **sha256** 做键，TTL 默认 30 秒。TTL 同时就是**撤销生效延迟的上界**；键用摘要是因为内存里的字典可能进崩溃转储 |
| 失败策略 | `RAG_INTROSPECT_FAIL_MODE`：`closed`（默认，拒绝）/ `open`（放行）。默认 closed 的理由：这是**安全**查询，"把后端打挂"不该成为一种绕过撤销的手段；代价是后端故障期间问答不可用，所以 health 会把当前策略报出来 |
| 失败不写缓存 | 把失败当结果缓存下来，会让后端的一次抖动变成这段时间内人人被拒（或人人放行） |
| 只对已验签的请求生效 | 机器人走 `X-Bot-Key`（没有用户身份，也就没有"这张凭证该不该承认"的问题）；"配了密钥但没开 require_auth"的迁移期也不受影响 |
| 不引入新依赖 | 用 `httpx`——它已由 `openai` 作为运行时依赖进了带哈希的 `requirements.lock`（0.28.1），因此不需要重新生成锁文件与重走供应链审计 |

**边界写进可观测处**（复核清单第 4.3 节要求"文档必须明确"）：`/api/health` 的
`auth.revocation` 报出启用状态/缓存秒数/失败策略，未启用时 `warnings` 里持续出现
"账号被停用或改密码后，旧 token 在自然过期前仍可调用问答接口"。文档里写一句不够——
这条边界的正确性取决于**配置**，而配置只有运行中的服务才知道。

### 验证

- `backend/tests/test_internal_introspect.py`：**12 例**——未配密钥 503、密钥不对 401、
  有效 token 返回 active、改密码/停用/删号立刻失效、验签失败按"无效"而不是"查询失败"、
  过期 token、iss/aud 不符、响应不回显 token 与原因、只接受 POST + JSON、
  以及**与全局鉴权同口径**（同一张 token 在 `/api/userinfo` 被 401 时 introspect 必须为 false）。
- `RAG/tests/test_rag_revocation.py`：**18 例**——未配置不拦人、TTL 内只问一次、TTL 过期重问、
  缓存键是摘要、fail_closed/fail_open、失败不写缓存、条目上限淘汰、已撤销结论也缓存、
  响应形状不对按失败处理、非 200 不算"凭证无效"、两个密钥名都认。
- `RAG/tests/test_rag_auth.py` 新增 11 例路由级：已撤销被拒（话术与旧后端一致）、
  未配置不额外拦截、fail_closed 拒绝、fail_open 放行、机器人路径不受影响、
  未认证请求不触发查询、health 口径与告警。
- 附带修掉一处**既有**缺陷：`health` 原先读模块级的 `_settings_boot`，而请求路径读
  `app.state.settings`——正常启动下两者取值相同，所以一直没暴露；一旦不一致，
  "health 说撤销查询开着"与"请求实际没查"就会分叉。现在 health 统一读运行期配置。

## 四、nginx 模式：把"两份配置各看起来都对"变成安装期可判定

对应复核清单第五节。

### 问题回顾

部署模板写 `RAG_AUTH_MODE=nginx`，而 nginx 站点配置里的 `auth_basic` 是**注释状态**。
照着两份模板部署的人会得到：RAG 认为"nginx 在鉴权"（自己不验签），nginx 其实没配认证
（语法与启动都正常）。**两边都健康、日志无异常，唯一后果是公网 RAG 没有访问控制。**

### 改了什么

1. **生产模板默认改 `RAG_AUTH_MODE=jwt`**（复核清单第 5.2 节推荐方案）。除了消除上述歧义，
   还让用户只登录一次旧知识库、不必再记一个 Basic Auth 口令，访问控制与旧系统账号体系同源。
   `deploy/env/rag.env` 里写清了"为什么默认是 jwt"。
2. **新增 `deploy/scripts/check_rag_auth.sh`**：机器可判定的门禁，退出码非 0 即失败。
   | 检查项 | 覆盖的失败模式 |
   | --- | --- |
   | 鉴权模式取值合法；生产档下不是 `disabled` | 拼错取值静默回落、生产漏配 |
   | jwt 档：两侧 JWT 密钥**同值**（含 `RAG_JWT_SECRET` / `JWT_SECRET` 两个名字） | 这套校验最容易踩的坑（表现为问答全 401） |
   | jwt 档：撤销查询要么两边配齐，要么明确告警 | "停用后在 token 到期前仍可用"这条边界被静默继承 |
   | nginx 档：`.htpasswd` 存在且非空、`auth_basic` 处于**启用**状态（正则匹配未注释行）、`nginx -T` **实际生效**配置里 `/rag/` 带认证 | 复核清单发现的原缺陷；只看站点文件会被 include 顺序或其它 location 覆盖骗过 |
   | 两种档位：RAG 只监听回环；nginx 屏蔽 `/api/internal/` | 直连后端端口绕过鉴权、内部接口暴露 |
3. **安装路径上强制**：`install_services.sh` 在"校验配置"与"启动服务"之间调用它，失败即终止安装
   （复核清单第 5.2 节"缺少任一条件则拒绝安装或启动"）。
4. **nginx 站点配置**新增 `location /api/internal/ { return 404; }`，并把 `/rag/` 的访问控制注释
   从"方案 A / 方案 B"改写成"生产默认 jwt；要用 nginx 档则按三步走，第 3 步是跑门禁脚本"。

### 验证

脚本本身用 6 种合成场景实跑（临时目录构造 `.env` 与站点配置，`nginx` 不在本机时该项降级为提示）：

| 场景 | 结果 |
| --- | --- |
| 一切正确（jwt + 两侧密钥同值 + 撤销查询配齐） | 4 项通过、0 失败、退出码 0 |
| 两侧 JWT 密钥不同值 | 失败并指名"必须完全一致"、退出码 1 |
| 撤销查询只配一半 | 失败并指出"会按未启用处理"、退出码 1 |
| nginx 档 + `auth_basic` 仍是注释（复核清单发现的原始缺陷） | 3 项失败、退出码 1 |
| nginx 档 + `auth_basic` 已启用 + `.htpasswd` 非空 | 5 项通过、0 失败 |
| 生产档 + `disabled` | 失败、退出码 1 |

## 五、旧后端 API 错误格式：按蓝图迁移到"正确状态码 + 不外发内部信息"

对应复核清单第七节。第 13 轮已经做完框架层（未知路径/方法不对/未捕获异常 → JSON），
本轮做**各蓝图自己返回的**错误。

### 改前改后

```text
改前：HTTP 200 + {"code": 500, "msg": "invalid literal for int() with base 10: 'abc'"}
改后：HTTP 400 + {"code": 400, "msg": "depth 必须是整数", "message": ..., "data": {...},
                  "request_id": "..."}
```

| 蓝图 | 改了什么 |
| --- | --- |
| `graph.py` | 7 处 `str(e)` 的 500 → `server_error(...)`（保留 `data` 形状）；`/search_name_kg` 改用 `json_body()`（数组/坏 JSON 改前是 500）；`depth` 非法 → 400；节点子图缺参数 → 400；去掉与 `logger.exception` 重复的 `traceback.print_exc()` |
| `workspace.py` | 11 处 `str(e)` 的 500 → `server_error(...)`；实体详情参数缺失 → 400、不存在 → 404 |
| `llm.py` | **删掉 `error_detail = str(e)`**（它会把绝对路径/连接串/库名送给客户端）；兜底 `except` 的 `logger.warning` + `traceback.print_exc()` 改为 `logger.exception`；问答通道的响应形状（`success`/`error`/`answer`/`kg_data`）刻意**保持不变**，因为它是前端 inference 页的契约，不在本次迁移范围 |
| `node.py` | 两处"静默 500"（HTTP 200、**且没有任何日志**）→ `server_error`；8 处参数校验/404 加上真正的 HTTP 状态；分页参数非整数 → 400；四个写接口的 `DbUtil` 结果改由 `_result_response` 透传业务码为 HTTP 状态（见下） |
| `db_utils.py` | 四个写方法的 `f"...失败: {str(e)}"` 改为安全文案 + `logger.exception`；`find_node_page` 的 except 不再吞掉异常（原先失败在客户端表现为"列表是空的"、日志里毫无痕迹，且 `error` 字段带着 SQL 与库路径回前端） |

`api_errors.error_payload` 增加 `data` 参数：列表接口失败时要保住空列表形状，
否则前端会在 `data.map` / `data.events` 上崩（这条原先只在 `server_error` 里做了）。

**写接口的业务码也要变成 HTTP 状态**：`DbUtil` 的写方法用 `{code, msg}` 表达结果
（200/400/404/500），而 `node.py` 的四个写路由一律 `jsonify(result)` → HTTP 200，
于是"节点不存在"在监控、反代与前端重试逻辑眼里是**成功**。现在统一走
`_result_response(result)`：HTTP 状态取同一个 code。前端两条分支都会显示后端文案
（`useNodeCrudPage` 既有 `res.code !== 200` 分支，也有读 `error.response.data.msg` 的
catch 分支），所以对用户可见行为没有影响。

**刻意保留的一处**：`/api/login` 与 `/api/sign_in` 的失败仍是 `HTTP 200 + code 403`。
它是登录页与快照用例的既有契约（前端按 `code` 分支），改成 4xx 属于跨端契约变更而不是
修缺陷；限流是新状态，用 429 表达（第 13 轮已做）。这条口径由
`backend/tests/test_api_errors.py::test_路由自己的响应形状不变` 钉住。

### 前端同步：失败路径的提示不能丢

状态码从 200 变成 5xx 之后，axios 走 reject 分支——**只有 catch 里才拿得到后端文案**。
逐个核对了受影响调用方，其中 5 处此前没有 `try/catch`（失败时页面静默不动、用户看不到原因），
本轮补上并与后端同批验证：

| 视图 | 补的东西 |
| --- | --- |
| `TimelineView` | catch → 提示 `apiErrorMessage(error, '加载时间轴失败，请稍后重试')` |
| `EntityDetail` | 同上（并说明 400 参数缺失 / 404 不存在的分流） |
| `HistoricalMapView` | 同上 |
| `GlobalSearch` | catch → 清空结果 + 提示（否则"搜索失败"与"没有匹配"在界面上分不出来） |
| `RelationAnalysis` | catch → 清空上一次的图 + 提示（否则画面上留着旧结果，用户会以为是本次的） |
| `EntityGraph` | catch 里补一句提示（原来只清空画布） |

已有的 `res.code === 200` 成功分支一律未动；`useNodeCrudPage` / `UserManagement` /
`TextEntityExtract` 等本来就有 catch 的调用方无需改动。

## 七、刻意没做的事

复核清单的**第二批之后**都不在本轮范围内，理由逐条如下：

| 复核清单条目 | 状态 | 为什么本轮不做 |
| --- | --- | --- |
| 第四批 5~8：整理 diff、按主题提交、整合远端 11 个提交、推送并确认真实 CI | **未做** | 属版本控制动作，需要用户决定提交策略与冲突解决口径；本轮把改动控制在"可增量提交"的范围（见文末） |
| 第三批 9~16：Python 3.11 统一环境 | **未做** | 需要新建环境 + 真实安装 `.[all]` + 四套测试在 3.11 全绿；本机实测 backend 用的仍是 Python 3.8 环境（`place-name-KG`）、RAG 是 3.11.15（`AI_Agent`），与复核清单第八节的现状一致。依赖声明已就位，锁文件必须等全量验证通过后再生成（复核清单第 8.2 节第六步，本轮没有提前锁） |
| py2neo 替换 | **未做** | 复核清单第九节明确要求"不要与 Python 版本统一绑在一次改动中"，顺序是先验证 3.11 可用、再抽适配层 |
| 关系 outbox | **未做** | 依赖产品决策（是否需要关系在线 CRUD），见下 |
| 关系在线 CRUD / 服务端问答历史 / 飞书分片 worker | **未做**（决策项） | 复核清单第十节列为产品决策，需用户定方向后实施 |
| RAG 数据版本自动发布 | **未做** | 复核清单第十一节建议"购买服务器后"实施 |
| systemd / nginx / 飞书 / 真实 LLM 验收 | **未做** | 需要真实服务器与凭据，属第十三节事项 |

另外两点如实说明：

- **`login_attempts` 的旧数据在升级时会被清空**。这不是"迁移"，是**有意丢弃**（理由见第二节）。
  升级后第一次登录的用户会从"零失败"开始计数，最坏后果是锁定晚一次生效。
- **撤销查询默认关闭**（`RAG_INTROSPECT_URL` 与密钥都不配 = 不查）。也就是说：
  本轮的代码交付了"能做到即时撤销"的能力，但**是否生效取决于部署方是否配这两项**。
  之所以不默认打开，是因为它需要 `INTERNAL_SERVICE_KEY` 这个新密钥在两侧同值——
  默认打开而密钥没配会变成"问答全部失败"，那比"撤销慢一点"更糟。因此默认不配、
  但在 health 与安装门禁里**持续告警**，让这件事无法被忽略。
