## 二、先修 CI 红灯：两个只在 CI 环境暴露的缺陷

推送第 12~14 轮改动后 GitHub Actions 立刻红了（`飞书机器人` job），原因是两个
**"本机绿、CI 红"**的缺陷。它们不是本轮清单里的条目，但清单第三批要求"确认真实 CI"，
而且这两个缺陷本身就是仓库卫生问题，所以先修。

### 2.1 测试夹具被 `.gitignore` 误伤（3 个 FileNotFoundError）

`feishu-bot/.gitignore` 里写的是 `data/`（本意是忽略运行期状态 `feishu-bot/data/bot.db`），
而 git 的目录规则会匹配**任意层级**——`feishu-bot/tests/data/eval_answers.json` 一并被忽略，
从未入库。CI 上该文件不存在，`tests/test_md_sanitizer.py` 的 3 个用例直接报错。

夹具自身的 `note` 字段写着它是"从 RAG 评测产物里固化下来的真实回答片段"——
也就是说**它本来就该入库**，只是一条过宽的忽略规则让它没进。

修法：`data/` → `/data/`（只忽略仓库根那一层），并把这个"为什么"写进 .gitignore。

### 2.2 渲染用例的跳过条件不完整（1 个 AssertionError）

`tests/test_render_subgraph.py` 里需要真起 Node 的用例原先只判断
`shutil.which("node") is None`，而产品代码的可用性预检要求 `render/node_modules`
**也存在**。CI 的 runner 自带 node 但没有 `npm install` 过的依赖目录，于是：

```text
用例 → 产品代码预检拦下（"缺少 Node 依赖"）→ 日志里没有假脚本的 stdout 片段 → 断言失败
```

本机装了依赖所以一直是绿的。修法两处一起改：

1. 用例侧统一按 `renderer.is_available()`（node + 依赖 + 脚本）判断，并新增
   `fake_render_env` 夹具：这些用例用的是**假 Node 脚本**（不 require echarts/resvg），
   造一个空 `node_modules` 就能让预检通过——于是它们在 CI 上**真的执行**，
   而不是被 skip 掉（它们考的正是"失败时的日志与产物清理"，是 CI 最该覆盖的降级路径）。
2. CI 的飞书 job 增加 `cd render && npm ci`，让**真实渲染**那两个用例也跑起来。

**验证**：把本机的 `render/node_modules` 临时移开后重跑该文件——
`13 passed, 4 skipped`（4 个是真正需要 npm 依赖的），无失败。改前同样的条件下是
`1 failed`。

## 三、第一批 1：口令策略只有一份实现

### 问题回顾

| 入口 | 改前 | 改后 |
| --- | --- | --- |
| 注册 / 改密码（`DbUtil`） | 10–64 | 10–64 |
| **首个管理员**（`create_admin.py`） | **6–20** | 10–64 |
| 前端注册表单 | 10–64 | 10–64 |

后果是"**权限最高的账号允许最弱的密码**"，同时 21–64 位的强口令反而设不上。

### 改了什么

新增 `backend/password_policy.py` 作为唯一口径（`MIN/MAX_PASSWORD_LENGTH` +
`password_problem()`），四个入口全部引用它。顺带明确了一件事：

**首尾空白由策略报错，而不是被静默去掉。** 这条与第二节的第 2 项是同一件事的两面：
前端原先 `password.trim()`，服务端也不检查空白——于是"用户输入"与"落库值"永远不一致，
而两边的判断都建立在被改写过的值上。现在策略明确返回"密码不能以空白字符开头或结尾"，
前端原样发送，用户看到的是原因而不是"用户名或密码错误"。

### 验证

- `test_password_policy.py`（12 例）：边界（9/10/64/65/空）、首尾空白报错、**不修改输入值**、
  短口令的**历史账号仍可登录**、注册与改密码走同一个函数、首管命令调用的是同一个函数。
- `test_create_admin.py` 里那条"口令长度越界"的用例原先把 `_read_password` 整体打桩成
  "抛 SystemExit"，只证明了"异常会中止"，没证明"哪些口令会被拒"——6–20 那套数值就藏在这个
  桩后面。现在改成桩 `getpass`（真正被测的是命令自己的策略判定），并补了"21 位必须被接受"
  与"首尾空白被拒"两条。

## 五、第一批 3：限流计数原子化（vibe 实测：旧实现 20 并发只记到 4）

### 问题回顾

改前是"SELECT failures → Python 里 +1 → UPDATE"：两个并发请求同时读到 3，
然后都写回 4——**实际发生两次失败，库里只加了一次**。爆破脚本要的就是"用并发把计数做废"。

### 改了什么

计数、窗口滚动、锁定判定全部收进**一条 UPSERT**（`login_guard._UPSERT_ATTEMPT`）：

```sql
INSERT INTO login_attempts (...) VALUES (:scope, :key, 1, :now,
  CASE WHEN :lockable = 1 AND 1 >= :threshold THEN :now + :lock_seconds ELSE NULL END, :now)
ON CONFLICT(scope, key) DO UPDATE SET
  failures = CASE WHEN :now - login_attempts.window_start_epoch > :window THEN 1
                  ELSE login_attempts.failures + 1 END,
  window_start_epoch = CASE WHEN ... THEN :now ELSE login_attempts.window_start_epoch END,
  locked_until_epoch = CASE WHEN :lockable = 1 AND (<同一个新计数表达式>) >= :threshold
                            THEN :now + :lock_seconds ELSE login_attempts.locked_until_epoch END,
  updated_at_epoch = :now
```

`ON CONFLICT ... DO UPDATE` 的 SET 表达式读的是该行的**旧值**，所以整条语句是一次原子读改写。
Python 侧只剩两个参数（now 与阈值）。

**编写过程中实测到一个真 bug**：`VALUES` 分支最初把 `locked_until_epoch` 写成 `NULL`，
于是"第一次失败就达到阈值"（`LOGIN_FAILURE_LOCK_THRESHOLD=1`）时**锁定根本没写进去**——
`test_机器重启换掉_monotonic_基准后锁定仍按配置时长生效` 立刻变红。修法是 INSERT 分支也带
锁定 CASE（新行的计数必然是 1，因此判据是 `1 >= :threshold`）。这条记在这里，是因为
"原子化"的常见坑正是"只改了 UPDATE 分支"。

### 验证（含与旧实现的对照）

用例 `test_并发失败计数不丢`：20 个线程各自带 app context 调 `record_failure`，断言计数为 20。

但"新实现通过"本身不能证明用例有牙，所以另做了一次对照实验（临时脚本，跑完即删）：
把 `_write` 换成改造前那份 Python 侧读改写，同样 20 并发：

```text
旧实现（Python 侧读改写）: failures = 4（期望 20）
新实现（单条原子 UPSERT）: failures = 20（期望 20）
```

**旧实现丢掉 16 次计数**——这既证明了缺陷真实存在，也证明用例确实能抓住它。
（该实验的结论写在这里而不是留一个"测试失败即通过"的用例：被测代码只有一个版本，
留一份注定失败的对照用例只会污染套件。）

## 六、第一批 4：限流自身故障时不再静默失效

### 问题回顾

改前"读不到限流表 → 记一条日志 → 继续放行"：数据库锁冲突、表损坏或迁移失败都会让爆破保护
**无声地消失**，而登录看起来一切正常。

### 改了什么

| 项 | 内容 |
| --- | --- |
| 新配置 | `LOGIN_GUARD_FAILURE_MODE` = `closed`（默认）/ `open`；拼错或留空一律取 **closed** |
| closed 行为 | 抛 `LoginGuardUnavailable` → 路由回 **503**（"登录服务暂时不可用，请稍后重试"） |
| busy 重试 | SQLite `busy`/`locked` 先重试 3 次（50/100/150ms）——那是"别人的写事务还没收尾"，不该让全站 503；其它异常不重试（重试多少次都一样） |
| 例外 | `record_success` 失败**不阻断登录**：凭证已验证通过，把服务端的记账问题转嫁给用户没有收益（风险上限写在它的文档字符串里） |
| 可观测 | 新增 `GET /api/health`（唯一免登录接口）：`{"status":"ok","login_guard":{"failure_mode":"closed"}}` |

新增 `/api/health` 的理由与边界都写在代码里：监控与 `selfcheck.sh` 要在**没有账号凭据**时探活，
而"登录是不是全 503"恰恰是最需要探活的时刻；它只回"活着"与那个策略开关，不含版本/路径/阈值。

### 验证

`test_login_guard.py` 新增 12 例：默认 closed 且读不到状态即拒绝、显式 open 放行、
非法取值回落 closed（大小写不敏感）、busy 重试后成功、重试耗尽按策略拒绝、
非 busy 错误**只调用一次**、`record_success` 失败不阻断、路由层 503、
`/api/health` 免登录且不泄露配置细节。

## 七、第一批 5：安装门禁拒绝占位密钥

### 问题回顾

部署模板里是 `CHANGE_ME_openssl_rand_base64_48` 这类值。部署者若把同一个占位符复制到两侧，
"非空 + 两侧同值"两条老检查**全部通过**——一串所有人都知道的值就这样成了生产密钥。

### 改了什么

`deploy/scripts/check_rag_auth.sh` 新增：

| 检查 | 判据 |
| --- | --- |
| 占位符 | 模式镜像 `RAG/scripts/check_secrets.py` 的 `ALLOWLIST`（那份回答"这些值**不是**泄露"，这里反过来用："这些值**不能**当密钥"） |
| 长度 | JWT 密钥与服务间密钥 ≥ 32 字符；Neo4j 口令 ≥ 12 字符 |
| 默认值 | Neo4j 口令不得是 `neo4j` / `password` / `changeme` 一类出厂值 |
| 覆盖范围 | JWT 密钥（两侧）、服务间密钥（两侧）、Neo4j 口令——每个字段的失败原因分开报 |

### 验证

新增 `backend/tests/test_deploy_auth_gate.py`（23 例）**直接执行那个 bash 脚本**，
用合成配置跑真货：

- 正常路径（真实随机密钥）通过；
- 两侧同一个占位符失败、只有一侧是占位符失败、服务间密钥占位符失败、Neo4j 占位符/默认口令失败；
- 密钥过短失败（JWT 与 Neo4j 各一条）；
- **与密钥扫描器同口径**：把同一批样本（占位符 7 个 + 真实值 2 个）同时喂给
  `check_secrets.py` 的 ALLOWLIST 与门禁，断言两侧的"是不是占位符"判定一致
  ——这条直接对应清单的验收项"密钥扫描与部署门禁的占位符口径一致"；
- nginx 档的旧检查仍在（auth_basic 注释失败 / 已启用通过 / 内部接口屏蔽 / 回环监听）。

> 写这组用例时先踩了自己一个坑：测试助手一开始让 `auth_basic` 跟着 `nginx_mode` 走，
> 于是"auth_basic 仍是注释要失败"那条永远测不到——两个开关是**独立**的，

## 八、第一批 6：SSE 问答先鉴权再检查 runtime

### 问题回顾

`POST /api/query` 的顺序是"runtime → 鉴权 → 撤销检查"，而 `/api/query/json` 是反的。
于是 runtime 加载失败时，**匿名请求**会先拿到 503 与脱敏后的加载错误——服务状态与内部故障
信息泄露给了未认证的人；两条通道口径也不一致。

### 改了什么

统一为 **鉴权 → 撤销检查 → runtime → 限流 → 参数校验 → 执行**，并把这个顺序写进路由的
文档字符串（顺序是契约的一部分，不该靠读代码猜）。

### 验证

`test_rag_auth.py` 新增 2 例：runtime 加载失败 + 匿名 → 两条通道都 401 且响应体里
既没有 `load_error` 也没有内部路径；已认证请求 → 503（如实回报，否则运维会以为"问答正常"）。

## 九、第一批 7：撤销策略必须是显式选择

### 问题回顾

"`RAG_INTROSPECT_URL` 与服务密钥都不填"就等于接受"停用账号 / 改密码后旧 token 在自然过期前
（默认 7 天）仍能调用 RAG"。而这条边界的代价只有 health 告警能看见——告警会被忽略，
正如当初那个布尔鉴权开关一样（这条教训刚在第 13 轮整改里付过一次）。

### 改了什么

生产档（`RAG_REQUIRE_ACTIVE_VERSION=true`）+ jwt 档下二选一，都不做则**拒绝启动**：

```env
RAG_REQUIRE_REVOCATION_CHECK=true    # 要求撤销查询必须配齐（配不齐即拒绝启动）
RAG_ALLOW_DELAYED_REVOCATION=true    # 显式接受延迟撤销
```

两处细节：

- `RAG_REQUIRE_REVOCATION_CHECK` 是**真正的开关**（不配齐就拒绝启动，与是否生产档无关），
  而不是一句注释——否则"要求"没有任何执行者。
- 显式接受后**不再发告警**：决定已经写在配置里，反复告警只会训练人忽略告警。
  "显式接受"与"漏配"的区别留在 health 字段里（`policy` / `delayed_revocation_accepted`）。

health 的 `auth.revocation` 扩成三态 + 上界：

```json
{"enabled": true, "policy": "enforced", "max_delay_seconds": 30.0, "delayed_revocation_accepted": false}
```

`policy` = `enforced` / `delayed` / `not-applicable`；`max_delay_seconds` 启用时就是缓存 TTL，
未启用时为 `null`（上界由签发端的 `JWT_TTL_SECONDS` 决定，**本服务不猜**）。

### 验证

- RAG 侧 8 例（`test_rag_revocation.py`）：生产档未配且未显式接受 → 拒绝；显式接受 → 放行且
  policy=delayed、上界为 None；配齐 → policy=enforced、上界=TTL；非生产档不阻塞；
  不验签的档位 policy=not-applicable；两个开关同时出现以"查询可用"为准。
- 安装门禁 2 例（`test_deploy_auth_gate.py`）：生产档未配且未接受 → 失败；显式接受 → 通过。
  **两处口径一致**是清单的验收项，所以两处都有用例。

## 十、第一批 8：systemd 依赖与 backend 可达状态

- `deploy/systemd/china-war-rag.service` 增加
  `After=network-online.target china-war-backend.service` 与对应的 `Wants=`。
- 同时写清**它保证什么、不保证什么**：`After`/`Wants` 只管启动顺序，不保证"backend 已经能
  响应请求"；那段时间的失败由 introspect 的失败策略兜底（`open` 放行 / `closed` 拒绝），
  且 health 会记下最近一次失败——这是有意的取舍，不是遗漏。
- health 的 introspection 快照新增 `last_ok_at` / `last_failure_at` / `last_failure_reason`：
  计数器只回答"历史上失败过几次"，运维要的是"现在通不通、上次不通是什么时候、为什么"。
  失败原因只取第一行并截断到 200 字符（health 会被采集，不必把连接串复制进去）。
- 用例：`test_rag_servce_声明依赖_backend`（读 unit 文件里 `After=`/`Wants=` 的实际内容）
  与 2 条 introspection 状态用例。

### 11.2 "整合远端落后的 11 个提交"——**结论相反：不能整合**

清单第 5.1 / 第三批都写了"获取远端 11 个提交、解决冲突"。复核后确认**这条要改成"不能做"**，
依据是三条实测：

```text
$ git log --oneline HEAD..origin/main        # 输出为空
$ git merge-base HEAD legacy-private/main     # 无共同祖先
$ git log --oneline legacy-private/main..HEAD | wc -l   # 124
```

1. **那 11 个提交不在 `origin`**。它们属于 `legacy-private`——一个 `push=no_push` 的**旧备份仓库**。
   当前分支的 `behind 11 / ahead 115/124` 是因为 `main` 的上游被设成了
   `legacy-private/main`（误导性配置），而不是公开仓库落后。
   `origin/main` 与本地 `HEAD` 在本轮推送前就是同一个提交。
2. **两条历史没有共同祖先**（项目重写过历史）。合并它需要 `--allow-unrelated-histories`，
   等于把重建之前的整棵树重新拉进来。
3. **那段历史里带着已轮换的凭据**：抽查 `57eea5b:backend/model_search.py` 仍能读到
   明文 Neo4j 口令。合并会把本轮之前**刻意清掉**的凭据重新写进公开仓库历史——
   这正是清单另一处（`git filter-repo` 条目）想避免的状态。

因此本轮的处置是：**不合并**；建议把 `main` 的上游从 `legacy-private/main` 改回
`origin/main`（需要你确认，因为它涉及本地 git 配置口径），并把这条"为什么不能整合"
写进现状文档，避免下一轮再照抄一次。
