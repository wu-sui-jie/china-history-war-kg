## 二、批次 1 收尾：环境统一（审计清单 §5.7~5.9）

审计方已建好 `china-war-py311` 并跑通四套测试，本节只做**剩下的三步**。

### 2.1 E-7：先冻结 ruff 口径，再统一版本

全仓此前**没有任何 ruff 配置**，于是两个版本各用自己的默认规则集，而默认集在
0.14.4 → 0.16.8 之间扩大了。实测同一条命令、同一目录：

```text
ruff 0.14.4（CI 的 RAG / 飞书 job）   →  All checks passed!
ruff 0.16.8（pyproject 与本机 3.8 环境）→  RAG 480 错 / 飞书 74 错
```

两个版本恰好各装在一个本机环境里，**本地怎么跑都不会暴露差异**——这正是它一直没被发现的原因。

处置顺序按审计清单的要求反过来：**先**在根 `pyproject.toml` 写死
`[tool.ruff.lint] select = ["E4","E7","E9","F"]`（= 0.14.4 的默认集，也就是 CI 一直实际执行的
那一套），**再**把三处 ruff 版本统一到 0.16.8——判定不变，只是口径不再随版本漂移。

新默认集多出来的 550 余条（UP045 204、UP006 57、RUF100 57、I001 40…）属风格现代化，
**不在本次范围**：一次改 550 处会让"哪一处改动引入回归"无法归因。其中确实形状像 bug 的
几类（B023 闭包捕获循环变量、PLW1510 subprocess 未给 check=、DTZ005 不带时区的 now()）
已在配置段注释里点名，建议作为独立一轮按类别处理。

### 2.2 §5.7：3.8 / 3.11 双跑 + 把 LegacyAPIWarning 变成门禁

## 三、批次 2：让流程跑得通（P1-1 / P1-2 / P2-20）

### 3.1 P1-1 上传脚本的 tar 排除规则全部失效

`EXCLUDES` 原先全带尾斜杠，而 rsync 与 GNU tar 的处理不同——实测同一棵树：

```text
带尾斜杠  --exclude '.git/' --exclude 'node_modules/'
  →  ./.git/ ./.git/config ./sub/node_modules/x.js 全都进了包
不带尾斜杠 --exclude '.git' --exclude 'node_modules'
  →  ./ ./keep/ ./keep/a.txt ./sub/
```

本机没有 rsync（Windows Git Bash），**必然走 tar 分支**，于是 `.git`（约 108 MB，含历史里的
明文口令）与两个 `node_modules`（各约 300 MB）被整包传到服务器——与文件头写的意图正好相反。

现在模式一律不带尾斜杠，并新增 `backend/tests/test_upload_excludes.py`（4 例）：
**直接从脚本里读 `EXCLUDES` 喂给真 tar**，而不是在测试里重抄一份（重抄只能证明"抄的那份对"）。
另外 `--mirror` 在 tar 分支原先被静默忽略（tar 删不掉服务器上多余的文件），现在直接报错退出。

### 3.2 P1-2 release 门禁与鉴权门禁互相矛盾，整个发布链必挂

workflow 设 `RAG_REQUIRE_ACTIVE_VERSION=true` 却没配鉴权档 → 生产档下
`RAG_AUTH_MODE=disabled` **拒绝启动** → "启动服务"及其后每一步必然失败，
而文档只说它"仍待手动触发演练"。

选"去掉生产档"而不是"补鉴权档"：后者要给 smoke / 契约 / 浏览器三套工具都接上凭证
（得先在 CI 里造一张旧后端的 JWT），改动面远大于它验证的东西；而生产配置的正确性
本来就该由部署门禁（`check_rag_auth.sh`）在安装期管，本 pipeline 的职责是
"数据制品 + 代码能产出一个可发布的包"。

生产档本身仍被**反向验证**：新增一步断言"生产 + 未配鉴权必须被拒绝启动"，
免得那段说明变成没有执行者的注释。（该步骤用单条 `python -c`，不用 heredoc——
本文件以前的解析失败正是因为 YAML 里出现了内联多行 Python。）

### 3.3 P2-20 jwt 档下飞书机器人每问必 401

jwt 档推出 `require_auth=True`，而机器人只发 `X-Bot-Key` → 401；机器人侧的降级文案
只说"RAG 不可用"，运维会朝反方向修。四处一起收口：

- `deploy/env/rag.env`：`RAG_BOT_API_KEY` 从"可选"改成"本模板必填"并写清原因；
- `deploy/README.md`：第 5 条必改项；
- `check_rag_auth.sh`：按"仓库里有没有 `feishu-bot/.env`"判断——要部署机器人却没配
  → 拒绝安装；不部署只提醒（不是每个部署都接机器人，不该一票否决）；
- `/api/health` 的 `warnings` 增加同一提示（运行期也能看到）。

## 四、批次 3：安全口径与数据完整性（P1-3 / P1-4 / P1-5）

### 4.1 P1-3 限流的来源 IP 可被一个请求头伪造（后端 + RAG 同一根因）

nginx 用的是 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`——语义是
"**客户端自带值在最前**、真实地址追加在后"，而两处代码都取 `[0]`，取到的正是攻击者可控的
那一段：每次换一个伪造首段就换一个限流桶，IP 维度完全失效（只剩账号维度的 5 次锁定，
换账号即可）。nginx 早已正确下发 `X-Real-IP`，只是没人用。

两处统一：优先 `X-Real-IP`，退而取 XFF 的**最右段**。用例 5 例：后端 2 例（5 次不同伪造
首段必须落在同一个桶）+ RAG 3 例（含"未显式信任反代时任何转发头都不采信"）。

### 4.2 P1-4 编辑节点会把图谱的 name 写没、属性全部静默丢弃

两个根因叠在同一个接口上：

**根因 a**：`update_node` 只读 `data.get("name")`，而前端从来不发它——前端按实体发
`EventName` / `PersonName` / `OrgName` / `geo_name`。于是 `new_name` 恒为 None，一路作为
`job.node_name` 传到 `SET n.name = $name`，把图谱属性写成 null（等价于删除）；
SQLite 那边因为归一化循环会把名字救回来，所以**只有图谱坏掉、主存储看不出来**。
现在名称从归一化后的属性里取，取不到就回 400（宁可拒绝，也不要把图谱写坏）。

**根因 b**：属性快照用的是 API 键名，而重放路径 `neo4j_props()` 按 **SQLite 列名**取值 →
全部取到 None 再被 `if v is not None` 过滤掉，属性一个都同步不过去，函数却回
`sync_status: success`。现在快照用归一化并过滤后的列名（与 `create_node` 同口径）。

**再加一道兜底**：`upsert_node` 不再无条件写 name（改 `coalesce($name, n.name)`），
重放路径也会从快照里回退取名——修前落库的旧 pending 行重放时不会再把名字抹掉。

用例 7 例，**走真接口**（缺陷就发生在"路由传了什么给 DbUtil"这一段上）。

> **部署时动作**（审计清单要求写进验收）：修复后需要跑一次
> `backend/sync_sqlite_to_neo4j.py` 才能补回已经被清掉的图谱 `name`。

### 4.3 P1-5 飞书机器人异常终止后提问永久卡死

`processing` 在 `_CLAIMED_STATUSES` 里，进程被强杀（SIGKILL / OOM / `os._exit(0)` /
停机超时后退出）会永久留下这一行 → 飞书重投被当重复丢弃 → 那条提问永久消失，
占位卡在 24h TTL 内也不恢复。

新增 `Dispatcher.recover_stuck_events()`：启动时把超时（默认 10 分钟）的
`processing` 与 `received` 扫回可认领状态。用**时间窗**而不是一律恢复，是为了不把
"正在跑"的任务抢回来（那会让同一条提问被回答两次）。恢复失败不影响启动。
用例 4 例（含"恢复后重投能再认领"的端到端）。

## 五、批次 4：撤销链路与信息暴露（P2-9 / P2-1 / P2-2~4 / P3-3）

### 5.1 P2-9 并发击穿与检查顺序

同一 token 的并发请求原先各发一次后端查询（TTL 到期瞬间尤其明显），后端不可用时
每个请求都要在 3 秒超时上排队；而撤销检查又排在**限流之前**，一个客户端就能用并发
请求把协程全占在"等后端"里。

现在：按 token 摘要做 single-flight（并发方 `await asyncio.shield(同一个 Future)`）、
失败结论做 5 秒负缓存、撤销检查移到限流之后（SSE 与 JSON 同序）。

负缓存那一处值得说明它**不是**"把失败当结论缓存"：缓存下来的仍然是按失败策略得出的
那个结论，与逐次判定**结果完全一致**，省下的只是"每个请求都排一次 3 秒超时"。

### 5.2 P2-1 故障与撤销要分开

旧实现把"问不到后端"也当成"凭证已失效"，回 401「登录已失效，请重新登录」，日志也写成
"拒绝已失效的凭证"。后端抖一下，全体用户被"登出"，而重新登录拿到的 token 仍会被同样
拒绝——用户与运维都被指向了错误的方向。

`Verdict` 新增 `unavailable` 字段：撤销 → 401；无法确认 → **503**（`error_code=server_busy`），
日志文案与判定一致。

### 5.3 P2-2 / P2-3 脱敏工具在，只是没统一用上

`_public_text()` 早就写在 `server/api.py` 里，但 **SSE 的 error 帧（`server/sse.py`）拿不到它**，
而同一个文件里另有三个匿名端点的失败分支（`/api/dicts`、`/api/demo/examples` 两处）
漏过脱敏——工具在，只是没统一用上。

实现移到 `lib/redact.py` 供两条链路共用；四类文案统一过它。用例 8 例，其中一条用
"把 `dicts.json` 做成目录"制造**真实带路径的异常**（`IsADirectoryError`），
而不是拿一个不含路径的 JSON 解析错误来假装验证脱敏。

### 5.4 P2-4 旧后端的异常原文

`llm_pipeline` 的 `error_detail = str(e)`（会把 Ollama / Neo4j 连接串、主机与内部路径
送给客户端）、两处 SSE `message`、`report_builders` 的 Neo4j 异常原文（viewer 权限即可读到，
通常含 bolt URI）全部改成 `brief_error()`（第一行 + 截断）或"类型名 + 详见服务端日志"。

### 5.5 P3-3 容量拒绝映射为 503

`sse.py` 特意为容量拒绝定义了独立错误码，而 `_ERROR_HTTP_STATUS` 把它和 `internal`
一起映射成 500 → 按状态码决定要不要重试的调用方不会重试。改 503。

## 八、执行中踩到的四个坑（都值得留档）

1. **本工具的 heredoc 会吃掉反斜杠**：`\n` 会被还原成真实换行，于是我几次改写脚本时
   匹配失败、甚至有两次把 `RuntimeError("...\n...")` 写成了字面换行导致语法错误。
   后来改成"用编辑工具做精确替换"就再没出过——**这条只影响我的操作方式，不影响仓库**，
   但把结论写在这里，免得下次重复。
2. **`str.replace(..., 1)` 命中了文件里重复出现的行**：`sync_compensation.py` 里
   `from models import Neo4jSyncJob, db` 出现多次，我删"未使用的 `db`"时删掉的是
   **另一个函数**在用的那一处，`stage_job` 当场报 `name 'db' is not defined`（测试立刻抓到）。
   教训：删重复行要按上下文定位，别按内容。
3. **我自己写的 CI 门禁吞掉了退出码**：`pytest | tee` 在 bash 里只看最后一条命令的状态，
   tee 永远成功 → "测试挂了"会被静默放过。同一类错误在我"重试推送"的循环里也犯过一次
   （`if git push | tail -2` 永远为真，于是"推送成功"是假的——实测远端还停在旧提交）。
   现在两处都显式计算退出码。
4. **冻结 `time.monotonic` 会让 asyncio 死锁**：`introspection.time` 就是标准库 `time` 模块，
   patch 它等于把**整个进程**的单调时钟钉死，而事件循环用同一个时钟算超时 → `asyncio.sleep()`
   永远不到期，pytest 卡在 90% 不动。三条并发用例已去掉时钟冻结并把原因写在用例里。
5. **缩小 `.gitignore` 作用域时没有清点"原来被覆盖的目录"（本轮唯一有外部影响的失误）**：
   P3-13 要求把裸的 `cache/` 限定作用域（怕它静默吞掉某个模块的 `tests/cache` 夹具）。
   我改成 `/cache/` 之后，**原先被那条裸规则覆盖的 `entity-event-relation/cache/` 变成未忽略**
   ——197 个抽取结果 JSON、22 MB，随下一次 `git add -A` 进了提交 `408b086` 并推到公开仓库。
   已用 `7e019c2` 收口：两个运行期缓存目录改为**显式列名**，并从索引移除那批文件
   （磁盘上的文件保留，抽取链的复现路径不受影响）。
   教训写进 `.gitignore` 的注释里：**改一条规则的作用域时，要连"它原来覆盖了谁"一起清点**，
   只看根目录那一个是不够的——这条与 `data/` 那次事故是同一类错，只是方向相反
   （那次是"漏掉了不该忽略的"，这次是"放开了本该忽略的"）。

> **遗留（需要你决定）**：`408b086` 已推送，那批缓存文件仍在 `origin/main` 的**历史**里。
> 仓库是公开的，而缓存内容是抽取结果（上游源码文本受版权约束、本就不入库），
> 是否重写历史（`git filter-repo` + force-push）彻底清掉，按第 13 轮同类问题（历史里的明文凭据）
> 的处理方式，应当由你决定——我没有在本次擅自 force-push。
