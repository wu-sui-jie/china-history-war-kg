## 二、对照基础设施（本轮的前置，也是后续重构的兜底）

### 2.1 它解决什么问题

工作单对 R3.2 的要求是"先给现有接口建「响应快照对照」脚本（同请求打修复前后两个实例，diff 响应），否则无兜底"。
这是因为旧后端没有任何自动化测试：重构改了行为，只能靠人肉点页面发现。

`tools/snapshot_responses.py` 提供的就是这个兜底：**同一组请求，在两个版本的实例上各打一遍，
逐字段对比响应**。diff 为空，就说明重构只改了结构。

### 2.2 怎么用（操作手册）

```bash
cd backend

# 1) 重构前：起一个自己的实例（不要用开发中的 5000，避免互相干扰）
BACKEND_PORT=5001 python app.py        # 另开一个终端，或放后台

# 2) 采集基线
python tools/snapshot_responses.py capture --out /tmp/before.json --base http://127.0.0.1:5001

# 3) 改代码……

# 4) 重启实例后采集新快照，再对比
BACKEND_PORT=5001 python app.py
python tools/snapshot_responses.py capture --out /tmp/after.json --base http://127.0.0.1:5001
python tools/snapshot_responses.py diff /tmp/before.json /tmp/after.json
```

`diff` 的输出按请求分组：一致的打印"一致"，有差异的列出 JSON 路径与前后值（如
`! data.counts.entities: 9925 -> 9900`），最后给总差异数。差异为 0 时打印"完全一致"。

**为什么用 5001 而不是 5000**：开发中的实例会随你改代码重启，基线快照就失去意义；
自己起一个专属实例，整个重构过程里它的代码状态是可控的。

**token 从哪来**：脚本用 `jwt_util.encode()` 给库里 id 最小的 admin 签一个 token，不需要在脚本里存口令。

### 2.3 设计取舍

| 决定 | 原因 |
| --- | --- |
| 只覆盖**只读**接口 + 写接口的**参数校验失败**路径 | 脚本跑在真实库上（5316 地点 / 9925 节点），绝不能因为对照本身改坏数据 |
| 不纳入 `/api/ai/inference*` 与 `/api/extract/entities-events` | 会调大模型/外部服务，结果本身不确定，放进来只制造噪音 |
| 不做事先归一化，逐字段精确对比 | 归一化会掩盖真实差异；差异由人判断是不是预期变化。唯一例外是 `--ignore` 指定的运行时字段（默认忽略 `process_time` 等） |
| 覆盖 37 个请求 | 含四类节点的分页查询、四种关系图、质检与对账、地图与时间轴、以及写接口的 4 条校验失败路径 |

### 2.4 它抓到的第一个问题：总览接口 90 秒超时

基线采集时 `POST /search_name_kg {}` 直接 `ReadTimeout`。逐层定位推翻了一个假设、证实了另一个：

| 假设 | 实测结论 |
| --- | --- |
| 参数化 `id(n) IN $ids` 让 planner 无法用 NodeByIdSeek、退化成全表扫描 | **证伪**：预热后 369 ms（内联字面量）vs 473 ms（参数化），都在亚秒级。所以**保留参数化**写法，不为一个 28% 的差距放弃统一的安全基调 |
| 全图分支的 path 查询是瓶颈 | **证实**：`MATCH path = (n)-[r*1..1]-(m) RETURN relationships(path)` 要为每条路径构造 Path 对象，实测 **202 s**（7470 节点 / 3.5 万行）；改成 `MATCH (n)-[r]-(m) RETURN r` 后 **120 s**，语义等价（子图对比 714 条关系集合完全一致） |
| 超时是本轮改动引入的 | **证伪**：运行中的 dev server 仍用改动前的默认 `load_all=True`（Flask 无 reloader，不重启不生效）；重启后走限量分支，**0.78 s** |

三段实测数据合起来说明一件事：**"全图加载"这个模式本身就是不可用的**（即使优化后仍要 120 s，
且响应体几十 MB）。`MAX_LOAD_ALL_NODES=3000` 的拦截不是保守，是必需。

## 三、P2-1 第一步：拆出报表构建器

### 3.1 拆分边界怎么定的

没有凭"看起来相关"来分组，而是用 AST 算**调用闭包**：

1. 从 11 个 `build_*` 函数出发；
2. 反复加入它们调用到的私有辅助（`_*`），直到闭包稳定；
3. 检查闭包里的每个函数**是否被闭包外的函数引用**——结果是 **0 个**；
4. 再检查闭包引用的模块级名字（常量、单例）是否只被闭包使用，同样确认。

结论：33 个函数（11 个报表构建器 + 22 个私有辅助）+ 6 个常量构成一个自洽的块，可以整块搬走。

期间还发现一个容易漏的点：`load_current_dataset_meta` **不以 `_` 开头**，所以第一版闭包分析没抓到它——
它是 AST 报出来的"被引用但不在闭包内"的函数。这类命名不统一的函数是机械分析的盲区，必须靠反向检查兜住。

### 3.2 迁移结果

| 项 | 结果 |
| --- | --- |
| `app.py` | 3827 → **2555 行**（顶层函数 90 → 57 个） |
| 新增 `report_builders.py` | 1369 行：报表构建器 + 私有辅助 + 类型标签常量 + 数据集元信息读取 |
| 新增 `db_handle.py` | Neo4j 单例句柄独立成模块，避免 `app` ↔ `report_builders` 循环依赖（两边共用同一个连接实例，已用 `is` 验证） |
| `app.py` 的改动 | 删除迁移的块，改为 `from report_builders import (...)` |

### 3.3 验证与抓到的 4 处漏 import

对照结果：37 个请求**逐字段 diff 完全一致**。

但在"先跑一遍"时 diff 报了 15 处差异，全是 500，错误信息是 `name 'os' is not defined` 之类：

| 漏掉的名字 | 为什么会漏 |
| --- | --- |
| `os`、`json`、`logger` | 生成新模块时我按"依赖分析报告"写 import，而那份报告只统计了**跨模块符号**，标准库与模块级 logger 被当成"app.py 里已有" |
| `APP_PATH` | 它是 app.py 的模块级常量，迁移的函数用它拼路径；新模块需要自己的同名常量 |
| app.py 的顶层 `traceback` | 上一轮我做"函数内 import 上提"时，用的正则 `^\s*import traceback$` 把**刚加到顶层的那个**也一起删了 |

后两条特别值得记：一条说明"迁移函数时要连带迁移它依赖的模块级状态"，另一条说明
**批量脚本的正则要区分缩进层级**。这四处如果只靠打桩冒烟是发现不了的——
打桩脚本只调用我想到要调的接口，而 500 出现在我没调的那几个上。

用 `ruff check --select F821`（未定义名字）做了全量复查，现在干净。

## 四、P2-5 第一步：两处热点下推 SQL

工作单点名的三个 N+1 热点里，先做了两个**改法明确、口径好保**的。第三个（`build_map_overview`）
与时间轴的瓶颈需要先测量，见第七节。

### 4.1 `_coordinate_issue_rows`：逐地点 COUNT

| | |
| --- | --- |
| 原实现 | `for place in Place.query.all(): _place_related_event_count(place.id)` —— 5316 个地点 = **5316 次 COUNT 查询** |
| 改法 | 一次 `GROUP BY` 预取 `{place_id: 行数}`，循环里改成字典取值 |
| 口径 | 计数用 `count(id)` 而不是 `count(distinct event_id)`——原实现统计的是**关系表行数**，保持完全一致 |
| 附带 | 单点查询函数 `_place_related_event_count()` 保留（可能被别处用），但加了注释：批量场景必须用 `_place_event_counts()` |

### 4.2 `_isolated_node_rows` / `_count_all_isolated_nodes`：全量拉取到 Python

| | |
| --- | --- |
| 原实现 | 拉 8 张关系表的**全部外键列** + 四类节点**全量**进 Python 做集合差（本库约 1.7 万关系行 + 9925 个节点对象），每次质检请求重来一遍；`_count_all_isolated_nodes` 更是调用 `_isolated_node_rows(limit=99999)` 再取长度 |
| 改法 | 新增 `_isolated_filter(model)`（SQL 侧 `NOT EXISTS`，Event 要看四张关系表、其余各看一张），查询加 `LIMIT`，计数走 `COUNT` |
| 顺序 | 显式 `order_by(id.asc())`——原实现依赖 rowid 顺序（SQLite 下通常等于 id 顺序，但没保证） |
| 语义 | `NOT EXISTS` 与外键为 NULL 的关系行天然不匹配，等价于原实现的"过滤 None 后做差集" |

验证：与拆分前的基线对照，37 个请求**完全一致**（含 `isolated_nodes` 的列表与计数、
`coordinate_missing` 与 `coordinate_low_confidence` 两项）。实测质检接口约 **1.0 s**。
