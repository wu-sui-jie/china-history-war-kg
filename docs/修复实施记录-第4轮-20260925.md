## 二、S3-1：对照工具补边界，ruff F821 固化进 CI

**请求清单从 63 条扩到 67 条**，补的都是审核点名的缺口：

- `limit` 边界：`/api/node/search_by_name` 的缺省 / 0 / 负数 / 超大 / 非数字各一条。
  顺带发现工具自己在 `find_node_page` 上写错了参数名（`current`/`limit` 与 `type`），
  那两个参数路由根本不读——等于一直在采默认页、`node_type` 过滤从未被覆盖，已改为
  `pageNum`/`pageSize`/`node_type`。
- 非 1 号节点：新增 `{node_id}` 占位符，采集时从 `/api/find_node_page` 现取第一个
  id ≠ 1 的 Event；取不到就跳过并在 stderr 提示，不用写死的假 id 充数。
- 动态版本号：新增 `{version_id}`（从 `/api/dataset/versions` 取首个版本）+ 未知版本号样本。
- 对照逻辑补了**路径比对**：占位符解析值变化（数据变了）也会报出来，否则两侧各自解析到
  不同节点时会静默判为"一致"。

**ruff F821 进 CI**：`legacy-backend` job 里加 `ruff check --select F821 --target-version py38`
（版本钉死 0.16.8）。第一次全量跑就报 59 处未定义名，全在 `import_json_to_sqlite.py`——
`18e43eb`（公开仓库整理）把关系类型别名表迁到 `relation_types.py` 时，顺手删掉了
`_safe_text`/`_safe_float` 却没补 import，而这两个名字在文件里有 56 处调用。
这是"检查只在本机跑过"的直接代价：审核无法复现，真问题就一直躺着。

## 四、S3-3：P2-5 剩余（两个总览构建器）

工作单要求"先确认瓶颈是否如假设"。新增 `backend/tools/profile_overviews.py`：统计每次调用的
wall time、SQL 语句数（SQLAlchemy `before/after_cursor_execute` 钩子）与 cProfile 热点。

改动前实测（真实库，Event=1050 / Place=5316 / EventPlaceRelation=6849）：

| 函数 | 耗时 | SQL 条数 | 其中 SQL 自身 |
| --- | --- | --- | --- |
| `build_map_overview()` | 2.68 s | 6313 | 0.35 s |
| `build_timeline_overview()` | 2.16 s | 5251 | 0.30 s |

**结论：瓶颈是语句条数**（每条语句的 ORM 往返），不是数据库。据此下推为批量取数：
质量标记的两个计数各改成 GROUP BY 一次（`_bulk_duplicate_counts` / `_bulk_event_relation_counts`，
截断口径每表 999 → 合计 999 与原实现逐字段对齐，事件-事件表两侧相加再减自环）；
参与方三类各一次查询取代每事件三次；地点/事件关系行、事件、地点按 `in_()` 分批取回后在
Python 里分组。

改动后：

| 函数 | 耗时 | SQL 条数 |
| --- | --- | --- |
| `build_map_overview()` | 0.13 s（**17x**） | 17 |
| `build_timeline_overview()` | 0.054 s（**40x**） | 22 |

**中途踩到的坑**：第一版批量实现让 1386 处对照差异冒出来——全是参与方 `related_events`
的次序。原因是原单事件查询走的是 SQLite 的 `MULTI-INDEX OR` 计划（先扫 `idx_eea_event_a`
再扫 `idx_eea_event_b`，各自 rowid 升序），而 10 条截断的成员依赖这个次序。批量版改成
"先 a 侧再 b 侧"两趟填（自环只在 b 侧落一次）+ 显式 `ORDER BY id`，差异归零。

## 七、S3-7：Neo4j 全文索引评估（BE-8）

旧后端十处名称检索都是 `toLower(n.name) CONTAINS toLower($q)`，前缀通配使索引失效、只能全扫描。
新增 `backend/tools/evaluate_fulltext_index.py`：**默认只读**；`--with-index` 才建索引，
且跑完自己删；写入基准用 `__FullTextBench` 临时标签并必清理（本轮跑完核对：索引列表为空、
基准节点残留 0、节点总数 7470 不变）。

实测（Neo4j 5.25 社区版，7470 节点，8 个代表关键词，每项取 5 次最好成绩）：

| 方案 | 耗时 | 命中集与现状的差异 |
| --- | --- | --- |
| 现状 `CONTAINS` 扫描 | 5.2 ~ 16.6 ms | — |
| 全文索引（standard 分析器） | 3 ~ 16 ms | 多命中最多（「巨鹿之战」1 → 898，完全不存在的词也命中 29 条） |
| 全文索引（cjk 分析器 + 短语查询） | 1.4 ~ 4.2 ms | 多字关键词完全一致；单字「秦」漏 76 条 |

索引构建（存量数据）约 650 ms；写入 300 节点 69 ms → 91 ms（1.08x，噪声级）。

**结论：暂不上。** 扫描最坏 11~17 ms，远没到用户能感知的量级；而换写法要承担命中集变化
（standard 分析器按单字切分 + OR 语义，用户搜"巨鹿之战"会看到 898 条）与索引迁移成本。
触发条件是图规模涨到数万节点——工具会打印两处判断（是否成瓶颈 / 命中集是否一致）与
"上的配方"（cjk 分析器 + 短语查询 + 单字回落 `CONTAINS`），不靠人记笔记。

## 八、S3-8：编码治理（FE-13）

前端 `typeAliasMap` 里认五个 GBK 乱码 key（如 `鎴樹簤浜嬩欢` = 战争事件），那是把
"UTF-8 字节被按 GBK 读"的问题藏在展示层：数据是坏的、只是看起来对，任何新入口都会再犯。

- 源头：`common_utils` 新增 `repair_mojibake` / `repair_mojibake_props`。判据是"能否 GBK 编码后
  再按 UTF-8 解码且结果不同"——真实中文在这步通常直接失败，对正常文本是恒等操作；
  真的复原时写一条 warning 日志并带字段名。接入两个写库出口：
  `import_json_to_sqlite._safe_text`（导入侧）与 `node_property_mapping.neo4j_props`
  （同步/建图侧的唯一属性出口）。
- 展示侧：删掉五个乱码 key，并留注释说明改在源头修；新增 `tests/unit/knowledge.test.ts`
  显式断言乱码会原样透传——再有人想加回乱码兼容时，这条测试会提醒他去修数据。

**存量数据核实**：SQLite 九张表全列扫描 + Neo4j 标签与全属性扫描，均未命中乱码模式，
所以这次退役不会让现有数据显示异常。
