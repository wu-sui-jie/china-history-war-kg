## 一、EER-15：评估指标随进程漂移（先复现，再修）

### 1.1 复现——第 8 轮的"不可复现"结论是**样本量不够**得出的

命令（同输入，只换 `PYTHONHASHSEED`）：

```bash
cd entity-event-relation
for s in 0 1 2; do PYTHONHASHSEED=$s python evaluate.py --output /tmp/eval-$s; done
```

修前实测（全量 pred = `output/中国历代战争简史/9_final_all.json`）：

| seed | filtered_pred | gold | tp | fp | fn | 关系 P | 关系 R | 关系 F1 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | 888 | 1099 | 739 | 149 | 360 | 0.8322 | 0.6724 | 0.7438 |
| 1 | 888 | 1099 | 743 | 145 | 356 | 0.8367 | 0.6761 | 0.7479 |
| 2 | 888 | 1099 | 741 | 147 | 358 | 0.8345 | 0.6742 | 0.7458 |

实体与事件指标三个种子完全一致（实体 tp/fp/fn=1021/7854/105、事件 281/745/39），
**漂移只在关系抽取**，`filtered_pred` 也稳定在 888。

**第 8 轮为什么判错（含一处本人记录勘误）**：第 8 轮跑了**两个独立进程各一次**、看到两边
`results.json` 逐字段一致，于是记成"真实存在的不可复现点只有 `error_samples`"并把 EER-15 降级。
问题不在"同进程"（本文初稿写成"第 8 轮在同一个进程里跑"，**这是错的**，由第 10 轮审核更正），
而在**样本量**：漂移的表现是"某些种子下相似度并列的取舍不同"，2 次运行完全可能落在同一个结果上
（本轮三颗种子给出 3 个不同 tp 值，只抽 2 次就有约 1/3 的概率抽到同一对），而且第 8 轮没有显式
控制 `PYTHONHASHSEED`，无法说明抽到的是哪两颗种子。把样本量提到 3 颗显式种子，漂移就露出来了。
所以这次的降级**不成立**；同时确认 `error_samples` 也不可复现，但那只是漂移的一部分。
**教训应当是**：验证"可复现"要显式控制哈希种子并多抽几颗，2 次一致说明不了任何事。

> 也顺手解释掉第 7 轮那个 `890 vs 888`：本轮三颗种子下 `filtered_pred` 恒为 888，
> 说明那一处更像**产物换代**而非匹配抖动。第 7 轮的原始数字无法复原，不再追。

### 1.2 根因

关系评估的贪心一对一匹配直接迭代两个**集合**：

- `filter_relations()` 返回 `set`，`build_gold_triples()` 返回 `set`，而
  `evaluate_relations()` 写的是 `for pred in pred_triples:` 与 `gold_list = list(gold_triples)`；
- Python 对字符串哈希做**每进程随机化**，同一集合在不同进程里的迭代顺序不同；
- 匹配里"相似度并列"用 `combined > best_score`（严格大于）取舍，并列时先遍历到的赢，
  于是换进程就换一个匹配方案，tp/fp/fn 跟着动。

同类隐患还有 `evaluate_entities.match_entities()` 的内层 `for gold_name in unmatched_gold`（同样是集合）。

### 1.3 改法

| 位置 | 改法 |
| --- | --- |
| `optimal_evaluator.py` | 把贪心匹配抽成 `match_relation_triples(pred_triples, gold_triples, event_mapping)`：内部先 `gold_list = sorted(gold_triples)`、再 `for pred in sorted(pred_triples)`，返回 `{tp, matched_gold, gold_list, unmatched_predictions}`。`evaluate_relations` 改为调用它，自身不再持有匹配循环 |
| 同上 | `match_entities` 内层改 `for gold_name in sorted(unmatched_gold)` |
| 同上 | `error_samples` 三处实体样例与关系样例都定序后再截前 20（原来按遍历顺序截，成员会变） |
| 同上 | `build_event_mapping` 的 `scores.sort(reverse=True)` 加注释说明为什么它是全序（元组逐元素可比、下标唯一），防止后人"优化"成只按相似度排序 |

为什么让 `match_relation_triples` 自己定序、而不是只让调用方定序：输入本来就是集合，
**定序是这条匹配的契约**——放在函数内部，任何调用方（含将来的）都拿不到漂移的结果。
这也顺带给了测试一个干净的观测点（不必去 mock 私有方法，见第四节）。

## 二、EER-4：三条噪声地名正则从未生效

`war_extraction/utils/normalizer.py:269-271` 的 raw string 写成 `r".*等\\d+方国$"`——
raw string 里 `\\` 是**两个字符**，正则引擎解释为"一个字面反斜杠"，于是这三条只能匹配
`等\d方国` 这种不存在的字面量。"等3方国"这类描述性字符串一路穿过噪声过滤，进了地理编码队列。

改法：三处双反斜杠改单反斜杠。用例 `tests/test_normalizer_noise.py`：四条正例
（`夏等3方国` / `商等12国` / `羌等5部落` / `羌方等30部落`）+ 五条反例（`方国`、`鬼方`、
`三苗`、`牧野`、`殷墟等遗址`）+ 四条其它噪声规则的对照（`今河南一带`、`渭水流域`、`中原`、
`汉水与渭水之间`），防止顺手改坏别的规则。**修前 4 例失败**。

## 三、EER-11：缓存索引原子写（本轮只做原子性这一半）

`CacheManager._save_index` 原本是 `open(index_path, "w")` 全量重写——这个调用一执行就把索引
截断成 0 字节，随后才写内容；进程在中间被杀（Ctrl-C、OOM、断电）留下半截 JSON，
下次 `_load_index` 解析失败 → `CacheManager.__init__` 抛异常 → **整个抽取任务还没开始就崩**，
且 `cache/` 里那 22MB 缓存在人工删掉索引前完全不可用。

改法（`war_extraction/core/cache_manager.py`）：

| 项 | 改法 |
| --- | --- |
| 写入 | 新增 `_write_json_atomic()`：写同目录临时文件 → `flush` + `fsync` → `os.replace` 原子替换；失败清掉临时文件 |
| 落点 | 索引与**结果文件**都走它（半截的结果文件比没有缓存更糟：读时 `json.load` 抛异常打断流水线） |
| 悬挂条目 | `get()` 发现"索引有、文件无"时摘除条目并落盘，不再无限堆积 |
| 损坏条目 | 结果文件被外力写坏时按未命中处理并摘除，不抛异常打断整条流水线 |
| 损坏索引 | 索引本身解析失败时打印警告并按空索引继续（不静默删文件，便于排查） |

用例 `tests/test_cache_manager.py`（6 例，**修前 4 例失败**）。模拟"被杀死的进程"用的是
**注入异常**（把 `json.dump` 换成"先写半截再抛"），比真去 kill 进程稳定，且同样能证明
"任何时刻磁盘上的索引都是完整的旧版或新版"。

**没做**：TTL / 孤儿文件 GC（第 1.3 节那个改法下，索引写失败时结果文件会作为孤儿留在
`cache/`）、以及相对 CWD 路径锚定——按阶段 1 的原计划留给阶段 2。

CI 挂法：`.github/workflows/ci.yml` 的 `legacy-backend` job 里加一步

```yaml
working-directory: entity-event-relation
run: python -m pytest tests -q
```

（该 job 已经装了 `pip install -e entity-event-relation`，无需新增依赖。）

两条设计取舍值得记下来：

1. **评估可复现那条用例开 4 个不同 `PYTHONHASHSEED` 的子进程**跑真实代码路径，
   **显式固定 4 颗种子**而不是"随便跑两次"——修前跑两次也可能碰巧一致（第 8 轮就是这么误判的），
   所以这里的断言是"4 颗种子必须给出同一个结果"，把"抽到的种子太少"这个漏洞堵掉。
   也没有采用"给 CI 钉一个固定 `PYTHONHASHSEED`"的做法：那是把症状藏起来，真实用户机器上
   的种子由解释器随机决定。
2. 用例先确认**修前失败**才入库：`git stash push` 三个源文件 → 10 例失败 → `git stash pop` →
   21 例全绿。失败信息可直接读（"PYTHONHASHSEED=1 与 =0 的 error_samples 不同"）。

`tests/fixtures/relation_slice_repro.json` 是 EER-15 的最小复现夹具：从 15MB 的
`9_final_all.json`（按 `.gitignore` 不入库）用 delta debugging（缩减目标性质 =
"seed 0 与 seed 1 的结果不同"）缩到**2 条关系、2 个事件、527 字节**。缩减脚本是一次性工具，
未入库；夹具文件头的 `_note` 记了来源与缩减方法。
