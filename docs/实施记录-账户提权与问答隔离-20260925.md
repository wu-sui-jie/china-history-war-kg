## 二、问题一：用户管理页（提权闭环）

### 2.1 为什么要做

角色体系（admin/editor/viewer）此前已贯穿写接口 403、菜单下发、路由拦截与界面徽标，但
**提权只能手写 SQL**（`UPDATE UserInfo SET role = ...`），没有界面入口；菜单裁剪也只有 viewer
一个分支，admin 与 editor 看到的完全一样，没有"仅管理员可见"的位置。方案 A 把提权变成管理员
页面上的一次下拉选择，同时把菜单裁剪从两级改成三级。

### 2.2 后端

| 项 | 实现 |
| --- | --- |
| 鉴权 | 新增 `@require_admin`。**刻意不复用 `require_write_role`**——editor 若能改角色，就能把自己升成 admin，权限体系会被自己打散 |
| 列表 | `GET /api/admin/users`：id / 账号 / 昵称 / 角色（`UserInfo.to_dict()`，天然不含口令字段） |
| 改角色 | `POST /api/admin/users/<id>/role`，body `{"role": ...}` |
| 防呆① | 不能改自己的角色 → 403。否则最后一个管理员把自己降级后系统失管，只能回到手写 SQL |
| 防呆② | 角色值必须落在 `ROLE_RANKS` 白名单（viewer/editor/admin）→ 400，提示里列出允许值 |
| 其他 | 用户不存在 → 404；改成功写一条 info 日志（谁把谁的账号改成了什么） |
| 菜单 | `get_menu()` 三级裁剪：非 admin 去掉 `/admin/users`；非 editor 去掉 `/workspace/manage`；分组内再按 `ADMIN_MENU_IDS` / `EDITOR_MENU_IDS` 过滤 |

角色职责与三处口径（改权限时要一起改的地方）写进了 [backend/README.md](../backend/README.md)；
服务器上的提权操作（界面 + SQL 兜底 + "下次登录生效"的提醒）写进了
[deploy/README.md](../deploy/README.md)。

### 2.3 前端

- `api/module/admin.ts`：`listUsers()` / `updateUserRole(id, role)`；
- `views/admin/UserManagement.vue`：账号/昵称/角色下拉/保存。自己那一行禁用下拉与保存按钮并
  标注"当前登录账号"；未改动时保存按钮禁用；保存成功提示"已把 X 设为「编辑」，该用户
  **下次登录生效**"；失败按服务端文案提示并回滚显示（重新拉列表）；
- 路由 `/admin/users`（`requiresRole: 'admin'`）；
- 守卫从"是不是 admin/editor"改成**分级比对** `roleSatisfies`（`admin ⊃ editor ⊃ viewer`），
  角色未知一律不满足（fail-closed）；提示文案按 required 区分（管理员页 / 数据运营页）；
- store 的菜单**取自后端下发的内容**（`menuMap.get('/admin/users')`），不写成内置常量——
  内置常量会无条件进导航栏，等于把后端对 editor/viewer 的裁剪撤销掉。

### 2.4 验证（真实 SQLite + Flask 测试客户端，22 项全通过）

用临时账号 `zc_perm_test`（跑完删除，实测残留 0 条）；真实账号 `wusuijie`/`123456` 只读、未改：

- **接口鉴权**：admin 可列用户且不含口令字段；viewer 列用户 403；viewer 改角色 403；
  `role='superuser'` → 400（"角色取值非法，只允许：viewer/editor/admin"）；admin 改自己 → 403
  （"不能修改自己的角色，请让另一位管理员操作"）；改不存在的用户 → 404；
- **提权与生效**：升为 editor 后**落库**且写接口放行（`/delete_node` 非 403）、viewer 写接口
  仍 403、viewer 只读接口仍放行；
- **菜单三级**：admin 有用户管理 + 数据运营组 + 文本抽取；editor 无用户管理、有数据运营组与
  文本抽取；viewer 三者都没有，但首页/时间轴/地图/RAG 仍在；
- **回退**：降回 viewer 后写接口 403、菜单同步收回数据运营组与文本抽取；
- **文本抽取接口**：viewer 调 `/api/extract/entities-events` → 403。

前端新增 18 例（用户管理页 6 + 路由守卫分级 12，含"viewer 直达 `/admin/users` 被拦"与
"editor 进不去用户管理但能进数据运营页"）。

> 写测试时踩到一个坑并记在这里：Vue Router 对"导航到当前路径"的重复导航**不跑守卫**，
> 而多个用例共用一个 router 实例——不退开的话后续用例会静默跳过守卫（假通过）。
> 已改成每次先退到中立页再访问。

## 三、问题二：问答记录按账号隔离

### 3.1 根因（方案文档已查清，这里复述关键一条）

RAG 是独立服务、**会话历史不在服务端**，而是 RAG 前端存在自己的 localStorage 里，key 全局
唯一（`ragv5-session-v3`）；主应用以同源 iframe 嵌入 RAG，两者共享同一个 localStorage，
而主应用从不把自己的身份传给 RAG——于是同一浏览器上任何账号打开 RAG 看到的都是同一份记录，
"改名/删除会话"任何账号都能操作这份共享数据。

同病相连的三处，本轮同批处理：RAG 会话（`ragv5-session-v3`）、旧问答助手（`chatHistory`）、
文本实体识别（`extractHistory`）。

### 3.2 主应用侧

- 新增 `utils/userScopedStorage.ts`：
  - `scopedStorageKey(base, uid)` → `chatHistory:u3`；**账号未知时退回原 key**，行为与改造前
    一致（不会因为拿不到 uid 就把记录写丢）；
  - `readScoped`：该账号没有自己的记录时，把老版本的全局记录**归档**到
    `<base>:legacy-archived`（不再自动加载）。**不归属第一个登录的人**——把别人的提问记录
    交给谁都可能是错的。归档只做一次，原 key 随即删除；
  - localStorage 抛异常（隐私模式/配额）时读给兜底、写静默失败。
- `inference/index.vue`（chatHistory）与 `TextEntityExtract.vue`（extractHistory）接入，并在
  mount 时 `await userStore.ensureUserInfo()`：BasicLayout 的 `loadUserInfo()` 没 await，而
  子组件 mounted 先于父组件执行——直接读 `userInfo.id` 会拿到空对象，隔离就退化成共享 key。
- `RagAssistant.vue`：iframe load 后 `postMessage({type:'cw-user', uid}, '/')`；账号变化时重建
  iframe 并重发。**不把 uid 拼在 iframe URL 上**（URL 会进浏览器历史与各级访问日志）；
  targetOrigin 用 `'/'`（HTML 规范：只发给同源文档），换成独立域名部署时要同步改。

### 3.3 RAG 前端侧

- 新增 `utils/userScope.ts`：uid 持有、`storageKeyFor(uid)`、身份桥（**只认同源**、只认
  `cw-user`、重复 uid 不重复回调、返回解绑函数）；
- `stores/session.ts`：存储 key 改为按账号组装；新增 `applyUserScope(uid)`，顺序是
  **先把当前内存状态写回原 key → 换 uid → 读新 key**。这个顺序是关键：反了会把上一个账号的
  会话写进新账号的桶里（串数据），测试正面钉住了它；切换时同时清掉上一账号的瞬态状态
  （中断在途流、清空当前回答与选中轮）；
- `main.ts` 装桥：store 可能在组件挂载前就被创建（App.vue 就会用到），所以放在这里而不是
  某个组件里；
- 独立访问 `:8000` 收不到消息 → key 不带后缀 → 行为与改造前完全一致。

### 3.4 安全边界（如实写进代码注释与文档）

方案 A 只解决"**串记录**"，不防"**冒充**"——同源之下，懂控制台的账号可以改 uid 去看别人的记录。
对演示/局域网形态足够；决定公网部署、或要求"记录不可被冒充查看"时上方案 B（主应用传 JWT +
RAG 服务端验签），那一步本轮没做，触发条件写在方案文档里。
