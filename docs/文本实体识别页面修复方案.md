## 一、结论速览

这个页面**不是另一套识别实现**，而是离线抽取链的同一个引擎（共享编排
`war_extraction/core/extraction_runner.py` + 同一套提示词）换了运行条件。所以差距不在流程设计上，
而在**模型**与**后处理**两处。

一句话定性：**慢的根因是模型，差的根因是后处理缺失，还有一个隐患是超时值自相矛盾。**

### 问题清单与修复顺序

| 编号 | 问题 | 定性 | 优先级 | 修复阶段 |
| --- | --- | --- | --- | --- |
| P0-1 | 用本地 `deepseek-r1:7b`（推理模型）跑强模型才吃得下的长提示词 | **缺陷（性能）** | P0 | 阶段一 |
| P0-2 | `json_mode` 参数被静默忽略，模型拿不到 JSON 格式约束 | **缺陷（正确性）** | P0 | 随阶段一自动解决 |
| P1-1 | 前端 5 分钟超时 < 实测 6 分 22 秒，nginx 同为 300 秒 | **缺陷（可用性）** | P1 | 阶段二 |
| P2-1 | 关系引用的实体不在实体表里，悬空边直接进前端图谱 | **缺陷（正确性）** | P2 | 阶段四 |
| P2-2 | 同一名字可同时出现在人物表与组织表（跨类型冲突未剔除） | **缺陷（正确性）** | P2 | 阶段四 |
| P3-1 | 无进度反馈；等待文案要求用户"保持页面打开"；完成提示跨页面时歧义 | 体验 | P3 | 阶段三 |
| P3-2 | 无取消能力；刷新页面会丢失在跑的识别结果 | 体验（技术边界） | P3 | 阶段三（文案）/ 阶段五（可选） |

### 明确不做的四项（详见第七节）

1. **不做服务端识别缓存** —— 任意用户文本命中率约等于 0，收益不抵成本；
2. **不做识别结果入库** —— 用户未审校的文本不该进已发布数据集；
3. **不做"处理流程与离线完全一致"** —— 离线的发布门槛会筛选掉用户本该看到的结果，语义错位；
4. **不处理 Ollama 退场与旧问答** —— 已明确移出本次范围。

## 三、问题清单（含证据与根因）

### P0-1 模型与推理成本（慢的根因）

**现象**：241 字符要 6 分 22 秒。

**证据**：`backend/blueprints/llm.py:231` 用 `llm_pipeline.OllamaAdapter("deepseek-r1:7b")`，
而 `deepseek-r1:7b` 是**推理模型**，无论任务难易都先生成大段思维链再吐 JSON；
三套提示词是按强模型调优的规模（5.9k / 5.5k / 4.1k 字符），7B 模型每次照单全收。

**对比**：离线链路用的是 DeepSeek 云端 `deepseek-flash`
（`entity-event-relation/config/.env`，产物 metadata 里 `model_served: deepseek-flash`），
并且客户端会**显式关闭思考模式**（`war_extraction/core/llm_client.py:38,76-89`）。

**根因**：一个 7B 级推理模型跑 6k 字符提示词 + 复杂输出 schema，单次调用被推到 95 秒。

### P0-2 `json_mode` 是哑参数（差的根因之一）

**现象**：模型输出不被约束成 JSON，解析失败会触发重试（`max_retries=3`，每次 `sleep(1)`），
既慢又可能整段失败进 `partial_errors`。

**证据**：

```python
# backend/llm_pipeline.py:60
def call(self, prompt, temperature=0.1, max_retries=3, json_mode=False):
    # 函数体内 json_mode 从未被使用（全模块只出现这一次），请求里没有 format
```

而三个抽取器**全部**以 `json_mode=True` 调用：
`entity_extractor.py:210`、`event_extractor.py:254,352`、`relation_extractor.py:514`。

离线侧是真的用了：`war_extraction/core/llm_client.py:112-113` 传
`response_format={"type":"json_object"}`，还带"服务不支持时降级重试一次"。

**这条会随阶段一自动解决**：`DeepSeekClient` 的同名参数是真参数。

### P1-1 超时值自相矛盾（隐患）

| 层 | 值 | 位置 |
| --- | --- | --- |
| 实测单次识别 | **382 秒** | `backend/logs/backend.log:18715-18716` |
| 前端 axios | 300 秒 | `frontend/src/config/index.ts:20` |
| nginx（旧后端段） | 300 秒 | `deploy/nginx/china-war.conf:132` |
| Ollama 客户端 | **无上限** | `backend/llm_pipeline.py:65-71`（未传 timeout） |

超时值在 2026-09-24 从 10 分钟下调到 5 分钟（`docs/项目审查与修复历史.md:411`，commit `5132a1a`），
而 2026-09-26 的实测是 6 分 22 秒——**需求已超过上限**。当前状态最可能的表现是
"页面报超时，但后端仍在算完"。

另注：同一份 nginx 文件的 **RAG 段（第 82 行）已经在用 600s**，所以调高旧后端那段有现成先例。

### P2-1 悬空边进入前端图谱（正确性）

**现象**：关系里引用的实体未被实体阶段抽到时，`graphData`（`TextEntityExtract.vue:499-617`）
的节点只从实体表与事件来，连线从关系来，于是图谱上出现**没有落点的连线**。

**证据**：离线链在 `entity-event-relation/main.py:779` 的 `cleanup_relation_conflicts` 专门
清理这类边，并统计到这是一个**常态量级**（`entity-event-relation/output/中国历代战争简史/published/quality_report.json`）：
`dangling_relations_dropped` = 事件-地点 39、事件-组织 4、事件-人物 20、事件-事件 17，
其中 `target_not_found` 80 条。

在线链只做"名称非空 + 关系名在枚举内"的过滤（`backend/llm_pipeline.py:356-403`），
**没有目标实体存在性检查**。

### P2-2 跨类型冲突未剔除

离线有 `cleanup_entity_conflicts`（`entity-event-relation/main.py:106`）做人名/组织名的
跨类型互斥与同规范名归并；在线只按名字去重（`backend/llm_pipeline.py:275-278`），
所以同一名字可以同时出现在人物表和组织表。

### P3-1 / P3-2 等待体验

- 加载态是静态文案（`TextEntityExtract.vue:163-167`），原文写"这可能需要2分钟到5分钟"——
  与实测 6 分 22 秒不符，**换模型后还会第二次变错**；
- 无已用时，用户无法区分"还在跑"与"已卡死"，因此会去按刷新——而刷新会让结果丢失；
- 完成/部分失败/失败提示走全局 `layer.msg`（`TextEntityExtract.vue:652,657,663`），
  用户切到别的页面后弹出来会产生歧义；
- 无取消能力（`AbortController` 只存在于旧问答页 `frontend/src/views/inference/index.vue:169`）。

### 补充说明：切页面不会丢结果（这不是缺陷）

已核实：切到其他路由时请求**不会中断**（axios 请求不属于组件生命周期，路由守卫
`frontend/src/router/index.ts:43` 也不取消在途请求），后端同样会算完（Flask 默认
`threaded=True`，客户端断开不会杀掉视图函数）。结果会照旧写进该账号的 localStorage 历史。

真正会丢结果的只有**刷新页面与关闭标签**（请求随页面销毁）。这是技术边界，
不需要用"限制用户行为"的方式去防，见阶段三。

## 四、与离线链路的关系（事实澄清）

| 层次 | 在线 | 离线 |
| --- | --- | --- |
| 编排 / 抽取器 / 提示词 | **完全同一份代码** | 同 |
| 分段参数 | `chunk_size=1200, overlap=150`（`llm_pipeline.py:408`） | `1800 / 200`（`war_extraction/config.py:132-133`） |
| LLM 客户端 | 本地 Ollama（将被替换） | DeepSeek 云端 |
| 分段缓存 | 不传，不读不写（`extraction_runner.py:169-172`） | 有 `CacheManager` |
| 后处理 | 逐字段归一 + 按名字去重 + 关系枚举过滤 | 实体回填 + 冲突清洗 + 事件归并 + 关系派生 + 悬空边清理 + 发布子集 + 地理编码 |

**该共用的（纯纠错，与"发布"无关）**：

| 环节 | 位置 | 收益 |
| --- | --- | --- |
| 悬空边过滤 | `main.py:779` | 直接修掉 P2-1 |
| 跨类型冲突剔除 | `main.py:106` | 直接修掉 P2-2 |
| 实体回填（可选） | `main.py:962` | 补上悬空边的根因 |

实体回填的默认值已核实是**枚举合法**的（`war_extraction/utils/vocabulary.py` 的 `ROLES`
含 `关键人物`、`统帅`，`ORG_TYPES` 含 `军事势力`），所以不会引入枚举外取值。
但它会给回填实体自动填上角色（`main.py:999-1014`），会让用户看到文本里没写死的角色——
建议**先只回填名字、不填角色**，或列为可选项。

**不该共用的（有意设计，不是遗漏）**：

- `split_publishable_outputs`（`main.py:441`）的发布门槛会把事件分进 published/candidate。
  用户页面上要的是"模型对这段文本读出了什么"的忠实反射；被门槛筛掉会让人误以为"没识别到"。
- `backend/llm_pipeline.py:356-361` 的注释已记录这个分工："本函数的返回值是直接给前端渲染的
  载荷……离线链那条路的对应处理在 `main.split_publishable_outputs`（枚举外进候选区）。"
  在线没有候选区，只能丢弃——这是取舍，不是缺陷。
- 事件归并、别名收敛、过宽概括过滤：为整书尺度设计，在 1000 字符单段上收益小、误伤风险实在。

## 五、阶段性任务

### 阶段一（P0）：模型切换到 DeepSeek 云端

**目标**：把单次识别从 6 分钟量级降到几十秒量级，并让 `json_mode` 真正生效。

**改动点**

| # | 文件 | 位置 | 改什么 |

| 1 | `backend/blueprints/llm.py` | `:229-232` | `OllamaAdapter("deepseek-r1:7b")` 改为 `DeepSeekClient()`（`from war_extraction.core import DeepSeekClient`，已在 `war_extraction/core/__init__.py:5` 导出）；日志同步改口径 |
| 2 | `backend/blueprints/llm.py` | `:234-239` | "LLM客户端初始化失败"的文案从"Ollama 没起"改为"密钥无效 / 配额不足"（`DeepSeekClient` 对 401 直接抛 `LLMAuthError` 不重试，`llm_client.py:118-122`） |

**关键前提（已核实）**：密钥与配置齐全——`entity-event-relation/config/.env` 内
`DEEPSEEK_API_KEY`（35 位，已设置）、`DEEPSEEK_MODEL`、`API_BASE_URL` 三项齐备；
客户端按 `__file__` 绝对路径加载 `.env`（`war_extraction/core/llm_client.py:17-18`），
**不受后端工作目录影响**。

**不需要额外做的**：`OllamaAdapter.call` 与 `DeepSeekClient.call` 签名逐参数一致
（`llm_pipeline.py:60` vs `llm_client.py:91`），抽取器只依赖鸭子类型的 `call`，
所以**不需要改编排、不需要改提示词**。

**完成指标**

| 指标 | 判据（怎么测） | 目标 |
| --- | --- | --- |
| M1.1 不再用本地模型 | `backend/logs/backend.log` 中该接口不再出现"使用本地Ollama模型" | 0 次 |
| M1.2 耗时（核心） | 用 2.3 节那段 241 字符文本，连续跑 3 次取中位数 | **≤ 60 秒**；上界不得 > 120 秒 |
| M1.3 结果不退化 | 同上 3 次，每次 `code=200` 且**不返回 `partial_errors`**；事件数 ≥ 1、地点/组织/人物数 ≥ 1 | 全部满足 |
| M1.4 确定性改善 | 同上 3 次的事件数一致（不再出现 1 vs 2 那种漂移） | 一致 |
| M1.5 回归 | 跑 `backend` 与 `entity-event-relation` 两侧与抽取相关的用例 | 全绿 |

**风险**

- **引入计费**：每次识别 4~5 次云端调用，输入侧每次数千 token。配额与计费口径需要先确认，
  页面本身已限 `editor`（`base-routes.ts:50` 注释写明"会消耗配额"），这是现成的闸门；
- **最坏路径仍可能超时**：单次调用 60 秒 × 重试 2 次 × 调用 4 次，理论上限远超 300 秒，
  所以阶段二不可跳过；
- **模型版本漂移**：产物与页面结果的"口径"从"某个本地模型"变成"云端当前版本"，
  云端升级会改变结果——这是换取速度与质量的代价，需知悉。

| 场景 | 结果 |
| --- | --- |
| `nginx -t` | 语法/指令校验通过（这一步是 CI 的 `check_deploy_config.py` 判不了的） |
| 后端 1 秒返回 500 + `{code,msg}` | 客户端拿到 **HTTP 500 与后端 JSON 原文**（含那句 `msg`），1.02 秒 —— 反代不吞后端文案 |
| 后端 12 秒才返回 | 600s 超时下完整通过（12.01 秒，HTTP 200） |
| 把 `proxy_read_timeout` 压到 2s、后端要 5 秒 | 客户端拿到 **nginx 的 `504 Gateway Time-out` HTML**（2.01 秒）。这就是"页面超时"长什么样，也是残余缺口的下限：**后端最坏耗时必须留在 600s 以内**，否则用户看到的是这张 HTML 页而不是后端文案 |

顺带两条实测记录（含一次自我纠正）：

- `proxy_buffering off` 对 SSE 的作用**没能复现**：5 帧、间隔 0.4 秒的流式响应，
  缓冲开与关的逐帧到达时刻一致（`[0.006, 0.407, 0.807, 1.208, 1.609]` vs `[0.018, 0.42, 0.821, 1.221, 1.622]`）。
  指令本身按 nginx 文档保留（对 SSE 的标准做法，且响应头已带 `X-Accel-Buffering: no`），
  但**"任何缓冲都会让回答憋住"这句话在本机是未证实的**，别拿它当因果结论。
- 头一版用 `curl -w %{time_starttransfer}` 量"首字节"，那个值量的是**响应头**到达时刻
  （缓冲开关都会立刻转发响应头，所以两配置量出来都是 0.00x 秒），已换成逐字节读再量。

## 七、范围边界（明确不做）

| # | 不做的事 | 理由 |
| --- | --- | --- |
| 1 | **服务端识别缓存** | 缓存键是文本内容哈希（`war_extraction/core/cache_manager.py:102-109`），任意用户文本命中率约等于 0。离线缓存是为"改一次配置重跑整本书"设计的，在线没有这个场景。替代做法：前端已有按文本去重的历史记录（`TextEntityExtract.vue:725`），可在发起识别前提示"这段文本已识别过，是否直接查看历史结果"，零服务端成本 |
| 2 | **识别结果入库** | 用户未审校的文本进已发布数据集会破坏版本可追溯性（产物由 `git_commit` + `artifact_sha256` 自证，见 `entity-event-relation/docs/数据迭代记录.md`）。且在线返回形状与 `import_json_to_sqlite.py` 的硬依赖不同（`entity-event-relation/README.md:713-760`）。现状"只导出 MD/JSON"是正确的边界 |
| 3 | **处理流程与离线完全一致** | 发布门槛（`main.py:441,566`）会筛选用户本该看到的结果，语义错位；离线后处理是为整书尺度设计的 |
| 4 | **Ollama 退场与旧问答处理** | 已明确移出本次范围 |
| 5 | **假进度条** | 后端无阶段回流，做出来就是假的；真实进度见阶段五 5a |
| 6 | **引入任务队列** | 项目无 celery/redis 等组件，为一个接口引入不划算 |
