## 问题一：账户权限如何升级？

### 现状

- 三种角色（admin / editor / viewer）已贯穿后端写接口（403）、菜单下发、路由拦截、界面徽标；
- **但提权的唯一途径是手写 SQL**：`UPDATE UserInfo SET role = 'editor' WHERE account = '...'`，没有界面入口；
- `get_menu()` 目前只有 viewer 一个裁剪分支——admin 与 editor 的菜单完全相同，没有"仅管理员可见"的菜单项，这也堵住了未来放管理功能的位置。

### 方案 A（推荐）：管理员界面的「用户管理」页

后端两个接口 + 前端一个页面，把提权变成管理员页面上的一次下拉选择：

| 项 | 内容 |
| --- | --- |
| 后端接口 | `GET /api/admin/users`（列表：id/account/name/role）、`POST /api/admin/users/<id>/role`（改角色，body: `{role}`） |
| 鉴权 | **新增 `@require_admin` 装饰器**（仅 admin）。不能复用 `require_write_role`——editor 若能改角色，权限体系会被 editor 自己打散 |
| 防呆 | ① 不能修改自己的角色（防止最后一个管理员把自己降级后系统失管）；② 目标角色值白名单（admin/editor/viewer），经 `safe_identifier` 同级的严格校验 |
| 前端页面 | `views/admin/UserManagement.vue`：用户表格（账号/昵称/角色下拉/保存），套 layui 表格，无需复用 CRUD 组合式函数 |
| 菜单 | `get_menu()` 增加 `/admin/users`（用户管理）项，**仅 admin 角色下发**——裁剪逻辑从两级改三级 |
| 前端配套 | `api/module/admin.ts`；路由加 `requiresRole: 'admin'`（守卫的 `WRITE_ROLES` 拆成按 meta 比对：requiresRole 值 ∈ [admin,editor,viewer] 分级比对）；store 白名单加 id |

工作量：后端约 60 行、前端约 180 行（页面 + 菜单三处 + 守卫分级）。**注意**：守卫现有 `WRITE_ROLES = ['admin','editor']` 的写法是"是否拥有写权限"，加 admin-only 页面后要改成"meta.requiresRole 是否被当前角色满足"的分级行（admin ⊃ editor ⊃ viewer）。

### 方案 B（最简，零代码）：SQL 提权文档化

把提权 SQL 与角色职责表写进 `backend/README.md` 与 `deploy/README.md`（目前提权 SQL 只散在实施记录里）。适合"只有一个管理员"的当前形态；做了方案 A 后此文档仍保留作为兜底。

### 提权生效时机（两个方案都要写明的坑）

- 写接口的 403 / 403 放行是**每次请求实时查库**的——提权后调接口立即生效；
- **菜单是登录时拉取的**——被提权的用户需要重新登录（或刷新触发 `loadMenus`）才能看到新菜单。建议：管理员改完角色后，界面提示"该用户下次登录生效"。

## 问题二：问答记录为什么不随账号隔离？

### 根因（三层叠加）

1. **RAG 是独立服务且无用户体系**：服务端只有 5 个无鉴权接口（query/health/dicts/demo/query_json），**会话历史不在服务端**；
2. **RAG 前端把会话存 localStorage，key 全局唯一**：`RAG/frontend/src/stores/session.ts:43` 的 `STORAGE_KEY = 'ragv5-session-v3'`，没有账号维度；
3. **主应用与 RAG 之间没有身份传递**：主应用以同源 iframe（`/rag/`）嵌入 RAG，iframe 与主应用共享同一个浏览器的 localStorage，而主应用的登录身份（token/userInfo）从不传给 RAG——RAG 前端根本不知道"现在是谁在问"。

结论：同一台浏览器上，**任何主应用账号打开 RAG 看到的都是同一份会话记录**（你截图里管理员与普通用户的记录一字不差，连时间戳都相同）；"改名/删除会话"任何账号都能操作这份共享数据。不同浏览器之间本来就不共享，所以跨机器不串。

### 同病相连的三处（应同批处理）

| 位置 | 存储 key | 现状 |
| --- | --- | --- |
| RAG 智能问答（iframe） | `ragv5-session-v3` | 本次问题主角 |
| 旧问答助手 `inference/index.vue`（入口已下线，代码仍在） | `chatHistory` | 同样全局共享 |
| 文本实体识别 `TextEntityExtract.vue` | `extractHistory` | 同样全局共享；**且该页面普通用户可用，抽取会消耗 LLM 配额**——是否限 editor 建议一并决策 |

### 方案 A（最小改动，推荐先做）：按主应用账号分存储 key

原理：把"当前是谁"告诉 RAG，RAG 的存储 key 按账号分开——`ragv5-session-v3` → `ragv5-session-v3:{uid}`。

| 步骤 | 位置 | 内容 |
| --- | --- | --- |
| 1 | 主应用 `views/knowledge/RagAssistant.vue` | iframe `load` 后向 `iframe.contentWindow.postMessage({type: 'cw-user', uid: <userInfo.id>}, '/')`；账号切换（登录/登出）时重发并重建 iframe（已有换 key 重建机制可复用） |
| 2 | RAG 前端启动（`main.ts` 或 session store 初始化） | `window.addEventListener('message')` 监听 `{type:'cw-user'}`，校验 origin（同源）后记录 uid；收到 uid 变化时**重载会话存储**（key 变了，重新读 localStorage） |
| 3 | RAG `stores/session.ts` | `STORAGE_KEY` 改为函数 `storageKeyFor(uid)`：有 uid → `ragv5-session-v3:u{uid}`；无 uid（独立访问 :8000）→ `ragv5-session-v3`（行为不变，老记录留在默认 key） |
| 4 | 主应用内两个页面 | `inference/index.vue` 与 `TextEntityExtract.vue` 在**主应用内**，可直接读 store——key 拼接 `chatHistory:{uid}`、`extractHistory:{uid}`；首读时对旧 key 做一次性迁移（旧记录归属第一个使用者或直接归档），避免"全员看到旧历史" |

安全边界（如实）：方案 A 只解决"**串记录**"，不防"**冒充**"——同源之下，懂控制台的 viewer 理论上可以改 uid 看别人的记录。对演示/局域网形态足够；公网部署需要方案 B。

工作量：RAG 前端约 40 行、主应用约 20 行。**注意**：`session.ts` 有 RAG 前端测试覆盖（schema v3 / 隔离区 / 配额裁剪），改 key 逻辑要同步改测试。

### 方案 B（完整）：身份传递 + RAG 服务端验签

- 主应用 postMessage 传 **JWT**（不要拼在 iframe URL 上——URL 会进历史与日志），RAG 前端存 sessionStorage，之后每个 `/api/query` 请求带 `X-User-Token` 头；
- RAG 服务端用 PyJWT + 与 backend **共享的 `JWT_SECRET`** 验签（RAG `.env` 增加该配置；验签只确认身份，不引权限体系），服务端日志即可按用户记账——这也顺带为 RAG 未来按用户限流/审计铺路；
- 会话历史**仍放前端按 uid 分 key**（方案 A 的 2、3 步照做）。不建议本轮把历史迁到服务端——那需要新表、迁移与接口，工作量一个数量级。

工作量：在方案 A 之上 +RAG 服务端验签依赖与中间件约 80 行、密钥配置管理。**触发时机**：决定公网部署、或要求"记录不可被冒充查看"时再上。

### 方案 C：接受现状

把 RAG 定位为"共享演示环境"写进 `RAG/README.md` 与集成约定——零代码，但与刚建立的账号体系观感冲突，不推荐。

## 推荐与顺序

1. **问题一做方案 A**（用户管理页）——角色体系已建，界面提权是闭环的最后一格；顺带把 get_menu 升为三级裁剪；
2. **问题二先做方案 A**（uid 分 key）——三处存储同批改；方案 B 等公网部署需求明确再做；
3. 文本抽取页是否对 viewer 隐藏/限 editor，随问题二一并定（涉及 LLM 配额归属）。
