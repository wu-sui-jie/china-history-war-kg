## 三、最高优先级问题：登录限流时间不能使用 monotonic 持久化

### 3.1 问题位置

文件：

```text
backend/login_guard.py
```

当前数据库字段：

```text
window_start
locked_until
updated_at
```

写入和比较使用：

```python
time.monotonic()
```

### 3.2 问题原因

`time.monotonic()` 是当前机器从启动以来经过的时间，只适合进程内和同一次系统启动期间计算时间差。

示例：

```text
机器已运行 5 天：monotonic = 432000
数据库锁定截止：locked_until = 432900

机器重启后：monotonic = 30
```

服务会比较：

```text
30 < 432900
```

账号可能被错误锁定几十万秒。

也可能出现反向问题：旧窗口被当成已经过期，导致限流失效。

### 3.3 修改方案

数据库中持久化的时间统一使用：

```python
time.time()
```

或 UTC epoch：

```text
1790340000.0
```

`time.monotonic()` 只用于不落库的短期耗时，例如单次 HTTP 请求计时。

建议给表字段增加语义说明：

```text
window_start_epoch
locked_until_epoch
updated_at_epoch
```

若不改列名，也要修改注释和迁移说明。

### 3.4 兼容旧数据

旧表里已经存在的 monotonic 值不能与 epoch 混用。

升级时选择一种策略：

1. 清空 `login_attempts` 表；或
2. 增加 `clock_version`，旧版本数据启动时作废。

登录限流数据是临时安全状态，不是业务数据，升级时直接清空最简单。

### 3.5 验收标准

新增测试：

- [ ] 写入值接近当前 epoch；
- [ ] 模拟进程重启后锁定仍正确；
- [ ] 模拟机器重启后时间基准变化；
- [ ] 过期锁定自动放行；
- [ ] 旧 monotonic 数据不会造成超长锁定；
- [ ] IP 窗口和账号窗口分别正确。

## 四、最高优先级问题：token 撤销没有覆盖 RAG

### 4.1 当前状态

旧后端已经实现：

```text
UserInfo.token_version
UserInfo.disabled
```

旧后端请求流程：

```text
JWT 验签
→ 查询 UserInfo
→ 检查 disabled
→ 检查 JWT.ver == UserInfo.token_version
```

但 RAG 只检查：

```text
签名
exp
iss
aud
user_id/sub
```

RAG 不查询 UserInfo，所以管理员停用用户或增加 token_version 后，旧 token 仍可调用 RAG，直到 JWT 自然过期。

### 4.2 解决方案选择

#### 方案 A：短有效期

将访问 token 改为 15–30 分钟，并增加刷新机制。

优点：

- RAG 不需要回查 backend；
- 结构简单；
- 被盗 token 的有效窗口较短。

缺点：

- 需要 refresh token 或重新登录；
- 当前前端没有刷新机制。

#### 方案 B：Backend Token Introspection

backend 新增内部接口：

```text
POST /api/internal/token/introspect
```

RAG 向 backend 查询：

```json
{
  "active": true,
  "user_id": 3,
  "role": "viewer",
  "token_version": 2,
  "disabled": false
}
```

内部接口使用服务间密钥保护，并设置 30–60 秒缓存，避免每个 RAG 请求都打 SQLite。

#### 方案 C：共享 Redis

backend 和 RAG 读取：

```text
user:<id>:token_version
user:<id>:disabled
```

适合未来多实例部署，当前阶段不需要立即引入。

### 4.3 当前推荐

当前还没有服务器、用户规模小，建议分两步：

1. 先增加 refresh token，将 access token 缩短到 30 分钟；
2. 若需要“管理员停用后立刻阻止 RAG”，再增加 introspection。

在完成前，文档必须明确：

> token_version 即时撤销目前只对旧后端有效，RAG 最迟在 JWT 到期后失效。

### 4.4 验收标准

- [ ] 用户正常 token 可调用 backend 和 RAG；
- [ ] 修改 token_version 后 backend 立即 401；
- [ ] 修改 token_version 后 RAG 在设计时间内 401；
- [ ] disabled 用户 backend/RAG 都拒绝；
- [ ] 角色变更后的 RAG 行为符合设计；
- [ ] introspection 服务不可被公网匿名调用；
- [ ] backend 不可用时 RAG 采用明确的 fail-open 或 fail-closed 策略。

## 五、最高优先级问题：RAG nginx 模式只声明，没有证明 nginx 已启用认证

### 5.1 当前状态

部署模板：

```env
RAG_AUTH_MODE=nginx
```

但 nginx 配置仍为：

```nginx
# auth_basic "china-war";
# auth_basic_user_file /etc/nginx/.htpasswd;
```

因此部署者如果直接复制两个模板：

```text
RAG 认为 nginx 在鉴权
nginx 实际没有鉴权
```

服务仍能正常启动，但公网 RAG 没有访问控制。

### 5.2 推荐方案

#### 推荐：生产默认使用 JWT

将生产模板改为：

```env
RAG_AUTH_MODE=jwt
```

配置 RAG JWT 验签密钥/公钥。这样用户只需要登录旧知识库，不需要再输入 nginx Basic Auth 密码。

#### 如果继续使用 nginx 模式

安装脚本必须自动校验：

1. `/etc/nginx/.htpasswd` 存在；
2. 生成后的 nginx 配置包含启用状态的 `auth_basic`；
3. nginx `-T` 输出中 `/rag/` 确实有认证；
4. 缺少任一条件则拒绝安装或启动。

不能仅依靠注释提醒。

### 5.3 验收标准

JWT 模式：

- [ ] 匿名请求 `/rag/api/query` 返回 401；
- [ ] 有效旧后端 JWT 可访问；
- [ ] 错误签名、错误 issuer/audience 被拒；
- [ ] 浏览器 iframe 正常携带 token。

nginx 模式：

- [ ] 未认证访问 `/rag/` 返回 401；
- [ ] 后端 8000 只监听回环；
- [ ] 外网无法直连 8000；
- [ ] `nginx -T` 能看到 auth_basic 生效。

当前停机和消息丢失已修复，但仍是单 worker。用户量扩大后再做 session_key 分片和全局并发控制。

### 10.5 非对称 JWT

当前 HS256 可用。正式多服务部署后可以升级为 backend 私钥签名、RAG 公钥验证。

- 很难区分各轮修改边界。

6. 运行完整测试；
7. 推送；
