## 2.1 首个管理员口令策略不一致

### 问题

普通注册和修改密码的策略是：

```text
10–64 位
```

但首个管理员命令仍是：

```text
6–20 位
```

涉及文件：

- `backend/create_admin.py`
- `backend/db_utils.py`
- `frontend/src/views/login/index.vue`
- `backend/tests/test_create_admin.py`

后果：

- 首个管理员可以使用 6–9 位弱口令；
- 21–64 位安全长口令无法通过首管命令设置；
- 测试和文档存在两套密码标准。

### 修改方法

建立唯一密码策略模块，例如：

```text
backend/password_policy.py
```

提供：

```python
MIN_PASSWORD_LENGTH = 10
MAX_PASSWORD_LENGTH = 64

def password_problem(password: str): ...
```

以下入口全部复用：

- 注册；
- 修改密码；
- `create_admin.py`；
- 管理员重置密码；
- 前端提示；
- 测试。

### 验收

- [ ] 首管命令拒绝 9 位以下密码；
- [ ] 接受 10–64 位密码；
- [ ] 旧账号的历史短密码仍可登录；
- [ ] 新设置密码统一执行新策略；
- [ ] 文档、前端、后端、测试只有一套数值。

## 2.2 前端会静默 trim 密码

### 问题

登录页当前对密码执行：

```ts
password: loginForm.password.trim()
```

密码和账号、昵称不同，不应被静默修改。如果历史密码或命令行创建的密码包含首尾空格，前端发送的内容与用户输入不一致，导致无法登录。

### 修改方法

只 trim：

```text
account
name
```

密码保持原始字符串：

```ts
password: loginForm.password
```

如果产品明确禁止首尾空格，应由统一密码策略返回错误，而不是前端自动删除。

### 验收

- [ ] 前端按原值发送密码；
- [ ] 注册、登录、修改密码行为一致；
- [ ] 首尾空格策略由后端明确决定；
- [ ] 增加含首尾空格密码的测试。

## 2.3 登录限流并发计数不是原子的

### 问题

当前逻辑接近：

```text
SELECT failures
→ Python 中 failures + 1
→ UPDATE failures
```

两个并发请求可能同时读到 `failures=3`，然后都写回 4。实际发生两次失败，但数据库只增加一次。

现有测试覆盖了 epoch、锁定窗口和迁移，没有覆盖多线程/多请求竞争。

### 修改方法

将计数更新收敛到一条原子 SQL，或使用 `BEGIN IMMEDIATE`。

示意：

```sql
INSERT INTO login_attempts (...)
VALUES (...)
ON CONFLICT(scope, key) DO UPDATE SET
  failures = CASE
    WHEN :now - login_attempts.window_start_epoch > :window
      THEN 1
    ELSE login_attempts.failures + 1
  END,
  ...;
```

账号锁定截止也应在同一条事务路径中计算。

### 验收

- [ ] 20 个并发失败请求最终计数为 20；
- [ ] 并发请求达到阈值后不继续放行；
- [ ] IP 与账号两个维度都通过并发测试；
- [ ] SQLite busy 时有明确重试或失败策略。

## 2.4 登录限流数据库故障时 fail-open

### 问题

当前限流表读取或写入失败时：

```text
记录日志
→ 允许登录继续进行
```

如果数据库锁冲突、表损坏或迁移失败，爆破保护会自动失效。

### 修改方法

增加配置：

```env
LOGIN_GUARD_FAILURE_MODE=closed
```

建议：

- 开发环境可用 `open`；
- 生产环境使用 `closed`；
- 已知 SQLite 临时锁可短暂重试；
- 其它错误返回 503，不继续认证。

### 验收

- [ ] 生产模式读取限流状态失败时返回 503；
- [ ] 临时 busy 会进行有限次数重试；
- [ ] 开发模式可显式选择 fail-open；
- [ ] health 能显示当前失败策略。

## 2.5 生产占位密钥可能通过一致性检查

### 问题

部署模板中包含：

```env
NEO4J_PASSWORD=CHANGE_ME
JWT_SECRET=CHANGE_ME_openssl_rand_base64_48
INTERNAL_SERVICE_KEY=CHANGE_ME_openssl_rand_hex_32
```

部署门禁主要检查非空和两侧同值。如果部署者把同一个占位符复制到两侧，存在通过检查的可能。

### 修改方法

部署脚本明确拒绝：

```text
CHANGE_ME*
your_*
example*
placeholder*
空值
```

同时检查最低长度：

```text
JWT_SECRET >= 32 bytes
INTERNAL_SERVICE_KEY >= 32 bytes
Neo4j 密码不得为默认值
```

### 验收

- [ ] `CHANGE_ME` 及其变体全部失败；
- [ ] 两侧相同占位符仍失败；
- [ ] 真实随机密钥通过；
- [ ] 密钥过短失败；
- [ ] 密钥扫描与部署门禁的占位符口径一致。

- [ ] 刷新流程可用；

## 2.7 RAG introspection 默认仍可被关闭

### 问题

当 `RAG_INTROSPECT_URL` 与服务密钥都不配置时，RAG 跳过撤销查询，只给 health 告警。

这意味着：

```text
管理员停用账号 / 用户改密码
→ 旧后端立即拒绝
→ RAG 仍可能接受旧 token，直到 JWT 到期
```

部署模板虽然默认填了 URL，密钥为空时门禁会阻止半配置；但如果部署者同时删除 URL 和密钥，目前只是告警。

### 修改方法

在生产 JWT 模式下二选一：

```env
RAG_REQUIRE_REVOCATION_CHECK=true
```

或显式接受延迟撤销：

```env
RAG_ALLOW_DELAYED_REVOCATION=true
```

不能通过“两个值都不填”隐式接受 7 天撤销延迟。

### 验收

- [ ] 生产 JWT 模式未配置 introspection 时拒绝启动；
- [ ] 显式允许延迟撤销时才可启动；
- [ ] health 显示撤销策略和最大延迟；
- [ ] 安装脚本与服务启动判定一致。

## 2.8 Introspection 缓存存在并发击穿

### 问题

同一 token 缓存失效时，多个并发请求可能同时向 backend 发起 introspection，形成重复查询。

### 修改方法

实现 per-token single-flight：

```text
同一个 token 同时只允许一个在途查询
其他请求 await 同一个 Future
```

或为 token 摘要建立短时异步锁。

### 验收

- [ ] 100 个同 token 并发请求只产生一次 backend 查询；
- [ ] 查询失败后锁正确释放；
- [ ] 不同 token 可并行查询；
- [ ] 缓存容量与淘汰策略在并发下正确。

## 2.9 RAG 成为 backend 的强依赖，但 systemd 未声明依赖

## 2.10 SSE 问答在鉴权前检查 runtime

### 问题

`POST /api/query` 当前顺序：

```text
runtime 检查
→ 鉴权
→ 撤销检查
```

runtime 加载失败时，匿名请求会先得到服务状态和脱敏后的加载错误。

`/api/query/json` 则是先鉴权，两条通道不一致。

### 修改方法

统一顺序：

```text
鉴权
→ 撤销检查
→ runtime
→ 限流
→ 参数校验
→ 执行
```

### 验收

- [ ] runtime 正常或失败时，匿名请求始终先得到 401；
- [ ] SSE 与 JSON 通道顺序一致；
- [ ] 未认证请求不消耗限流配额；
- [ ] 未认证请求看不到 runtime/load_error。

## 2.15 Outbox 并发领取与数据重导并发仍未验证

### Outbox 并发

API 手工重试与 systemd timer 可能同时运行，并领取同一 pending 任务。

需要状态机：

```text
pending → processing → done/abandoned
```

任务领取使用原子 SQL，记录 worker_id 和 lease_until，超时可重新领取。

### 数据重导并发

执行全量导入时，如果用户仍可在线编辑：

- 在线修改可能被清空；
- outbox dataset_version 可能切换；
- SQLite/Neo4j 可能产生短暂混合状态。

### 修改方法

增加维护模式：

```text
进入维护模式
→ 禁止写接口
→ 确认 pending outbox 为 0
→ 备份
→ 重导
→ 全量同步 Neo4j
→ 重建 RAG
→ 对账
→ 退出维护模式
```

### 验收

- [ ] 两个重试进程不会同时执行同一任务；
- [ ] worker 崩溃后 lease 可恢复；
- [ ] 重导期间写接口返回 503；
- [ ] 重导前后 dataset_version 一致；
- [ ] 重导失败可从备份恢复。

继续叠加 Python 迁移后，一旦失败，难以区分是业务修改、依赖升级还是远端冲突导致。

### 原因二：旧后端尚未在 3.11 验证

151 项测试当前是在 Python 3.8 中通过的。

### 原因三：依赖集合不同

Python 3.11 环境当前缺少部分旧后端依赖；Python 3.8 环境缺少 RAG/飞书依赖。

### 原因四：SQLAlchemy 版本差异

旧环境存在 SQLAlchemy 1.x 风格代码，例如：

```python
Model.query.get(id)
```

统一目标是 SQLAlchemy 2，需要迁移为：

```python
db.session.get(Model, id)
```

### 原因五：py2neo 是高风险旧依赖

需要验证：

```text
Python 3.11 + py2neo + Neo4j 5.x
```

长期再替换为官方 Driver。

### 原因六：统一 lock 尚未生成

必须先完成安装和测试，再锁精确版本；不能先锁一个未验证组合。
