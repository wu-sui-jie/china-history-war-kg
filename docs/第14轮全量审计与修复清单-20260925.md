#### P1-1 【已实测】部署上传脚本的 tar 回退分支，排除规则全部失效

**位置**：`deploy/scripts/04_upload_from_local.sh:48-66`（排除模式都带尾斜杠）、`:97-98`、`:115-118`

**现象**：GNU tar 与 rsync 对尾斜杠的处理不同——`--exclude 'node_modules/'` 在 rsync 下正常，在 tar 下**完全不生效**。实测复现：

```text
带尾斜杠  --exclude '.git/'  --exclude 'node_modules/'
  →  ./ ./.git/ ./.git/config ./keep/ ./keep/a.txt ./sub/node_modules/x.js
不带尾斜杠 --exclude '.git'  --exclude 'node_modules'
  →  ./ ./keep/ ./keep/a.txt ./sub/
```

**触发条件**：脚本头部明确把 Windows Git Bash 列为支持平台，而本机 `command -v rsync` **无输出**（未安装），正好走 tar 分支。

**后果**：`.git`（约 108 MB，含文档已披露的历史明文口令）、`frontend/node_modules`（约 320 MB）、`RAG/frontend/node_modules`（约 282 MB）全部打包上传到服务器；`--mirror` 在该分支被静默忽略。脚本第 14 行的注释写明"代码同步时排除 node_modules、.git"——意图与行为相反。

**改法**：排除项去尾斜杠（或改用 `--exclude-vcs`）；tar 分支遇到 `--mirror` 明确报错退出，不要静默忽略。

**验收**：本机（无 rsync）跑一次 `--code-only --dry-run` 之类的干跑，断言产物列表里不含 `.git/`、`node_modules/`；或加一条用假 `rsync` 不存在时的 tar 列表用例。

#### P1-3 【已实测】限流的来源 IP 可被一个请求头伪造（后端与 RAG 两处，同一根因）

**位置**：
- `deploy/nginx/china-war.conf:74` 与 `:127`：`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`
- `backend/login_guard.py:499`：`forwarded = (request.headers.get("X-Forwarded-For") or "").split(",")[0].strip()`
- `RAG/server/api.py:527`：`first = fwd.split(",")[0].strip()`
- `deploy/env/backend.env:38`：`LOGIN_TRUST_FORWARDED_FOR=true`
- `deploy/env/rag.env:43-44`：`RATE_LIMIT_TRUST_FORWARDED_FOR=true` + `RATE_LIMIT_TRUSTED_PROXIES=127.0.0.1`

**现象**：`proxy_add_x_forwarded_for` 的定义是"**客户端自带的值放在最前**，真实地址追加在后"。代码取 `[0]`，取到的正是攻击者可控的那一段；nginx 在第 73 行已经正确设置了 `X-Real-IP = $remote_addr`，但两份代码都没用它。RAG 侧的可信代理是 `127.0.0.1`，而同机 nginx 的 peer 就是 `127.0.0.1`，所以这道"可信代理"校验也挡不住伪造的首段。

**后果**：攻击者每次请求带一个不同的 `X-Forwarded-For`，IP 维度的限流完全失效，在线爆破只剩账号维度的 5 次锁定（换账号即可）。这与 `login_guard.py:493` 的文档字符串"采信它等于把限流交给攻击者决定"正好相反——思路是对的，取错了段。

**改法**：改读 `X-Real-IP`（nginx 已下发），或按可信跳数取最右段（`split(",")[-1]`，取决于代理层数）。两处一起改，口径保持一致。

**验收**：各加一条用例——同一真实来源伪造 5 个不同首段，断言计数累加在同一个 key 上（改进前会得到 5 个不同 key）。

#### P1-4 【已复核】前端每次编辑节点，都会把图谱节点的 `name` 写没，并且属性更新全部静默丢弃

**位置**：`backend/blueprints/node.py:119`、`backend/db_utils.py:419`、`:427`、`backend/model_search.py:110`、`backend/sync_compensation.py:364`

这是**两个根因叠在同一个接口上**，都会静默损坏图谱数据：

**根因 a：`name` 取错字段**

`node.py:119` 读的是 `data.get("name")`，但前端从来不发 `name`——它发的是 `EventName` / `PersonName` / `OrgName` / `geo_name`（`frontend/src/composables/useNodeCrudPage.ts:135-141` 按 `nameField` 组装；`EventNode.vue:194`、`PersonNode.vue:108`、`PlaceNode.vue:122` 定义）。于是 `new_name` 是 `None`，一路作为 `job.node_name` 传下去，最终 `model_search.py:110` 执行 `SET n += $props, n.name = $name`，把 Neo4j 的 `name` 属性写成 null（等价于删除）。

SQLite 那边因为 `db_utils.py:421-424` 的归一化循环会把名字救回来，所以**只有图谱坏掉、主存储看不出来**。

**根因 b：outbox 属性快照键名错**

`db_utils.py:427` 的快照是 `{"name": new_name, **(properties or {})}`——`properties` 里是 **API 键名**。而重放路径 `sync_compensation.py:364` 走 `neo4j_props()`，后者按 **SQLite 列名**取值（`backend/node_property_mapping.py:157`）。键名对不上，全部取到 `None` 再被 `if v is not None` 过滤掉，于是属性一个都同步不过去，函数却返回 `sync_status: success`。

对照 `create_node`（`db_utils.py:379` 传的是已归一化的 `filtered_data`）——同一件事在两条路径上口径分叉。

**后果**：编辑过的节点在图谱里变成无名节点；`model_search.py:622/697` 的 `node['name']` 抛 KeyError 并被 `:749-753` 吞掉，`/search_name_kg` 返回 **200 + 空图**（静默失败），`/api/graph/node_context` 直接 500。属性（朝代、起止日期等）的修改永远同步不过去。修复后需要跑一次 `backend/sync_sqlite_to_neo4j.py` 才能补回已被清掉的 `name`。

**改法**：
1. `new_name = normalized_properties.get("name") or data.get("name")`，为空时回 400（而不是把图谱写坏）；
2. 快照改用 `DbUtil._normalize_payload(node_type, properties)` 的结果，与 `create_node` 统一口径。

**验收**：一条用例走真接口——编辑一个节点后断言 ① 图谱节点的 `name` 仍在且是新值 ② 某个被改的属性在 `job.properties_json` 里是可被 `neo4j_props()` 认出的列名。第 ② 条尤其重要，因为它同时钉住了根因 b。

#### P1-5 【已复核 + 代理本地模拟】飞书机器人异常终止后，提问永久卡死

**位置**：`feishu-bot/bot/dispatcher.py:60`、`:636-652`，`feishu-bot/main.py:82-124`

**现象**：`processing` 被列进 `_CLAIMED_STATUSES`。任务执行中进程被杀（SIGKILL / OOM / 双重 Ctrl-C 的 `os._exit(0)` / `stop()` 超时后退出）会永久留下 `status='processing'` 的行，飞书重投同一 `event_id` 会被当重复丢弃。对照实验：模拟"取走 → 标 processing → 重投"得到 `duplicate=1, enqueued=1, queue=0`，而 `received` 档重投得到 `enqueued=2`——代码只给 `received` 留了恢复口。

**后果**：该提问永久丢失，用户那张"正在检索史料…"的占位卡在 24 小时 TTL 内不会恢复。

**改法**：启动时把 `processing`（以及超阈值的 `received`）扫回可重认领状态；或给认领加"`processing` 超过 N 分钟视为未完成"的时间窗。

**验收**：一条用例——写一行 `processing`，跑一次启动恢复，断言该行回到可认领状态且重投会被执行。

**E-7：统一 ruff 版本不是一个"改个数字"的动作，它会直接让 RAG 的 lint 门禁变红**

这条改变了批次 6 里 P3-12 的处理方式，**必须在 5.7/5.8 之前想清楚**。

同一个命令、同一个目录，只换 ruff 版本：

```text
$ cd RAG && python -m ruff check server config contracts lib data scripts evaluation tests
AI_Agent  环境（ruff 0.14.4，= CI 的 RAG job）        →  All checks passed!
china-war-py311（ruff 0.16.8，= pyproject 钉的版本）  →  Found 484 errors.
```

错误构成（前几类）：`UP045` 204、`UP006` 57、`RUF100` 57（无用的 `noqa`）、`I001` 40、
`UP035` 20、`UP037` 8、`S110` 8、`PLW1510` 8、`B023` 8。

原因：**仓库里没有任何 `[tool.ruff]` 配置段**（根 `pyproject.toml` 没有，RAG 下也没有

0.14.4 → 0.16.8 之间扩大了。

所以正确的顺序是：**先定目标 ruff 版本 → 补一个显式的 `[tool.ruff]` 配置段（把 `select`/
`ignore` 写死）→ 按需清理或忽略那 484 条 → 最后才统一版本号**。反过来做（直接把 CI 的
0.14.4 升到 0.16.8）会让 RAG 的 lint job 当场变红。

### C.1 会让人误判的两件事

**① PATH 上的 `python` 是微软商店的占位桩，仍然坏着**

```text
$ python -c "print('hello')"
（无任何输出）  退出码 = 49
```

`which -a python` 的首项是 `C:\Users\<你>\AppData\Local\Microsoft\WindowsApps\python`（商店桩，真正的解释器没装），它排在 `/e/anaconda/python` 之前。**后果**：README 与各文档里写的 `python -m pytest tests -q`、`python app.py`、`python RAG/scripts/check_docs.py` 全都静默什么都不做，退出码还不为 0——如果只看"没报错"就会以为跑过了。

**这是环境里最该先处理的一件事**，三个办法任选：把 Windows 设置里"应用执行别名"下的 `python.exe` / `python3.exe` 关掉；或调整 PATH 顺序让 anaconda 在前；或所有命令直接写解释器绝对路径（本文附录 A 就是这么写的）。

**② `rsync` 未安装**

`command -v rsync` 无输出。这意味着 `deploy/scripts/04_upload_from_local.sh` 会走 tar 回退分支——**也就是 P1-1 的触发条件在本机是成立的**。修 P1-1 之前，本机执行上传会把 `.git` 与 `node_modules` 传到服务器。
