# 系统集成与入口约定

> 本文档讲的是**入口合并**，不是代码合并：RAG 仍是独立服务、独立进程（代码已并入同一仓库）；
> 合并的是"用户从哪里进入"和"对外只有一个域名"。同时把**跨模块的约定**集中在这里——
> 路径与端口、两个服务的划分、并入模式构建、nginx 分流、安全边界、四个 Python 模块的环境口径、排障。
>
> RAG 自身的架构、功能与部署见 `RAG/README.md`、`RAG/docs/current-status.md` 与 `RAG/docs/deploy.md`。
> 项目级的其他文档：[README.md](README.md)（总索引）、[项目现状与后续计划.md](项目现状与后续计划.md)（唯一状态源）、
> [项目审查与修复历史.md](项目审查与修复历史.md)（历次审查与修复的按主题归纳）。

## 一、两个服务怎么划分（为什么不做代码合并）

| 系统 | 运行时 | Web 框架 | 职责 |
| --- | --- | --- | --- |
| 旧知识库系统（`backend/` + `frontend/`） | Python 3.11 | Flask + SQLAlchemy + py2neo | **管数据维护**：图谱 CRUD、账号与角色、质检、地图与时间轴 |
| RAG 问答系统（`RAG/`） | Python 3.11 | FastAPI + pydantic + chromadb | **管问答**：检索、引用、流式输出 |

把 RAG 做成 Flask 蓝图会同时引入依赖冲突、启动耦合与部署耦合，还会废掉 RAG 已过审的部署链路
（版本固定、health 校验、CORS 启动门禁、冒烟脚本）。因此边界定在 HTTP：
**旧系统管数据维护，RAG 管问答，反代把两者拼成一个入口。**
离线抽取（`entity-event-relation/`，包名 `war_extraction`）与飞书机器人（`feishu-bot/`）是另外两个部分：
前者**离线跑、不参与 Web 运行**，后者是**独立进程**（不占端口、不在浏览器链路上）。

## 二、路径与端口约定

| 服务 | 端口 | 对外路径 | 说明 |
| --- | --- | --- | --- |
| 旧前端（layui 管理台） | 开发 3001 / 生产由 nginx 发 | `/static/*`（vite base） | 菜单与页面 |
| 旧后端（Flask） | 5000 | `/api/*` 及其余 | 图谱 CRUD、质量台、旧问答 |
| RAG 后端（FastAPI） | 8000 | `/rag/*` | 页面与接口都在这个前缀下 |

**关键约定**：`/rag/*` 去掉前缀后正好对上 RAG 自己的路径约定——页面在 `/*`、接口在 `/api/*`。
所以**一条反代规则同时覆盖页面与接口**：

```text
浏览器  /rag/              → RAG 服务  /              （前端 dist 的 index.html）
浏览器  /rag/assets/x.js   → RAG 服务  /assets/x.js
浏览器  /rag/api/query     → RAG 服务  /api/query     （SSE 问答）
```

浏览器只访问 **http://localhost:3001** 一个入口：`/api` 由 vite 代理到 5000、`/rag` 代理到 8000。
同机进程也可以**直连** RAG 的接口而不走反代：飞书机器人按 `RAG_BASE_URL`（默认 `http://127.0.0.1:8000`）
调用 `POST /api/query/json`（非流式问答，一次取完整结果；需要 `X-Bot-Key` 共享密钥或有效 JWT）。
机器人不经过旧后端，也不依赖 `/rag/*` 前缀。

## 三、四个 Python 模块统一 3.11 的环境口径

**结论：四个 Python 模块（旧后端、旧前端不涉 Python、RAG、飞书机器人、离线抽取链）全部运行在
Python 3.11；本地共用一个环境，生产按服务拆环境是隔离选择而不是版本要求。**

| 场景 | 环境 | 说明 |
| --- | --- | --- |
| 本地开发（唯一推荐） | `conda activate china-war-py311`（Python 3.11.16） | 四个模块共用，命令行一律写 `conda activate china-war-py311`；本机绝对路径只允许出现在根 README 的「本机环境备注」 |
| 生产（第一台服务器） | `china-war-backend` 与 `china-war-rag`（**均 3.11.16**） | 按服务拆开是为了隔离依赖与故障面；systemd 单元引用的是环境**路径**（`envs/china-war-backend/bin/python`），与 Python 版本无关 |
| 本地遗留 | `place-name-KG`（Python 3.8） | **仅为 CI 的 3.8/3.11 双跑过渡档保留**，3.8 待废弃；服务器侧的 3.8 环境已于 2026-09-26 删除。开发与部署一律 3.11 |

**依赖安装（本地，两步，缺第二步旧后端直接起不来）**：

```bash
conda activate china-war-py311
pip install --no-cache-dir -r requirements.lock    # 根：119 包，带 sha256
pip install -e entity-event-relation               # 抽取链是仓库内的正式包 war_extraction，不在锁里
```

- 根 `requirements.lock` 是**唯一的三方依赖来源**，覆盖四个模块的全部三方依赖（119 包、2998 个哈希）；
  生成与自检见 `scripts/gen_unified_lock.py`。
- `pip install -e entity-event-relation` 不能省：`backend/llm_pipeline.py` 与 `backend/blueprints/llm.py`
  会 `import war_extraction`，而根 `pyproject.toml` 的 extras 只声明三方依赖、**不包括这个仓库内的包**。

**服务器侧安装（`deploy/scripts/01_setup_server.sh`）**：

- **默认走 `requirements.txt`**；根 `requirements.lock` 需要显式 `USE_UNIFIED_LOCK=1` 才用。
- 为什么不是默认用锁：锁由 Windows 生成，`uvloop>=0.15.1` 未固定版本（根因是 `uvicorn[standard]`
  被 `--strip-extras` 剥掉 extras、Linux 专有包不在 Windows freeze 里），在 Linux 上
  `--require-hashes` 会拒绝安装。**统一 lock 的跨平台完整性待补**——生成器需保留 extras（或按平台补全
  Linux 专有包），并让 CI 在 Linux 上真装一遍；这是唯一能拦住"Windows 生成的锁在服务器上装不上"的办法。
  详见 [项目现状与后续计划.md](项目现状与后续计划.md) 3.2。

**CI（`.github/workflows/ci.yml`）**：`rag` job 用 3.11；`legacy-backend` job 仍是 **3.8/3.11 双跑**
（过渡档，3.8 待废弃）；本地 3.8 环境 `place-name-KG` 就是为这一档保留的。

## 四、开发环境怎么跑（含并入模式构建）

四个终端各用各的环境，顺序如下（完整前置条件见根 `README.md` 的「运行项目」）：

```bash
# 1) 构建 RAG 前端（并入模式：base=/rag/、接口前缀=/rag/api，参数在 RAG/frontend/.env.integration）
cd RAG/frontend && npm run build:integration && cd ../..

# 2) 启动 RAG 服务（同源托管：检测到 frontend/dist 就把产物挂到 /）
cd RAG && python scripts/run_server.py --port 8000 --version <版本>

# 3) 启动旧后端（Flask，:5000）
cd backend && python app.py

# 4) 启动旧前端（vite 代理把 /rag 转发到 8000、/api 转发到 5000）
cd frontend && pnpm dev
```

浏览器访问 `http://localhost:3001`（菜单「知识图谱 → RAG 智能问答」）。
飞书机器人若要一起跑：`python feishu-bot/main.py`（可选的独立进程）。

改动前的自检（不需要浏览器）：

```bash
curl -s http://127.0.0.1:3001/rag/ | grep assets     # 资源前缀必须是 /rag/assets/...
curl -s http://127.0.0.1:3001/rag/api/health         # 应返回 RAG 的 health JSON
```

### 构建产物模式（踩过的坑，也是白屏的唯一原因）

`dist/` 只有一份，`npm run build`（base=/）与 `npm run build:integration`（base=/rag/）**互相覆盖**。
并入环境下若误用普通模式构建，index.html 会引用 `/assets/...` 而不是 `/rag/assets/...`，
浏览器在 3001 上请求这些路径拿到 404，表现为 **iframe 一片空白且控制台不报错**（只有 Network 面板能看到 404）。
这也解释了 RAG 前端**必须以并入模式构建**的原因：它的接口前缀被参数化成 `/rag/api`
（原先是写死的根绝对路径 `/api/...`，挂到子路径后会打到旧 Flask 的 `/api/*` 上——两边同前缀，必然串台）。

- 页面经 `/rag/` 访问（开发 3001 反代、生产 nginx）→ 必须 `npm run build:integration`；
- 独立部署（直连 RAG 服务根路径）→ 用 `npm run build`；
- 在 RAG 前端跑过 `npm run build` 或 `npm run verify` 之后，若要继续用并入入口，记得补一次
  `npm run build:integration` 把产物换回来。

构建时会往产物里写 `build-mode.txt`（`integration` / `standalone`，跟随 `--outDir`），
RAG 服务启动时读它与 `index.html` 的资源前缀交叉核对，结果进启动日志与 `/api/health` 的 `frontend_mode`——
**两种构建互相覆盖不再只靠文档提醒**。

## 五、生产部署：nginx 分流

```nginx
upstream china_war_backend { server 127.0.0.1:5000; }
upstream rag_backend       { server 127.0.0.1:8000; }

server {
    listen 80;
    server_name your.host;

    # 旧后台前端静态资源（vite base = /static/）
    location /static/ {
        alias /path/to/china-war/frontend/dist/;
        try_files $uri $uri/ =404;
    }

    # RAG 智能问答：页面与接口都在 /rag/ 下，整体转发并去掉前缀。
    # proxy_pass 结尾的斜杠就是"去掉 /rag"（等价于开发环境 vite 的 rewrite）。
    location /rag/ {
        proxy_pass http://rag_backend/;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # SSE 关键项：RAG 的回答是流式响应，任何缓冲都会让回答"憋住不出字"
        proxy_buffering off;
        proxy_cache off;
        proxy_set_header Connection "";
        # RAG 的 SSE_MAX_DURATION_SECONDS 默认 300，这里留足余量
        proxy_read_timeout 600s;
        proxy_send_timeout 600s;
    }

    # 内部服务间接口只走回环，公网直接 404
    location /api/internal/ { return 404; }

    # 旧后端（含 /api/*）
    location / {
        proxy_pass http://china_war_backend;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

前端与接口同源之后，**浏览器侧完全不涉及 CORS**（不需要给 RAG 配 `CORS_ALLOW_ORIGINS`）。
完整的 nginx 站点模板、systemd 单元、初始化与自检脚本、安装门禁都在 `deploy/` 下，
操作步骤与排障见 `deploy/README.md`。

## 六、生产必改的两个 RAG 环境变量（不改也能启动，但行为是错的）

### 1. 限流会退化成全体用户共享一个桶

RAG 默认按**直连来源 IP** 计数，且不信任转发头（防伪造）。放到反代后面，
所有用户对 RAG 来说都来自 `127.0.0.1`，于是 `RATE_LIMIT_PER_MINUTE=30` 变成**全站合计 30 次/分钟**。

```bash
RATE_LIMIT_TRUST_FORWARDED_FOR=true
RATE_LIMIT_TRUSTED_PROXIES=127.0.0.1      # nginx 与 RAG 同机；不同机填 nginx 的出口 IP
```

同样的口径也用在登录限流上：**默认不采信 `X-Forwarded-For`**（那是客户端自己能写的头，采信等于把限流
交给攻击者决定）；显式 `LOGIN_TRUST_FORWARDED_FOR=true` 时才按转发头计数，且取 `X-Real-IP`
或 XFF 的**最右段**——nginx 的 `$proxy_add_x_forwarded_for` 语义是"客户端自带值在最前、真实地址追加在后"，
取 `[0]` 取到的正是攻击者可控的那一段。

### 2. 生产档与 `CORS_ALLOW_ORIGINS=*` 互斥，会直接启动失败

RAG 的启动门禁规定：显式生产档（`RAG_REQUIRE_ACTIVE_VERSION=true`）下若 CORS 仍是通配符，
服务**拒绝启动**（避免无登录的公开问答接口被任意站点调用）。同源反代本身不需要 CORS，
但这个门禁仍会触发，需要显式表态：

```bash
# 二选一：
CORS_ALLOW_ORIGINS=https://your.host     # 收窄到实际站点
ALLOW_PUBLIC_CORS=true                   # 或者显式承认"就是要公开"
```

## 七、安全边界（务必知道）

- **旧后台的登录门禁管不到 RAG**：Flask 的全局 `before_request` 只作用于经过它的请求，
  而 `/rag/*` 被反代直接送去了 8000，不经过 Flask。旧前端路由上的守卫只是前端守卫，绕过成本为零。
- **RAG 的鉴权必须显式配置**：`RAG_AUTH_MODE` 三档——
  - `jwt`（生产默认）：`RAG/server/auth.py` 用与旧后端共享的密钥验签（HS256，强制 `exp`，
    校验 `iss`/`aud`），两条问答通道都要求 `Token` 头（也认 `Authorization: Bearer`）；
  - `nginx`：要求服务只监听回环，且 nginx 侧 `auth_basic` 必须真的生效——由
    `deploy/scripts/check_rag_auth.sh` 读 `nginx -T` 的**实际生效配置**判定；
  - `disabled`：只在开发环境用，**显式生产档下服务拒绝启动**。
- **密钥（两份配置各看起来都对是不行的）**：
  - jwt 档下两侧 `RAG_JWT_SECRET` 与 `JWT_SECRET` 必须**同值**（同值校验是最容易踩的坑，
    表现为问答全 401）；
  - 撤销查询需要 `RAG_INTROSPECT_URL` + 与 backend 同值的 `RAG_INTERNAL_SERVICE_KEY`
    （backend 侧名 `INTERNAL_SERVICE_KEY`），未配置时 `/api/health` 持续告警；
  - **占位符不能当密钥**：`check_rag_auth.sh` 拒绝 `CHANGE_ME_...` 一类占位符、拒绝过短的密钥
    （JWT 与服务间密钥 ≥ 32、Neo4j 口令 ≥ 12）、拒绝出厂默认口令，判据与
    `RAG/scripts/check_secrets.py` 的 ALLOWLIST 同口径；
  - 安装期强制：`install_services.sh` 在"校验配置"与"启动服务"之间调用该门禁，失败即终止安装。
- **"验签通过"不等于"凭证仍然有效"**：改密码/停用账号后旧后端立刻拒绝该 token，
  而 RAG 若不做第二步就会一直放行到 token 自然过期（默认 7 天）。因此 RAG 会向旧后端的
  `POST /api/internal/token/introspect` 确认凭证状态，结论缓存 `RAG_INTROSPECT_TTL_SECONDS` 秒
  ——**该 TTL 即撤销生效延迟的上界**。失败策略 `RAG_INTROSPECT_FAIL_MODE` 默认 `closed`
  （后端不可用时拒绝而不是放行，避免"把后端打挂"成为一种绕过撤销的手段）；生产档 + jwt 档下
  必须显式选择 `RAG_REQUIRE_REVOCATION_CHECK=true` 或 `RAG_ALLOW_DELAYED_REVOCATION=true`，都不做则拒绝启动。
  该内部接口只走回环，nginx 对 `/api/internal/` 前缀直接返回 404。
- **撤销与故障要分开**：撤销 → **401**；无法确认（后端不可用）→ **503**。不要把"问不到后端"当成
  "凭证已失效"——那会让后端抖一下时全体用户被登出，而重新登录拿到的 token 仍会被同样拒绝。
- **旧后端的鉴权状态码已规范化**：未带 Token、Token 过期或伪造 → **HTTP 401** +
  响应体 `{"code": 401, "msg": ...}`；Token 有效但角色无写权限（`viewer` 调写接口）→ **HTTP 403**。
  两者都带真实状态码，`curl -w "%{http_code}"` 即可判断。前端 `api/http.ts` 对 401 统一清凭据并跳登录。
- **角色三级**：`admin ⊃ editor ⊃ viewer`，三处口径必须同改（后端接口 403 / 菜单下发 / 路由 `requiresRole`）。
  `GET /user/menu` 是菜单唯一来源（按角色三级裁剪）；RAG 问答对全部角色开放，旧问答助手与文本抽取限 editor 及以上。
- **密钥扫描覆盖全仓**：`python RAG/scripts/check_secrets.py --root .`（CI 的 `secret-scan` job 跑的就是它）。
- **iframe sandbox 不是隔离手段**：`allow-scripts` + `allow-same-origin` 对**同源**页面不构成安全隔离
  （脚本可移除自身 sandbox、可直接访问父页面），它的作用是限制弹窗/顶层导航/下载。真正的隔离要靠
  RAG 独立域名部署或反代层鉴权。**不要把 iframe sandbox 描述成访问控制。**

## 八、跨应用身份通道：`cw-user` postMessage 契约

RAG 服务没有用户体系，会话历史存在它自己页面的 localStorage 里；旧前端以 iframe 嵌入时两者
同源、共用同一个 localStorage，所以"当前是谁在问"必须由旧前端告诉它。这是问答记录按账号隔离的接缝——
**曾经只改一半就全线串数据**（桥已改成传对象、store 仍按字符串处理，activeUid 变成 `"[object Object]"`，
所有账号落进同一个桶），因此把字段与时机钉在这里。

| 项 | 约定 |
| --- | --- |
| 发送方 | 旧前端 `frontend/src/views/knowledge/RagAssistant.vue` |
| 接收方 | RAG 前端 `RAG/frontend/src/utils/userScope.ts` 的 `installHostUserBridge()` |
| 载荷 | `{ type: 'cw-user', uid: string, role: 'admin' \| 'editor' \| 'viewer' \| '', token: string }` |
| 发送时机 | iframe 每次 `load` 之后（早于 load 发会丢消息）；uid 变化时重建 iframe 后重发。**首次解析出账号不重建** iframe（否则首次进入会白加载一遍） |
| targetOrigin | `'/'`（只发给同源文档）；RAG 若改为独立域名部署，这里要同步改成那一个源 |
| 接收校验 | `event.origin` 必须等于自身 origin，否则整条忽略；`uid` 只接受 `[A-Za-z0-9_-]{1,64}`，其余按"没有账号"处理（否则对象或超长串会被拼成 `:u[object Object]` 这种谁都不是的桶） |
| 收到之后 | 桥**只回调、不改 activeUid**；换桶（① 先把当前状态写回旧桶 → ② setActiveUid → ③ 读新桶）由 `RAG/frontend/src/stores/session.ts` 的 `applyUserScope()` 独占负责。顺序反了会把上一个账号的会话写进新账号的桶 |
| token 怎么传 | 用 postMessage 而不是拼进 iframe URL（URL 会进浏览器历史与各级访问日志，而 token 是登录凭证）；RAG 侧内存保管、不放 localStorage（主应用会在 iframe 每次 load 后重发） |

存储 key 由 uid 决定：有账号用 `ragv5-session-v3:u{uid}`，没有账号（独立访问 `:8000`）沿用
`ragv5-session-v3`，行为与改造前一致。**uid 非空时只读账号桶**，不回落旧全局键——升级前那份
记录不属于任何账号，不能被先登录的人收编。主应用侧同理：老版本的全局记录被**归档**到
`<base>:legacy-archived`，不归属第一个登录的人。

边界（如实说）：这是**只解决"串记录"、不防"冒充"**的一层——同源之下懂控制台的账号可以改 uid 去读别人的
会话。防冒充靠的是第七节那套服务端验签与凭证撤销（已在生产形态启用）。

两侧的对应用例：发送方 `frontend/tests/component/rag-assistant-scope.test.ts` 与
`frontend/tests/component/inference-scope.test.ts`（载荷形状、targetOrigin、"load 之后才发"、首次解析不重建、
登出落对桶）；接收方的装配级用例 `RAG/frontend/tests/unit/user-scope-wiring.test.ts`（照 `main.ts` 的真实
接线方式）、单元 `user-scope.test.ts` 与 `session-user-scope.test.ts`、浏览器级
`RAG/frontend/tests/e2e/user-scope-isolation.spec.ts`。**凡是改这条契约，必须同时改这三层里的相关用例。**

## 九、数据不会自动跟着旧库更新

入口合并**不解决数据同步**：RAG 的 `data/snapshot`、`data/index` 是离线制品，旧库改了图谱数据，
RAG 不会自动感知。换数据版本仍是固定流程：

```bash
cd RAG
python scripts/export_snapshot.py     # 治理快照
python scripts/build_index.py         # 文本与向量索引
python scripts/run_server.py --port 8000 --version <新版本号>   # 重启并固定版本
```

## 十、故障排查

| 现象 | 多半是 |
| --- | --- |
| 页面能开，但问答请求 404 / 打到旧后端 | RAG 前端用了默认模式构建（前缀 `/api`）。改用 `npm run build:integration` 重建 |
| 页面白屏、资源 404 | dist 是默认模式（`/assets/...`）而反代在 `/rag/` 下；同样用 `build:integration` 重建 |
| 回答"憋住"，最后一次性全出来 | 反代缓冲没关：确认 `proxy_buffering off` 与 `proxy_read_timeout` |
| 多人同时用就开始 429 | 限流按反代 IP 计数：按第六节第 1 条设 `RATE_LIMIT_TRUST_FORWARDED_FOR` |
| 问答全部 401（jwt 档） | 两侧 JWT 密钥不同值（或换了密钥只改一边）；也可能机器人 `RAG_BOT_API_KEY` 为空——`check_rag_auth.sh` 与 `/api/health` 的 `warnings` 都会指出 |
| 改了 `RAG/frontend/vite.config.ts` 但 `npm run dev` 没生效 | `vue-tsc -b` 会在同目录生成 `vite.config.js`（已 gitignore），Vite 解析顺序里 `.js` 优先于 `.ts`，于是读到旧配置。删掉 `vite.config.js` 与 `vite.config.d.ts` 再跑 |
| RAG 服务启动即失败，日志提到 CORS | 生产档 + `CORS_ALLOW_ORIGINS=*`：见第六节第 2 条 |
| RAG 服务启动即失败，日志提到鉴权档 | `RAG_AUTH_MODE=disabled` 但处于显式生产档，或 `nginx` 档却监听在非回环地址：见第七节 |
| 停用账号/改密码后仍能问答 | 撤销查询没配齐（`RAG_INTROSPECT_URL` + 两侧服务间密钥）：看 `/api/health` 的 `auth.revocation.policy` |
| 侧边栏找不到某菜单项 | 菜单唯一来源是 `GET /user/menu`（后端 `get_menu()`，按角色三级裁剪）。加菜单项要改三处（后端菜单 / store 白名单 / 路由），见 `frontend/README.md` |
| 登录后一会儿就跳回登录页 | Token 过期（默认 7 天，`JWT_TTL_SECONDS` 可调）或 `JWT_SECRET` 变了（未配置时每次重启随机生成）。前端对 401 会清凭据回登录页 |
| 登录返回 429 / 503 | 429 是限流命中（`Retry-After` 里有等待秒数）；503 是限流自身故障且策略为 `closed`（`LOGIN_GUARD_FAILURE_MODE`） |
| 管理台改完节点，图谱看不到 | 双写失败会留下待补偿任务：`python backend/retry_sync.py --list` 看清单，或调 `GET /api/sync/pending`。**`abandoned` 的条目通常意味着 Neo4j 侧有同名同类型节点**，需人工核对 |
| 直接开 `:8000` 白屏、控制台一堆 `/rag/assets/*` 404 | dist 是并入模式，只能在 `/rag/` 前缀下访问。要么走旧前端的 `/rag` 入口，要么用 `npm run build` 重建回默认模式 |
| 文档里的 `python -m ...` 命令静默什么都不做 | PATH 上的 `python` 是应用商店占位桩（退出码 49）。先做一次 `python -c "print(1)"` 确认 |
