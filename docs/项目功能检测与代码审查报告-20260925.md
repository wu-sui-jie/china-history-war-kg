# 项目功能检测与代码审查报告（2026-09-25）

## 1. 审查结论

本项目四大模块都已有可运行代码、文档和较完整测试，作为**本机/内网、共享知识库、小团队单实例**系统，主体功能已经成形；但不能认定为“整体功能齐全、账户完全隔离、可直接公网生产”。

总体判断：

- **功能成熟度：中上**。查询、图谱、抽取、RAG、飞书接入的主链路都已实现。
- **生产就绪度：中等**。存在账户与数据迁移、双库一致性、公开接口鉴权、部署模板凭据、CI 覆盖等关键缺口。
- **账户隔离：部分实现，不是安全隔离**。旧后端有登录和角色授权；问答记录主要靠浏览器 localStorage 按 uid 分桶，能防普通换号串记录，不能防同源控制台冒充；共享知识图谱数据没有租户/所有者维度。
- **当前最危险的问题**不是普通页面 bug，而是：数据重导会删除账户、固定凭据随部署模板入库、RAG 公网接口无用户鉴权、SQLite 删除节点可能留下孤儿关系。
- **数据提取质量目前没有得到可信证明**：现有参考标注存在结构违规、重复、错误字段和不可追溯问题；评估器又同时存在过严与放水口径，当前 F1 不能直接代表真实正确率。

建议定位：当前版本适合作为**内部共享知识库的候选版本**；完成 P0/P1 修复和真实集成验收后，再作为正式生产版本。

## 3. 账户与数据隔离分析

### 3.1 隔离矩阵

| 范围 | 当前实现 | 结论 |
| --- | --- | --- |
| 登录凭据 | 账号唯一；新密码使用 Werkzeug 哈希；旧明文密码登录后自动升级 | 基本合格 |
| 接口认证 | 除登录/注册外，旧后端统一校验 JWT；伪造/过期返回 401 | 合格 |
| 角色授权 | `admin/editor/viewer`；写接口和管理员接口服务端校验，角色变更实时查库 | 基本合格 |
| 知识图谱业务数据 | Event/Place/Person/Organization/关系表没有 `owner_id`、`tenant_id`、`created_by` | **完全共享，不是账户隔离数据** |
| 旧问答历史 | 浏览器 localStorage 按 `uid` 分 key | 只防普通换号串数据，不防本机控制台读取/修改 |
| 文本识别历史 | 同上，localStorage 按 `uid` 分 key | 同上 |
| RAG 会话历史 | 主应用 postMessage 下发 uid，RAG 前端按 uid 分桶 | **弱隔离**；uid 无服务端签名，可冒充 |
| RAG 服务端 | 无用户体系；SSE `/api/query` 无鉴权；JSON 接口仅支持可选共享 `X-Bot-Key` | **没有账户隔离** |
| 飞书会话 | `session_key = open_id:chat_id`，消息与历史按该 key 查询 | 在单实例 SQLite 内隔离较好 |
| 飞书使用范围 | 无用户/群白名单 | 企业内任何可访问该机器人者都能消耗 RAG/LLM 配额 |

### 3.2 账户隔离最终判断

如果“账户隔离”指：

1. **不同账号拥有不同私有知识库数据**：当前没有实现。
2. **不同账号看不到对方问答记录**：普通操作下基本分开，但不是安全边界；浏览器端 uid 可伪造。
3. **不同角色不能执行越权写操作**：大部分已实现，服务端角色校验是有效的。
4. **RAG 与旧系统共享统一可信身份**：没有实现。
5. **飞书用户与旧知识库账号打通**：没有实现，两套身份完全独立。

所以不能简单回答“用户账户已隔离”。准确说法是：**旧后端完成了认证与角色授权；用户私有数据、RAG 身份和跨模块身份没有形成服务端强隔离。**

## 4. 高优先级缺陷

## P0-1 数据重导会删除全部用户账号和角色

证据：`backend/import_json_to_sqlite.py:538-557` 在 `--yes` 后执行 `db.drop_all()` / `db.create_all()`，而 `UserInfo` 与业务表使用同一个 SQLAlchemy metadata，因此用户表也被删除。脚本随后只导入实体和关系，不恢复用户。

影响：

- 更换抽取数据集或重新导入时，所有账号、密码哈希、角色都会消失。
- 管理员账户消失后，系统只能重新注册 viewer，再手工改 SQLite 才能恢复管理能力。
- 文档把该命令描述为“重建整个 SQLite 库”，但没有把“账户也会被清空”作为独立风险和备份/恢复步骤。

建议：

- 不再使用 `drop_all()`；只清理 4 类实体与 4 类关系业务表。
- 或把认证库与知识库拆成两个 SQLite 文件。
- 修复前至少自动备份并恢复 `UserInfo`，且增加“导入后账号与角色不变”的测试。

## P0-2 部署模板包含非空固定密码和 JWT 密钥

证据：`deploy/env/backend.env:9,13` 的 `NEO4J_PASSWORD` 和 `JWT_SECRET` 都是非空固定值，其中 JWT 值长度 32、字符种类和熵都像真实密钥，不是 `.env.example` 的空占位符。该文件被 Git 跟踪，部署文档又要求直接复制为 `backend/.env`。

影响：

- 即使这些值不是当前生产凭据，也形成“不安全默认值”：使用者复制后忘记轮换，就会多套部署共享同一凭据。
- 当前密钥扫描脚本根目录是 `RAG/`，不会扫描仓库根的 `deploy/`；旧模块 CI 的 grep 也只扫 `backend` 和 `entity-event-relation`，因此此问题不会被 CI 阻断。

建议：

- 立即确认这些值是否在任何环境使用；如使用过，轮换 Neo4j 口令和 JWT 密钥。
- 模板只保留空值或明显占位符。
- 将密钥扫描提升到仓库根，覆盖 `deploy/`、`feishu-bot/`、工作流和全部 tracked 文本文件。

## P1-1 RAG 无统一账户鉴权，公网部署时可绕过旧系统登录

证据：`RAG/server/api.py:495-542` 的 `/api/query` 只有限流，没有 JWT 或用户身份校验；`/api/query/json` 的 `X-Bot-Key` 也是可选共享密钥。`deploy/nginx/china-war.conf` 的 `/rag/` 认证仅是注释掉的可选 `auth_basic`。

影响：

- 知道 `/rag/` 地址即可直接调用 RAG，不受旧系统 admin/editor/viewer 控制。
- 公开部署时可消耗模型费用和限流配额。
- 浏览器会话 uid 只用于 localStorage key，不是服务端身份，无法阻止读取其他 uid 桶。

建议：

- 旧后端签发的 JWT 由 RAG 服务端验签，SSE 和 JSON 接口都要求可信身份。
- 将 user id、role 放入服务端验证后的请求上下文，而不是信任 postMessage。
- 若暂不改代码，生产 nginx 必须强制认证且 RAG 只监听回环地址。

## P1-2 SQLite 外键实际关闭，删除节点可产生孤儿关系

证据：

- 模型声明了外键：`backend/models.py:233-289`。
- 普通连接钩子 `backend/app.py:200-209` 只设置 WAL、synchronous、busy_timeout，没有执行 `PRAGMA foreign_keys=ON`。
- 当前本地数据库实测 `PRAGMA foreign_keys = 0`。
- `backend/db_utils.py:313-360` 删除实体时直接 `db.session.delete(node)`，没有先删除关系行，也没有 ORM cascade。

当前库实测暂时没有孤儿关系，但这是潜在一致性缺陷。一旦管理台删除一个已有关系的事件/人物/地点/组织，SQLite 关系表可能残留无效外键。

建议：

- 每个连接启用 `PRAGMA foreign_keys=ON`。
- 明确关系删除策略：`ON DELETE CASCADE` 或业务层先预览并删除关联关系。
- 增加删除带关系节点的失败测试/级联测试。

## P1-3 SQLite → Neo4j 双写只有错误提示，没有可靠补偿

证据：`backend/db_utils.py:187-417` 的节点创建、修改、删除均先提交 SQLite，再调用 Neo4j；Neo4j 失败后返回 `sync_status=failed`，但没有 outbox、重试队列或自动补偿。

影响：

- SQLite 是主数据，但前端图谱查询主要读 Neo4j；同步失败后，管理台列表与图谱展示会长期不一致。
- 创建节点时 Neo4j 已创建、属性更新或 SQLite 回写 id 失败，也可能出现半完成状态。
- 质检计数只能发现数量差，不能自动修复字段或关系差异。

建议：

- 增加持久化 outbox/sync_jobs 表，按操作重试并记录最终状态。
- 提供单节点/单批次重同步接口和管理页面。
- 写操作返回 202/部分成功时，前端明确展示待同步状态，而不是只在 toast 中提示。

## P1-4 旧前端登录页生产资源路径错误

证据：

- `frontend/src/views/login/index.vue:24` 使用绝对 `/login.jpg`。
- `frontend/src/views/login/index.vue:226` 使用 `url(background.jpg)`。
- 构建警告显示 `background.jpg` 未解析；构建后图片位于 `dist/background.jpg`，CSS 位于 `dist/assets/*.css` 并仍引用相对 `background.jpg`。
- nginx 只把 `/static/` alias 到整个 dist，`/login.jpg` 会落到旧后端，`/static/assets/background.jpg` 也不存在。

影响：生产部署下登录主图和背景图可能 401/404，构建本身仍返回成功，现有组件测试不会发现。

建议：使用 import 资源或 `${BASE_URL}`/`/static/login.jpg`，并增加构建产物资源存在性检查或浏览器登录页冒烟。

## P1-5 空角色启动迁移会自动提升为 admin

证据：`backend/app.py:171-193` 的 `ensure_user_table_schema()` 对所有 `role IS NULL OR role=''` 的历史账户执行 `role='admin'`。这与 `DbUtil.get_role()` 的最小权限兜底原则相反。

影响：任何由于导入、手工写库或旧版本遗漏产生的空角色账户，在下一次启动时都会被提升为管理员。

建议：

- 自动迁移默认回填 `viewer`。
- 只允许通过一次性、显式指定账号的管理员引导命令创建首个 admin。
- 增加“空角色重启后仍为 viewer”的迁移测试。

## 5. 中优先级缺陷与功能缺口

## P2-1 关系管理功能不完整

旧系统有 4 类关系表和大量关系查询，但在线写接口只覆盖节点 CRUD。代码扫描显示关系表写入只存在于 `import_json_to_sqlite.py`，前端没有关系新增、修改、删除 API。

结论：如果“节点关系管理”包含关系维护，则该模块并不齐全；当前更准确的描述是“节点管理 + 关系查看/离线导入”。

## P2-2 RAG 向量可用状态存在假阳性

`TextSearcher.vector_available=True` 只说明 Chroma 集合、id 数量和 embedding client 已装配。查询时 embedding HTTP 失败，`search_vector()` 返回空，调用层静默回退关键词，但 health 仍可能报告向量可用。

本次实际导致 RAG 后端 349 个测试中 1 个失败。建议区分：

- `vector_artifact_ready`
- `embedding_client_configured`
- `embedding_probe_ok`
- `last_vector_error`
- `effective_text_mode`

并让测试完全脱离外部 embedding 网络，使用 stub 向量客户端。

## P2-3 RAG 并入模式体积门禁会假通过

`RAG/frontend/scripts/check-bundle.mjs` 的正则只识别 `src="/assets/..."`，但 `build:integration` 产物使用 `/rag/assets/...`。本次执行输出：

```text
入口 gzip 0.0 kB / vendor gzip 0.0 kB / 首屏合计 gzip 0.0 kB
体积门禁通过
```

这不是有效检测。应解析 HTML URL，不要把前缀写死；若未找到 entry/vendor，应直接失败，不能按 0 通过。还应增加 standalone/integration 两种产物测试。

## P2-4 飞书机器人没有进入 CI

当前 `.github/workflows/ci.yml` 有 RAG、旧后端/抽取、旧前端任务，没有 `feishu-bot` 测试任务。机器人本地 279 项通过，但后续提交可以在 CI 全绿的情况下破坏机器人。

建议新增 Python 3.11 job：安装 `feishu-bot/requirements.txt`，运行 pytest、ruff，并至少跑一次 render 脚本的降级测试。

## P2-5 飞书机器人并发和滥用边界不足

- `Dispatcher` 使用一个无界 `queue.Queue()` 和单 worker。
- 一个 20–30 秒的 RAG 请求会阻塞所有其他用户。
- 消息突发时队列无上限，可能持续占内存。
- 没有 `FEISHU_ALLOWED_CHAT_IDS`/用户白名单。

作为个人或小团队起步版可接受，但不应宣称团队化功能齐全。建议按 `session_key` 分片串行、全局限制并发、队列设上限、忙时快速回复，并加白名单。

## P2-6 首个管理员仍依赖手工改库

注册固定创建 viewer。全新数据库没有 admin 时，用户管理页无法使用，部署文档要求手工 SQLite `UPDATE`。这是可部署但不完整的引导流程。

建议增加一次性 `create-admin` CLI：仅在无 admin 时执行，从终端安全读取密码并写哈希；不要开放匿名 HTTP 首管接口。

## P2-7 API 错误状态和输入校验不统一

旧后端多个接口把业务 `code=400/404/500` 放在 JSON 中，但 HTTP 状态仍为 200；部分接口直接 `request.json.get()`，空体或错误类型会变成 500；多处把 `str(e)` 原样回给客户端。

影响：前端、监控和调用方不能稳定依赖 HTTP 语义，也可能泄露内部错误细节。建议统一错误处理器和输入 schema。

## P2-8 CI 密钥扫描范围不完整

- `RAG/scripts/check_secrets.py` 的 ROOT 是 `RAG/`。
- 旧模块 CI grep 只扫 `backend`、`entity-event-relation`，且文件类型有限。
- `deploy/`、`feishu-bot/`、根目录脚本和工作流未纳入统一扫描。

这正是固定部署凭据未被阻断的原因。

## P2-9 RAG 静态检查未闭环

本次完整 Ruff 检查发现 7 项，CI 的名为 `lint` 的 job 实际没有执行 Ruff。虽然当前 6 项是无占位 f-string、1 项是 import 顺序，不是业务故障，但说明文档中的“自动化门禁闭环”表述偏乐观。

## 7. 四大模块完整度评估

### 7.1 旧知识库（backend + frontend）

**已具备**：登录注册、JWT、三级角色、用户管理、节点 CRUD、图谱查询、全局搜索、关系分析、时间轴、地图、数据看板、质检、旧问答、文本识别、RAG 嵌入入口。

**缺陷/缺口**：

- 知识数据全局共享，无用户/租户隔离。
- 关系只能查和离线导入，缺在线 CRUD。
- 数据重导会删除账号。
- 删除节点可能留下孤儿关系。
- SQLite/Neo4j 双写无可靠补偿。
- 登录页生产资源路径错误。
- 首个 admin 需手工改库。

**评价**：共享知识库主功能较完整；数据治理和多用户生产能力不完整。约 **70%–75% 生产完成度**。

### 7.2 数据提取（entity-event-relation）

**已具备**：分段、缓存、实体/事件/关系三阶段抽取、合并、规范化、候选/发布分层、地理编码、导出和自动评估框架。

**重新审查后的关键结论**：

- 本地存在完整 `9_final_all.json` 和 `published/final.json`，上一版报告称“没有最终产物”是错误判断，现已更正。
- 现有产物是 2026-08-18 的旧 prompt 结果，不代表当前代码。
- 当前宏观 F1 约 0.4468，但评估参考和评估器均存在严重口径问题，不能当作真实准确率。
- 实体和事件低精确率中包含大量 gold 漏标和粒度不一致；同时预测也确有重复、噪声和错分类。
- 关系 F1 被 gold 预过滤显著高估；关系方向和派生规则还存在明确代码缺陷。
- 正式全量重跑应放在 gold 与 evaluator 修复之后，而不是立即重跑。

**评价**：工程流程完成度约 **75%–80%**；但语义正确性可信度目前只有 **35%–45%**，不应直接把现有产物作为高可信知识库。详细证据见第 6 节。

### 7.3 RAG

**已具备**：问题理解、实体链接、图谱/文本/向量检索、融合重排、引用、面板、SSE 与 JSON、缓存、限流、降级、数据版本、制品审计、发布脚本、前端多会话和导出。

**缺陷/缺口**：

- 无用户级服务端鉴权。
- 向量可用状态可能假阳性，本次 1 个测试失败。
- 并入模式体积门禁无效。
- 发布 workflow 尚未在干净 commit + 正式数据制品上完整演练。
- 数据不是实时读取旧库，管理台更新后必须人工重建 snapshot/index 并重启。

**评价**：功能最丰富、工程化最好，但生产身份与发布闭环仍缺。约 **80%–85% 完成度**。

### 7.4 feishu-bot

**已具备**：长连接、消息去重、单聊/群聊 @、RAG 非流式问答、两段式卡片、引用、示例题、子图降级、会话历史、`/new`、纠错反馈、清理脚本。

**缺陷/缺口**：

- 真实飞书租户人工验收仍未完成。
- 无 CI job。
- 无用户/群白名单。
- 单 worker + 无界队列，不适合多人并发。
- 与旧知识库账号体系不打通。
- 纠错只落 SQLite/运营群，没有完整的处理状态闭环界面。

**评价**：个人/小团队功能闭环基本完成，团队化和运维闭环不足。约 **75%–80% 完成度**。

## 8. 跨模块闭环情况

| 链路 | 状态 | 问题 |
| --- | --- | --- |
| 抽取 → SQLite | 有脚本 | 破坏性重建且会删用户 |
| SQLite → Neo4j | 有全量/增量同步 | 在线双写失败无自动补偿 |
| SQLite/原文 → RAG snapshot/index | 有离线脚本 | 不自动同步，存在数据陈旧窗口 |
| RAG → 旧前端 | iframe + nginx 前缀 | 身份只靠 postMessage，非可信隔离 |
| RAG → 飞书 | JSON API + 可选 Bot Key | 可用，但共享密钥不是用户身份 |
| 飞书 → 旧账号体系 | 无 | 两套身份、权限、审计各自独立 |
| 全仓库 CI | 部分覆盖 | feishu-bot、根级密钥扫描、RAG Ruff 缺失 |

结论：四个模块不是四个完全孤立的半成品，但也还没有形成“统一身份、统一数据版本、自动同步、统一审计”的完整平台。

## 10. 最终回答

- **整体功能是否有缺陷？** 有，而且包含数据丢失、凭据管理、数据一致性、生产资源路径和鉴权边界等实质缺陷。
- **用户账户是否隔离？** 只完成了旧后端的认证和角色授权；知识数据不隔离，问答历史只是浏览器弱隔离，RAG 没有服务端账户隔离。
- **四个模块是否功能齐全？** 主链路基本齐全，但都存在未闭环项。旧知识库缺关系在线维护和可靠双写；抽取模块的参考标注、评估器和关系后处理均需整改，现有分数不能证明正确性；RAG 缺可信身份与发布闭环；飞书机器人缺真实租户验收、CI、白名单和并发能力。
- **能否上线？** 内网、小团队、共享数据场景可以在修复 P0/P1 后试运行；公网、多租户或正式生产目前不建议直接上线。
