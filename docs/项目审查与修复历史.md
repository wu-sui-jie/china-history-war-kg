## 1. 凭据与密钥

**问题（影响面：公开仓库）**：初始提交 `57eea5b` 的 `backend/model_search.py` 可取回 Neo4j 明文口令、
`backend/jwt_util.py` 可取回 JWT 密钥——README 当时那句"源码里不再有明文凭据"只对 HEAD 成立。
本机 `backend/.env` 里也仍是那套历史口令，于是这条敞口在连续几次审查里被反复标为"最紧急"却一直没执行。
后续又发现两处同类：`deploy/env/*.env` 模板里躺着看起来像真密钥的固定值（`NEO4J_PASSWORD`、`JWT_SECRET`）；
旧模块 CI 的 grep 只扫 `backend` 与 `entity-event-relation`，`deploy/`、`feishu-bot/`、工作流都不在扫描范围。

**现在怎么处理**：

| 项 | 落地 |
| --- | --- |
| 实际轮换（2026-09-25） | Neo4j：`ALTER USER neo4j SET PASSWORD '<随机新口令>' CHANGE NOT REQUIRED`（`CHANGE REQUIRED false` 语法在 Neo4j 5 报错）；`backend/.env` 的 `NEO4J_PASSWORD` 与 `JWT_SECRET`（`secrets.token_urlsafe(48)`）同步原子更新，无断连窗口 |
| 密钥扫描 | `RAG/scripts/check_secrets.py` 增加 `--root`（默认仍是 `RAG/`）；补 `.env` 形态的 `KEY=value` 规则（原正则只认 `key: "value"`，这正是固定凭据能躺在模板里的原因）；`SKIP_DIRS` 里误放的 `env` 改为 `.venv`/`venv`/`virtualenv`/`site-packages`；白名单放行 `test[-_]?(key\|secret\|token\|password)` 与 `do[-_]?not[-_]?use` |
| CI | 新增 `secret-scan` job，在仓库根执行 `--root .` |
| 部署门禁 | `deploy/scripts/check_rag_auth.sh` 拒绝占位符（模式镜像 `check_secrets.py` 的 `ALLOWLIST`）、密钥长度（JWT 与服务间密钥 ≥ 32、Neo4j 口令 ≥ 12）、出厂默认口令（`neo4j`/`password`/`changeme`），且每个字段的失败原因分开报 |
| 模板 | `deploy/env/backend.env`、`rag.env`、`rag-secrets.env` 三个模板均已是空值或明显占位符 |

**验证证据**：拿一份复刻当年模板内容的样本（`NEO4J_PASSWORD=Xk92LmQ7vB4nR8tZ` 与 32 字节 `JWT_SECRET`）
试扫——两行都被命中且退出码 1，而 `CHANGE_ME` / `your-api-key-here` 占位符样本不误报；仓库根全量扫描
0 命中。`backend/tests/test_deploy_auth_gate.py` **24 例**直接执行那个 bash 脚本，其中一条把同一批样本
（占位符 7 个 + 真实值 2 个）同时喂给 `check_secrets.py` 的 ALLOWLIST 与门禁，断言"是不是占位符"的判定
两侧一致。旧口令实测失效、新口令连接成功（7470 节点无损）。

**还没做**：① `git filter-repo` 重写历史（凭据已轮换、紧迫性低，**建议暂缓**；若做需 `--replace-text`
加强推并通知所有协作者重新 clone）；② `deploy/env/*.env` 里那些值是否曾在真实环境使用过，只能由部署方
确认并按需轮换（代码侧无法判定，这一层改动只保证"这类值不会再静默进库"）；③ 2026-09-25 有一次 `.gitignore`

公开仓库，已用 `7e019c2` 从索引移除（磁盘文件保留），**历史里仍在**，是否重写历史同样待决策。

## 2. 鉴权、角色与登录安全

**问题（影响面：全部写接口与登录）**：一轮审查把这条列为"最紧迫三件事"之一，具体是——

- 身份用**模块级全局 `user_id`** 承载，多线程下并发串号，`/api/userinfo` 可能返回"最近一次任意请求"的用户；
- token 无 `exp`、不校验时效，等于永久凭证；鉴权失败是「响应体 `code: 403` + HTTP 200」，`curl -w "%{http_code}"` 看不出失败；
- 注册即获得全部写权限，没有角色模型；前端路由守卫只处理 404，`requireAuth: true` 全库无一处读取；
- `DbUtil.get_role()` 空值兜底返回 `admin`，而启动迁移又把 `role IS NULL OR ''` 的历史账号**每次都**回填
  `admin`——同一个空值，读接口按 admin 放行、写库也提成 admin，方向与最小权限相反；
- 口令策略不一致：首个管理员命令允许 6–20 位，注册与改密码要 10–64 位（**权限最高的账号允许最弱的密码**，
  而 21–64 位的强口令反而设不上）；前端还会静默 `password.trim()`，使"用户输入"与"落库值"永远不一致；
- 登录无任何限流；加上限流后，落库时间用的是 `time.monotonic()`（**只在同一次开机内可比**：开机 5 天后
  写下的锁定截止 432900，重启后 monotonic=30 → 判定"还要锁 432870 秒"；反向则把有效锁定当作已过期、限流失效）；
- 限流计数是"SELECT → Python +1 → UPDATE"（20 并发实测**只记到 4**，爆破脚本要的正是"用并发把计数做废"）；
- 限流自身故障时是 fail-open（读不到表就记条日志继续放行），保护**无声消失**。

**现在怎么处理**：

| 层 | 落地 |
| --- | --- |
| 身份 | 删除模块级 `user_id` 与四处 `global`，改 `flask.g.user_id`；`/api/userinfo` 读当前请求身份 |
| 鉴权语义 | 未带 / 伪造 / 过期 token → **HTTP 401** + `{"code": 401, "msg": ...}`；Token 有效但角色无写权限 → **HTTP 403**；放行路径收敛为常量 `PASS_URLS` |
| 角色模型 | `admin ⊃ editor ⊃ viewer`；`backend/roles.py` 放角色常量与鉴权装饰器；`@require_write_role` 挂 4 个写接口；`@require_admin` 管 `/api/admin/*`（**刻意不复用 `require_write_role`**——editor 若能改角色就能把自己升成 admin）；`get_role` 与 `UserInfo.to_dict()` 空值兜底都改 `viewer`；启动迁移回填 **`viewer`** |
| 菜单 | `get_menu()` 三级裁剪（`ADMIN_MENU_IDS` / `EDITOR_MENU_IDS`），后端下发是菜单唯一来源，前端菜单取自 `menuMap.get(...)` 而不是内置常量（内置常量会无条件进导航栏，等于把后端裁剪撤销） |
| 口令策略 | 新增 `backend/password_policy.py` 作为唯一口径（`MIN/MAX_PASSWORD_LENGTH` + `password_problem()`），注册、改密码、`create_admin.py`、前端注册表单四处引用；**首尾空白由策略报错，不静默去掉**；前端只 trim 账号与昵称 |
| 登录限流 | `backend/login_guard.py`：同 IP **每次尝试**计数（默认 10 次/分钟、60 秒窗口）+ 同账号**连续失败**计数（默认 5 次锁 15 分钟）；超限 **429** + `retry_after` + `Retry-After` 头；落库时间改 UTC epoch，列名带 `_epoch` 后缀（注释会被忽略、列名不会），旧表**整表作废**（monotonic 与 epoch 互算需要知道当时的开机原点，库里没有这个字段；限流是临时安全状态，最坏后果是锁定提前放行一次） |
| 原子计数 | 计数、窗口滚动、锁定判定全部收进一条 `ON CONFLICT ... DO UPDATE` UPSERT（`login_guard._UPSERT_ATTEMPT`）。**注意**：Python 侧仍会先 `read_state()` 读一次旧值用于写日志的 `before`，并向 SQL 传 5 个参数——原子性成立的是"计数与锁定判定" |
| 故障策略 | `LOGIN_GUARD_FAILURE_MODE`：`closed`（默认，抛 `LoginGuardUnavailable` → **503**）/ `open`；非法取值一律取 closed；SQLite `busy`/`locked` 先重试 3 次（50/100/150 ms），其它异常不重试；`record_success` 失败**不阻断登录**（凭证已验证通过，不该把服务端记账问题转嫁给用户） |
| 探活 | 新增免登录 `GET /api/health`（只回"活着"与限流失败策略，不含版本/路径/阈值/库名）——因为"登录是不是全 503"恰恰是最需要探活的时刻 |
| 撤销 | `UserInfo` 增 `token_version` / `disabled` 列，`before_request` 每次回库校验：改密码 / 停用 / 删号后旧 JWT 立刻失效。新增 `POST /api/user/password`（校验旧口令 + 新口令策略，成功后 `token_version + 1`）与 `POST /api/admin/users/<id>/status`（停用同时 `+1`，**不允许停用自己**） |
| 来源 IP | 两处统一：优先 `X-Real-IP`，退而取 `X-Forwarded-For` 的**最右段**。nginx 用的是 `$proxy_add_x_forwarded_for`，语义是"客户端自带值在最前、真实地址追加在后"，而代码取 `[0]` 取到的是攻击者可控的那一段——每换一个伪造首段就换一个限流桶 |
| 注册 | `ALLOW_SELF_REGISTRATION` 默认 `true`（不改变既有行为），**公网部署必须设 `false`**；注册成功也算一次 IP 尝试（被滥用的正是"成功建号"这个动作） |

**验证证据**：`backend/tests/test_login_guard.py`（10 → 17 → 29 → 33 例，含"把 `monotonic` 打桩成 30
后剩余锁定必须仍是 ~900 秒"这条 monotonic 哨兵、并发失败计数、XFF 取段、重复账号）、
`test_password_policy.py` 12 例（边界 9/10/64/65/空、首尾空白、**不修改输入值**、短口令老账号仍可登录）、
`test_role_backfill.py` 5 例（含"回填后的账号调写接口确实拿到 403"）、`test_admin_users.py`、
`test_menu_trim.py`、`test_privilege_chain.py`、`test_node_delete_cascade.py`、
`frontend/tests/component/login-failure.test.ts` 7 例（含"登录不校验口令长度"——服务端本来接受 6~9 位的
老账号口令，前端照搬新策略会把老用户锁在门外，这是修复过程中自己踩到并纠正的坑）。
**并发原子性的对照实验**：把 `_write` 临时换回改造前的 Python 侧读改写，同样 20 并发 → `failures = 4`；
新实现 → `failures = 20`。这条对照比"新实现通过"更能证明用例有牙。
**API 级端到端回归** 20/20 通过（鉴权三态 401、身份不串号、注册建 viewer、viewer 写接口 403、
真实节点创建→更新→删除的双侧同步、对账接口）。

**还没做**：① 访问 token 有效期没有直接调短——本系统只有 access token、没有 refresh token，
调到 15–30 分钟等于部署后所有人立刻被登出、之后每半小时再登出一次；撤销需求已由 `token_version` 覆盖；
② JWT 仍长期放在 localStorage（近期方案"短期 access token + 刷新"与长期方案"HttpOnly Cookie + CSRF"
都是**认证架构变更**，会牵动前端全部请求路径，需独立立项）；③ 用户管理页的启用/停用/解锁/重置密码/
强制下线 + 安全审计日志——**后端接口早已具备**（`POST /api/admin/users/<id>/status` 会连 `token_version`
一起 +1，`POST /api/user/password` 也在），真正缺的是前端入口，属前端功能开发。

## 3. 账户提权界面化与问答记录按账号隔离

**问题一（提权只能手写 SQL）**：角色体系已贯穿写接口 403、菜单下发、路由拦截与界面徽标，但提权的唯一途径是
`UPDATE UserInfo SET role = ...`；`get_menu()` 只有 viewer 一个裁剪分支，admin 与 editor 看到的菜单完全相同，
没有"仅管理员可见"的位置。

**问题二（问答记录不隔离）**：三层叠加——RAG 是独立服务且**会话历史不在服务端**；RAG 前端把会话存在
localStorage 且 key 全局唯一（`ragv5-session-v3`）；主应用以同源 iframe 嵌入 RAG、两者共享同一份
localStorage，而主应用从不把自己的身份传给 RAG。结果：同一台浏览器上**任何账号打开 RAG 看到的都是同一份
记录**（管理员与普通用户的记录一字不差、连时间戳都相同），"改名/删除会话"任何账号都能操作这份共享数据。
同病相连的还有两处：旧问答助手 `chatHistory`、文本实体识别 `extractHistory`。

**现在怎么处理**：

| 问题 | 落地 |
| --- | --- |
| 提权界面化 | `GET /api/admin/users`（id / 账号 / 昵称 / 角色，`UserInfo.to_dict()` 天然不含口令）、`POST /api/admin/users/<id>/role`（body `{"role": ...}`）；防呆：不能改自己（403）、角色值白名单（400）、用户不存在（404）、改成功写一条带**旧角色**的 info 日志；`views/admin/UserManagement.vue`（自己那一行禁用下拉并标注"当前登录账号"、未改动时保存按钮禁用、保存后提示"下次登录生效"）；守卫从"是不是 admin/editor"改成**分级比对** `roleSatisfies`（`admin ⊃ editor ⊃ viewer`，角色未知一律不满足，fail-closed） |
| 问答隔离（方案 A：按 uid 分 key） | 主应用新增 `utils/userScopedStorage.ts`：`scopedStorageKey(base, uid)` → `chatHistory:u3`；**账号未知时退回原 key**（不会因为拿不到 uid 就把记录写丢）；`readScoped` 把老版本全局记录**归档**到 `<base>:legacy-archived`（**不归属第一个登录的人**——把别人的提问记录交给谁都可能是错的），归档只做一次；`inference/index.vue` 与 `TextEntityExtract.vue` 在 mount 时 `await userStore.ensureUserInfo()`（BasicLayout 的 `loadUserInfo()` 没 await，而子组件 mounted 先于父组件执行，直接读 `userInfo.id` 会拿到空对象、隔离退化成共享 key） |
| 跨应用身份通道 | `RagAssistant.vue` 在 iframe 每次 `load` 之后 `postMessage({type:'cw-user', uid, role}, '/')`；**不把 uid 或 token 拼在 iframe URL 上**（URL 会进浏览器历史与各级访问日志）；账号变化时重建 iframe 并重发，**首次解析出账号不重建**（否则首次进入会白加载一遍）。RAG 侧 `utils/userScope.ts` 只认同源、只认 `cw-user`、重复 uid 不重复回调、`normalizeUid()` 要求 `[A-Za-z0-9_-]{1,64}`（否则按"没有账号"处理——原先对象或超长串会被拼成 `:u[object Object]` 这种谁都不是的桶） |

**一次真实事故（值得单列）**：隔离功能**第一版上线后在浏览器里没有生效**——换了账号，RAG 会话列表与
提问历史一字不差。根因是一次只改了一半的契约变更加装配处职责不清：桥被改成传 `{uid, role}` 对象后，
在回调**之前**就 `setActiveUid(scope.uid)`，而 store 的 `applyUserScope(uid)` 第一句是"与当前 uid 相同就返回"
——uid 已被桥改掉，于是它**永远直接返回、桶从来没换过**；更糟的是 `String({...})` 得到 `"[object Object]"`，
所有账号拼出同一个 key。这是典型的**接缝 bug**：桥的单测过（回调收到了 uid）、store 的单测也过
（直接调 `applyUserScope` 时换桶正常），**合起来**不工作。修复方式是把职责固定下来——**桥只负责解析与
转交，`activeUid` 由 store 独占**，去重改用桥自己的 `lastNotifiedUid`；`applyUserScope` 是换桶唯一入口，
顺序写成 ①`persist()` 写回**旧**桶 → ②`setActiveUid(新)` → ③读新桶替换内存状态，并用 `loadedScope`
（"当前内存状态来自哪个桶"）判断，不再依赖调用方有没有改过全局 uid。

**验证证据**：提权侧——真实 SQLite + Flask 测试客户端 22 项通过（临时账号 `zc_perm_test`，跑完实测残留 0 条），
前端新增 18 例（用户管理页 6 + 路由守卫分级 12，含"viewer 直达 `/admin/users` 被拦"）。
隔离侧——`tests/unit/user-scoped-storage.test.ts` 8 例、`tests/component/rag-assistant-scope.test.ts` 4 例、
`RAG/frontend/tests/unit/user-scope.test.ts` 5 例与 `session-user-scope.test.ts` 5 例、**既有 47 例单测未改一行
仍全绿**（独立访问 `:8000` 行为不变，含直接断言 `ragv5-session-v3` 的持久化/迁移/配额用例）；
装配级用例 `user-scope-wiring.test.ts`（照 `main.ts` 的真实接线方式）**修复前 4 例全红、修复后全绿**；

变异验证——把 `storageKeyFor` 改成无视 uid（复现原症状）该用例**立刻失败**。

**边界（如实说）**：方案 A 只解决"**串记录**"，不防"**冒充**"——同源之下懂控制台的账号可以改 uid 去看别人的
记录。要防冒充得走方案 B（主应用传 JWT + RAG 服务端验签），触发条件是公网部署；
**这个触发条件后来已经满足**（RAG 服务端验签已落地，见主题 7）。另外，文本实体识别已定为**限 editor 及以上**
（它会调大模型消耗配额，只读账号不该有入口），三处同口径：后端菜单裁剪 + 路由 meta + 接口 `require_write_role`。

## 4. 注入与 XSS

**问题（影响面：任意 Cypher 执行、存储型 XSS）**：问答主链路把用户实体用 f-string 拼进 Cypher
（`WHERE n.name = '{entity}'`），含单引号即可注入、可执行含 `DETACH DELETE` 的任意语句；另有
`id(n) = {node_id}` 拼接、`MATCH (n:{node_type})` 标签注入、关系类型注入，原先的手工
`replace("'", "\\'")` 转义未处理反斜杠、可绕过。前端 inference 页有三处 `v-html` + MarkdownIt `html: true`
+ 全库无 DOMPurify，自写渲染器把后端文本拼进 HTML 标签，模型输出混入 HTML 即存储型 XSS。

**现在怎么处理**：所有拼进 Cypher 的地方改参数化（问答实体查询、按 ID 查节点、按名搜索、默认图谱加载、
事件-组织/事件-人物关系查询、实体关系与路径搜索）；标签与关系类型因 Cypher 不支持参数化，统一经
`common_utils.safe_identifier()` 白名单校验（字母/数字/下划线/汉字，长度 ≤ 64）后内联，手工转义全部删除；
`model_search.get_nodes_by_type` 的非法标签改抛 `ValueError`（由路由转成明确错误而不是 500 堆栈）；
`import_json_to_sqlite` 的 `DELETE FROM {table}` 也加白名单。前端：MarkdownIt 关闭 `html: true`、
引入 DOMPurify 在**出口统一净化所有进 `v-html` 的内容**、思考过程渲染器改为"先转义原始文本再套格式化标签"、
代码高亮的转义不再引用 `md` 实例本身。iframe 的 sandbox 措辞**如实降级**：`allow-scripts` +
`allow-same-origin` 对**同源**页面不构成安全隔离（脚本可移除自身 sandbox、可直接访问父页面），
它的作用是限制弹窗/顶层导航/下载；真正的隔离要靠 RAG 独立域名或反代层鉴权——这条结论已写进代码注释。

**验证证据**：注入型标签（`` Event`) DETACH DELETE n // ``、`Event' OR 1=1`、超长串）全部被拒；

`tests/unit/knowledge.test.ts` 6 例。**另一条纪律**：`deploy/README.md` 与 `docs/集成与入口约定.md`

## 6. 双写一致性（对账 / outbox / graph_key）

**问题（影响面：管理台列表与图谱长期不一致，且没人知道差在哪一条）**：写节点/属性都是"先提交 SQLite，
再调 Neo4j"，失败时只在响应里带一句 `sync_status=failed`——没有记录、没有重试、没有补偿；
三处 `except Exception: pass` 把同步失败吞掉，`update_node` 还**无条件**返回 `sync_status: success`；
`delete_node` 先删 Neo4j 后删 SQLite（SQLite 提交失败即两侧永久不一致），且"无 `neo4j_id` 时按名回退"
取第一个同名节点，同名多于一个时可能删错；全量同步里"新旧节点判定"用 `n.created`，而存量节点同样带该属性，
于是**全部计为新建、`nodes_updated` 恒为 0**；`_create_relationship` "先查后建"而非 `MERGE`，重跑产生重复边。

**现在怎么处理**：

| 项 | 落地 |
| --- | --- |
| 对账口径 | `build_sync_reconciliation()` 逐类型对比两侧计数并输出 `status`（`ok`/`mismatch`/`unknown`）与 `diff`，接入 `/api/quality/report`，工作台 summary 暴露 `sync_mismatch`；Neo4j 不可达时不再因 `diff is None` 误报 `consistent=true`。**口径修正**：原用行数对比，而 SQLite 关系表允许同名行、Neo4j 按 (标签, 名称) 唯一合并——实测 `Place mismatch 2433` 全部来自重名行（5316 行 / 2883 个 distinct 名称，与 Neo4j 节点数分毫不差），改为 `COUNT(DISTINCT name)` 并把实测依据写进 docstring |
| 失败可见 | 三处 `except: pass` 改为捕获 `sync_err` 写入响应（`msg` 带原因、`data.sync_status` 给真实状态、`data.sync_error`）；SQLite 已提交的事实不因 Neo4j 失败而回滚 |
| 删除顺序 | 改为**先删 SQLite 并提交、再删 Neo4j**；按名回退改为"**同名唯一才动**"（`DbUtil._find_neo4j_by_name()`，多于一个返回说明并跳过）；孤儿清理 `collect_orphans()` / `prune_orphans(execute=False)` 默认只打印清单、`--yes` 才真删，判定同时看 `neo4j_id` 与 `(标签, 名称)`，宁可漏报也不误删 |
| 全量同步 | `_create_node` 用 `ON CREATE/ON MATCH` 写临时标记 `_sync_new` 再 `REMOVE`（正确区分新建与命中存量）；`_create_relationship` 改 `MERGE` + `SET r += $props`，属性改走 map 参数 |
| 稳定图谱键 | `graph_key = "<NodeType>:<SQLite 主键>"`（`backend/graph_key.py`）。按名字 MERGE 会把同名节点合成一个、改名又会被当成新建；按 `id(n)` 定位不抗重建（全量重导、恢复备份后 id 全变）。改造前建的无键节点在第一次 upsert 时被**认领**（`MATCH (n:Label {name}) WHERE n.graph_key IS NULL → SET n.graph_key`），因此升级后不会凭空多出一份重复节点。`neo4j_id` 保留并回写，但降级为**观测信息**，不再是任何写入路径的定位依据 |
| 事务 outbox | 业务修改与待办在**同一次 SQLite 提交**里落库（`flush` → `stage_job` → `commit`），提交后再尝试立即写 Neo4j——崩溃窗口只剩"写完 Neo4j 没标 done"，而那一侧幂等。任务里保存 `operation` 与 `from_name`；`apply_job()` 成功后只在原值为空时回写 `neo4j_id`；`next_retry_at` 退避落库（30 秒 → 2 分钟 → 10 分钟 → 1 小时 → `abandoned`），进程重启不会让退避归零 |
| 删除纳入 | 有了稳定键，"按名重放删除有歧义"这个原理由不再成立，`node_delete` 已纳入 outbox |
| 重导 | 新增 `app_meta` 表存"数据重导代数"，`import_json_to_sqlite.clear_migration_tables()` 重导时 `bump_dataset_version()` **作废所有 pending 任务**（否则会把上一批数据重新写进图谱，且没有任何报错） |
| 删掉的旧机制 | `DbUtil._find_neo4j_by_name` / `_delete_neo4j_by_name` / `_update_neo4j_by_name` 三个"按名回退"辅助函数——它们正是"同名多于一个时改错对象"的来源；历史遗留节点改由 upsert 的认领步骤接管 |

**另有一条独立缺陷（编辑节点把图谱的 name 写没）**：`update_node` 只读 `data.get("name")`，而前端从来不发它
（按实体发 `EventName`/`PersonName`/`OrgName`/`geo_name`），于是 `new_name` 恒为 None，一路作为
`job.node_name` 传到 `SET n.name = $name` 把图谱属性写成 null（等价于删除）；SQLite 那边因为归一化循环
会把名字救回来，所以**只有图谱坏掉、主存储看不出来**。第二个根因：属性快照用 API 键名，而重放路径
`neo4j_props()` 按 **SQLite 列名**取值 → 全部取到 None 再被 `if v is not None` 过滤掉，属性一个都同步不过去，
函数却回 `sync_status: success`。修法：名称从归一化后的属性里取、取不到回 400（宁可拒绝也不要把图谱写坏）；
快照用归一化并过滤后的列名（与 `create_node` 同口径）；`upsert_node` 不再无条件写 name
（改 `coalesce($name, n.name)`），重放路径也会从快照回退取名。

**验证证据**：真实 Neo4j 5.25.1 上先用独立标签（`OutboxProbeNode`）逐个验 Cypher——upsert 新建/同键再
upsert 不新建、改名不留影分身、历史同名节点清理、认领历史节点、删除幂等；再用真实 SQLite + 真实 Neo4j
做端到端（创建 → 回写 `graph_key`/`neo4j_id` → 改名后同键节点数仍为 1 → 删除后图谱剩余 0，三个任务全
`done`）。用例：`backend/tests/test_sync_compensation.py` 10 → 23 例（含"同事务提交，提交失败时业务与待办
一起回滚"、"回写不覆盖已有非空 id"、"退避到期判定"、"重导作废后不重放"）、
`test_node_delete_cascade.py` 5 例（含"绕过业务层直接插孤儿关系行会被数据库拒绝"，这条同时是"外键真开着"
的证据）、`test_node_write_integrity.py` 7 例（走真接口——缺陷就发生在"路由传了什么给 DbUtil"这一段）。

**还没做**：① **关系（四类）进 outbox**——关系没有主键可对标，要用"两端 `graph_key` + 关系类型"拼，
那是一次独立重构（还要处理关系删除、关系属性变更两类动作）；当前组合是"节点级 outbox + 关系靠全量/增量
同步兜底"，边界已写进 `backend/README.md`；② **P2-10（outbox 重放与合并的竞态）**：`stage_job` 提交后才调
`_try_sync_now`，而 `job` 因 `expire_on_commit` 会重新 SELECT，若另一请求在这几十毫秒内把同一 `graph_key`
的 pending 任务合并成 `node_delete`，先到的**更新**请求会对图谱执行**删除**而 SQLite 行还在。
**机制已确认但没有复现用例**，独立审计也把它单列（"先补用例再改"）——可行方向是"重放前把 `operation` 与
属性快照读进局部变量"或给任务行加乐观锁/版本号，两者都要能被用例证明；③ 删除失败仍不进队列（SQLite 已经删了，
按名重放删除需要"同名同类型唯一"这类判断，有歧义的动作不自动做）；④ 补偿的**管理页面**未做（接口
`/api/sync/*` 与命令行入口 `backend/retry_sync.py --list` 已就位，运维路径完整）。

## 7. RAG 服务端鉴权与凭证撤销

**问题（影响面：公网模型额度、账号状态失效延迟）**：`/api/query`（SSE）没有任何鉴权；
`/api/query/json` 只有一个**可选**共享密钥；nginx 的 `auth_basic` 是注释掉的。知道 `/rag/` 地址就能调用
问答接口，不受旧系统角色控制、消耗模型配额；浏览器侧那个 uid 只用来拼 localStorage key，**不是服务端身份**。
第二条更隐蔽：**"验签通过"不等于"凭证仍然有效"**——改密码/停用账号后旧后端立刻拒绝该 token，而 RAG 若不做
第二步就会一直放行到 token 自然过期（默认 7 天）。第三条是顺序问题：SSE 的顺序是"runtime → 鉴权 → 撤销检查"，
于是 runtime 加载失败时**匿名请求**会先拿到 503 与脱敏后的加载错误（服务状态与内部故障信息泄露给未认证的人）。

**现在怎么处理**：

| 项 | 落地 |
| --- | --- |
| 验签 | 新增 `RAG/server/auth.py`，用标准库自实现 HS256：`header.alg` 必须严格等于 `HS256`（同时挡 `alg=none` 跳过验签与 `RS256` 算法混淆）、`hmac.compare_digest` 常量时间比较、`b64decode(..., altchars=b'-_', validate=True)` 严格解码、**强制 `exp`**（缺 exp 的是永久凭证）、30 秒时钟容忍。**为什么不用 PyJWT**：RAG 依赖由带哈希的锁文件管理、CI 用 `--require-hashes` 装，环境里既没有 PyJWT 也没在 `requirements.txt` 声明，为这一处引入新依赖要重新生成锁文件并补一次供应链审计，而 HS256 验签只用 `hmac`+`hashlib`+`base64` 就写得完整 |
| 通道准入 | `/api/query`（SSE）要求请求头 `Token`（也接受 `Authorization: Bearer`）为有效 JWT；`/api/query/json` **JWT 或 `X-Bot-Key` 满足其一即放行**（飞书机器人没有用户身份、旧后端也不会给它签 token，要求 JWT 等于把这条调用方堵死）。身份进 `request.state.identity`，不再依赖浏览器 postMessage 自述的 uid |
| 模式分档 | `RAG_AUTH_MODE` = `jwt`/`nginx`/`disabled`（旧布尔 `RAG_REQUIRE_AUTH` 仍接受：`true` ≡ `jwt`、`false` ≡ `disabled`）；**显式生产档下 `disabled` 拒绝启动**（原先只打 WARNING，而 WARNING 会被忽略）；`nginx` 档 + 非回环监听拒绝启动（否则同网段可直连后端端口绕过 nginx，"配了 nginx 认证"是一句假话）；模式拼错（`none`/`off`/`false`/`basic`）拒绝 |
| 声明校验 | JWT 补 `iss` / `aud`（验签只证明"这把密钥签的"，`iss`/`aud` 才证明"是谁为谁签的"）；`sub` 与 `user_id` 都认（签发端将来只发 `sub` 时两端不必同时上线） |
| 撤销查询 | 新增 `POST /api/internal/token/introspect`（`X-Internal-Service-Key`），判定**复用 `DbUtil.token_status`**（与旧后端自己的守卫逐条一致，否则会出现"旧后端拒绝、RAG 却放行"的裂缝）。三条安全边界：未配置密钥 = **503**（一个匿名的 introspection 接口不只是信息泄露，还等于给攻击者第二条探测手段）；失败原因不回给调用方（走白名单 `_PUBLIC_FIELDS`）；只走回环且 nginx 对 `/api/internal/` 直接 404 |
| 查询器 | `RAG/server/introspection.py`：按 token 的 **sha256** 做键（键用摘要是因为内存字典可能进崩溃转储）、TTL 默认 30 秒（**TTL 即撤销生效延迟的上界**）、`RAG_INTROSPECT_FAIL_MODE` 默认 `closed`（"把后端打挂"不该成为一种绕过撤销的手段；代价是后端故障期间问答不可用，所以 health 会把策略报出来）、**失败不写缓存**（把失败当结果缓存会让后端的一次抖动变成这段时间内人人被拒或人人放行）、single-flight（并发方 `await asyncio.shield(同一个 Future)`）、失败结论做 5 秒负缓存（缓存下来的仍是按失败策略得出的结论，与逐次判定结果一致，省下的只是"每个请求都排一次 3 秒超时"） |
| 失败与撤销分流 | `Verdict` 新增 `unavailable`：**撤销 → 401；无法确认 → 503**（`error_code=server_busy`）。原先把"问不到后端"也当成"凭证已失效"回 401「登录已失效，请重新登录」——后端抖一下全体用户被"登出"，而重新登录拿到的 token 仍会被同样拒绝，用户与运维都被指向错误方向 |
| 策略显式化 | 生产档 + jwt 档下二选一，都不做则**拒绝启动**：`RAG_REQUIRE_REVOCATION_CHECK=true`（要求撤销查询必须配齐）或 `RAG_ALLOW_DELAYED_REVOCATION=true`（显式接受延迟撤销）。显式接受后**不再发告警**（决定已写在配置里，反复告警只会训练人忽略告警）。health 的 `auth.revocation` 扩成三态 + 上界：`{"enabled", "policy": "enforced"/"delayed"/"not-applicable", "max_delay_seconds", "delayed_revocation_accepted"}`，未启用时上界为 `null`（由签发端 `JWT_TTL_SECONDS` 决定，本服务不猜） |
| 通道顺序 | 统一为 **鉴权 → 撤销检查 → runtime → 限流 → 参数校验 → 执行**，并写进路由的文档字符串（顺序是契约的一部分，不该靠读代码猜）。撤销检查**放在限流之后**，否则一个客户端就能用并发请求把协程全占在"等后端"里 |
| 可观测 | health 的 introspection 增加 `last_ok_at` / `last_failure_at` / `last_failure_reason`（计数器只回答"历史上失败过几次"，运维要的是"现在通不通、上次不通是什么时候、为什么"；失败原因只取第一行并截断到 200 字符） |
| 前端 | 主应用 postMessage 载荷增加 `token`；`RAG/frontend/src/api/authToken.ts` 内存保管（**不放 localStorage**——主应用会在 iframe 每次 load 后重发）+ 严格清洗（含空白/换行的值一律归零：进 HTTP 头会被 fetch 拒绝，甚至有注入额外头的空间）；`http.ts`/`sse.ts` 两类请求都带身份头 |

**修复过程中自己查出并修掉的缺陷**：第一版 `_resolve_identity` 一上来就看 `RAG_REQUIRE_AUTH`，于是"只配了
密钥、忘了开开关"（正是配置校验会提示的那种疏忽）会让它返回空身份、再被兜底分支判成 401——一个只想观察的
配置会把线上问答整体打断。正确的切分是：**开关只决定"验不过时拦不拦"，与"要不要尝试验签"是两件事**。
另修掉一处既有缺陷：health 原先读模块级的 `_settings_boot`，而请求路径读 `app.state.settings`，一旦不一致
就会出现"health 说撤销查询开着"与"请求实际没查"的分叉。

**验证证据**：`RAG/tests/test_rag_auth.py`（34 → 46 → 57 → 60 → 67 例）、`test_rag_revocation.py`
（18 → 26 → 31 例，查询器部分 26 例 + 路由级 60 例某口径合计 86）、`backend/tests/test_internal_introspect.py`
**12 例**（含未配密钥 503、密钥不对 401、改密码/停用/删号立刻失效、**与全局鉴权同口径**——同一张 token 在
`/api/userinfo` 被 401 时 introspect 必须为 false）。真机实测三态：有效 token → `active=true`、
**已删号账号的 token → `active=false`**、垃圾串 → `active=false`，RAG 侧据此返回 401「登录已失效，请重新登录」；
health 报 `revocation.enabled=true, policy=enforced, max_delay_seconds=30, fail_mode=closed, revoked=1`。
**顺带的坑**：冻结 `time.monotonic` 会让 asyncio 死锁（`introspection.time` 就是标准库 `time` 模块，
patch 它等于把整个进程的单调时钟钉死，而事件循环用同一个时钟算超时 → `asyncio.sleep()` 永远不到期），
三条并发用例已去掉时钟冻结并把原因写在用例里。

**还没做**：① HS256 共享密钥仍是现状（非对称签名 `RS256` + JWKS 在方案里列为"推荐"，未做——它需要
密钥分发与轮换机制，与当前单机形态不匹配）；② JWT 仍长期放 localStorage（见主题 2）。

## 8. RAG 健康观测与构建门禁

**问题（影响面：运维被假信号误导、回归无人拦）**：

- `vector_available=True` 只说明"制品能加载 + 客户端已装配"，而查询侧 embedding 是**网络调用**——密钥失效/
  端点不可达时制品与客户端依然完好，查询静默降级成关键词，health 却报"向量可用"。这直接导致 RAG 349 例里
  有 1 例长期失败（`test_text_mode_passthrough_and_autodowngrade`）。
- 体积门禁**假通过**：`check-bundle.mjs` 把资源前缀写死成 `/assets/`，而 `build:integration` 的产物引用
  `/rag/assets/...` → 一条都匹配不上，打出"入口 0.0 kB / vendor 0.0 kB / 首屏合计 0.0 kB，体积门禁通过"。
  **一个永远为真的门禁比没有门禁更糟**：真实回归也会显示为通过。
- 构建模式标记 `build-mode.txt` 原先写死 `./dist/`，不跟随 `--outDir`（用 `--outDir dist-plain` 跑 e2e 时
  把并入模式 dist 的标记改成了 `standalone`，产物没动但服务启动会按错误模式核对）。
- 脱敏工具 `_public_text()` 早就写在 `server/api.py` 里，但 **SSE 的 error 帧拿不到它**，同文件里另有三个
  匿名端点的失败分支漏过脱敏——工具在，只是没统一用上。

**现在怎么处理**：

| 项 | 落地 |
| --- | --- |
| 向量状态 | 拆成 `vector_artifact_ready` / `embedding_client_configured` / `embedding_probe_ok`（None = 尚未探测）/ `last_vector_error` / `effective_text_mode` / `vector_error_count`，由 `TextSearcher.vector_status()` 统一产出；向量通道**报错**时 `mode` 如实报 `keyword`（判据是"本次调用里错误计数是否增加"，与"返回空结果"——可能是真的没有近邻——分开）；health 增 `vector` 子对象，`embedding_probe_ok is False` 进 `warnings`；**不做启动期网络探测**（那会把服务可用性绑到外部端点超时上） |
| 测试离线化 | `tests/conftest.py` 提供确定性桩向量客户端（文本哈希派生、单位长度），`test_chain_smoke` 的 runtime 夹具换上它 |
| 体积门禁 | 前缀自解析（从 `index.html` 的引用推断 assets 目录）；URL→文件路径按 `/assets/` 锚点切分（base 是 `/rag/` 时页面引用 `/rag/assets/x.js` 但文件在 `dist/assets/x.js`）；**未找到入口/vendor 直接失败**（不允许再出现 0 kB 通过）；引用文件不存在也失败（原先 `gzipSize` 读不到就返回 0，把"文件没了"也算成 0 体积）；standalone 与 integration 各 8 例 |
| 构建标记 | `configResolved` 里取 `config.build.outDir`，`closeBundle` 按它写；服务启动读它并与 `index.html` 资源前缀交叉核对（缺标记时回退解析前缀），结果进启动日志与 `/api/health` 的 `frontend_mode` |
| 脱敏 | 实现移到 `lib/redact.py` 供两条链路共用，四类文案统一过它；`brief_error()` 取第一行并截断 |
| 日志 | `setup_rag_logging()` 给 `rag.*` 命名空间挂控制台 + `logs/server.log`（5MB×5），在 `server/api.py` **模块级**调用（加载期日志才不丢） |
| 状态码 | 容量拒绝（`sse.py` 特意定义了独立错误码）从 500 改 **503**——按状态码决定要不要重试的调用方不会重试一个 500 |

**验证证据**：`RAG/tests/test_vector_health.py` 6 例（三字段各自独立、缺客户端不声称可用、查询期失败留下
原因且模式如实降级、hybrid 下向量半边故障同样降级、向量返回空不算故障、health 子对象与告警），
外加原先失败的 `test_text_mode_passthrough_and_autodowngrade` 转绿；`tests/unit/check-bundle.test.ts` 8 例，

`RAG/tests/test_error_redaction.py` 8 例，其中一条用"把 `dicts.json` 做成目录"制造**真实带路径的异常**
（`IsADirectoryError`），而不是拿一个不含路径的 JSON 解析错误来假装验证脱敏。

**还没做**：无（`embeddings.embed()` 超批上限改 `raise` 而非静默截断这一点也已完成——分批是
`vector_pipeline` 的职责，那里本就有形状断言）。

## 9. 数据完整性与导入安全

**问题（影响面：数据丢失、孤儿关系）**：`import_json_to_sqlite.py` 的 `run()` 在 `--yes` 后执行
`db.drop_all()` + `create_all()`，而 `UserInfo` 与知识表**共用同一个 SQLAlchemy metadata**——换一份抽取
数据集重导会把全部账号、口令哈希与角色一起删掉，管理员账号消失后只能重新注册 viewer 再手工改库。
`models.py` 声明了外键，但 `PRAGMA foreign_keys` 默认是**关**的（本机实测 `= 0`），声明因此只是一句注释；
删掉一个已被关系引用的事件，关系表会留下指向不存在 id 的孤儿行。另外 `account` 列无 `unique` 约束，
"先查后插"存在并发竞态。

**现在怎么处理**：

| 层 | 落地 |
| --- | --- |
| 导入 | 删掉 `db.drop_all()`，只保留 `create_all()`（对已存在的表是空操作，正好"补齐新表、不动老表"）；`clear_migration_tables()` 只清 4 类实体 + 4 类关系表并在 docstring 写明"不动 `UserInfo` 等非知识表"；删除顺序改**先关系、后实体**（原先相反，靠一句 `PRAGMA foreign_keys = OFF` 兜着——而那个 PRAGMA 在 SQLAlchemy 已开启的事务里是**静默无效**的，SQLite 明确要求它在事务外执行）；导入前后各取一次"账号数 + {账号: 角色}"快照，**不一致直接退出码 1** 并提示从备份恢复 |
| 外键 | 连接钩子里 `PRAGMA foreign_keys=ON`（必须逐连接、且事务外，连接钩子正是事务外）；四张关系表的外键补 `ondelete='CASCADE'`（**只对新建的表生效**，存量库靠业务层路径）；业务层 `DbUtil.delete_node` 先删引用方关系行、再删实体行，与实体同一次提交；删除范围由 `_relation_models_for` 的显式映射给出（不拼表名，拼错了会静默变成"什么都没删"）；响应带 `removed_relations`（删除是级联的，操作者要知道这一下删掉的不止一个节点） |
| 账号 | `account` 加 `unique=True`，`add_user` 改为"先校验空值、再插入、捕获 `IntegrityError`"；重复账号由 `code 500` 改 **409**（客户端错误报成服务端故障会让监控误判）并在插入前先查存在性；**唯一索引建不上时拒绝启动**（重复账号会让注册不再被拦，且 `authentication` 用 `.first()` 取行可能比对到另一行的口令哈希） |
| 角色 | 启动迁移由回填 `admin` 改回填 `viewer`（见主题 2） |

**验证证据**：`backend/tests/test_import_preserves_users.py` 4 例，其中一条用**打桩把 `db.drop_all` 换成
"一被调用就 `pytest.fail`"**而不是读源码断言，另三条分别验账号与角色逐条不变、不带 `--yes` 时拒绝执行且零
改动、旧知识数据确实被替换（防止"什么都没干"也算通过）。`test_node_delete_cascade.py` 5 例：外键确实是开
的（查 `PRAGMA` 值）、删事件连带删四类关系且计数归零、删地点/人物/组织各自连带自己的关系且不牵连事件、
只删引用被删节点的那几条、**绕过业务层直接插孤儿关系行会被数据库拒绝**。

**还没做（部署时动作）**：修复"编辑节点把图谱 name 写没"之后，需要跑一次
`backend/sync_sqlite_to_neo4j.py` 才能补回已经被清掉的图谱 `name`（见主题 6）。

## 10. 前端工程债

**问题（影响面：可维护性、生产行为与开发态不一致、生产资源 404）**：`inference/index.vue` 3300+ 行
（占全库 21%），同时聚集 XSS、SSE 无 `AbortController`（卸载后流继续写入、loading 悬挂）、聊天历史深度
watch 全量 `JSON.stringify` 写 localStorage（5MB 配额溢出且静默吞异常）；四个 CRUD 页约 250 行复制粘贴；
接口层名存实亡（多数页面裸调 `Http.xxx` + 字符串 URL）；**mockjs 无条件 import 且在 `dependencies`、
已实证打进生产包**，而 `/user/menu` 的菜单唯一数据源是硬编码 mock（后端菜单接口从未生效）；
baseURL 硬编码 `http://${hostname}:5000` 使 vite 代理对 axios 不生效；类型检查**完全不可用**（项目锁
TypeScript 4.9 而 Vue 3.5 的 `.d.ts` 需要 TS 5.x）；登录页三处资源路径在生产下 401/404 而构建仍返回成功。

**现在怎么处理**：

| 项 | 落地 |
| --- | --- |
| mockjs | `bootstrap()` 内 `if (import.meta.env.DEV && VITE_ENABLE_MOCK !== 'false') await import('./mockjs')`，移入 `devDependencies`；生产走真实 `GET /user/menu`；CI 断言产物不含 mockjs；2026-09-25 完全移除 |
| 同源化 | baseURL 改同源相对路径 `/`（axios 与 SSE fetch 走同一条通道，HTTPS 下不再混合内容），timeout 10 分钟 → 5 分钟（SSE 走 fetch、不受此值影响，已注明）。**这一步引入过回归**：不带 `/api` 前缀的旧接口打到 Vite 自己被 SPA fallback 吃掉，axios 解析 JSON 直接报错——vite 代理补一条精确正则 `^/(create_node\|update_node\|delete_node\|search_name_kg\|user/(menu\|permission))$` |

## 12. 抽取链正确性与工程债

**问题（影响面：已产出的评估结论、缓存可用性、两份编排漂移）**：

- **recall 公式错误**：`optimal_evaluator.py` 把实体 recall 按**预测数**加权（`avg_r = Σr·pred_cnt / total_pred`），
  既非 micro 也非 macro，**已产出的 F1 数值有误**；另有一处 gold 为空时的 `ZeroDivisionError`。
- **空结果污染缓存**：`except Exception` 捕获一切异常后返回空结果，上层当成功写入缓存——与 `main.py`
  注释宣称的"不缓存失败"直接矛盾，失败片段只能手工 `--refresh-cache` 救。
- **产物缺模型名**：metadata 不记录模型名称与 API base，换模型重跑后产物无法自证来源（附学术评估的项目硬伤）。
- **三条噪声地名正则从未生效**：raw string 写成 `r".*等\\d+方国$"`——raw string 里 `\\` 是**两个字符**，
  正则引擎解释为"一个字面反斜杠"，于是这三条只能匹配不存在的字面量，"等3方国"这类描述性字符串一路穿过
  噪声过滤、进了地理编码队列。
- **缓存索引非原子写**：`CacheManager._save_index` 是 `open(index_path, "w")` 全量重写——这个调用一执行就把
  索引截断成 0 字节，进程在中间被杀留下半截 JSON，下次 `_load_index` 解析失败 → `CacheManager.__init__`
  抛异常 → **整个抽取任务还没开始就崩**，且 `cache/` 里那 22MB 缓存在人工删掉索引前完全不可用。
- **两份平行编排**：backend 的 `llm_pipeline` 与离线链路 `main.py` 各有一份抽取编排，**"平行演化易漂移"
  不是风险预警、是已经发生了**——backend 调 `event_extractor.extract(chunk_text, chunk_entities)`，而第 2 个
  形参是 `place_list: str`，于是第 3 阶段提示词里被塞进 `places=[PlaceEntity(geo_name='牧野', ...)]` 这种
  Python repr；**不报错、不改变 HTTP 状态码、接口照常 200**，只是让模型拿着一串 repr 去抽事件（典型静默降级）。

## 13. 评估口径与可复现性

**问题（影响面：学术结论的可信度）**：两条独立的问题，且都被"只跑两次看不出问题"掩盖过。

**第一条：指标随进程漂移。** 同一 pred / gold / config 连跑两次，关系抽取的 tp/fp/fn 与 F1 就不同
（实测 `filtered_pred` 890 vs 888、关系 F1 0.739 vs 0.750）。根因是关系评估的贪心一对一匹配直接迭代两个
**集合**（`filter_relations()` 与 `build_gold_triples()` 都返回 `set`），而 Python 对字符串哈希做**每进程
随机化**，匹配里"相似度并列"用 `combined > best_score`（严格大于）取舍、并列时先遍历到的赢，于是换进程就
换一个匹配方案。同类隐患还有 `match_entities()` 的内层 `for gold_name in unmatched_gold`。

**这里有一次需要如实记录的误判**：更早一次复核跑了**两个独立进程各一次**、看到两边 `results.json` 逐字段
一致，于是记成"真实存在的不可复现点只有 `error_samples`"并把该问题降级。问题不在"同进程"（当时的说法
本身也不准确，后来更正为"两个独立进程"），而在**样本量**：漂移的表现是"某些种子下相似度并列的取舍不同"，
2 次运行完全可能落在同一个结果上（换成 3 颗种子给出 3 个不同 tp 值，只抽 2 次就有约 1/3 的概率抽到同一对），
而且当时没有显式控制 `PYTHONHASHSEED`、无法说明抽到的是哪两颗种子。把样本量提到 3 颗显式种子，漂移就露出来了。

**第二条：关系指标对"事件-事件关系类型判错"完全不敏感。** 关系类型原先只走模糊比对（阈值 40），而五个
规范的事件-事件关系类型**两两 `fuzz.ratio` 都是 50**（都带"关系"二字、4 字中 2 字 → `2*2/8=50`）——
**全部过阈值**。实测：标注固定为 `(E1, 顺承关系, E2)` 时，预测 `(E1, 因果关系, E2)` 与 `(E1, 并列关系, E2)`
**修前都是 tp=1**。也就是说，只要事件的 head/tail 对得上，关系类型判错也照样拿满分。（初稿把机制写成
"评估把 `因果关系` 归一成 `顺承关系` 所以算匹配"——**这个说法是错的**：实测 `因果关系` 归一后仍是
`因果关系`，因为 `config/relation_types.json` 的映射覆盖了 `optimal_evaluator.py` 里那份硬编码变体表；
真正的机制比重，见上。）**附带的坑**：`optimal_evaluator.py` 先用硬编码 `relation_map` 建 `normalize_map`、
再用 `normalizer.relation_map` **覆盖**它，于是硬编码表里被 config 覆盖的条目**形同虚设**——
改那份硬编码表可能看不到任何效果。

**现在怎么处理**：

| 项 | 落地 |
| --- | --- |
| 定序化 | 把贪心匹配抽成 `match_relation_triples(pred_triples, gold_triples, event_mapping)`：内部先 `gold_list = sorted(gold_triples)`、再 `for pred in sorted(pred_triples)`。**让函数自己定序而不是只让调用方定序**——输入本来就是集合，**定序是这条匹配的契约**，放在函数内部任何调用方（含将来的）都拿不到漂移的结果，也顺带给了测试一个干净的观测点。同类改动：`match_entities` 内层遍历前定序、`error_samples` 三处样例定序后再截前 20（原来按遍历顺序截、成员会变）、`build_event_mapping` 的 `scores.sort(reverse=True)` 加注释说明为什么它是全序（元组逐元素可比、下标唯一），防止后人"优化"成只按相似度排序 |
| 依赖口径 | **不采用**"给 CI 钉一个固定 `PYTHONHASHSEED`"的做法：那是把症状藏起来，真实用户机器上的种子由解释器随机决定。用例显式开 4 个不同种子的子进程跑真实代码路径，断言"4 颗种子必须给出同一个结果" |
| 关系类型口径 | 新增 `OptimalEvaluator.relation_types_match()`：**两侧都落在五个规范事件-事件关系类型里时要求精确相等**，其余自由文本关系名（事件-地点/人物/组织那类写法不唯一）仍走模糊比对。`filter_relations` 的预筛**保持原样**（类型错的预测仍作为 FP 计入，而不是被筛掉后不算账） |
| 阈值敏感性 | 新增 `tools/threshold_sensitivity.py` 做四阈值 OAT 扫描，产物指纹打在表头（避免把"产物换代"误读成"阈值敏感"） |
| 标注规范 | 新增 `entity-event-relation/data/annotations/README.md`：标注范围与粒度、三份文件逐字段口径（含关系名取值表与实测条数）、事件名归一原则、**五条已知局限**、以及"改标注的流程"（改完必须重跑一次对照评估并写进实施记录） |
| 历史基线 | 两个评估快照（`evaluation/latest`、`evaluation/recheck-micro-20260925`）的 `results.json` metadata 加 `snapshot_note`，写明"这是定序化之前的产物、其 tp/fp/fn 属于某一颗哈希种子下的一次结果、定序化后重跑值是 743/145/356、**不要拿它当当前代码的回归基线**"（只多这一个键、数值未动） |

**口径变更前后对照（同一份产物，指纹 `885b0d9ec340a50b`）**：

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 实体 F1 | 0.2042 | 0.2042（不受影响） |
| 事件 F1 | 0.4175 | 0.4175（不受影响） |
| 关系 tp/fp/fn | 743/145/356 | **714/174/385** |
| 关系 F1 | 0.747861 | **0.718671** |
| 宏观平均 F1 | 0.4565 | **0.4468** |

丢掉的 29 个 tp 逐条拆出来是 **30 条预测三元组**（29 条 `顺承关系` + 1 条 `条件关系`）不再算命中——它们原先
都靠"模糊相似度 50 > 阈值 40"顶替了标注里**另一种**规范类型。即改前的关系 F1 里约 **4% 是白送的**。
**这是口径变更，不是模型退化**；引用历史记录里的 0.7479 时必须注明它属于旧口径。

**阈值敏感性结论**（写进报告时必须带上）：① **事件指标对 `event_sim_threshold` 高度敏感**——0.25→0.55 时
事件 F1 从 0.4606 掉到 0.3430、**极差 0.1176**（宏观平均 F1 极差 0.0430），所以"事件 F1 0.4175"这个数
**必须与阈值一起读**，单独引用会误导（"调参刷分"的空间就在这里：把阈值降到 0.25 就能换来 +0.043 宏观 F1）；
当前 0.35 落在区间中段、不是悬崖边。② 关系指标对 `relation_threshold` 最敏感（极差 0.0538），但**改完
之后它的敏感性来源变了**：规范事件-事件类型走精确比对、不再受阈值影响，剩下的敏感性只来自自由文本关系名，
口径上比改前更干净；另外 60→70 处出现非单调（0.6816→0.6835），引用单点数值时别把趋势读过头。
③ 实体指标对它的阈值几乎不敏感（极差 0.0056），且与其它三个阈值完全无关。
④ 四阈值极差分别是 0.1176 / 0.0538 / 0.0056 / 0.0070；重跑命令 `python tools/threshold_sensitivity.py`
（约 8 分钟）。

**标注已知局限里最要紧的两条（都是实测的，不是猜测）**：① **部分关系标注的 head 不在事件标注名单里**
——`event-place` 479 条中 230 条、`event-org` 527 中 136、`event-person` 592 中 183、`event-event` 168 中 80；
评估时 `build_gold_triples` 只保留"head 能映射到预测事件"的关系，**这批 gold 三元组根本不进分母**，
报告里引用"关系标注 1766 条"时必须注明这一点；② **未做标注者间一致性（IAA）**——单人标注，给不出可靠性
上界。

**验证证据**：定序化后 seed 0~5 **六次运行的 `results.json` 递归对比，除 `metadata.evaluated_at` 外逐字段
相同**（含 `error_samples` 的成员与顺序），关系 tp/fp/fn 恒为 743/145/356、F1=0.747861（这个值恰好等于
修前 seed 1 那一组，属巧合）；`tests/fixtures/relation_slice_repro.json` 是最小复现夹具——从 15MB 的
`9_final_all.json` 用 delta debugging（缩减目标性质 = "seed 0 与 seed 1 的结果不同"）缩到 **2 条关系、
2 个事件、527 字节**。

**还没做**：① 占位词宽口径在产物侧的实际效果、以及提示词修复后的抽取质量，都要真跑一次整本抽取才能看
（与缓存失效的重跑合并成一次最省）；② 抽取链的 gold 与评估参考数据"需要先重建"这一结论尚未执行

（**已决定往后放**：先把工程完善）。

## 14. 飞书机器人

**问题（影响面：提问永久丢失、停机卡死、配额被任意消耗）**：

- **停机死锁**：`stop()` 用 `queue.put(None)` 哨兵唤醒 worker——队列满时永久阻塞，`main.py` 的停机流程
  走不到 `close()`。
- **消息永久丢失**：先写 `processed_events` 认领、再入队；队列满被拒后事件已标记处理，飞书重投被自己的
  去重记录挡掉，那条提问永久消失。
- **假承诺**：卡片回调队列满也回 `正在查询…`。
- **异常终止后卡死**：`processing` 在 `_CLAIMED_STATUSES` 里，进程被强杀（SIGKILL / OOM / `os._exit(0)` /
  停机超时后退出）会永久留下这一行 → 重投被当重复丢弃，占位卡在 24h TTL 内也不恢复。
- **滥用边界不足**：一个无界 `queue.Queue()` + 单 worker（一个 20–30 秒的 RAG 请求阻塞所有其他用户）；
  没有用户/群白名单（企业内任何能访问该机器人的人都能消耗 RAG/LLM 配额）；jwt 档推出后**机器人每问必 401**
  （它只发 `X-Bot-Key`），而机器人侧的降级文案只说"RAG 不可用"，运维会朝反方向修。

**现在怎么处理**：

| 项 | 落地 |
| --- | --- |
| 停机 | worker 改 `get(timeout=0.5)` 轮询 `_stop`，停机只依赖一个 Event；`stop()` 只置位 + join，超时记 WARNING 并说明队列剩余条数。**不用哨兵消息唤醒**：哨兵路径的问题就是"队列满是阻塞点"；代价是停机最多慢 0.5 秒 |
| 不丢消息 | 认领 → 入队 → **入队成功才 confirm**；失败时 `release()` 把状态改成 `rejected_busy`（可重投）；卡片回调无 `event_id` 则删掉内存窗口键。**入队失败痕迹保留在库里**而不是删除——删除会让"被拒了多少次"在事后完全查不到。事件状态机 `received → accepted → processing → done` + `rejected_busy`/`failed`；`processed_events` 新增 `status` 列（老库由 `bot/db.py` 的加列迁移补上、默认 `accepted`）；**`failed` 刻意不参与重投重试**——异常很可能发生在"回答已经发出去"之后，重投会给用户发第二条回答，比静默丢掉一条更难解释 |
| 卡死恢复 | `Dispatcher.recover_stuck_events()`：启动时把超时（默认 10 分钟）的 `processing` 与 `received` 扫回可认领状态。用**时间窗**而不是一律恢复，是为了不把"正在跑"的任务抢回来（那会让同一条提问被回答两次）；恢复失败不影响启动 |
| 白名单 | `FEISHU_ALLOWED_CHAT_IDS` / `FEISHU_ALLOWED_OPEN_IDS`（逗号分隔，**命中任一即放行**，两个都空 = 不限，内网默认行为逐字不变）；判定在服务端，**卡片回调同样过闸**（否则被移出名单的群仍能点旧按钮继续提问）；不在名单内**不回执**——回一句"无权使用"等于对外暴露机器人存在，而白名单的用意本就是不想让这些人用 |
| 队列上限 | `queue.Queue(maxsize=QUEUE_MAX_SIZE)`（默认 200），**非阻塞 `put_nowait`**：本方法跑在飞书 SDK 的 ws 事件循环线程里，`put()` 阻塞会把 ping/重连一起卡住、触发飞书判定"未应答"而重投——比丢消息更糟。满时计数 + 记日志 + 可选提示。`QUEUE_MAX_SIZE<=0` 直接拒绝（`queue.Queue(maxsize<=0)` 表示**无界**，正是本项要修的问题，不能让人以为填 0 是"关闭限制"） |
| 忙时提示 | 用独立后台线程发送（发消息是几百毫秒的 HTTP 调用，在回调线程里做会拖住心跳），按会话冷却（默认 30s，避免提示本身变成新的消息风暴），失败只记日志 |
| 机器人密钥 | 四处一起收口：`deploy/env/rag.env` 把 `RAG_BOT_API_KEY` 从"可选"改成"本模板必填"并写清原因；`deploy/README.md` 列为第 5 条必改项；`check_rag_auth.sh` 按"仓库里有没有 `feishu-bot/.env`"判断——要部署机器人却没配 → 拒绝安装，不部署只提醒（不是每个部署都接机器人，不该一票否决）；`/api/health` 的 `warnings` 增加同一提示。真机实测：**原先 `feishu-bot/.env` 里 `RAG_BOT_API_KEY` 存在但值为空**，写入同值（64 字符随机）后门禁由 10/11 变 11/11 |
| 探测分类 | 机器人探测把 401/403 归为"该地址可能不是 RAG 服务"，真因通常是 `RAG_BOT_API_KEY` → 单独归类并直指该配置；`DEGRADED_CODES` 原先零引用（真正判定是硬编码）→ 让它成为判定集并补上漏掉的 `rate_limited` |

**验证证据**：`feishu-bot/tests/test_dispatcher.py`（8 例新增，含"队列满时 `stop()` 不阻塞"——不放行则用例
挂死、"被拒事件可被重投"、"已坐实的认领仍去重"、"卡住事件的启动恢复"、"老库补列迁移"）；
用例总数 279 → 289 → 297 → **301**；`ruff check .` 通过；CI 新增 `feishu-bot` job（装它自己的
`requirements.txt`——`lark-oapi` 版本刻意锁死、不共用 RAG 锁文件——跑 pytest 与 ruff，并加
`cd render && npm ci` 让真实渲染用例执行而不是被跳过）。

**还没做**：① 分片 worker（按 `session_key` 分片串行 + 全局并发上限）与监控——单 worker 串行是当前设计里
写明的事实，改成按 `session_key` 分片会动到"会话内消息必须按顺序处理"这条硬约束的验证方式，需要独立的并发
用例集；② 真实飞书租户的人工验收（长连接、卡片按钮重投、运营群投递）仍未做；③ 与旧知识库账号体系不打通
（两套身份、权限、审计各自独立）。

**验证证据**：GitHub Actions **全绿**（`gh run view 36141221016`，commit `10d3f08`；另一次 `36141768733`，

① 夹具被过宽的 `.gitignore` 误伤（上面已述）；② 渲染用例的跳过条件不完整（只判断 `shutil.which("node")`
而产品代码预检还要求 `render/node_modules` 存在）——用例侧统一改按 `renderer.is_available()` 判断并加
`fake_render_env` 夹具，这些用例考的是"失败时的日志与产物清理"，是 CI 最该覆盖的降级路径；
③ 一条**同期新写的用例**在 CI 上假失败——CI runner 自带 nginx（本机没装），门禁脚本走进 `nginx -T` 分支，
而用例的合成站点文件在临时目录里、根本不会被 nginx 加载，拿一份不含被测对象的快照去证明被测对象只能得到
假失败。修法是给该项加前置条件（`NGINX_SITE` 不在 `/etc/nginx/` 下时跳过并说明原因），并补一条用例复现
该场景（把假的 `nginx` 放进 PATH），让它在任何机器上都能跑而不是只在 CI 上偶发。

**还没做**：① 统一 lock 的**平台完整性**（详见 [项目现状与后续计划.md](项目现状与后续计划.md)）；② `git filter-repo`
历史重写（含 `cache/` 那次）；③ `main` 的上游指向待用户确认后改回 `origin/main`；④ 已废弃的 Python 3.8
CI job 与本地 `place-name-KG` 环境（等双跑稳定一段时间后再删，服务器侧的 3.8 已于 2026-09-26 删除）。

## 16. 文档体系

**问题（影响面：接手成本、死链、数字漂移）**：RAG 的测试数与版本号曾有多套口径并存；`docs/README.md`

## 附录 B：前车之鉴

**验证方法论**

1. **验证"可复现"必须显式固定多颗哈希种子做子进程比对**。只跑两次说明不了任何事——两次完全可能碰巧
   落在同一个结果上（附录 A 第 1 条就是这么误判的）。反过来，也不要"给 CI 钉一个固定 `PYTHONHASHSEED`"：
   那是把症状藏起来。
2. **"新实现通过"不能证明用例有牙**，要做对照实验。限流原子化的做法是把旧实现临时装回去、同样 20 并发
   跑一次（旧实现只记到 4、新实现记满 20）——这既证明缺陷真实存在，也证明用例确实能抓住它。
   （结论写进记录而不是留一个"注定失败"的用例：被测代码只有一个版本，留对照用例只会污染套件。）
3. **先确认"修前失败"再入库**。多处用例都做了这一步：`git stash push` 三个源文件后 10 例失败、
   退回手写版本串后 3 例失败、退回纯模糊比对后 2 例失败、把 sentinel 分支改坏后 2 例失败、
   装配级用例修复前 4 例全红、变异验证（把提交路径改成直接 return / 把 `storageKeyFor` 改成无视 uid）。
4. **单侧单测都过不代表接缝正确**。凡是"两个模块约定一个消息/格式"的地方，都要有一条**照真实装配方式
   接线**的用例；浏览器级用例留给"只有真环境才暴露"的那部分。（隔离功能第一版没生效正是这一类。）
5. **静态检查通过不代表行为不变、更不代表视觉正确**。问答页重构时类型检查与 133 个单测都发现不了
   `isFirstLoad` 未复位，只有真浏览器 + 真产物能看出来。
6. **重建"行为不变"要有对照，且对照本身要先验证覆盖面**。67 请求快照抓到的 15 处 500（漏 import）出现在
   打桩脚本根本不会调的接口上；而**一个永远为真的门禁比没有门禁更糟**（体积门禁 0.0 kB 通过、`pytest | tee`
   吞掉退出码、`git push | tail` 永远为真）。
7. **检查只在本机跑过 = 真问题一直躺着**。ruff F821 进 CI 后首次全量跑就报 59 处未定义名；两个 ruff 版本
   恰好各装在一个本机环境里，本地怎么跑都不会暴露口径差异。
8. **口径/契约的变更必须一次改完并同时改测试**——改一半比不改更危险（表现为数据串桶，比"功能没做"更难发现）。
9. **对照前先确认端口只有一个监听者**。Windows 的 `SO_REUSEADDR` 允许两个进程同时绑同一端口，
   请求会被旧的接走一半（实测出现 4 处差异，换干净端口后归零）；Git Bash 下 `pkill -f app.py`
   **匹配不到 Windows 进程**，要用 `netstat -ano` + `taskkill /PID <pid> /F`。
10. **管道只看最后一条命令的退出码**（`pytest | tee`、`git push | tail -2`）——要显式计算 `PIPESTATUS`。

**仓库与文件操作**

11. **改 `.gitignore` / 排除规则的作用域时，要连"它原来覆盖了谁"一起清点**。两次同类事故方向相反：
    裸 `data/` 吞掉了该入库的测试夹具（CI 3 个 FileNotFoundError），把 `cache/` 改 `/cache/` 又放开了
    本该忽略的 22 MB 运行期缓存（进了公开仓库历史）。
12. **批量脚本要区分缩进层级、删重复行要按上下文定位**。正则 `^\s*import traceback$` 把刚提到顶层的那个
    也一起删了（拆模块时报 500）；`str.replace(..., 1)` 删"未使用的 `db`"时删掉的是**另一个函数**在用的
    那一处，`stage_job` 当场 `name 'db' is not defined`。
13. **迁移函数时要连带迁移它依赖的模块级状态**（`APP_PATH`、logger、标准库 import）；**AST/机械分析的盲区
    要靠反向检查兜住**（`load_current_dataset_meta` 不以 `_` 开头，第一版闭包分析没抓到）。
14. **不改历史快照**。`evaluation/latest` 一类"某一颗种子下的一次结果"要加注说明而不是就地更新；
    要覆盖它必须显式指定路径并打警告。
15. **`git status` 里的 ahead/behind 取决于上游指向**，会把"不能整合的旧备份仓库"显示成"落后 11 个提交"。

**工具与环境的坑**

16. **CRLF 会让 Linux 上整个脚本一行都跑不了**，而本机与 CI 都发现不了——`.gitattributes` 是必需的。
17. **PATH 上的 `python` 可能是应用商店的占位桩**（静默无输出、退出码 49），文档里的 `python -m ...`
    会静默什么都不做。先做一次 `python -c "print(1)"`。
18. **冻结 `time.monotonic` 会让 asyncio 死锁**（`introspection.time` 就是标准库 `time` 模块，
    patch 它等于把整个进程的单调时钟钉死，而事件循环用同一个时钟算超时）。
19. **`pkill -f "env-switch.sh"` 会匹配并杀掉自己那条 ssh 命令行**（远端 shell 命令行里含这个字符串），
    表现为"命令无任何输出"——用 `env-swi[t]ch` 这类中括号技巧避开自匹配。
20. **Vue Router 对"导航到当前路径"的重复导航不跑守卫**，多个用例共用一个 router 实例时不退开会让后续
    用例静默跳过守卫（假通过）。
21. **同目录残留的 `vite.config.js` / `vite.config.d.ts`**（`vue-tsc -b` 的历史产物、已 gitignore）
    会**盖住** `.ts`，症状是"改了配置不生效"。
22. **写工具链的 heredoc 会吃掉反斜杠**（`\n` 被还原成真实换行），改动脚本时匹配失败甚至写出语法错误——
    改用精确替换工具。
23. **本机 pip 缓存权限问题**（`[Errno 13] Permission denied: ...\pip\cache\...`）加 `--no-cache-dir` 即可，
    与项目无关；记在这里免得下一个人以为是依赖解析失败。

**文档纪律**

24. **文档不要比代码说得满**。这条已经反复付学费（附录 A 第 11、12、13 条）：写得比代码满的句子，
    下一个人会当成事实继续引用。
25. **数字只写一处、引用而不复制**，否则同一件事会有两套口径（RAG 前端 67 vs 79、门禁 23 vs 24、
    机器人 279 vs 297）。
26. **产物指纹与评估数值必须一起记**，否则"产物换代"与"匹配抖动"无法区分。
