## 三、HS256、JWT 与 RAG 鉴权

### 1. HS256 密钥的作用

用户登录后，backend 生成 JWT：

```text
账号密码验证成功
→ backend 生成 JWT
→ 前端保存 JWT
→ 后续请求携带 JWT
```

JWT 大致包含：

```json
{
  "user_id": 3,
  "role": "editor",
  "iat": 1790310000,
  "exp": 1790914800
}
```

HS256 密钥用于给 JWT 生成签名。它的作用是：

- 证明 token 由服务端签发；
- 检查 token 内容是否被修改；
- 防止用户把 viewer 修改成 admin；
- 让 RAG 验证 backend 签发的登录身份。

HS256 不负责隐藏 JWT 内容。JWT 可以被解码查看，因此不能在 JWT 中保存密码和 API Key。

如果 HS256 密钥泄露，攻击者可以伪造任意账号 token，因此密钥必须：

- 只放 `.env`；
- 不提交 Git；
- 不写日志；
- 使用足够长的随机值；
- 生产环境定期轮换。

### 2. 当前 RAG 鉴权仍未默认启用

当前已经实现 JWT 验签能力，但部署模板仍是：

```env
RAG_REQUIRE_AUTH=false
# RAG_JWT_SECRET=
```

如果直接复制模板部署，RAG 仍不要求登录。正确方案是给鉴权模式明确分档：

```env
RAG_AUTH_MODE=jwt
# 或
RAG_AUTH_MODE=nginx
# 仅开发环境允许
RAG_AUTH_MODE=disabled
```

生产环境出现 `disabled` 时应拒绝启动，而不是只输出警告。

### 3. 推荐使用非对称签名

当前 HS256 要求 backend 和 RAG 共用同一密钥。长期更推荐：

```text
backend 持有私钥并签发 JWT
RAG 只持有公钥并验证 JWT
```

可以使用 RS256 或 ES256。这样即使 RAG 服务被入侵，也不能伪造用户 token。

### 4. JWT 建议字段

建议 JWT 包含：

```json
{
  "sub": "3",
  "iss": "china-war-backend",
  "aud": "china-war-rag",
  "jti": "唯一token编号",
  "ver": 2,
  "role": "editor",
  "iat": 1790310000,
  "exp": 1790311800
}
```

RAG 验证：

- 签名算法；
- `iss`；
- `aud`；
- `exp`；
- `sub`；
- 必要时验证 token 版本。

## 四、问答历史服务端存储

### 1. 当前方式

当前问答历史保存在浏览器 localStorage：

```text
ragv5-session-v3:u1
ragv5-session-v3:u2
```

优点：简单、不需要服务器数据库。

问题：

- 换电脑后历史不存在；
- 清理浏览器数据后历史丢失；
- 同一浏览器脚本可以读取不同 uid 的 key；
- JWT 只能保护问答接口，不能保护浏览器本地历史；
- uid 和 JWT 中的 user_id 没有服务端绑定。

### 2. 服务端存储的含义

在服务器数据库中增加：

```text
rag_sessions
- id
- user_id
- title
- created_at
- updated_at

rag_messages
- id
- session_id
- role
- content
- citations
- created_at
```

请求历史时：

```text
浏览器携带 JWT
→ RAG 从 JWT 读取 user_id
→ 只查询该 user_id 的会话
```

不能接受浏览器自己传来的 user_id 作为权限依据。

### 3. 是否现在必须做

如果项目暂时只是自己或少量内部用户使用，可以先保留 localStorage。

以下情况出现时再改服务端存储：

- 公网多用户；
- 问答内容敏感；
- 需要跨设备同步；
- 需要备份和搜索历史；
- 需要真正防止账号之间读取历史。

## 五、Token 撤销

JWT 通常在过期前一直有效。即使用户修改密码、账号被禁用或 token 被盗，旧 token 仍可能继续使用。

Token 撤销是指：

> 让一个尚未过期的 token 提前失效。

### 推荐方案

#### 1. 缩短有效期

将访问 token 从 7 天缩短到 15–30 分钟。

#### 2. token_version

用户表增加：

```text
token_version
disabled
```

JWT 增加：

```json
{
  "ver": 2
}
```

修改密码、禁用账号或强制下线时：

```text
token_version += 1
```

旧 token 的版本与数据库不一致，立即失效。

#### 3. 黑名单

给 JWT 增加 `jti`，将需要撤销的 jti 存入黑名单。每次请求检查黑名单。

当前项目建议先采用：

```text
短有效期 + token_version
```

## 六、SQLite→Neo4j 补偿队列与 Outbox

### 1. 问题来源

项目同时写两个数据库：

```text
SQLite：主数据
Neo4j：图谱展示和图查询
```

写入流程可能出现：

```text
SQLite 成功
Neo4j 失败
```

结果是管理台有数据，但图谱没有数据。

### 2. 补偿队列

Neo4j 写入失败后记录待办：

```json
{
  "operation": "node_create",
  "node_type": "Person",
  "node_id": 123,
  "payload": {"name": "白起"},
  "status": "pending"
}
```

后台程序稍后重试。这个待办列表就是补偿队列。

### 3. 当前补偿实现仍存在的问题

#### 问题 A：不是事务 Outbox

当前近似流程：

```text
提交 SQLite
→ 调 Neo4j
→ 失败后再写补偿任务
```

如果 SQLite 提交后进程崩溃，补偿任务还没写入，仍然会永久不一致。

#### 问题 B：成功重放后没有回写 neo4j_id

本地临时数据库实测：

```text
重试成功
SQLite.neo4j_id 仍然是 None
```

后续更新和删除仍无法可靠定位 Neo4j 节点。

#### 问题 C：更新可能变成新建

更新失败任务没有保存原 Neo4j ID、旧名称和操作类型，重放时统一按新名称创建/合并节点，可能留下旧节点并创建重复节点。

#### 问题 D：删除和关系不补偿

当前不覆盖：

- 节点删除失败；
- 四类关系同步失败；
- 关系删除；
- 关系修改。

#### 问题 E：没有自动重试

当前只支持人工 API 或 CLI 重放，不是后台自动补偿。

#### 问题 F：重导后旧任务可能失效

知识数据重导后节点 ID 可能变化，但旧 `neo4j_sync_jobs` 仍可能存在，重放会把上一批数据重新写入 Neo4j。

### 4. 正确的事务 Outbox

业务修改和 outbox 任务必须在同一个 SQLite 事务中写入：

```text
BEGIN
修改业务表
写入 outbox
COMMIT
```

后台 worker 读取 outbox 并写 Neo4j。

推荐表：

```text
neo4j_outbox
- id
- dataset_version
- operation
- aggregate_type
- aggregate_id
- graph_key
- neo4j_element_id
- idempotency_key
- payload_json
- status
- attempts
- next_retry_at
- last_error
- created_at
- updated_at
```

`operation` 支持：

```text
node_create
node_update
node_delete
relation_create
relation_update
relation_delete
```

### 5. 使用稳定图谱键

不应长期依赖 Neo4j 内部数字 ID。建议每个节点写入：

```text
graph_key = "Event:123"
```

Cypher 使用：

```cypher
MERGE (n:Event {graph_key: $graph_key})
SET n += $properties
```

这样重试、重建和重命名都更可靠。

### 6. 自动重试

后台 worker 或 systemd timer 定期重试：

```text
30 秒 → 2 分钟 → 10 分钟 → 1 小时 → abandoned
```

监控：

- pending 数量；
- oldest pending age；
- 失败率；
- abandoned 数量。

数据重导前要求 pending 为 0，或者取消旧 dataset_version 的任务。

## 七、飞书机器人队列

### 1. 当前问题

有界队列可以防止内存无限增长，但当前仍有两个问题。

#### 停机死锁

`stop()` 使用阻塞的：

```python
queue.put(None)
```

队列满且 worker 正在执行长任务时，stop 会永久阻塞。本地诊断结果：

```text
stop_thread_alive_with_full_queue = True
```

#### 消息永久丢失

当前顺序是：

```text
先写 processed_events
→ 再尝试入队
→ 队列满后丢弃
```

因为事件已经被标记处理，飞书重投同一事件也会被去重，消息永久丢失。

### 2. 解决方法

worker 使用：

```text
stop_event + queue.get(timeout=0.5)
```

不要用可能阻塞的 sentinel 入队。

事件状态改成：

```text
received
accepted
processing
done
rejected_busy
failed
```

只有入队成功后才标记 accepted。队列满时返回真实繁忙状态，不要返回“正在查询”。

### 3. 会话分片 worker

使用：

```text
hash(session_key) % worker_count
```

保证：

- 同一会话顺序执行；
- 不同会话并发；
- 全局 semaphore 控制 RAG 并发。

监控：queue size、oldest task age、active workers、RAG 耗时、超时与发送失败。

## 八、共享知识库与多租户

### 1. 当前项目是共享知识库

所有用户看到同一套历史战争知识数据。

角色区别：

| 角色 | 权限 |
| --- | --- |
| viewer | 查看 |
| editor | 修改知识数据 |
| admin | 用户管理和全部操作 |

这不是每个用户一套数据库。

### 2. 多租户的含义

多租户是多个学校、公司、团队或项目的数据完全隔离。例如学校 A 看不到学校 B 的数据。

业务表需要增加：

```text
tenant_id
或 workspace_id
```

所有查询按 workspace 过滤。

### 3. 当前是否需要

如果项目目标是所有用户共同维护一套中国战争史知识库，不需要多租户。

应在文档中明确：

> 本系统是共享知识库。账号角色控制操作权限，不提供每账号独立的知识数据。

只有未来面向多个独立机构或多个独立知识项目时才引入多租户。

## 九、旧后端 API 规范

### 1. 当前问题

部分接口：

- JSON 中 `code=400/404/500`，但 HTTP 状态仍为 200；
- 空 JSON 或类型错误可能变成 500；
- 将 `str(e)` 原样返回前端；
- 每个路由手工验证参数，规则不统一。

### 2. 解决方案

建立统一错误响应：

```json
{
  "code": "NODE_NOT_FOUND",
  "message": "节点不存在",
  "data": null,
  "request_id": "..."
}
```

HTTP 状态统一：

| 情况 | HTTP |
| --- | ---: |
| 参数错误 | 400 |
| 未登录 | 401 |
| 无权限 | 403 |
| 不存在 | 404 |
| 冲突 | 409 |
| 限流 | 429 |
| 内部错误 | 500 |
| 下游服务不可用 | 503 |

用 Pydantic 定义请求 schema，使用 Flask 全局 error handler。内部异常写日志，对客户端只返回安全错误信息。

## 十一、登录和注册安全

当前 `/api/login` 和 `/api/sign_in` 没有完整的限流和账号锁定。

正式公网部署前建议：

1. 同 IP 登录限制，例如 10 次/分钟；
2. 同账号失败 5 次锁定 15 分钟；
3. 生产关闭自由注册，改成管理员邀请或邀请码；
4. 密码长度提高到 10–64；
5. 修改密码时增加 token_version；
6. 记录登录成功、失败、提权与降权审计日志。

单机可以先用 SQLite 计数，多实例时使用 Redis。

## 十三、py2neo 与 Neo4j 官方 Driver

### 1. py2neo 的作用

py2neo 是第三方 Python Neo4j 客户端，当前旧后端使用它：

```python
from py2neo import Graph
```

它负责连接 Neo4j、执行 Cypher、返回节点和关系。

问题是 py2neo 已长期不维护，对现代 Python 和 Neo4j 的长期兼容性风险较高。

### 2. Neo4j Driver 的作用

Neo4j Driver 是 Neo4j 官方 Python 客户端：

```python
from neo4j import GraphDatabase
```

作用与 py2neo 相同，但由 Neo4j 官方持续维护。

建议增加适配层：

```text
backend/neo4j_client.py
```

业务代码只调用项目自己的：

```text
create_node
update_node
delete_node
run_query
```

适配层内部使用官方 Driver，避免业务代码直接依赖驱动细节。

## 十四、Python 环境统一方案

### 1. 结论

可以统一，推荐先统一到：

```text
Python 3.11
```

暂时不需要升级 Python 3.12。

当前两个环境的主要差异：

```text
Python 3.8：backend + entity-event-relation
Python 3.11：RAG + feishu-bot
```

主要历史阻塞是 py2neo，不是 Flask 或抽取代码本身。

### 2. 为什么选择 3.11

- RAG 已在 3.11 通过 389 项测试；
- 飞书机器人已在 3.11 通过 289 项测试；
- Chroma 已在 3.11 使用；
- 抽取包声明支持 `>=3.8`；
- backend 代码没有必须依赖 3.8 的核心语法；
- 当前已有稳定的 3.11 环境。

### 3. 为什么暂不升级 3.12

直接升级 3.12 会同时引入：

- 新 Python 版本；
- Chroma 原生依赖兼容；
- lark-oapi 兼容；
- py2neo 兼容；
- RAG 锁文件重建。

建议先完成 3.11 统一，再单独建立 3.12 CI 实验矩阵。

### 4. 开发与生产环境建议

开发机可以使用一个统一环境：

```text
china-war
Python 3.11
```

安装 backend、RAG、feishu-bot、war_extraction 和测试依赖。

四个模块仍然是不同进程，不是合成一个程序。

生产环境可以选择：

- 一个 Python 3.11 环境，适合单机小规模部署；
- 同一 Python 3.11 版本、按服务拆虚拟环境或容器，适合正式生产。

重点是统一 Python 版本；生产是否共用一个 `.venv` 可以根据运维方式决定。
