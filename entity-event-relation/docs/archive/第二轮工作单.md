## 2. A 组：上一轮收口后仍未闭合

### A1 枚举外计数只在最后一道收敛处有出口

**现象。** `reduce_event_event_relations` 在枚举外类型上的行为已经是"保留 + 可选计数"（`war_extraction/utils/relation_rules.py:208-222`，`if quarantine is not None: quarantine.append(rel)`）。四处调用点里**只有一处传了 `quarantine`**：

| 调用点 | 传 `quarantine` |
| --- | --- |
| `main.py:768-772`（最终清理） | **是** |
| `war_extraction/extractors/relation_extractor.py:402` | 否 |
| `war_extraction/extractors/relation_extractor.py:486` | 否 |
| `war_extraction/processors/result_merger.py:379` | 否 |

**关键澄清（别误判）**：**数据不会丢**——枚举外条目无论有没有 `quarantine` 都留在返回值里，`quarantine` 只是"这批有多少条"的计数通道（见该函数 docstring `:176-184`）。所以这不是 bug，是**口径没定**。

**要改成什么（二选一，建议选 ②）。**

- ① 三处也传 `quarantine`：必须在同一段里去重，否则同一条会被数多次（该条可能同时出现在抽取器输出与合并输出里，`main.py` 那道又是第三遍），计数会偏大。
- ② **明确"只在最后一道收敛（`main.py`）计数"**，在 `relation_rules.py` 的 docstring 与三处调用点各加一行注释说明"中间环节不计数，避免重复计数；要看总数就看质量报告的 `event_event_relations_outside_enum`"。

**验收。** 选 ② 时：注释到位；`test_枚举外的事件事件关系会进候选区` 等既有用例保持通过。选 ① 时：新增用例，构造"同一条枚举外关系经过三次收敛"，断言最终计数为 1 而不是 3。

**风险。** 这条容易被下一个人误读成"没传 quarantine = 丢数据"（本轮复核一开始就这么误判过），所以选 ② 时**注释必须写明"为什么看起来该传却没传"**。

### A2 门禁"枚举外关系名"不扣已知例外

**现象。** `_GATE_PATHS` 里该项是四类 `outside_enum` 直接求和，**不减** `KNOWN_ENUM_EXCEPTIONS`：

```python
("枚举外关系名", lambda r: sum(len(r["enum_values"][key]["outside_enum"]) for key in RELATION_CATEGORIES)),
```

而 `KNOWN_ENUM_EXCEPTIONS` 登记了 `event_organization_relations/指挥所`（1 条、有意不修），且只在 `print_report` 里被点名，不影响门禁值、也不影响 `compare_with_baseline`。结果是这个门禁项**恒 ≥ 1**——与它上方注释"一个永远非零的门禁项会让下一个人反复去查同一件事"自相矛盾。

**要改成什么。** 门禁值扣掉已登记的例外，同时保留"点名"输出：

```python
("枚举外关系名", lambda r: sum(len(r["enum_values"][key]["outside_enum"]) for key in RELATION_CATEGORIES)
                             - _known_exception_count(r)),
```

其中 `_known_exception_count` 按 `KNOWN_ENUM_EXCEPTIONS` 的 `"类别/取值"` 键去扣（扣之前要确认该取值确实在报告里，避免把"已消失的例外"也扣掉）。

**验收。** 体检输出里"枚举外关系名"变成 **0**（当前唯一一条是已知例外）；`--baseline` 仍能比增减；新增用例：伪造一条**未登记**的枚举外取值，断言门禁值 +1 而不是被扣掉。

**风险。** 扣减逻辑若写成"减 `len(KNOWN_ENUM_EXCEPTIONS)`"这种硬减，将来新增真实问题时会被误扣——必须按键匹配。

### B3 悬空边：空名/空关系被丢但不计数

**现象。** `main.py:733-741` 的 `_drop_dangling`：

```python
if not rel.EventName or not rel.relation:
    continue                                     # ← 丢，但不计数
if not _event_allowed(rel.EventName):
    dropped_dangling[attribute] += 1             # ← 计数
    continue
```

而该函数 docstring 承诺"丢掉事件端对不上最终事件名单的边，**并计数**——悬空边数要能被体检脚本与质量报告看见"。空名/空关系这一支是**无痕丢弃**——正是本项目反复吃亏的那个模式。

**要改成什么。** 在 `dropped_dangling` 里加一个分项键（如 `"empty_name_or_relation"`）并计数；或退一步把 docstring 改成"空名/空关系不计入悬空边（它们不是悬空，是残缺）"。**建议前者**，因为"残缺"也该被看见。

**验收。** 新增用例：构造一条 `relation` 为空的关系，断言计数增加且该条不在产物里。

### B4 diagnostics 为空时早退，连带把 `text_cleaning` 变成 null

**现象。** `main.py:918-920`：

```python
diagnostics = dict(getattr(run, "diagnostics", None) or {})
if not diagnostics:
    return                                        # ← 早退：text_meta 也没挂上
```

`text_meta`（`{"text_cleaning": …}`）与 `extraction_diagnostics` 是**同一次挂载**。所以一旦 diagnostics 为空，`text_meta` 也不会写进 `events.metadata`，随后 `_artifact_body` 的 `pop("text_cleaning", None)` 取到 `None`，顶层 `metadata.text_cleaning` 就**静默变成 null**——用的是"看起来正常、实际没记录"的表现形式。

当前 `run_extraction` 恒返回带键的 diagnostics，所以只是**潜在**缺陷，但这条链有一个无提示的失效口。

**要改成什么。** 把两件事解耦：先挂 `text_meta`（只要它有值），再按需挂 `extraction_diagnostics`：

```python
if not diagnostics and not text_meta:
    return
```

**验收。** 新增用例：让 `run.diagnostics` 为空但带 `text_meta`，断言产物顶层 `metadata.text_cleaning` 非 null。

### B5 `by_category` 与整体不是同一次匹配

**现象。** `evaluate_relations` 里跑了两遍匹配：整体用 `filter_relations`（并集，`:1043`），分类用 `filter_relations_by_category` 分桶各自跑（`:1073`）。两者结果**对不上**（实测 `evaluation/run_20260926_after3/results.json`）：

| 整体 `counts` | **806** | **4557** |
| `by_category` 四类之和 | **803** | **4560** |

差 3 条。成因是并集匹配时不同类目的预测会**竞争同一条 gold**，分桶匹配时各自独立认领。现有的 `test_分类容器与选值口径一致` 只断言"过滤容器一致"（`by_category` 的条目并起来等于 `filter_relations` 的条目），**没覆盖匹配结果的差异**。

**要改成什么（二选一，建议 ①）。**

- ① **一次匹配、按类目切分**：用并集那次匹配的结果，给每条预测关系打上类目标签，再按类目汇总 TP/FP/FN。这样 `summary.relation_f1` 与 `by_category` 可互相校验。
- ② 明确"两者口径不同、不可互相印证"，并在报告里加一行提示；同时把 `by_category` 的分母含义在文档里写清。

**验收。** 选 ① 时：新增断言"四类 TP 之和 == 整体 TP、四类 FP 之和 == 整体 FP"；现有 `test_分类容器与选值口径一致` 保留（它管过滤，新用例管匹配）。选 ② 时：报告与文档都写明不可互证。

### B7 `evaluate.py` 的 `candidate_path` 指向 `published/final.json`

### C1 发布过滤丢掉整类事件-事件关系（本轮唯一建议动手的一项）

**现象。** `main.py:424-434` 的 `is_high_confidence_event_event_relation`：

```python
if relation == "因果关系":
    return any(token in evidence for token in ["因此", "于是", "导致", "引发", "致使", "造成"])
if relation == "顺承关系":
    return all(name and name in evidence
               for name in [rel.EventName_A, rel.EventName_B])
return relation == "并列关系"          # ← 兜底：除这三类外一律 False
```

于是五个规范类型里有**两个永远返回 False**：`包含关系` 与 `条件关系`。实测（同一份产物）：

| | 顺承关系 | 因果关系 | 并列关系 | 包含关系 | 条件关系 |
| --- | ---: | ---: | ---: | ---: | ---: |
| raw `9_final_all.json` | 798 | 40 | 47 | **28** | **1** |
| published `final.json` | 11 | 25 | 41 | **0** | **0** |

而 `published/final.json` 是下游 SQLite / Neo4j / RAG 的输入——也就是说**这两类关系在知识库里根本不存在**，不是"少"，是"没有"。

**要改成什么。** 给 `包含关系` 与 `条件关系` 各自一条可验证的证据规则，而不是靠兜底 False：

- `包含关系`（父事件包含子事件）：可判"两个事件名在证据里同时出现，且时间区间存在包含关系"，或退一步用 `包含/隶属/属于/其中` 一类线索词；
- `条件关系`：线索词（`如果/若/一旦/前提/条件`）；
- 若一时定不出规则，**至少**把兜底改成"这三类之外的规范类型按『证据非空 + 类型合法』放行"，让它们有机会进入 published，把"信任门槛"交给后续的评估。

**动哪里。** `main.py` 的 `is_high_confidence_event_event_relation`；若规则依赖时间区间，需要把事件的起始/结束年份传进来（该函数当前只看 `evidence` 与两个事件名，签名要扩）。

**验收。** 新增用例：构造一条 `包含关系` 与一条 `条件关系`（各带合证据），断言它们出现在 `published/final.json`；再构造一条证据为空的，断言仍被挡。

**风险（重要）。** 改这个函数 = **改整个知识库的内容**（总方案 3.6 节）。所以：**本轮只改函数 + 加用例**，让它随 E 组的产物换代、SQLite 重导、Neo4j 重同步、RAG 快照重建**打包发布**。单独改这个函数而不发布，只会让 `published/` 与库里的数据不一致。

## 7. 不要破坏什么

这些是第一轮/上一轮已经做对、且有测试钉住的，改本轮任何一项时都不要回退：

1. **评估的可复现性**：`match_relation_triples` 先按内容定序再贪心匹配；不要用固定 `PYTHONHASHSEED` 掩盖顺序依赖。
2. **规范事件-事件关系类型要求精确相等**（`relation_types_match`）：五个类型两两 `fuzz.ratio` 都是 50，退回纯模糊会让类型判错也拿满分。
3. **gold 侧按集合去重、pred 侧按条计数**这个不对称是**有意设计**（标注侧 21 条完全重复关系是标注缺陷），有断言钉着（`test_标注侧仍按集合去重`）。B5 只能改**匹配次数**，不能改这个不对称。
4. **枚举权威表是唯一来源**：下游一律引用 `war_extraction/utils/vocabulary.py`，不再各抄一份；`test_enum_synchronization.py` 直接读前端 `.vue`、RAG `field_map.py`、导入脚本三份文件比对，改一处漏一处它就会红。
5. **派生关系的"同句证据"不变式**：传进规则函数的 `sentence` 由 `_entity_sentence` 保证含该实体名，规则里只判线索词；线索词优先用连写形式或两字以上短语（单字命中率过高）。
6. **关系阶段降级不写缓存**（`RelationStageDegraded`）：数据不丢、失败可见、可重试三条同时成立，别改成"静默返回降级结果并记为成功"。
7. **缓存键的因子只增不减**：`CACHE_CONFIG_FILES` 刻意不含 `eval_config.json`（调评估阈值不该让整本缓存失效）；把 B 组任何一项涉及的配置加进去之前想清楚要不要付重跑钱。
