## 1. 先理解"参考集"是什么

参考集就是一套**人工核验过的标准答案**：对某段原文，明确列出"这里一共有哪些事件、哪些实体、
它们之间有哪些关系、每个字段该填什么"。评估时把它与模型的抽取结果比对，算出精确率与召回率。

**它为什么必须人工做**：如果标准答案也是模型生成的，那"模型对不对"这件事就没有参照——
只会得到"两个模型不一致的地方在哪"。这个项目当前正卡在这里。

**它现在的状态**（必须知道的四件事）：

1. 三份文件放在 `data/annotations/`：`sample_events.json`（323 条事件）、
   `sample_entities.json`（地点 406 / 人物 506 / 组织 279 行）、`sample_relations.json`（四类共 1,766 行）。
2. **它不是人工标注**：据项目负责人说明，是"几个人用不同模型把整本书分成几份、每个模型负责两份，
   最后把各份结果汇总"，**字段没有做人工处理**直接当标注用。
3. **因此它有一批结构性问题**（体检脚本 `tools/artifact_health_check.py` 的 `annotations` 段每次都会报）：
   关系的 `head` 不在事件表（`event-place` 230 / `event-org` 136 / `event-person` 183 / `event-event` 56）、
   `tail` 不在对应名单（194 / 106 / 180 / 69）、实体重复行（地点 28 / 组织 37）、
   事件日期里有 1~3 位残缺年份 14 处、21 条完全重复的事件-事件关系。这些关系在评估时**根本不进分母**，
   所以"关系召回率"的分母比文件看起来的小。
4. **它还能用来干什么**：当词表（书里真实存在的名称）、当别名表来源（`config/aliases.json`）、
   当回归与可复现性检测的参照。**不能用来干**：当精确率/召回率的分母。
   > 注：`data/annotations/README.md` 现在写的是"只有一名标注者、没有 IAA"，与上面第 2 条的
   > 实际情况不一致；那处更正**待标注所有人确认**后再改（别顺手改）。

| # | 交付物 | 具体形态 |
| --- | --- | --- |
| 1 | 事件表 | 每条事件一个**稳定 ID**；身份 = 名称 + 朝代 + 起始时间 + 地点（现在四处口径不一致，见整改方案 阶段 1 第 1 项）；字段与 `sample_events.json` 一致（含 `Person`/`Scale` 这类历史命名，**不要顺手改名**，改名要连评估器一起动） |

| 3 | 关系表 | 每条 `head / relation / tail`，**并且 head 必须在事件表里、tail 必须在对应实体表里**（旧 gold 的最大结构性缺陷就是这条不成立） |
| 4 | 证据与坐标 | 每条事件与关系都带**原文 evidence + 章节 + 字符区间**。这是"可审计"的全部意义：没有它，改标注、复现指标、判"这条到底对不对"都无从下手 |
| 5 | 数据集切分 | **development / test** 两份：调提示词与阈值只看 development，**test 最后一次使用**（用一次少一次） |
| 6 | 两份记录 | ① **IAA**（至少一部分数据由两人独立标注、算出标注者间一致率并仲裁）；② **旧标注判定实验**的结论（见下面第 4 节第 0 步） |

**格式**：沿用现有三份 JSON 的文件名与字段（评估器 `optimal_evaluator.py` 直接读它们），
新增字段只增不改（评估器忽略不认识的键）。**新老并存**：重建期间旧文件保留，

这样"换参考集"和"改评估口径"两件事不会被绑在一起。

## 3. 开工前必须定的口径（不定就会各判各的）

   具体战役（"三峰山之战"）**算**、迁都会盟这类非军事事件**不算**；子事件**平铺**为独立事件、

2. **事件身份**（已定）：名称 + 朝代 + 起始时间 + 地点。同名不同年代的事件**各记一条**。

```text
   按朝代或章节切（不随机按条切，否则会出现"测试集的关系、其事件在开发集"的泄漏）
   python tools/freeze_baseline.py     → 记产物/标注/配置/提示词的 sha256 与本次 git 提交

⑧ 跑通评估                             机器
   python evaluate.py                  → 在 development 上
   python tools/diff_annotation_sets.py --old data/annotations --new data/annotations/v2
   → 至此解锁：E4 的 gold 补标、E5 的 few-shot、以及那次"攒批重跑"
```

**一个必须存在的回环**：③ 里一定会撞到"口径没写清"的地方（例如"这条算不算过宽概括"）。
**别各判各的**——停下来把结论写进 ① 的口径文档、补一个真实样例，再继续。
这是"不同人判出同一批数"的唯一保障。

**增量性**：子集之间独立，先做完的那个可以先冻结、先解锁重跑（当时就是按这个把明当 dev 的）。
**注意 dev/test 的划分不是一次定死的**：划分依据是「dev 要够大到判得动差异」，三块齐了之后就该重看
一遍（2026-09-27 就换成了 dev = 唐 + 秦汉）。

### 第 0 步：旧标注判定实验（半天，先做这个）

抽 **30~50 条**旧 gold 的条目，回原文核验，统计"正确 / 漏标 / 错标 / 无法判断"。
用一个数字决定：旧标注是**可修**（在它上面改）还是**只能当词表**（推倒重标）。

- 抽样与定位直接用现成工具：`tools/sample_for_review.py`（分层随机 + 稳定定位键）
  + `tools/expand_review_context.py`（把上下文换成**原文**那一段并标出证据位置）。
- 判定口径用 [`抽样判定规范.md`](抽样判定规范.md) 的三档与固定前缀——**B 组刚用同一套判过 350 条**，
  口径是热的、可直接复用。
- 顺带产出：旧 gold 的**错误类型分布**（漏标多还是错标多？粒度不一致占多少？），
  它决定第 3 步要把力气花在"补漏"还是"纠错"。

### 第 1 步：定口径、写样例（半天）

把第 3 节的口径连同**每条口径 2~3 个真实样例**写成一份短文档（就加在 `data/annotations/README.md` 里），
样例比定义有效——判的人遇到分歧时看的是样例。

### 第 2 步：跑出草稿（本地，几十分钟，花费很小）

不要让人从零开始读原文。先用现有抽取链把该子集跑一遍，得到**候选**事件/实体/关系，
人工只做"核验 + 增删改"：

```bash
cd entity-event-relation
python main.py data/dynasty_subsets/明.txt        # 草稿（明子集 13 段 × 3 阶段 = 39 次调用，成本很小）
python tools/expand_review_context.py --sample <草稿抽样>   # 若需要，把上下文换成原文
```

**注意**：草稿只是"待核验的候选"，**评级不看它**——否则又回到"模型对模型"。

### 第 3 步：逐条核验（主要工作量，可分批）

按原文逐条做四件事：**判**（留 / 删 / 改）、**补**（漏掉的补上）、**填证据**（原文句子 + 字符区间）、
**判字段**（时间/地点/主动方/结果/归属/角色）。判定口径与写法照 `抽样判定规范.md` §5 的逐字段规则。

- 顺序建议：**先事件，再实体，最后关系**——关系依赖前两者的名单（旧 gold 最大的毛病就是关系先写了、
  事件表里却没有）。
- **一律回原文**，不要只看草稿给的证据句（B 组的经验：`崤底之战` 的年份写在**前一段**，
  只看证据段会冤枉它）。
- 拿不准就标"无法判断"并写清卡在哪，**不要硬判**（判不准的比例本身是要报出去的数）。

### 第 4 步：双人复核与 IAA（至少覆盖一部分）

抽一部分（如 20%）由第二个人**独立**标一遍，算一致率；不一致的逐条仲裁并把结论写进口径文档。
IAA 的作用不是"证明标得对"，而是给出**这套标注自身的噪声上界**——没有它，"指标 25% 是模型差
还是标注差"永远说不清。

### 第 5 步：切 development / test 并冻结

按朝代或章节切两份（**不要随机按条切**：同一场战役的事件与关系要落在同一边，否则会出现
"测试集里的关系，其事件在开发集"这种泄漏）。冻结时记录：

- 文件指纹（`python tools/freeze_baseline.py`）、原文版本与清洗统计、
  切分边界、当时的 git 提交。

### 第 6 步：跑通评估并出第一组可信指标

```bash
python evaluate.py --output <仓库外临时目录>          # 在 development 上
python tools/artifact_health_check.py                 # 新参考集的结构问题应为 0（head/tail 违规、残缺年份）
```
第一条验收：**head/tail 违规 = 0、残缺年份 = 0、完全重复 = 0**（旧 gold 分别是 605 / 549 / 22 / 14）。
若这几项不为 0，说明第 3 步没做干净。

**三条省力的办法**（都已在流程里）：

1. **先判事件**（351 行）：事件是"分母里的分母"，而且实体与关系的名单都依赖它——

2. **草稿未定位的那 12%** 里，关系那部分多半是**多余关系**（目标实体不在头事件的叙述里，
   正是 E2 要收紧的那类）——批量判"删除"比逐条找原文快得多。
3. **子集之间独立**：先做完的那个可以先冻结、先解锁阶段三那次重跑；
   三个子集也可以分给不同的人并行（但**先一起判 20~30 行对齐口径**，否则各判各的）。

## 7. 纪律（动参考集等于动分母）

1. **改参考集必须留档**：改前改后各跑一次 `evaluate.py`，逐字段对照（除 `metadata.evaluated_at`），
   差异要有解释；再用 `tools/diff_annotation_sets.py` 出一份逐条 diff（机械证据）；
   在 [`../../../docs/项目审查与修复历史.md`](../../docs/项目审查与修复历史.md) 记一笔。
   这条写在 `data/annotations/README.md` §四，**已经吃过一次学费**（"产物换代被当成匹配抖动"）。
2. **参考集不进下游**：`import_json_to_sqlite.py` 从不读标注，所以重建期间不影响线上数据。
3. **别为了让指标好看而放宽参考集**：口径是给"预测侧与参考集两侧"定的，只在一侧放松等于自欺。
4. **新旧参考集并存**，用开关切换；不要就地覆盖（否则旧指标无法复现）。
5. **别手改 `annotation_id`**：它是内容派生的（名称 + 朝代）。改名称后要重算，
   `diff_annotation_sets.py` 会把"存量 ID 与现算不一致"单独报出来——那是提示"这条的名称被改过"。
