## 0. 结论摘要

八条，按重要性排序。只读这一节也能知道该怎么决策。

1. **当前三个 F1 都不能直接当"模型准确率"读**：实体 20.42%、事件 41.75%、关系 71.87%、宏观 44.68%（实测）。其中实体是"精确率极低、召回率极高"（P=11.50% / R=90.67%），关系是"分母被系统性剔除"（见第 4 条）。
2. **被评估的产物验证不了当前代码**。产物由 2026-08-18 的提交 `133a9aa` 生成（`metadata.prompt_version = prompt-v2-20260420`），此后**后处理与评估代码改过多轮**（`main.py` 6 次、`relation_extractor.py` 7 次、`result_merger.py` 3 次，都在产物生成之后）。但要说清一点：**提示词文本本身从未改过**——三份 `prompts/*.py` 的 blob 哈希自初始提交至今完全相同（见 2.5）。所以现在这些分数评的是旧产物，且执行重跑要全额重新付费（196 条缓存全部失效）。原旧文档与模块 README 把这件事说成"提示词改过、效果未验证"，那是**不准确**的。
3. **低分是四类原因叠加**，不是单一原因：① 抽取侧真实过抽取与规则派生过量；② 参考标注漏标、重标、粒度不一致——而且据说明这批"标注"本身是**多模型分片产出后直接汇总、未经人工处理**的结果（见 2.4.1），所以当前指标测的其实是模型之间的分歧；③ 评估器有具体实现缺陷（宽松配对、循环过滤、身份口径不一致）；④ 产物与当前后处理/评估代码错配（2.5.1）。把低分整体归因于"模型没训练/微调"是**不成立的**——本模块根本没有训练环节（见第五节）。
4. **关系 F1 71.87% 是虚高的**。评估先把 18,146 条预测关系过一遍 gold，只有"已经像某条 gold"的 888 条进入精确率计算，其余 17,258 条不计 FP。去掉这道预过滤后复算：参与评估的预测关系 5,415 条，P=16.18%、R=79.71%、**F1=26.90%**。
5. **实体低分里有相当一部分不是模型错**。只把预测地点按名称去重（不动任何模型输出），实体 F1 就从 20.42% 升到 26.98%。原因是两侧**身份口径本来就不一致**：预测侧按"名称 + 朝代 + 现代地名"保留同名多行（洛阳 40 行、长安 33 行），评估侧把 gold 压成名称集合后逐行判 FP。
6. **提示词确有可修的具体缺陷**，但要精确定位，不是"写得不好"：人物/组织角色枚举自相矛盾（提示词里出现了枚举外的 `关键人物`）、`FULL_EVENT_PROMPT` 输出模板缺 `id` 字段导致事件名映射静默失败、关系 evidence 允许填"事件描述"与"必须是原文句子"自相矛盾。
7. **改抽取之前必须先看第三节**。下游 `backend/`（SQLite 导入、Neo4j 同步、在线抽取接口）、`frontend/`（4 个 CRUD 页 + 图谱筛选下拉）、`RAG/`（快照导出、图谱检索白名单）、`deploy/` 都依赖产物的**具体键名与枚举取值**。其中大量依赖是**静默的**——改错了不报错，只表现为"某一类数据变成 0"或"数字变了"。
8. **正确的顺序是：先固化基线 → 再重建评估口径 → 再修评估器 → 再修抽取与后处理 → 最后才付费整本重跑**。先重跑后修评估，钱花了仍然得不到可信结论。**已定的 6+3 项取舍见第 10 节决策记录。**

### 0.7 E 组第一处落地（E2：`Commanders` → `将领`，2026-09-27）

#### 2.4.1 标注的来源（据项目负责人 2026-09-26 说明，**与 `data/annotations/README.md` 的表述不一致**）

`data/annotations/README.md` 写的是"只有一名标注者、没有 IAA"，但据说明，实际制作过程是：

> 几个人用**不同的模型**把整本书分成几份，每个模型负责两份，最后把各份结果**汇总**起来，**字段没有做人工处理**，直接作为标注数据使用。

这条信息**改变了 2.4 节全部数字的解释**，必须写进文档：

1. **当前"gold"不是人工标注，而是另一批模型的输出**。因此第 2.1 节的指标实际测的是"模型 A 的产出"与"模型 B/C/D 汇总产出"之间的**分歧**，而不是"抽取对不对"。实体精确率 11.50% 里有相当一部分是**模型之间的口径差异**，不是抽取错误。
2. **2.4 节那些结构性缺陷有了统一解释**：`head` 大量不在事件表、21 条完全重复关系、同名多行、命名风格不统一——这正是"多模型分片产出后直接拼接、没有做实体与事件对齐"的典型特征。它们不是标注者的疏漏，而是**汇总环节缺失**。
3. **结论要更硬**：这批数据连"人工参考集"都算不上，只能算**多模型输出的合并结果**。在它被人工逐条核验之前，任何基于它的指标（无论高低）都不能作为抽取质量或模型能力的证据。
4. **`data/annotations/README.md` 的表述需要更正**（该文件现在会让后续接手的人误以为存在人工标注）。这项更正留给标注所有人确认措辞后再做——本文只记录事实与影响。

由此还得到一个可执行的诊断项：既然 gold 是多模型产出，那么"预测侧大量 FP"需要用**原文**而不是 gold 来判定（抽出来的实体在原文里到底有没有出现）。这是唯一不依赖 gold 的质量检验，见 4.1 节第 1 条与附录 A 的复现说明。

#### 2.5.1 一处需要更正的事：提示词文本从未改过

那版本串为什么变了？因为**派生机制是后来才加的**。可查的时间线：

| 提交 | 日期 | `config.py` 里的 `PROMPT_VERSION` |
| --- | --- | --- |
| `a0e4c63` | 2026-08-17 | `"prompt-v2-20260420"`（硬编码） |
| `133a9aa` | 2026-08-18 | `"prompt-v2-20260420"`（产物生成于此） |

| `7c1f862` | 2026-09-25 | 改为 `f"{_PROMPT_BASELINE}+{prompt_source_hash()}"` → `prompt-v2-20260420+a1fb7839` |

**后果（可操作）**：`cache/cache_index.json` 的 **196 条记录全部写着 `context.prompt_version = "prompt-v2-20260420"`**（不带哈希），与 `7c1f862` 之后的派生值不相等，因此**这 196 条缓存全部不命中**。重跑整本将重新调用模型 196 次（196 条缓存条目全部是 `stage = long_text_chunk` 的分段调用），等于全额付费——**尽管提示词一个字都没改**。注意不要用"改回版本串"的方式强行复用：缓存里存的是**过后处理链的结果**（含规则派生关系），而后处理代码此后改了多轮，强行复用会把旧的派生关系一并带回来。

**顺带更正一处陈旧表述**：模块 `README.md` 说"整理时筛掉了 392 条旧条目，保留当前版本的 196 条"。那次筛选在 2026-09-21 做，当时 `PROMPT_VERSION` 还是不带哈希的硬编码值，所以判断没错；但 `7c1f862`（2026-09-25）引入派生机制后，这 196 条也一并失效了。也就是说**缓存目录里的条目现在是清一色的死条目**（约 22 MB），"保留当前版本"这句话已经不再成立。

### 2.6 指标怎么算的、上限在哪里

三个指标都是标准的准确率/召回率/调和平均，**没有"最高只能到多少"的固定限额**，但本项目当前口径下它们的**实际可达上限远低于 100%，而且不可知**。逐层算一遍（数字取自 2.1 的实测）：

```text
P  = TP / (TP + FP)          分母是"预测侧"
R  = TP / (TP + FN)          分母是"参考侧"
F1 = 2PR / (P + R)  等价于   2TP / (2TP + FP + FN)
```

| 层 | TP | FP | FN | P = TP/(TP+FP) | R = TP/(TP+FN) | F1 = 2TP/(2TP+FP+FN) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 实体 | 1,021 | 7,854 | 105 | 1021/8875 = 11.50% | 1021/1126 = 90.67% | 2042/10001 = 20.42% |
| 事件 | 281 | 745 | 39 | 281/1026 = 27.39% | 281/320 = 87.81% | 562/1346 = 41.75%（见注） |
| 关系 | 714 | 174 | 385 | 714/888 = 80.41% | 714/1099 = 64.97% | 1428/1987 = 71.87% |

> 注：事件层 `P` 的分母是 1,026，而预测的唯一事件名是 1,028——差 2 条。原因是 `evaluate_events` 用 `fp = len(pred_names) - len(event_mapping)` 算 FP（`optimal_evaluator.py:479`），而那 2 条被映射到了"不在 gold 事件名单里的名字"，于是既不算 TP 也不算 FP。数值影响很小，但引数时要知道分母不是预测总数。

**为什么实际达不到 100%，有四个机制：**

1. **P 与 R 在这份参考集上是结构性对立的**。P 的分母是预测条数、R 的分母是参考条数（实体层：`TP+FP` = 8,875 行预测，`TP+FN` = 1,126 个参考名称）。参考集只覆盖原文里一部分合法内容，所以模型若想提高 P，唯一办法是**少抽**（只抽参考集里有的那些），必然放弃其余真实存在的实体；若想提高 R，就必须把参考集之外的合法实体也抽出来，P 必然下降。实体层 P=11.50% / R=90.67% 正是这个结构的产物——**能同时达到的水平由参考集的完整性决定，不由模型决定**。
2. **两侧身份口径不对称**：预测侧逐行计数（地点 5,316 行），参考侧压成名称集合（378 个）。同名多行必然记 FP。这是纯口径造成的分数损失：实证只把预测地点按名称去重（不动模型输出），实体 F1 就从 20.42% 升到 26.98%。
3. **匹配阈值决定 P/R**，它们不是数据的固有属性。事件相似度阈值从 0.35 提到 0.90，召回率从 87.81% 掉到 49.06%、F1 从 41.75% 掉到 23.31%——同一份产物，换个"尺子"就能得到完全不同的数。
4. **关系层的分母是浮动的**：gold 三元组只保留"head 能被映射到预测事件"的关系，阈值一变，进入分母的 gold 就从 1,099 变成 695。跨版本比较因此没有意义。

**三条结论**：

1. 在修好参考集与口径之前，**"离上限还有多远"是不可知的**，所以不能拿 F1 的高低排优先级（关系 71.87% 看起来最高，实际最不可信）。
2. **不要以 100% 为目标**。对知识图谱这类下游用途，**精确率比召回率重要得多**——抽错的实体与关系会进库并被问答引用，而缺失的信息只是"没有"。合理的做法是分别给 P 和 R 定目标（例如进图谱的关系要求 P 高、R 可以低），而不是追一个综合 F1。当前关系层恰好相反：P 被评估方法虚高到 80.41%，真实约 16.18%。
3. **报告指标时必须同时给出口径**：预测文件哈希、参考集版本、四个阈值、评估器版本。同一份产物在不同阈值下的 F1 差 18 个百分点，只说一个数没有意义。

#### 2.6.1 100% 是可达的——这正是它的危险之处

**让抽取结果恰好等于参考集，P=R=F1=100%。** 不需要模型更聪明，只需要输出那 1,126 个实体名、320 个事件名、1,099 条关系，不多不少。

所以必须记住：**这项指标衡量的是"与参考集一致的程度"，不是"与史实相符的程度"。** 推论有三条：

1. 100% 可达 ≠ 正确。一个学会"照抄参考集"的实现能拿满分而毫无价值。
2. 当前 44.68% **不代表"离能力上限还差 55 个百分点"**，它只表示"与这份参考集的一致程度是 44.68%"。
3. 换一份参考集（例如未来人工核验的子集），同一份产物会得到完全不同的 F1。那时分数变了，**模型并没有变**。

因此 **F1 回答不了"模型差不差"这个问题**——要回答它，只能用抽样人工精确率（把"正确"定义为"与原文相符"，见阶段 1 附）。

#### 2.6.2 给定参考集，理论上限可以算，但需要先知道参考集的完整度

设 `G` = 参考集条目数（实体 1,126 / 事件 320 / 关系 1,099），`T` = 原文里真实存在的合法条目总数（未知，且 `T ≥ G`），参考集完整度 `c = G / T`。

- 若目标只是**最高 F1**：最优策略是只输出 `G` 里的条目 → F1 = 100%（这就是 2.6.1 说的照抄）。
- 若目标是**覆盖原文的真实内容**（这才是产品要的）：模型必须输出 `T` 条，其中 `G` 条命中、`T − G` 条落在参考集之外，于是

```text
精确率上限 = G / T = c
召回率上限 = 100%
F1 上限    ≈ 2c / (1 + c)
```

代入感受一下量级：实体层若 `c = 0.5`，F1 上限 ≈ 66.7%；若 `c = 0.15`，上限只有约 26%。**当前实体 F1 20.42% 到底是"离满分很远"还是"已接近天花板"，完全取决于 `c`，而 `c` 当时未知**——这就是"必须先重建参考集"的定量理由。

`c` 是可以估出来的，而且正落在阶段 1 附的抽样工作里：在抽样核验中，统计判为"正确且在参考集内"的条数 `a`、"正确但参考集外"的条数 `b`，则

```text
c ≈ a / (a + b)
```

抽样一次就能同时得到"抽样精确率"和"参考集完整度"，两个数都是后续判断的基准。

> **第一次实测（B 组判定完成后，见 §0.6）**：事件层 `c ≈ 28.1%`、实体层 `≈ 21.4%`、关系层 `≈ 4.9%`。
> 套进上面的公式，实体层 F1 上限约 `2c/(1+c) = 35%`，而当前是 20.42%——**离天花板不远了**，
> 这与"参考集只覆盖了原文的一小部分"是同一件事的两面。
> **有一条口径必须记牢**：`a`/`b` 要按**指标实际用的匹配规则**判定（事件是评估器的模糊配对，
> 不是"名字完全相同"）——用后者的口径算，事件层会得到 12.5%，比 28.1% 低一倍多，
> 那段差距是配对口径而不是覆盖率。

#### 2.6.3 一条记录具体怎么被判成 TP / FP / FN

三个指标用的是同一个公式，但**TP/FP/FN 怎么划**由三件事决定：两侧的身份口径、匹配阈值与是否一对一、是否先用 gold 过滤。逐层走一遍（当前代码的实际机制）：

**实体**（`evaluate_entities`）：每条预测实体依次与参考集里**尚未被认领**的名称比对——原字符串相等、或一方包含另一方且长度 ≥ 2、或 `fuzz.ratio ≥ 70` 即命中。命中则该预测行与该参考名一起被"认领"（**TP**）；没被任何预测认领的参考名 **FN**；没匹配上的预测行 **FP**。
例：预测"洛阳"有 40 行、参考集只有 1 个"洛阳" → 第 1 行 TP，其余 39 行全是 FP。这就是实体精确率只有 11.50% 的直接原因。注意"一对一"意味着同一参考名不会被两条预测重复领走，所以**召回率不靠多抽提高**。

**事件**（`evaluate_events`）：先做整体配对 `build_event_mapping`（相似度降序贪心，阈值 0.35，每个参考事件名只配一个预测事件名），得到 283 对；然后 `tp` = 配对命中的参考名（281）、`fp` = 预测唯一名数 − 配对数（1028 − 283 = 745）、`fn` = 参考名里没被配上的（39）。
例：预测"红巾军起义"配上了参考集的"英军挑起亚罗船事件"（相似度 0.25）→ 这一对让 `tp` 加 1，同时让预测侧少一个 FP。**错误的宽松配对会同时虚增 TP、压低 FP，两边都朝好看的方向走**——这是当前事件指标最大的问题。

**关系**（`filter_relations` + `match_relation_triples`）：第一步先用 `check_exists` 到参考集里找相似的 head/relation/tail，只有"已经像某条参考关系"的才留下（18,146 → 888 条），**其余 17,258 条既不算 TP 也不算 FP，直接从分母消失**；第二步把留下的放进集合去重，再做一对一贪心匹配（head 事件名模糊 + 关系类型精确或模糊 + tail 实体模糊）→ TP=714。
例：某事件有 17.5 条派生关系，其中只有 1 条"像"参考集里的某条（因为派生出来的多是"主战场/次要战场"这类，参考集恰好也有）→ 只有 1 条进评估，其余 16.5 条不计。于是精确率显示 80.41%，去预过滤复算只有 16.18%。

**一句话总结**：公式是标准的，但这些划分规则都是**可以选的**，所以同一份产物能算出完全不同的 P/R/F1。这就是为什么引用指标必须同时给口径。

#### 2.6.4 该给 P / R 定什么目标

不要定单一的 F1 目标——综合数会让精确率与召回率的问题互相掩盖。按**下游用途**分别定：

| 数据类型 | 用途 | 建议目标 | 理由 |
| --- | --- | --- | --- |
| 关系（进图谱的边） | 问答推理的输入 | P ≥ 90%，R 不设下限 | 错的边会让推理得出错误结论；缺边只是答不上来 |
| 实体（进图谱的节点） | 问答实体链接 | P ≥ 90%，R ≥ 60% 一类 | 错节点污染检索；漏节点只影响覆盖 |
| 事件核心字段（时间/地点/攻守方/结果） | 事件卡直接展示 | P ≥ 95% | 这些是直接展示给用户看的史实 |
| 事件名称 | 事件身份与跨库引用 | P、R 都要（如均 ≥ 80%） | 名称错了会导致跨库对不上 |
| 数值字段（兵力/战损） | 展示 | P 优先，**宁可留空** | 编造的兵力比"不详"危害大得多（见 4.2 节第 5 条） |

两条配套要求：① 每个目标都要带**抽样置信区间**（报"关系精确率 92% ± 3%"而不是"92%"），样本量决定敢下多细的结论；② 单独统计**"正确判断为不详的比例"**——模型在原文没有数字时写"不详"是正确行为，应当计分，而不是按"未填充"扣分（这正是 4.2 节第 5 条那个坏指标的反面）。

| 产物 | 事件数 | 地点 | 人物 | 组织 | 关系 | 说明 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| `9_final_all.json` | 1,050 | 5,316 | 2,492 | 1,067 | 18,146 | 全量，含未过发布过滤的事件 |

## 4. 逐层剖析：低分从哪里来

> **这一节的时效**：下面逐层列的是**改前**的实测状态，用途是说明「当初为什么低」（诊断依据），
> **不是待办清单**。其中绝大部分已在第一轮与第二轮修复（逐条状态见 **0.3 节**与
> [`整改落地说明与后续修改指南.md`](整改落地说明与后续修改指南.md)）；**仍未修的少数几项在 0.3.5 单列**。
> 照本节描述直接去动手之前，先确认那一条是不是已经修过了。

### 4.1 实体层（F1 20.42%，P 11.50% / R 90.67%）

召回率高达 90.67%，说明**大部分 gold 实体都能找回**；问题全在精确率。四类原因，不能都算模型错：

1. **gold 覆盖范围比抽取目标窄**。提示词要求抽"与战争/军事相关的所有实体"，产物包含地点 5,316 行、人物 2,492 行、组织 1,067 行；gold 唯一名称只有 378 / 506 / 242。抽查未匹配的预测，大量是**原文里真实出现的合法实体**（地点"釜山、保州、茅津渡、平海卫"，人物"胡林翼、僧格林沁、王在晋，组织"羌方、春陵军、蒙古诸部"）。这些全部记 FP。
2. **预测侧的同名多行**。地点 5,316 行里只有 2,883 个唯一名称，存在 2,433 条同名额外记录（洛阳 40 行、长安 33 行、襄阳 27 行、潼关 24 行）。原因是合并键含**名称 + 朝代 + 现代地名**（`result_merger.py:77-81`），而评估只按名称。工程侧要保留历史语境，评估侧当成重复 FP——**两侧身份口径不一致**。证据：只把预测地点按名称去重，F1 20.42% → 26.98%。
3. **预测侧确实有噪声**：地名被截断或括号拆裂（`东夷（山东`、`江苏一带）`）、组织里混进地点或事件概念（`零陵`、`黄巾起义`）、人物有 OCR 截断名。另有相当数量的一字名称（地点 215 行、组织 58 行、人物 25 行）需逐类判定。
4. **实体评估不使用别名归一**。`evaluate_entities()` 只做"原字符串相等 / 双向包含 / `fuzz.ratio ≥ 70`"，**没有调用 `normalize_entity()`**。因此 `aliases.json` 的 `孙滨 → 孙膑` 这类归一对实体指标完全不生效——标注文档里"别名归一后可以匹配"的表述与实现不符。

### 4.2 事件层（F1 41.75%，P 27.39% / R 87.81%）

1. **粒度不一致**：预测 1,028 个唯一事件名，gold 只有 320 个。预测包含大量章节级子战役与阶段行动（"三峰山之战""东乡之战""临朐之战"），其中不少在原文确有内容，但 gold 只标主要战争。在这种口径下合法细粒度事件也全部记 FP，所以 **P=27% 不能直接解释成"73% 是幻觉"**。
2. **匹配阈值 0.35 过低**：见 2.3，283 对映射里 114 对相似度低于 0.6，出现"红巾军起义 → 英军挑起亚罗船事件"这类跨战争错配。**高召回依赖的是宽松模糊匹配，不是模型质量**。
3. **同名不同事件被合并**：gold 里两个"扬州之战"、两个"平壤之战"分属不同年代，评估用名称集合会把它们并成一个。事件身份必须至少包含名称、朝代、时间、地点。
4. **提示词与代码的口径冲突**（这条是实打实的可修缺陷）：
   - `FULL_EVENT_PROMPT` 的输出模板**不含 `id` 字段**，而代码靠 `id` 把"完整事件"映射回"识别阶段"的规范事件名（`event_extractor.py:361-364`）。映射几乎必然失效，随后靠"规范化名必须在识别名单内"兜底，**不匹配就静默 `continue`**——不记日志、不计数。
   - `sub_events` 在代码里**已经不存在**（`models/events.py` 明确写"简化版：删除子事件"），但模块 `README.md` 仍宣称"子事件（时间 + 生命周期阶段）"，标注文件里也只有一个空占位数组。**没有任何填充者**，也没有生命周期/阶段逻辑。
   - `EVENT_TYPE_PROMPT` 与 `extract_event_type()` 是**死代码**（全仓无调用者），产物里的 `EventType` 实际来自 `FULL_EVENT_PROMPT`。需要产品决策：恢复"事件类型判定"这一阶段，还是删掉模板与 README 的宣称。
5. **字段填充率指标本身是坏的**：`evaluate_event_fields` 只判断"非空且不等于字符串 `null`"，**把"不详"算成已填充**。实测对照（1,050 个事件，用 `Normalizer.is_placeholder_value` 的占位词表判定"实质取值"）：

   | 字段 | 报告填充率 | 实质取值率 | 说明 |
   | --- | ---: | ---: | --- |
   | `TroopSize` | 99.6% | **39.7%** | 629 个事件写"不详" |
   | `Duration` | 99.6% | **43.9%** | 585 个事件写"不详" |
   | `Casualties` | 99.6% | **37.0%** | 657 个事件写"不详" |
   | `GeographicScope` | 99.6% | 99.0% | 这一项确实大部分有值 |
   | `Result` | 99.6% | 97.8% | 正常 |

   两点结论：① 报告里的"99.6%"有六成是把"不详"算成已填得出的假象；② **模型在原文没有数字时如实写"不详"，这是正确行为**——`is_placeholder_value` 的占位词表（`normalizer.py:219-240`）实际上承认了"不详"等于没有值，发布过滤（`main.py:315` 弱结果词表）也把"不详"当作无效值，只有字段填充率这一个指标把它算成已填。口径要统一到"不详 = 未填"。
   ③ 由此推出一条**不能违反的原则**：不要要求"所有属性都不能留空"，那会把现在这种如实的"不详"变成编造的数字。参见第 10 节第 12 条。

### 4.3 关系层（报告 F1 71.87%，实际约 26.90%）

1. **循环过滤（最严重的评估器缺陷）**：`filter_relations` 里的 `check_exists()`（`optimal_evaluator.py:261-280`）先去 gold 关系里找相似的 head/relation/tail，**只有"已经像某条 gold"的预测关系才进入评估**。18,146 条原始预测里只有 888 条进入精确率计算，其余 17,258 条不计 FP。而且这 888 条还要放进 `set` 去重，重复关系之间的 FP 也被消掉。标准做法：已对齐事件范围内的**全部**预测关系都要参与 TP/FP，不能先用 gold 判断"像不像"。
2. **规则派生关系过量（最大的数据质量缺陷）**：除 LLM 输出外，系统还从事件字段反向派生关系（`relation_extractor.py:217-265`）：
   - 地点：`Place` 字段第 0 个地点一律"主战场"、其余一律"次要战场"（无需任何证据）；含"议和/会盟"就给该事件**所有地点**加"议和地点"；含"粮草/后勤"就给**所有地点**加"补给地"；含"战略/关隘/都城"就给**所有地点**加"战略要地"。
   - 组织：`Aggressor→发起方`、`Defender→防守方`、`Allies→支援方` 无条件；再按**整段文本关键词**追加"同盟方/投降方/被俘方/议和方/调停方"——一个"议和"二字会给该事件所有组织挂上关系。
   - 人物：`Commanders→统帅`、`KeyPersons→参与者` 无条件；再用人名里**是否有某个字**推断角色（含"王/帝/君/公/侯/可汗"→君主、含"谋"→谋士、含"使"→使者）。
   - 证据复用：一次生成的所有关系共用同一条 evidence（`relation_extractor.py:234` `evidence = source_text or Remark or event_name`），实测 62%~72% 的关系 evidence 与所在事件的 `source_text` **逐字符相同**。这直接解释了"evidence 非空率 100%"与"能在原文中找到只有 46%~82%"的落差。
   - 结果：有关系的事件平均 **17.5 条**关系，极值 188 条（平定三藩之乱）、136（晋灭吴）、123（靖难之役）。这个数量级本身就不合理。
3. **事件-事件关系方向被按名称字典序改写**：`result_merger.py:348-371` 对"顺承/因果"用排序后的无向 pair 去重，`EventName_A > EventName_B` 时**直接交换两端**。即因果与先后方向可能由**汉字字典序**决定。`main.py:578-583` 只在 evidence 同时包含两个完整事件名时才换回来，而系统概括的事件名常常不在 evidence 里，所以错误方向可能保留到最终产物。这是数据正确性缺陷，不只是评估问题。
4. **"因果关系"被系统性降级为"顺承关系"**：`utils/relation_rules.py:36-39` 规定"模型说因果、但 evidence 里没有强因果词"时降级，而条件是 `has_sequential_keyword or evidence`——**只要 evidence 非空就降级**，几乎恒成立。后果是类型分布严重偏斜：产物 `顺承关系 798 / 并列 47 / 因果 40 / 包含 28 / 条件 1`，而 gold 是 `因果 80 / 顺承 59 / 并列 13 / 条件 10 / 包含 6`。
5. **非规范关系类型能落进最终产物**：全模块**没有任何 schema 校验层**（pydantic 模型里关系类型就是裸 `str`，无 `Literal`/`Enum`/validator）。唯一的 `normalize_relation` 只做归一，**不认识的原样返回**，不拦截也不告警。产物里因此有 20 种提示词枚举外的地点关系（`退守地`/`登陆地`/`会师地`/`终点`…）、人物侧的 `防守方统帅`/`向导`/`监督`，且 `published/final.json` 里也照样有。
6. **发布过滤会丢整类关系**：`is_high_confidence_event_event_relation` 只认"因果（需强因果词）/顺承（双名都在 evidence）/并列"，**其他类型一律返回 False** → `包含关系` 与 `条件关系` 永远进不了 `published`（raw 有 28+1 条，published 里 0 条）。
   **状态（2026-09-27）**：已修——按"有没有可判别的证据"分档（`因果` 仍要强因果词、
   `顺承` 仍要双名同现、`并列` 不变，`包含`/`条件` 与枚举外按"证据非空"放行；
   证据为空仍挡）。同一份旧产物上跑完整链路实测 published 变为 `包含 12 / 条件 1`；
   但**未上线**：它等于改整个知识库内容，必须随产物换代一起发布。见 §0.4 与指南 §1.24。
7. **raw 产物存在悬空关系**：按规范化名统计，`9_final_all.json` 里事件-地点 27 条、事件-组织 17 条、事件-人物 10 条关系的事件名在事件表里找不到（例如 `EventName='周文王东征'` 而事件表里是 `周文王东征灭崇之战`）。原因是实体关系的事件名只做名称标准化，不与最终事件名单对齐（只有事件-事件关系做了这道过滤）。`published` 侧靠精确名单把它们挪走了，所以只有 raw 是脏的。

### 4.4 证据与质量报告

`quality_report` 只检查 source/evidence **是否非空**，不检查"是否为原文句子、是否包含对应实体、是否支持该关系类型、是否来自正确事件、是否只是整段文本重复使用"。因此"missing_source_text = 0、missing_evidence = 0"**不能当作质量正确率**。

另外 `events.metadata` 在合并阶段丢失，导致质量报告里 `identified_event_count == final_event_count`、`postprocess_filtered_count == postprocess_merged_count == 0`——**这几项诊断事实上已经失效**（现存 `published/quality_report.json` 正是 `881/881/0/0`）。

### 4.5 输入文本质量会传导

输入是书籍转换出的长文本，存在 OCR 错字（`日军` → `目军`）、断词、年份数字被拆行；章节标题、总结段与具体战例混在同一输入里。分段器按 1800 字 / 重叠 200 字切分，边界优先句号（切点须超过 1260 字才采用，否则**按字符硬切**）。重叠段会重复抽取，同名实体又按朝代/现代名保留多行，重复被进一步放大。抽取前缺少 OCR 清洗与章节结构解析。

## 5. 关于"模型没有训练/微调"的判断

这个假设需要正面回答，因为它决定整条整改路线的走向。

**事实**：本模块**没有任何训练或微调环节**。它调用 `deepseek-chat` 做三轮提示词抽取（实体 → 事件 → 关系）；`data/annotations/` 是**评估参考数据**，不是训练集；全仓没有训练脚本、没有权重、没有 fine-tune 调用。

**所以**：

1. **"模型没训练"不是当前低分的可操作原因**。当前指标低的主因是可定位的：评估口径（第 4.3 节 1、3、4 条）、规则派生过量（4.3 节 2）、身份口径不一致（4.1 节 2）、产物与当前代码的错配（后处理与评估代码此后改过多轮，见 2.5.1）。这些与模型无关，改了立刻见效。
2. **提示词与参考数据确实有问题**，但也要精确归因：提示词的缺陷是"枚举自相矛盾、输出模板缺 `id`、evidence 口径自相矛盾"（第 4.2 节 4、4.3 节 2），不是"整体写得差"——而且**提示词文本自始至终没改过**（2.5.1），所以不存在"提示词越改越差"这回事；参考数据的缺陷是"多模型分片汇总、未经人工处理、无 IAA、无 train/验证/测试切分、违反自身规范"（第 2.4、2.4.1 节），所以它只能算**多模型的合并输出**，连"待审核参考集"都要打折，不能算可靠 ground truth。
3. **微调不是不该做，而是现在做没有意义**：在没有 IAA 保证、没有 train/dev/test 切分、没有稳定 schema 的条件下做微调，等于把噪声固化进权重，而且无法证明微调有效（因为评估器本身有缺陷、没有干净测试集）。**前置条件**：① 评估口径重建完成（第 6 节阶段 1）；② 事件与实体有稳定 ID；③ 标注有 IAA 与仲裁；④ 数据切分固定；⑤ schema 收敛到规范枚举。这五条具备之后再评估"提示词工程 vs 微调"哪个更划算。
4. 一个更划算的中间步骤：**在提示词里加真实语料的 few-shot 示例**（当前提示词只有"同域 JSON 示例"，没有真实语料/标注示例）。这属于"提示词工程"，成本远低于微调，且可以直接用 development 集验证。

#### 阶段 1 附：参考集重建之前，新抽出来的数据靠什么评估

> **执行状态：已完成**（2026-09-26）：新增 `tools/artifact_health_check.py`（机械一致性，可当 CI 门禁）与
> `tools/sample_for_review.py`（分层抽样导出 + 跨版本定位复核）；`evaluate_event_fields` 已改为
> 同时报「填充率」与「实质取值率」。

重建一套经过人工核验的参考集需要时间。在那之前的空档期**不要继续报宏观 F1**（它无法解释，见 2.6），改用下面四个**不依赖 gold** 的指标。这四个都不需要参考集，可以立刻用。

**(1) 抽样人工精确率** —— 最有用，也最省。

从产物里**分层随机抽样**（按实体类型、事件、关系分别抽，尽量覆盖不同朝代），人工逐条回原文判定"对 / 错 / 无法判断"。得到的是精确率的无偏估计加置信区间。

- 样本量参考：要把 95% 置信区间压到约 ±5 个百分点需约 380 条，±10 个百分点需约 96 条。分层抽样比纯随机更省。
- 优点：不依赖完整的参考集；直接回答"抽出来的东西对不对"这个真问题；顺带得到错误类型分布（这也正是阶段 3 的优先级依据）。
- 局限：**只测精确率，不测召回率**——"漏了什么"必须有参考集才能知道。

**(2) 原文可溯源性（groundedness）**。

把每条记录的证据字段规范化后在原文里查找，算"能在原文找到的比例"。项目此前做过一次，结果分档明显：地点 82%、事件 81%、人物 60%、组织 58%；关系证据 event-place 73%、event-person 70%、event-event 只有 46%。

- 优点：完全可自动化，且直接对应"证据可溯源"这个产品需求（RAG 要求 grounded answer）。
- 局限：能找到**不等于**引用得对（可能引了不相干的段落），找不到也不**一定**是错（引号、OCR、拼接差异）。所以它是信号，不是准确率，只能用来横向比较"哪一类数据最不可信"。

**(3) 机械一致性检查** —— 可自动化、可当 CI 门禁，用途是**防回归**而不是打分。

现在就能查出来的一批：悬空关系（关系的事件名不在事件表里；raw 产物有事件-地点 27 / 事件-组织 17 / 事件-人物 10 条）、枚举外取值（`OrgType`/`Role`/关系类型/`EventType`）、重复行、残缺年份（14 处）、把"不详"当有效值（见 4.2 节第 5 条）、事件-事件关系方向与时间字段矛盾（A 晚于 B 却标"顺承 A→B"）、同一段证据被几十条关系共用。

**(4) 稳定性 / 可复现性**。

同一输入在不同 `PYTHONHASHSEED` 下结果是否逐字段相同（`tests/test_evaluator_deterministic.py` 已钉住），以及同一提示词两次抽取的一致率。这测的是**可复现性，不是准确性**——两者不要混。

**旧标注在这个空档期还能帮一个忙**（承接 10.3"降级使用"）：把它的 320 个事件名、506 个人名、378 个地名当**抽样骨架**（按名字分层抽，避免只抽到边角数据）与**别名来源**；另外可以算一个"旧清单召回率下界"——旧清单里的名字有多少能被新产物匹配到。因为旧清单不全，这只是召回率的**下界**，但比没有强，而且能横向比较两次改动谁召回得更多。

**工程上需要的（待确认后再动手，本文不含代码改动）**：一个 `tools/` 下的产物体检脚本（固化上面第 3 项，输出可逐版对比的报告）、一个分层抽样导出脚本（产出人工核验用的表格模板）、以及把 `evaluate_event_fields` 的"不详算已填"改成"不详算未填"。

#### 阶段 1 附二：改完代码后，怎么证明这次比上一版好

> **执行状态：工具已就绪**（`tools/sample_for_review.py --compare`），抽样集需要人工判定后才能建立基线。

这是整套评估方法里最实用的一块，也是"参考集换了之后还能不能比"的答案。工具是**固定评估抽样集**（frozen evaluation sample）：一次投入、长期复用、不依赖参考集。

**建立（改代码之前做一次）**

1. 从当前产物按类型**分层随机抽样**，总量取 300~400 条（实体 / 事件 / 关系按各自规模分配）。
2. 每条记录一个**稳定定位**——不要用数组下标（换版本就错位），要用"原文里的位置 + 记录身份"，例如事件用「归一名称 + 朝代 + 起始时间 + 首个地点」，实体/关系用「原文段落 offset + 名称/三元组」。稳定 ID 落地后可以直接用 ID（这就是阶段 1 第 1 项稳定 ID 的一个实际用途）。
3. 人工逐条回原文判定"对 / 错 / 无法判断"，记下判据。**只判"这条记录本身是否成立"，不需要判"漏了什么"**（漏项要靠参考集）。
4. 得到基线数字：例如"旧产物抽样精确率：实体 ?%、事件 ?%、关系 ?%"，并附置信区间。

**复用（每次改完代码、重新抽取之后）**

5. 对同一批稳定定位重新判定：新产物在这些原文位置抽出的记录是否成立、原来的错误是否消失、有没有引入新的错误。
6. 比较两次的抽样精确率，并附置信区间——**置信区间重叠就不要声称"变好了"**。

**为什么这样比是可靠的**

- 被判的对象是**原文里的位置**，不是某个版本的数组下标，所以跨版本可比；
- 它不依赖参考集，所以参考集怎么换都不影响这条对比线；
- 它是抽样的，所以结论能外推到全书（这是统计推断，不需要全书人工核验）。

**配套的三条纪律**

1. **把"口径变化"与"质量变化"分两栏报**。有些改动会让分数下降但那是修正：删掉关系评估的 gold 预过滤后，关系 F1 从 71.87% 掉到 26.90%，这是修正不是退化。报告里必须分开。
2. **同口径对比要固定四件事**：四个阈值（`config/eval_config.json`）、参考集版本、预测文件哈希、评估器版本。`tools/threshold_sensitivity.py` 在表头打预测产物 sha256 就是这个思路。
3. **机械体检的数字当回归门禁**：悬空关系数、枚举外取值数、重复行数、残缺年份数这些是**绝对数字**、不依赖参考集，改动后应当不增加（除非是有意放宽口径，那要写明）。

### 7.1 两个入口：共享抽取，但模型与后处理都不同

**"文本实体识别"页用的抽取流程与技术，与本模块是同一套**——同一个 `run_extraction` 三阶段编排、同一批 extractor、同一批提示词。这一点有测试钉住：`backend/tests/test_orchestration_single_entry.py` 用桩 LLM 驱动两个入口，断言调用次数、阶段顺序、以及"钩子之前那两个阶段"的提示词**逐字符相同**。

但下面四项都不同，其中第一项影响最大：

| 维度 | 离线抽取链 | 在线"文本实体识别"页 |
| --- | --- | --- |
| **模型** | DeepSeek API，`DEEPSEEK_MODEL` 环境变量，默认 `deepseek-chat`（`war_extraction/core/llm_client.py:36`） | **本地 Ollama 的 `deepseek-r1:7b`**，硬编码在 `backend/blueprints/llm.py:231`（`OllamaAdapter`，`llm_pipeline.py:52`） |
| 分段 | 1800 字 / 重叠 200（`config.py` 默认值） | 1200 字 / 重叠 150（`llm_pipeline.py:383`，注释说明"backend 的分段比离线链路细"） |
| 缓存 | 读且写（`main.py:699-700`） | **不传 cache**（`llm_pipeline.py:380`）→ 不读不写，每次全量调模型 |
| 后处理 | `main.py` 的清理与发布链（实体回填、冲突清理、发布过滤、质量报告） | `llm_pipeline` 自己一套（角色归一、朝代纠正、空关系填 `参与者`/`参战方`/`关联`） |

**设计意图是明确的**，`backend/tests/test_orchestration_single_entry.py` 的 docstring 里写着：合并时选的语义是"**后处理各自保留**"，所以"两边逐字段 diff 为空"在本设计下不成立；测试只钉"共享阶段一致"。

**唯一需要记住的后果**：extractor、提示词与 pydantic 模型是**同一份代码**，所以改动它们会同时作用到两个入口；而两边模型不同（7B vs DeepSeek API），在离线链上的效果不代表在线侧的效果。**在线页不在本轮整改范围内**，其代码与表现由项目负责人另行处理。

### 10.2 仍未确定

1. **`data/annotations/README.md` 的更正措辞**：该文件现在写的是"评估唯一的对照来源""只有一名标注者、没有 IAA""抽样：全书事件（不是抽样片段）"，与实际（多模型分片汇总、未经人工处理）不符，会误导后续接手的人。更正内容至少应覆盖四点：制作方式（几个人、哪几个模型、怎么分片、谁汇总）、**有没有人工复核**（决定它能否算"待审核参考集"）、已知缺陷（直接引用 2.4 节那组实测数字）、仍可用的范围（词表/别名来源/抽样骨架，见 10.3）。措辞由标注所有人确认。

### 10.3 参考标注：旧数据能否继续使用

**问题**：现行三份 `sample_*.json` 是很早以前用不同模型分片提取后合并的，之后（据说明）提示词也改过多次，那这批标注还能用吗？

**先纠正一个前提**。仓库历史里三份提示词**内容一字未改**（见 2.5.1），所以"提示词改了很多次"这件事在仓库内不成立——那些改动若确实发生过，是在仓库建立之前。因此"标注与当前提示词口径漂移"这个论证**不成立**。

**但结论不变，原因更强**：gold 与当前流水线之间**从来没有对齐过**，不是"漂移了多少"的问题。原因是 gold 根本不是这条流水线产出的——它是几个人用各自的模型、各自的方式分片抽取后拼接的，没有 schema 约束、没有字段处理。所以拿它当准确性分母，测的永远是"两套互不相干的流程之间的差异"。

**结论：可以继续用，但要降级使用。**

| 用途 | 是否可用 | 说明 |
| --- | --- | --- |
| 作**候选清单/词表** | **可以** | 320 个事件名、506 个人名、378 个地名是真实存在于这本书里的内容，可作人工核验的起点，也是别名表（`config/aliases.json`）的来源 |
| 作**回归/可复现性检测**的参照 | 可以 | 用途是"同一输入两次是否一致"，与准确性无关（项目已有先例 `tests/fixtures/relation_slice_repro.json`） |
| 作**准确性指标的分母** | **不可以** | gold 自身未核验，且与流水线无口径关系 |
| 用于**跨版本的"改好没改好"判断** | **不可以，且最有害** | 会把"新旧口径差异"误读成"质量升降"，从而把提示词与后处理改坏 |

**为什么不能靠"清洗一遍"救活**：真正的结构问题（`event-place` 479 条里 230 条 head 不在事件表、21 条完全重复关系）不是脏数据，而是**引用对不上**——要把 head 对齐到具体事件，必须回原文判断"这条关系说的到底是哪一仗"，那等于重做。清洗只适用于小范围问题（重复行、14 处残缺年份）。

**一个低成本的判定实验（建议在重建前先做）**：从 gold 里抽 30~50 条样本**回原文逐条核验**，统计"正确 / 漏标 / 错标 / 无法判断"的比例。半天工作量，得到一个数字，就能决定旧标注是"修一修还能当辅助"还是"只能当词表"。这个实验本身就是重建流程的第一步，不浪费。

**重建方向（已定）**：

- **不要做**：把某次抽取的模型输出直接当新 gold。那会让评估变成"模型与自己的输出比"，F1 趋近 100% 而质量不变，且模型的错误一旦进入 gold 就再也改不掉（改对了反而掉分）。用模型产出做参照只适用于**可复现性/回归检测**，不适用于准确性。
- **可以做**：LLM 出草稿 + **人工对照原文逐条核验**（删错、补漏、按原文改正字段），并把"改动了多少"作为模型在该子集上的错误率估计；再取一部分双人复核算 IAA，最后切 development / test。子集化（如只做秦汉唐明）可行，但指标只能是**该子集的指标**，不能与全书数字并列比较。
- **铁律**：标注者**以原文为准，不以模型输出为准**；原文没写就留空或写"不详"。
- **附加原则**：标注与产物都**允许"原文没有"的字段留空或写"不详"**，并把"不详"统一按未填处理（见 4.2 节第 5 条）。要求"所有属性不能留空"会把如实的"不详"变成编造的数字——编造的战损与兵力会经 SQLite → Neo4j → RAG → 飞书问答被当作史实引用，这是这条整改线上后果最难回收的错。
