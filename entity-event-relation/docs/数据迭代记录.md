# 数据迭代记录（EER 抽取产物）

> **这份文档解决什么**：这个项目的知识库数据是**一版一版迭代出来的**，所以"这一版比上一版好在哪、
> 为什么好、下次怎么改"必须有地方写清楚。没有它，两版之间的差就分不清是**产物换代**、**口径变更**
> 还是**跑批抖动**——这三件事这个项目各付过一次学费（见 `../../../docs/项目审查与修复历史.md`
> 附录 A 第 15 条、§26）。
>
> **两条规矩**：
>
> 1. **换代只归档、不删除**（旧产物、旧库、旧快照、旧参考集都留着），本文件记下每一版的
>    **指纹 + 计数 + 指标**，让"任意两版能不能比、怎么比"有据可查。
> 2. **每次改完数据，往本文档加一行版本**，并写清"这一版动了什么、指标怎么变、为什么变"。
>    指标一律带口径（哪份参考集 / 哪次抽样 / 什么方法），否则下一轮会把口径差异读成质量升降。

## 四、为什么这一版比上一版好（因果链）

**一句话**：抽样精确率 +8.6 个百分点，**主要来自关系层（74.4% → 88.0%）**，而关系层正是这一版改得最多的一层。

具体对得上：

1. B 组那次 350 条判定给出一个很硬的结论：**42 条关系错里没有一条是"证据不足"，全部是类型判定错或方向标反**。
   所以改的方向就该是"关系类型与方向的判定规则"，而不是"收紧门槛"。这一版正是照这个结论改的
   （§二 第 1、2、9 条）——`统帅` 不再逐人派生、角色必须原文写出、事件关系的 A 按时序。
2. 于是机械指标先动：`统帅` 3016 → 327、`议和地点` 233 → 29、方向与时间矛盾 255 → 0；
   人工判定随后确认：关系层 74.4% → **88.0%**。
3. 事件层**没有明显变化**（90.1% → 88.9%，区间宽、在噪声内）：这一版对事件层只改了
   `StartDate` 不推算、`Place` 只写本场、`Result` 不写反这三处提示词，量级本来就小。**如实记着**。
4. 实体层 92.3% → **99.0%**：B 组当时指出实体错**全在附属性字段**（归属/角色/类型），这一版正好把
   `OrgName`/`Role`/`OrgType` 三处提示词改了 ✓。
5. 两处**不是"模型变好"而是"数据变干净"**的改善：悬空边 54 → 0（产物侧开始丢目标端对不上的边）、
   导入乱码 268 → 0（修了判据）。它们不影响抽样精确率，但直接影响**知识库里数据的可用性**。

**最弱的一层要单独记**：「关系:事件-事件」新抽样只有 **57.1%**（14 行 / 8 对 / 6 错，区间 `[33%, 79%]`
很宽）——与"错误类型里最大一类是**关系类型** 20 条"方向一致。**下一轮若再改抽取，重点在这里**，
不在事件字段。发布子集只收高置信的事件-事件关系（全量 1088 → 发布 210），所以它对入库的影响面
小于它对抽样精确率的影响。

## 五、已知缺陷与口径提醒（别当成"已经完美"）

1. **8 条关系没进知识库（0.05%）**：产物把关系头**标准化**（`standardize_event_name`），而库里事件名是
   原始写法，导入器精确查找对不上。两条可能的修法：产物侧按同一口径过滤，或导入器支持标准化名兜底。
2. **RAG 词典仍是从数据推导的**（未以权威表为种子）：所以它**收了 `交战`**（判定为"不加入"的值）、
   **丢了 `政治事件`/`议和`**（新数据里没有）。要落地"以权威表为准扩词典"，得改
   `RAG/data/snapshot/governance.py` 的词典构建。
3. **流程没有固定随机种子**（`seed` 恒为 `null`）：实测**同一份文本、同一套提示词跑两次，关系数差约 10%**。
   所以任何 A/B 比较都被这层噪声压着，判"有没有变好"要靠**区间不重叠**（这条已经写进验收口径）。
4. **10 条枚举外记录**已登记为"已确认例外"（`Role/地方势力`、`EventType/交战`、关系名
   `同盟方`/`支援地`/`驻防地`/`自杀`）：模型把别的字段的值抄了进来或造了关系名。
   **实测一条都没进发布子集**（被候选区挡住），不影响知识库。
5. **`条件关系` 在全量产物里 0 条**：枚举里声明了、数据里从没出现过。所以 C1 的验收只验到了
   `包含关系` 那一半。
6. **`seed`/抽样方法变了就不能直接比**：抽样精确率要跟历史比，必须**同方法**（同 350 条规模、
   同分层、同种子）。换方法就是换口径。

## 六、下一版怎么做（迭代流程）

按顺序，每一步都有验收口径：

| 步 | 做什么 | 验收 |
| --- | --- | --- |
| 1 | **改**：区分"进缓存键的改动"（提示词 / 四份 `config/*.json` / `models/*.py` / 模型名 / 分段参数）与不进的 | 不进的改动**走缓存重放**（免费）；进的**必须攒批**，否则每改一次付一次全额 |
| 2 | **重跑**：整本（或缓存重放） | 产物 metadata 里 `model_served` 与 `model` 一致；`relation_degraded_stages` 必须为 **0** |
| 3 | **体检**：`tools/artifact_health_check.py --baseline evaluation/baseline/health_check_after.json` | 退出码 **0**；且**逐项按每事件折算**看，别只看绝对条数。跑完**基于新产物重新生成入库基线** |
| 4 | **人工抽样判定**：同方法抽 350 条、人逐条判 | 精确率 + Wilson 区间；**与上一版区间不重叠才声称变好**（区间重叠就写"未观察到差异"） |
| 5 | **记录**：往本文档加一行版本（指纹 + 计数 + 三项指标 + 动了什么 + 为什么变） | 每条数字都带口径 |
| 6 | **发布**：导 SQLite → 同步 Neo4j → RAG 快照 + 索引 + 激活 → 前端验收 → 同步 `RAG/docs/current-status.md` 的数字 | `check_docs.py --strict` 通过；库里能看到 `包含关系`；账号数不变 |

**改完一定要顺手做的三件事**：① 新产物重新生成入库基线（否则"基线过期"用例变红，这是设计意图）；
② 若参考集/切分变了，重新冻结 `evaluation/baseline_reference_v2/`；③ `git` 提交时把**冻结记录与
产物指纹**一起带上。
