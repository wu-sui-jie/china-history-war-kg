## 0. 最重要的一件事：改动什么时候生效

同一批改动，生效时机分三类。**混淆这三类是后续最容易出的误判**——
"我改了代码但指标没变"通常不是改错了，而是这类改动要重跑才进产物。

| 改动类别 | 举例（本轮改的） | 生效时机 |
| --- | --- | --- |
| **评估侧** | `optimal_evaluator.py`、`evaluate.py`、`tools/*.py` | **立即**：对现有产物跑一次就用新口径，不需要重跑抽取 |
| **抽取侧** | 提示词、`extractors/`、`processors/`、`text_cleaner`、`text_splitter`、`main.py` 的派生与发布逻辑、schema 校验、事件身份键、`AliasNames` | **下次重跑抽取后**才体现在 `output/` 里的产物上。对旧产物跑评估**看不到**这些改动 |
| **下游侧** | `backend/import_json_to_sqlite.py`、`backend/llm_pipeline.py`、`frontend/**` | **重导库 / 重新构建前端**后才生效 |

**因此要记住**：现在 `output/中国历代战争简史/` 里的产物**仍是旧口径的产出**
（2026-08-18 由 `133a9aa` 生成）。本轮改后的所有指标数字，都是**对这份旧产物的重评**，
反映的是评估口径的修正；抽取侧的改进（关系量级、证据绑定、悬空边、枚举合法性）
**要等下一次整本重跑才会出现在产物里**。

### 1.2 质量报告的事件诊断项不再恒等

`events.metadata` 原先在"段间合并"和"最终清理"两步被丢掉，于是质量报告里的
`identified_event_count`、`postprocess_filtered_count` 等永远是"最终事件数/0"
（现存 `published/quality_report.json` 就是 `881/881/0/0`）。现在合并期按段汇总计数、
清理期带着它更新，缓存还原也带上它；分段诊断（含**关系阶段降级的段数**）挂到事件 metadata 上。

`quality_report.diagnostics` 新增四项可观测值：
`enum_out_values`（枚举外取值分项计数）、`dangling_relations_dropped`（悬空边丢了多少）、
`relation_degraded_stages`（关系阶段降级的段数）、`moved_to_candidate_by_enum`（因枚举不合法进候选区的条数）。

- 文件：`war_extraction/processors/result_merger.py`、`main.py`、`war_extraction/core/extraction_runner.py`
- 用例：`tests/test_artifact_provenance.py`

### 1.3 关系评估不再虚高（两条口径修正，缺一不可）

`filter_relations` 里原先有个 `check_exists()`：先用 gold 关系找相似的 head/relation/tail，
**只有"已经像某条 gold"的预测关系才进入评估**。实测 18,146 条预测关系里只有 888 条参与精确率计算，
其余 17,258 条不计 FP。**这一条已删除**——已对齐事件范围内的预测关系都进 TP/FP。

**第二条（第二轮补的）**：`filter_relations` 原先返回 `set`，于是**完全重复的三元组只算一次**，
重复项之间的 FP 被静默消掉。现在返回**按条**的列表：同一三元组出现 k 次就计 k 条预测，
其中 1 条可能成为 TP、其余 k-1 条必然落进 FP（一对一匹配天然给出这个结果）。

重复从哪来：**关系名归一把别名写法收敛到同一规范名**——产物里同时有
`巨鹿之战 主战场 巨鹿` 与 `巨鹿之战 发生地点 巨鹿`，归一后是同一条关系写了两遍。
实测已对齐事件范围内共 **747 条重复**（事件-地点 156 / 事件-人物 528 / 事件-组织 63 /
事件-事件 0），现在计入 FP，报告里由 `counts.filtered_pred_duplicates` 给出条数。

> **踩过的坑（记下来免得再犯）**：第一次复核这件事时按**原始行**去数，得到"重复 0 条"，
> 于是判断"这条修正不影响数字"。错在**归一之后才有重复**——按原始行数永远是 0。
> 教训：凡涉及"两侧口径"的计数，必须用**评估器实际使用的那套归一**去数。

与 gold 侧的**不对称是有意的**：gold 仍用 `set`——标注里重复的关系行（事件-事件有 21 条完全重复）
是标注缺陷，不该反过来要求预测也多输出一条。标注重复由体检脚本报出。

**关系 F1 因此从 71.87% 掉到 25.51%（两轮口径叠加），这是修正不是退化。**

- 文件：`war_extraction/evaluation/optimal_evaluator.py`
- **注意**：关系"分母浮动"的问题仍在（gold 三元组只保留 head 能被映射到预测事件的关系），
  所以跨版本比较关系召回率依然没有意义
- 用例：`tests/test_evaluator_capabilities.py` 的 `test_关系按条计数不吞重复三元组`

### 1.4 事件配对加了语义约束（第二轮修过一轮：原来过严）

原先只有"名称相似度 ≥ 0.35"一道门槛，实测出现过 `红巾军起义 → 英军挑起"亚罗船事件"`
（相似度 0.25）这类跨战争错配。现在相似度只是**入场券**，还要过朝代 / 起始年份 / 首个地点三类约束。

**第二轮复核：约束原来过严，成因是四处实现缺陷**（用 `tools/event_pairing_review.py` 实跑导出
144 对被拆配对后人工判读确认）。四处已逐条修好，配对从 176 对回到 **231 对**：

| 原缺陷 | 表现（实测案例） | 修法 |
| --- | --- | --- |
| 同名事件没有豁免 | 144 对被拆里 **22 对是同名**（`官渡之战 → 官渡之战`、`七国之乱 → 七国之乱`）；而事件 TP 本身就按名称集合算，拒绝同名配对等于自伤 TP | 归一后名称相等 → **直接放行** |
| 地点只比"首个有效地点" | `宁锦之战` 两侧是**同一对集合、顺序相反**（`锦州、宁远` vs `宁远、锦州`）也被拒；另有多值拆分把 `东夷（山东、江苏一带）` 切成两个半括号碎片，噪声规则漏掉它们 | 改按**地点集合**比（有交集或互相包含即相容）；`Normalizer` 补两条"半括号碎片"噪声规则 |
| 朝代按字符串相等 | `松锦之战` 预测`清`、标注明（明清之际同一场战争）；`五代十国` vs `后唐/后梁` 是口径粗细之差 | 改按**时代档位**判（相邻档位相容；认不出来的写法一律放行） |
| 年份拿标注残值比 | `天津保卫战` 标注 `StartDate="153"`（截断残值）与预测 `1900年6月` 比出"相差 1747 年" | 1–3 位纯数字的**残缺年份不参与**比较 |

剩下的 86 对被拆，人工判读 41 对（相似度 ≥0.7 的 27 对 + 中低 14 对）显示绝大多数是**真错配**：
`北京之战 → 英法联军攻占北京`（1900 vs 1860）、`东京陷落之战 → 天津陷落`（北宋 vs 清）、
`隋炀帝第一次东征高丽 → 康熙第三次亲征`（隋 vs 清）——约束在做的正是该做的事。

**事件 F1 因此从 41.75% 掉到 34.15%（两轮口径叠加：先因加约束降到 25.98%，再因修约束回到 34.15%）。**
配对统计（候选对数、按原因分项的拒绝数）写进 `event_extraction.mapping_stats`。

- 文件：`optimal_evaluator.py`、`config/eval_config.json`、`utils/normalizer.py`、
  `tools/threshold_sensitivity.py`（扫描时也带上这个口径）
- 复核工具：`python tools/event_pairing_review.py` → 导出 `evaluation/review/pairing_diff_*.csv`
- 用例：`tests/test_evaluator_capabilities.py` 的前 8 例（每一条都复现上面某个具体误杀案例）

### 1.5 实体评估改成两套身份口径并列

原先实体匹配只用"原字符串相等 / 双向包含 / `fuzz.ratio ≥ 70`"，**不调别名归一**。
现在同时给出：

- `mention` 口径（默认，与历史可比）：预测侧逐行计数、参考侧压成名称集合；
- `canonical` 口径：两侧先做别名归一，预测侧按规范名去重。

同一份产物上：mention F1 = 20.42%，canonical F1 = **26.98%**。这个差值是**口径差异**，
不是模型错误——顺带说明为什么"实体精确率只有 11.50%"不能直接读成"模型抽错了 88%"。

`entity_extraction.identity` 里还给出两侧粒度（`pred_rows`/`pred_unique_names`/`gold_rows`/`duplicate_rows`），
点位重复多严重一眼可见。

### 1.6 事件字段从"填没填"升级到"填得对不对"

- `evaluate_event_fields` 增加 `field_effective_rates`：占位词（"不详/未知/无/null"…）算**未填**。
  实测 `Casualties` 旧报告 99.6% 填充、实质取值只有 37.0%。
- 新增 `evaluate_event_field_accuracy`：在已配对事件上逐字段与标注比对，输出
  `comparable/correct/accuracy/coverage`。实测（231 对已配对事件）：**`Result` 16.1%、
  `Aggressor` 34.3%、`Defender` 42.8%** 是最差的三项，而 `Place` 96.5%、`Person` 91.5%、
  `DynastyName` 84.0%、`StartDate` 85.9%——这是"先修哪个字段"的依据。
  （第二轮把 `Place` 从"只比首个地点"改成"按集合比"，数值从 100% 降到 96.5%：**降的是虚高**，
  与配对集同时变大也有关系。）

### 1.7 报告能按维度下钻

- `relation_extraction.by_category`：四类关系各自的 P/R/F1（宏观平均会掩盖"哪一类在拖后腿"）；
- `event_extraction.by_dynasty`：按**标注侧朝代**分组的事件指标；
- `evaluate.py --also-published`：对 `published/final.json` 再评一遍，写进 `summary_published`。
  两份粒度不同（1050 vs 881 事件），**指标不可混用**，所以各自带文件哈希分开报。

### 1.8 事件-事件关系的方向不再由汉字字典序决定

原先 `result_merger.py` 对"顺承/因果"用**排序后的无向 pair** 去重，`EventName_A > EventName_B`
就直接交换两端——"谁先谁后"由汉字编码决定；而 `main.py` 只在证据同时含两个完整事件名时才换回来
（实测 914 条里只有 23 条满足），错误方向因此留在产物里。

现在方向按 **① 证据里两个事件名的出现顺序 → ② 事件起始年份** 判定；
**两者都判不出来时不合并 A→B 与 B→A**（不猜方向）。同一份关系数据的方向判定、
类型仲裁、去重与定序收成一份实现（`reduce_event_event_relations`），
抽取器、段间合并、最终清理三处共用。

- 文件：`war_extraction/utils/relation_rules.py`、`processors/result_merger.py`、`extractors/relation_extractor.py`、`main.py`
- 用例：`tests/test_relation_rules.py`（18 例）

### 1.9 "因果关系"不再被无条件降级成"顺承关系"

`arbitrate_event_event_relation` 的原条件是 `has_sequential_keyword or evidence`，
而 `evidence` 几乎恒成立（派生关系的证据直接取事件 `source_text`）——
于是"模型说是因果"几乎必然被降级。产物分布因此是 `顺承 798 / 因果 40`，而标注是 `因果 80 / 顺承 59`。
现在只有证据里**确实出现顺承词**才降级（顺带补齐了 `此后`/`过后` 这类漏掉的顺承词）。

### 1.10 派生关系绑定"同句证据"与"具体实体"

这是关系量级从"不合理"回到"可解释"的那一处。删掉的三条无条件规则：

| 原规则 | 现在 |
| --- | --- |
| `Place` 字段的**第 0 个地点一律"主战场"**（无需任何证据） | 只有该地点所在的那一句里出现交战线索才成立；主战场给**第一个有交战线索**的地点，其余记次要战场 |
| 整段文本出现"议和/粮草/战略"就给该事件**所有**地点挂上对应关系 | 线索词必须与地点**同句** |
| 整段出现"议和"就给该事件**所有**组织挂"议和方" | 线索词必须与该组织**同句** |
| 人名里含"王/帝/君/公/侯"→ 君主；含"谋"→ 谋士；含"使"→ 使者 | 君主/可汗只按**称号结尾**判定（`王翦` 不再是国君）；谋士/使者一律要求同句线索 |

**证据也从"整段 `source_text`"改成"实体名所在的那一句"**，找不到那一句时退一步用事件的
`source_text`（说明"这条关系的依据是事件字段，不是某句原文"，如实呈现）。

同一份旧产物的干跑实测（不动模型）：

| 指标 | 改前 | 改后 |
| --- | ---: | ---: |
| 有关系的事件平均关系数 | 17.5 条 | **7.7 条** |
| 极值（最多关系的事件） | 188 条 | **50 条** |
| 证据与事件 `source_text` 逐字符相同 | 62.6% | **24.1%** |

- 文件：`war_extraction/extractors/relation_extractor.py`
- 用例：`tests/test_derive_relations.py`（15 例）

### 1.12 悬空边在 raw 产物里也被清掉

实测 raw 产物有 54 条悬空边（事件-地点 27 / 事件-组织 17 / 事件-人物 10），
`EventName` 在事件表里找不到（例：`周文王东征`，而事件表里是 `周文王东征灭崇之战`）。

### 1.13 事件身份四处统一

改前四处口径互不相同：

| 位置 | 原键 |
| --- | --- |
| 抽取器 `_postprocess_events` | 只有规范化名称 |
| 合并期 `ResultMerger._event_merge_key` | 名称 + 朝代 |
| 清理期 `main.cleanup_events` | 名称 + 朝代 + 时间 + 地点 |
| 发布期 `published_event_key` | 名称 + 时间 + 地点（**少了朝代**） |

现在统一为 **归一名称 + 朝代 + 起始时间 + 首个地点**，唯一实现在
`war_extraction/utils/value_parsing.py::event_identity_key`，**五处**共用
（抽取器两处 + 合并期 + 清理期 + 发布期）。
连带效果：同名不同年代的事件不再被合并 → **事件计数与关系分母都会变**（属预期变化）。

### 1.14 缓存不再"改了规则还命中旧结果"

`CONFIG_VERSION` 原先是一个硬编码串，所以改了 `aliases.json` 或 `relation_types.json` 之后
缓存键一点不变，旧结果照样命中。现在：

- `config_version` = 4 个**会影响抽取产物**的 config 文件（`aliases.json`、`relation_types.json`、
  `dynasty_ranges.json`、`publish_rules.json`）的哈希；**刻意不含 `eval_config.json`**——
  调评估阈值不该让整本抽取的缓存失效（那是真金白银）；
- 新增 `schema_version` = pydantic 模型源码哈希（字段增删会改产物形状，那也该失效）。

### 1.15 提示词的三处具体缺陷

1. `FULL_EVENT_PROMPT` 的输出模板**缺 `id` 字段**，而代码靠 `id` 把"完整事件"映射回识别阶段的
   规范事件名——映射几乎必然失效，随后靠"名字必须在识别名单里"兜底，**不匹配就静默 `continue`**。
   已补 `id` 字段 + 明确要求回填 + 自检清单加一条。
2. 枚举自相矛盾：实体提示词里出现枚举外的 `关键人物`；`DynastyName` 的示例用了枚举外的"上古"。
   已把枚举扩到实际取值并说明对应关系。
3. 关系 evidence 口径矛盾（正文要求"必须是原文句子"，兜底段又允许"填事件描述"）。
   已统一为"只填原文原句，找不到就留空，不要用整段或概括顶替"。

另外删掉了 `EVENT_TYPE_PROMPT` 与 `EventExtractor.extract_event_type()`——全仓**零调用者**的死代码，
产物里的 `EventType` 一直来自 `FULL_EVENT_PROMPT`。

- **代价提醒**：提示词源码哈希变了 → `PROMPT_VERSION` 换代 → **三阶段缓存全部失效**
  （`config.py` 的 `PROMPT_VERSION_FILES` 注释里写了这件事）。

### 1.16 输入侧加了清洗与章节结构解析

- **输入清洗**（`war_extraction/core/text_cleaner.py`，`--no-clean` 可关）：清不可见字符、
  合并被折断的行内换行、按 `config/text_cleaning.json` 的 `ocr_fixes` 订正确知错字。
  统计写进 `metadata.text_cleaning`。**`ocr_fixes` 默认是空表**——猜出来的替换会静默改掉原文，
  比 OCR 错字本身更难查，所以只登记确知的。
- **分段优先在章节标题 / 段落边界切（带门槛的条件优先级）**：章节/段落切点须落在本段
  55% 之后、句末标点须在 70% 之后才采用，否则回退到字符位置。原先只找句末标点、切点不够就按字符硬切，
  而每段是独立送进模型的，硬切会把一章的开头切到上一段末尾。现在优先级是
  章节标题 → 段落空行 → 句末标点 → 字符位置；段落在 `ChunkExtraction.paragraph_id` 上有编号。
- **原文坐标字段 `source_offset`：已具备，但暂未接线**（第二轮工作单 B1 更正）。
  `ChunkExtraction.source_offset` 是**原文**坐标——清洗会改变文本长度（删不可见字符、
  合并折断的换行、替换错字），所以"清洗后坐标"与"原文坐标"是两回事，换算靠
  `clean_text_with_mapping` 维护的位置映射；`--no-clean` 时两者退化相等。
  **但产物里现在拿不到它**：chunk 级信息从不序列化（`events.metadata.extraction_diagnostics`
  只写段数/缓存命中/失败段数这类计数，没有段级 `paragraph_id`/`source_offset`），
  全仓读它的只有声明、两处赋值、注释与 `tests/test_round2_closeout.py` 的一条用例。
  所以**"人工抽检能回原文定位"这句话目前没有落地路径**，别当成已可用的能力。
  接线时机与方式：等参考标注重建（需要逐条回原文定位）时，把**段级**诊断写进
  `events.metadata.extraction_diagnostics.chunks[]`（每段 `paragraph_id` + `source_offset`
  + 字符区间）。这属于改产物形状，要走整改方案 3.5 的 7 步同步清单；
  不要给每条实体/事件都加偏移——那会显著增大产物体积，而抽检只需要段级起点。
- **"未接线"现在有机械守卫**（第三阶段 D2）：`tests/test_round2_closeout.py::test_source_offset仍未接线`
  按 AST 断言"除 `war_extraction/core/extraction_runner.py`（声明 + 两处赋值）外，
  生产代码**不读** `source_offset`"。这条守卫存在的理由不是"防手滑"，而是**这个状态原先
  只靠文档措辞维持**：写新功能（如人工抽检导出）的人不会知道它没接线，会直接读
  `chunk.source_offset`，然后在产物里找不到。接线时用例会变红并打印"要一起改哪四处"
  （用例本身、本节、README 的"仍未接线"条、整改方案 §3.5 的产物形状同步清单）。
  它按 AST 而不是文本匹配——`main.py` 的注释与 `text_cleaner.py` 的说明都出现过这个名字。

### 1.17 关系阶段失败不再被静默吞掉

原先关系阶段异常时返回"纯派生关系"、编排层记为成功、`ok=True`、**写进缓存**——
"关系阶段其实失败了"在产物里完全看不出来，而且下次命中缓存不再重试。
现在改为三件事同时满足（`RelationStageDegraded` 异常承载规则派生结果）：

- **数据不丢**：规则派生部分照常进产物；
- **失败可见**：该阶段记失败（`stage_ok` 不计、`partial_errors` 有记录、质量报告里
  `relation_degraded_stages` 计数）；
- **可重试**：该段 `ok=False` → **不写缓存**，下次运行重新调模型。

### 1.23 产物记录"实际服务的模型"，并按决策切到 flash + 关思考

**问题**：客户端只存环境变量里的**请求名**，从不读响应的 `model` 字段。而服务端把
`deepseek-chat` 这个别名路由到了 `deepseek-flash`——于是产物 metadata 里的 `model`
是**错的**（写着 `deepseek-chat`、实际跑的是 `flash`）。"产物自证"自证了错信息。

**现在**（三件事一起做）：

| 字段/行为 | 说明 |
| --- | --- |
| `metadata.model` | **请求名**（`DEEPSEEK_MODEL`） |
| `metadata.model_served` | **实际服务名**（取自响应的 `model`）；全部命中缓存没发生调用时为 `null`——那是"未知"，不拿请求名冒充 |
| `metadata.thinking_mode` | `disabled`（默认）或 `auto` |
| 自动关思考 | 命中 `deepseek-flash` / `deepseek-v4-pro` 时自动带 `thinking={"type":"disabled"}`；`DEEPSEEK_THINKING=auto` 可关掉这个行为 |
| 空内容守卫 | 返回空内容时直接报"大概率是思考模式吃掉了可见内容"，不让下游报一句莫名其妙的"JSON 解析失败" |

**为什么必须关思考**（实测，项目自己的密钥）：

| 请求 | served | prompt_tokens | 可见内容 |
| --- | --- | ---: | --- |
| `deepseek-chat` | `deepseek-flash` | 7 | 正常 |
| `deepseek-flash`（默认思考） | `deepseek-flash` | 33 | **空** |
| `deepseek-flash` + `thinking={"type":"disabled"}` | `deepseek-flash` | 7 | 正常 |

也就是说：**显式写 `deepseek-flash` 而不关思考，抽取链会拿到空字符串**——这是"改模型名"
最容易踩的坑。默认模型已按已定决策切到 `deepseek-flash`（`config/.env` 同改），
两条路径逐 token 一致，属零行为变化。

- 文件：`war_extraction/core/llm_client.py`、`utils/provenance.py`、`main.py`、`config/.env`
- 用例：`tests/test_round2_closeout.py` 的 `test_产物记录实际服务的模型` /
  `test_未发生调用时model_served如实为None`

### 1.24 事件-事件关系的发布门槛不再按类型一刀切（`包含关系`/`条件关系` 能进库了）

**改前**：`main.py` 的 `is_high_confidence_event_event_relation` 兜底是
`return relation == "并列关系"`，于是五个规范类型里 `包含关系` 与 `条件关系`
**永远返回 False**。实测同一份产物：raw 有 `包含关系` 28 条 + `条件关系` 1 条，
`published/final.json` 里 **0 条**。而 `published` 是下游 SQLite/Neo4j/RAG 的输入——
这两类关系**在知识库里根本不存在**（不是"少"，是"没有"），
而它们在权威表、前端图谱下拉、RAG 的 `_EVENT_EVENT_RELS` 里都已经是被支持的取值。

**改后**：按"**有没有可判别的证据**"分档，兜底不再拿类型当挡箭牌：

| 类型 | 门槛 |
| --- | --- |
| `因果关系` | 证据里有强因果词（原样保留，仍是最严的一条） |
| `顺承关系` | 证据里**同时出现两个事件名**（原样保留） |
| `并列关系` | 无额外要求（原样保留，本次没有顺手收紧它） |
| `包含关系` / `条件关系` | **证据非空即放行** |

> **表里原先还有一行"枚举外的类型"**（第三阶段 D1 已删）：那一格写的是
> "证据非空即放行"，而**它描述的行为永远不会发生**——分流处先调
> `_relation_enum_ok(rel, "event-event")`，枚举外的类型（如 `主战场`）在到达本函数之前
> 就被挡掉了（也有用例钉着：枚举外的事件-事件关系进候选区）。D1 把兜底收窄成上表四种，
> **其余（含枚举外）一律 `False`**，枚举外的判定只归 `_relation_enum_ok`（它同时负责计数）。
> 函数也因此从闭包提到了模块级（`main._is_high_confidence_event_event_relation`）——
> 闭包只能从"发布分流结果"侧面验证，而**枚举外类型在侧面看没有区别**
> （`_relation_enum_ok` 无论如何都会挡住它），所以侧面断言过不了这条契约。
> 调用点 `and` 顺序**仍然不能换**（换了会让"枚举外"的计数恒为 0），
> 但"正确性"不再依赖它。详见 §1.26。

**为什么这两类只要求"证据非空"、不用线索词。** 线索词规则试过，但它们**没有**
"因此/导致"（因果）或"两个事件名同现"（顺承）那样可靠的判别依据。实测产物里存活的
15 条 `包含关系`，带 `包含/一部分/属于` 这类词的只有 **2** 条；其余证据是**描述子事件的
原句**（如 `后胜于宁远、松山、锦州之战`）——语义上确实是父子关系（父战役含子战斗），
但没有任何可判别的词。只认线索词的话这一类在 `published` 里仍然是 0，
"永远进不了库"这个缺陷等于没修。所以门槛定在"证据非空"，与 `并列关系` 的现有口径同一量级，
把质量判断交给后续评估。

**证据为空一律挡**：放开的是"类型"，不是"证据"。在**同一份旧产物**上跑
`cleanup_relation_conflicts` → `split_publishable_outputs` 实测：
`published` 从 `包含 0 / 条件 0` 变为 **`包含 12 / 条件 1`**（另有 3 条 `包含关系` 因
事件端未同时进入发布子集而留在候选区）。`因果关系`、`顺承关系` 的门槛**没有**被顺手放宽
（有用例钉着：`test_放宽的只有包含与条件两类`）。

- 文件：`main.py`（只改这个门槛函数；第三阶段 D1 后它叫
  `_is_high_confidence_event_event_relation`，在模块级）
- 用例：`tests/test_round2_closeout.py` 的 `test_包含与条件关系能进发布子集` /
  `test_证据为空的包含与条件关系仍被挡` / `test_放宽的只有包含与条件两类` /
  `test_置信门槛不再替枚举外的类型兜底` / `test_置信门槛对包含与条件关系仍按证据非空放行`
- **上线纪律**：改这个函数等于**改整个知识库的内容**（整改方案 3.6）。本轮只改函数 + 加用例，
  **不要单独发布**——必须与产物换代、SQLite 重导、Neo4j 重同步、RAG 快照重建**打包成一次发布**
  （顺序见 §5.2）。单独改而不发布，只会让 `published/` 与库里的数据不一致。
  当前状态：**已修、未上线**。

### 1.26 第三阶段 D 组：把"阶段三要改的东西"变成可测量的数字（D1~D5）

第三阶段工作单把阶段三拆成 D/E/F 三组，**E/F 都有前置**（B 组抽样、C 组核验两条人工线尚未开始），
所以本轮只做 D 组。按工作单的口径：**这一批不改产物、不改指标**——只是让契约与记录自洽、
并给阶段三建好验收线。五项逐条如下。

| 项 | 改前 | 改后 |
| --- | --- | --- |
| **D1** 置信门槛的兜底 | `is_high_confidence_event_event_relation` 末行 `return bool(evidence.strip())`，而 docstring 声称"枚举外的类型…证据非空即放行"——**那个行为永远不会发生**（分流处先调 `_relation_enum_ok` 挡掉枚举外类型）。契约与实现不符，且"安全"完全依赖调用点的 `and` 顺序 | 兜底收窄成只放行 `包含关系`/`条件关系`，**其余（含枚举外）一律 `False`**；函数从闭包提到模块级以便直接断言契约。调用点的注解改成"这个顺序现在只影响计数，不影响正确性" |
| **D2** `source_offset` 未接线 | 状态只靠文档措辞维持：读它的人不会知道产物里没有这个字段，接线时也没人提示该改哪几处 | 新增 AST 守卫用例：除 `extraction_runner.py` 外生产代码不许碰 `source_offset`；变红时打印"接线要一起改的四处"。另加一条反面用例确认声明与赋值**还在** |
| **D3** 事件字段级门禁 | 13 项门禁全在关系与实体侧，而阶段三要改的正是 `Result`/`Aggressor`/`Defender`——改完只能靠看报告 | 新增三项绝对数字：**字段占位词 1897**、**攻守方非组织值 255**、**`Result` 弱值或占位 26**。都是**基线值**、不是"应当为 0" |
| **D4** 包含关系的父子区间 | 没有任何检查：`check_direction_vs_time` 只处理 `顺承关系`。而 `包含关系` 的语义是父含子，子事件区间应被覆盖 | 新增一项**只报数、不进门禁**：实测 28 条包含关系两侧年份都可解析，**10 条**子区间未被父区间覆盖。命名是"**与时间字段矛盾**"，不是"方向错了" |
| **D5** 「过宽概括」特征表 | `main._is_summary_only_event`（4 文本标记 + 2 事件名）与 `EventExtractor._is_summary_style_event`（4 名称标记 + 6 文本标记）**两套表、口径不同**，改一处另一处不动；`config` 里也没有对应键 | 合并进 `config/publish_rules.json` 的 `overbroad_event_markers`，两边都调 `publish_rules.is_overbroad_event`；体检新增"疑似清单 + 前 20 条样本"给 C 组补标与 E4 用 |

**三条要记住的口径**：

1. **D3 的三项是基线值，不是"应当为 0"**。旧产物上就有 1897 / 255 / 26 条命中，门禁的语义是
   "不应比上一版更多"。其中「事件字段写占位词」还有一层特殊性：如实写"不详"是**正确**行为
   （整改方案 2.6.4），E1 的改动方向正是"不确定就写不详"——**这一项上升可能是对的**，
   届时应更新基线并写明理由。
2. **对着旧报告比对照时，缺项要跳过而不是当成 0**。`compare_with_baseline` 现在返回
   `(变差项, 无法比较项)`：基线里没有这一节就跳过并点名（"这一项从此版才开始比"）。
   否则新门禁第一次对照就全红（A2 那个坑的第二次预防）。所以拿**旧报告**
   `health_check_before.json` 对照时会点名「攻守方非组织值」「`Result` 弱值或占位」两项
   "本次不比较"。
   **而"跳过"还有个反向的坑**：如果入库的基线**永远**缺那几节，这几项就等于没有门禁
   （每次只输出"本次不比较"，没人会注意）。所以同步入库了**当前基线**
   `evaluation/baseline/health_check_after.json`（读同一份产物、多了那几节），
   日常对照用它；并由用例 `test_入库基线能取到全部门禁项` 钉住"以后再加门禁项却忘了
   重生成基线"这种情况——那时用例直接变红并给出重生成命令。
   两份基线都记了**产物指纹** `source_sha256`（附录 B 第 26 条），入库的那份另用
   `--note` 写了一句话来历（工具新增 `--note` 参数）。
3. **D5 的合并属于抽取侧改动**：它改变抽取器丢哪些事件，要随重跑生效；且
   `publish_rules.json` 在 `CACHE_CONFIG_FILES` 里，**下一次重跑全部分段缓存会失效**
   （重跑是全额付费，这条要提前算清）。按工作单的约束，本批**没有**顺手调阈值。

- 文件：`main.py`、`war_extraction/utils/publish_rules.py`、`war_extraction/extractors/event_extractor.py`、
  `config/publish_rules.json`、`tools/artifact_health_check.py`- 用例：`tests/test_health_gate.py`（+6，D3 与"缺项跳过"的对照语义）、
  `tests/test_round2_closeout.py`（+4，D1 的契约断言与 D2 的 AST 守卫）、
  `tests/test_decision_filters.py`（+2，D5"config 改一处、两边同时变化"与并集完整性）
- 数字取用：攻守方/`Result` 的形态看体检报告的 `party_not_org` / `weak_result`；
  包含关系的矛盾条数看 `containment_vs_time`；过宽概括清单看 `overbroad_events`。
  **这三节都不进门禁**（D4/D5 先摸清存量，D3 的三项才进）

### 1.27 阶段三 E 组第一处：`Commanders` 派生 `将领`，不再派生 `统帅`（E2）

**改前的矛盾。** 事件的 `Commanders` 字段定义是「**双方主要军事指挥官**」（一个列表），
而关系枚举里 `统帅` 是「最高指挥官」（单数语义），派生规则却把列表里的**每一个人**
都挂成 `统帅`：

```python
person_sources = [("统帅", Commanders), ("参与者", KeyPersons)]   # 改前
```

后果实测：产物 **3,016 条 `统帅` 里 2,767 条（91.7%）来自这条规则**；有 `统帅` 关系的
977 个事件里 **698 个（71.4%）挂着 ≥2 条**，最多 17 条（`平定三藩之乱`、`安庆保卫战`）；
更直接的是同一个（事件, 人物）会**同时**挂 `统帅`（字段映射）与 `将领`（"率兵/统兵"线索），
这类自相矛盾有 **385 条**。

**B 组抽样给了判据。** 规则派生的 `统帅` 例 **10/10 被判错**，而判据里给出的正确说法都是"将领"：
"此役统帅为刘曜，石生并非此役统帅"、"此役明言不设元帅，郭子仪为九节度使之一"、
"张孝忠系从征节度使，统帅应为朱滔"、"马玉昆只率武卫左军担任北面一路，并非统帅"。
另有 14/17 条事件-人物关系错的人**就写在事件的 `Commanders` 字段里**（`刘曜救蒲阪` 的
Commanders 混着敌方石虎、`二破江南大营` 混着清军和春与张国梁）。

**改成什么。** 规则侧 `Commanders → 将领`（与枚举里"中级指挥官"的定义、字段的"列表"语义都相符），
`统帅` 只留给原文明确写出的最高指挥者（由关系阶段按原文抽）。

**干跑实测（同一份旧产物，不调模型）**：关系总数 7,950 → **7,565**、平均 7.7 → **7.4**、
极值 50 → **43**、证据复用 24.1% → **25.1%**；event-person 关系 4,379 → 3,994
（差的那 385 条正是上面那类自相矛盾）。**产物本身没变**——这些要重跑才进产物。

**新增门禁**：「同一事件多条统帅」（旧产物基线 **698**，见 `check_supreme_commander_claims`）。
**目标不是 0**：双方各有一位主帅是合理的（`赤壁之战` 的曹操与周瑜），要看的量级——重跑后
应当显著低于 698，剩下的只有关系阶段按原文抽的那些。

**顺带复核了方向判定（原计划里的第三项）**：`resolve_event_event_direction` 的逻辑没问题，
B 组那 7 条方向错例里 **5 条已被现有代码自动纠正**（证据给了时序或年份能判），剩下 2 条是
**时间数据不可用**：`周文王剪商羽翼之战` 一类两个事件都没有绝对年份（先秦）、
`汉军再攻洛阳` 两条年份相同（311）。**没有改规则**——试过的"同名跨朝代就不取年份索引"
会误伤（21 个同名跨代案例里很多是**同一场战役被不同分段标了不同朝代**，例如 `围攻废丘`
秦/西汉）。改为**把残余量做成报告项**：「顺承方向判不出来」= **277/798（34.7%）**
（证据能判 14 / 年份能判 507），这一档是"方向只能沿用模型给的顺序"的规模，是残余风险不是错误数。

**E3 的机械检查：先定口径，结论是"这条口径不能用"。** 试过"人物的 `OrgName` 是否在他自己的
`source_text` 里出现"：实测 65.5% 不出现，但里面绝大多数是**合法归属**（`禹`→夏部落、
`伊尹`→商——朝代号本来就不必写在那一句里），剔除"组织名含人名"的命名变体后仍有 64.5%；
反过来已知的 3 条归属错例里，`越侯`→东越 的"东越"**字面就在原文里**（他正在进攻东越）。
所以这条检查既误报又漏报，**不做门禁**。E3 真正需要的是"归属方向"的判据（谁属于哪一方），
而那一信息在字段里本来就不存在——与 `Commanders` 是同一个根因。

- 文件：`war_extraction/extractors/relation_extractor.py`（映射）、
  `tools/artifact_health_check.py`（新门禁 + 方向残余项）、
  `war_extraction/prompts/event_prompts.py` 与 `relation_prompts.py`（提示词，**待重跑生效**）
- 用例：`tests/test_derive_relations.py` 新增两条（`Commanders` 派生 `将领`、同一人物不再
  同时挂统帅与将领）；`tests/test_health_gate.py` 的对照语义跟着门禁项一起扩
- 提示词的三处改动（依据都是上面的错例，**改完必须重跑才有效果**）：
  `Commanders` 只写**直接指挥本场战事**的人（后续阶段才出现、只筑城/后勤/外交、战前已死
  只留方略的不要写）；事件关系的 `A` 必须是**按原文时序在前**的那一个；
  关系角色（`议和地点`/`补给地`/`驻防地`/`投降方`/`统帅`/`君主`）**必须由原文直接写出**

> **两份体检基线各是什么、该拿哪份比**：`health_check_before.json` 是加事件字段级检查
> **之前**的报告（所以它没有 `party_not_org`/`weak_result` 两节）；`health_check_after.json`
> 是**当前基线**，由 D3 之后的脚本生成。两者读的是**同一份产物**——本轮没有重跑，
> 产物的 `source_sha256` 都是 `885b0d9e…`。所以"after"记的是**改后的报告口径**，
> 不是"改后的产物"（别按 `baseline_after/` 理解）。**日常对照用 `health_check_after.json`**。

> **"与 `health_check_before.json` 一致"到底证明了什么（别读成"抽取侧没问题"）**：
> 两份基线读的是**同一份 8 月 18 日的旧产物**——`evaluation/baseline/` 与
> `evaluation/baseline_after/` 的 `artifact.sha256` 都是 `885b0d9e…`、
> `metadata.extracted_at` 都是 `2026-08-18 03:37:13`，两份体检报告的
> `counts` / `dangling_relations` / `direction_vs_time` 逐字段相同。
> 所以这项对照只说明一件事：**评估侧口径变更不改变体检项**。
> 它**证明不了任何抽取侧修复**——悬空边、枚举外取值、方向与时间矛盾、关系量级
> **都要等重跑后的产物**才能验证。别把"门禁未变差"当成"抽取侧已改好"而跳过重跑这一步。

### 3.3 抽取侧改动（需要重跑，或用干跑验证）

**先分清"让改动进产物"的三条路，它们的成本差一个数量级**（阶段三 E2 实测后补写）：

| 路径 | 花钱 | 拿到什么 | 什么时候能用 |
| --- | --- | --- | --- |
| **干跑**（在旧产物上直接调那个函数） | 免费 | 只有数字（关系数、量级、错例数…），**不改产物** | 规则类改动（派生关系、方向判定、发布过滤、字段后处理） |
| **缓存重放**（`main.py` 重跑、全部命中缓存） | 免费 | 一份新产物，但**新旧规则的结果并存** | **不要当"生效"用**，见下方实测 |
| **全额重跑**（真正调模型） | 全额 | 唯一干净的产物 | **提示词 / `config/*.json` / `models/*.py` / 模型名**的改动只能走这条 |

**为什么"提示词一改就必须付费"**：缓存键里含 `prompt_version`（提示词目录哈希）、
`config_version`（`aliases.json` / `relation_types.json` / `dynasty_ranges.json` /
`publish_rules.json` 四份的哈希）、`schema_version`（`models/*.py` 哈希）与 `model_name`。
也就是说**这五类东西改了，缓存里的 196 个分段条目全部不命中**（196 是 2026-08-18 那次留下的缓存条目数；**下一次整本重跑按当前分段器是 211 段**，两者不是同一件事——前者数的是缓存里有什么，后者数的是重跑要调用多少次）。这是架构的固有成本，不是流程安排；
能省的只有"把这类改动攒成一批、只跑一次"。

**为什么"缓存重放"不能当生效**（本轮实测，值得记牢）：缓存里存的是**每一段过后处理链的
完整结果**（实体 + 事件 + 关系，见 `extraction_runner.py` 的 `cache.set`），**不是模型的原始回答**。
于是它带着"生成那一刻的规则派生关系"；重放时 `main.enrich_relations_from_events` 会**再派生一次**
（它的注释写着"缓存读取与分段合并之后都要再跑一次"），而合并去重的键是三元组，所以
**旧规则派生的关系不会被新规则替换，而是并上去**。实测：把 `Commanders` 的派生名从 `统帅`
改成 `将领` 之后重放，载荷里同一个人变成 `统帅`（缓存里的旧结果）+ `将领`（新规则）+ `君主` 三条。
方案 §2.5 那句"强行复用会把旧的派生关系一并带回来"说的就是这个机制——**它的后果比那句话更重：
新旧并存**。

**推论（写给下一个要改规则的人）**：改完规则后用**干跑**看数字是可靠的；想让产物干净地
反映新规则，要么让缓存失效（付费），要么先把"可由事件字段重建的派生关系"改成**覆盖语义**
（而不是并存）——后者是个独立课题，且有取舍（同一（事件, 人物）上"模型抽的 `统帅`"与
"规则派生的 `将领`"该留谁，见 §1.27 记的那 132 对）。

干跑的做法：用旧产物的事件跑一次派生逻辑（不调模型）：

```bash
python - <<'PY'
import json
from collections import Counter
from war_extraction.models import Event
from war_extraction.extractors.relation_extractor import RelationExtractor

d = json.load(open('output/中国历代战争简史/9_final_all.json', encoding='utf-8'))
events = [Event(**e) for e in d['events']['events']]
ents = d['entities']
ex = RelationExtractor(None)
res = ex._build_derived_relation_result(
    events,
    "、".join(p['geo_name'] for p in ents['places']),
    "、".join(o['OrgName'] for o in ents['organizations']),
    "、".join(p['PersonName'] for p in ents['persons']),
)
allr = res.event_place_relations + res.event_organization_relations + res.event_person_relations
src = {e.EventName: (e.source_text or None) for e in events}
same = sum(1 for r in allr if r.evidence and r.evidence == src.get(r.EventName))
per = Counter(r.EventName for r in allr)
print("关系数", len(allr), "平均/事件", round(sum(per.values())/len(per), 1), "最多", per.most_common(1))
print("证据复用率", f"{same/len(allr):.1%}")
PY
```

期望（**阶段三 E2 第一处改动之后的值**）：关系数约 **7,565**、平均约 **7.4 条/事件**、
极值约 **43**、证据复用约 **25.1%**。（改之前是 7,950 / 7.7 / 50 / 24.1%：`Commanders`
不再逐人派生 `统帅` 之后，"同一人物同一事件既挂统帅又挂将领"的 385 条自相矛盾被收敛掉，
总数与极值随之下降。）这三个数是**同一份旧产物上干跑**出来的、与产物本身无关；
要让它们真的进产物必须重跑。**别把干跑值当成体检报告里的值**——体检读的是产物，
现在产物上是平均 17.5 条 / 极值 188 / 复用 62.6%（旧规则生成的）。

## 4. 后续修改指南（按场景）

> 每个小节的结构相同：**动哪几处 → 跑什么 → 有什么连带影响**。
> 核心纪律：**权威表是唯一来源，下游一律引用它**；改了不跑用例，就等于赌下游没写死。

### 4.1 新增/修改一个枚举取值（`OrgType` / `Role` / `EventType`）

以"新增 `OrgType="羁縻州"`"为例：

1. `war_extraction/utils/vocabulary.py` → 加进 `ORG_TYPES`；
2. `war_extraction/prompts/entity_prompts.py` → **两处**（属性说明那行 + §六 输出模板的
   `"OrgType": "组织类型（…）"` 提示文字）；枚举只加在下游校验里等于没加，模型不会稳定产出；
3. **不要**再动 `backend/import_json_to_sqlite.py`（它已 `from war_extraction.utils.vocabulary import ORG_TYPES`）；
4. 跑 `python -m pytest tests/test_enum_synchronization.py -q`；
   顺手跑一次 `python tools/artifact_health_check.py`——它会区分「已知例外」与
   「未登记取值」，新加的取值若忘了同步会在这里被点名；
5. 若已经重跑过抽取，还要重导库（否则库里 `org_type` 列只有旧值）。

`Role` 同理（`ROLES` + `entity_prompts.py`），`EventType` 同理（`EVENT_TYPES` + `event_prompts.py` §2）。
**`DynastyName` 例外**：按已定决策不强行统一取值（产物保留原文写法），权威表里只有

### 4.5 改发布过滤规则（`published` 子集）

1. **先确认这不是"改整个知识库内容"**：`published/final.json` 是下游 SQLite/Neo4j/RAG 的输入，
   改它下游**不会报错**，只会"数字变了"；改完**必须与产物换代、重导库、Neo4j 重同步、
   RAG 快照重建打包成一次发布**（§5.2 的顺序），单独改而不发布只会让 `published/` 与库里不一致；
2. 规则本身放 `config/publish_rules.json`（**`overbroad_event_markers`**、后缀、弱结果词、上古标记词），
   `main._is_summary_only_event` / `has_strong_result` / `has_credible_dynasty` /
   `cleanup_events` 都从那里读。**其中「过宽概括」那份表是抽取与发布共用的**
   （第三阶段 D5：`publish_rules.is_overbroad_event` 同时被 `main` 与 `EventExtractor` 调用），
   所以动它**不只是改发布子集，还会改抽取器丢哪些事件**——要随重跑生效；
3. **事件-事件关系的置信门槛在代码里，不在配置里**：`main.py` 的
   `_is_high_confidence_event_event_relation`（因果看强因果词、顺承看双名同现、并列无要求、
   `包含关系`/`条件关系` 看证据非空，其余含枚举外一律 False，见 §1.24 与 §1.26 的 D1）。这是**有意的**：
   `publish_rules.json` 在 `CACHE_CONFIG_FILES` 里，动它会让整本抽取缓存失效
   （＝多付一笔重跑钱），而这条规则只作用于已抽出的关系。要搬进配置就先把这笔钱算清；

4. 判定逻辑（`is_publishable_event` / `event_publish_score` / 各 `has_*` 谓词）在

5. 改前先记录 `backend/data/current_dataset.json` 的计数，改后逐项对比。

### 5.2 付费重跑的正确顺序（顺序不能乱）

**先看"什么时候跑最省"**（阶段三 E2 之后补写）：重跑的费用是**按次**的（每次都要重调整本
211 段的模型），而进缓存键的改动有五类——提示词、四份 `config/*.json`、`models/*.py`、
模型名。所以最省的做法是**把这类改动攒成一批只跑一次**，而不是"改一处跑一次"：

- **改规则（不进缓存键）→ 用干跑验证**（免费，见 §3.3），不必为了它重跑；
- **改提示词 / 配置 / 模型 → 攒批**：把 E1/E2/E3/E4 的提示词与配置改动、以及 E5 的 few-shot
  一起做完再跑；`E5` 必须等 development 集（C 组产出），所以它天然是"最后一批"；
- 第四轮（换模型）也会顶掉缓存键（`model_name` 在键里），要做就并进同一批。

判断标准很简单：**这一批里凡是"模型会说成什么样会变"的改动，都必须等这批跑完才能验收**；
凡是不影响模型输出的，跑不跑都一样，干跑就够。

```text
① 抽取产物换代（python main.py data/中国历代战争简史.txt）
→ ② 重新生成 Excel（跑一次 main.py 会自动做，或单独调 JsonToExcelConverter）
→ ③ import_json_to_sqlite.py --source .../9_final_all.json --yes   （清空并重导知识表，账号不受影响）
→ ④ sync_sqlite_to_neo4j.py
→ ⑤ RAG 快照重建 + 数据治理检查（RAG/scripts/check_docs.py --strict）
→ ⑥ 前端验收（4 个 CRUD 页 + 图谱页 + 数据集中心 + 质检页）
```

重跑前先记录 `backend/data/current_dataset.json` 的计数，跑完逐项对比。
**重跑后必须重跑体检脚本并与 `evaluation/baseline/health_check_before.json` 比对**——
悬空边、枚举外取值、方向与时间矛盾应显著下降，关系量级应落在"平均 7~9 条/事件"，
门禁「枚举外关系名」应为 **0**（已登记的例外已扣除；若不为 0，说明有**未登记**的新枚举外取值，
报告里会点名列出）。

**这次发布同时要带上 §1.24 的发布过滤修复**（`包含关系`/`条件关系` 进 `published`）：
它在重跑前对现有产物没有任何效果，只有随这次换代一起走完 §5.2 六步，

## 6. 注意事项与踩过的坑

1. **写脚本改文件时，heredoc 会吃掉反斜杠**（`\n` 变成真实换行），导致匹配失败、
   甚至把 `print(f"\n…")` 写成跨行的语法错误。改代码请用精确替换工具，
   不要用 shell heredoc 里带 `\n` 的字符串。（这一条在修复历史附录 B 第 22 条也记着。）
2. **改标注 = 改指标分母**。本轮只删了 `sample_events.json` 里一个**空**的 `sub_events` 占位
   （已定决策），评估器不读它，所以数值未受影响；除此之外没动标注。
   任何真正的标注改动都要按 `data/annotations/README.md` 第四节流程留档。
3. **"指标降了"不等于"变差了"**。本轮宏观 F1 从 44.68% 掉到 25.88%，全部来自口径修正。
   报告里必须分开写"口径变化"与"质量变化"，否则下一轮会把这次修正误读成模型退化。
4. **不要用固定 `PYTHONHASHSEED` 掩盖定序问题**，也不要给 CI 钉死它——
   真实用户机器上的种子由解释器随机决定。评估侧的排序是**代码层面的修正**
   （`match_relation_triples` 先按内容定序；新增的 `reduce_event_event_relations` 输出也定序）。
5. **不要为了"让指标好看"调阈值或收紧发布过滤**：调阈值只是换一种错法
   （旧口径下阈值 0.35→0.90 时事件 F1 从 41.75% 降到 23.31%、召回从 87.81% 降到 49.06%，见整改方案 2.6）；
   收紧发布过滤等于改整个知识库内容。
6. **不要为消除实体低分而删除"看起来像噪声"的实体**：历史上用"低质量人名黑名单"整条丢弃，
   结果是预测压根不产生这个名字、连配对机会都没有。正确做法是**别名归一**
   （`entity_classifier.py` 有明确注释，且有用例防止黑名单复活）。
7. **改完记得更新文档**：本轮改了行为的有 `entity-event-relation/README.md`，
   决策与阶段状态回写到整改方案（§0.1 与各阶段状态行），跨轮次归纳写进
   `docs/项目审查与修复历史.md`。文档不要比代码说得满——这条已经反复付学费。
