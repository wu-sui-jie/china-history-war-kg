## 2. D 组：现在就能做（不依赖人工线）

### D1 C1 的函数兜底与枚举校验层职责重叠

**现象。** 上一批为 C1 给 `is_high_confidence_event_event_relation` 换了兜底：

```python
if relation == "并列关系":
    return True
return bool(evidence.strip())      # ← 兜底：非空证据即放行
```

而它的 docstring 写着「`包含关系` / `条件关系` / **枚举外的类型**：证据非空即放行」。
**实际不会发生**——`published` 分流处的条件链是：

```python
EventName_A in published_event_names
and EventName_B in published_event_names
and _relation_enum_ok(rel, "event-event")        # ← 枚举外在这里就被挡掉
and is_high_confidence_event_event_relation(rel)
```

所以 `主战场` 这类枚举外的类型**永远到不了那个兜底**，进候选区（也有用例钉着：
`test_枚举外的事件事件关系会进候选区`）。

**问题在哪**：函数**契约**（docstring）描述了一个它并不产生的行为，而"安全"完全依赖调用点的
`and` 顺序——上一批自己在那行写过"**取值合法性检查必须排在 `is_high_confidence...` 之前**"，
等于承认这个顺序是脆的。下一个人若为了"先算便宜的"而调换顺序，注释还会替这次改动背书：
"函数自己说了枚举外也放行"。

**要改成什么（二选一，建议 ①）。**

- ① 把兜底**收窄**成它真正负责的范围，让契约自洽、不再依赖调用顺序：

  ```python
  if relation in {"包含关系", "条件关系"}:
      return bool(evidence.strip())
  return False        # 其余（含枚举外）由上层 _relation_enum_ok 负责
  ```
- ② 只改注释：写明"枚举外的类型由上层 `_relation_enum_ok` 拦截，本函数不负责判定它们"，
  并把"顺序不能换"的理由就近写上。

**验收。** 选 ① 时新增断言：`is_high_confidence_event_event_relation` 对枚举外类型（构造一条
`主战场` + 非空证据）返回 **False**；选 ② 时只改注释，既有用例保持通过。

**风险。** 这条**不改 `published` 集合**（现状与改后一致），所以它不影响 C1 的"未上线"状态。
真正的风险是放着不管：契约与实现不符 + 顺序敏感，是两个未来缺陷的温床。

### D2 `source_offset` 的"未接线"状态缺机械守卫

**现象。** 上一批选了 B1 的 ②：文档如实改成"已具备字段，但尚未接入产物"。核实结论一致——
生产代码里 `source_offset` **只在 `extraction_runner.py` 被声明与赋值**，无任何读取点：

```
war_extraction/core/extraction_runner.py:133   source_offset: int = 0        （声明）
war_extraction/core/extraction_runner.py:288   source_offset=_source_offset(…)（赋值）
war_extraction/core/extraction_runner.py:363   source_offset=_source_offset(…)（赋值）
main.py:999                                    仅注释里提到
```

产品里出现 **0 次**。

**问题在哪**：现在这个"未接线"只靠**文档措辞**维持。下一个人写新功能（比如"人工抽检导出"）时
不会知道它没接线，很可能直接读 `chunk.source_offset` 却发现**产物里没有**；
反过来，将来真接线时也没有任何提示"该改哪几处文档与哪条用例"。

**要改成什么（二选一，建议 ①）。**

- ① **加一条 AST 守卫用例**（与项目既有做法一致——`test_orchestration_single_entry.py` 就用 AST
  断言"不许自建阶段循环"）：断言除 `extraction_runner.py` 外，生产代码**不读** `source_offset`；
  一旦有人接线，用例变红并逼他同时更新文档与用例。用例里写明"接线时要改哪三处"。
- ② 不加守卫，只在 §1.16 与本节各写一句"接线时要走产物形状同步七步（总方案 §3.5）"。

**验收。** 选 ① 时：新用例通过；文档里不再出现"人工抽检有共同定位坐标"这类**已可用**的表述
（现状已经是"暂未接线"，保持即可）。

**风险。** 选 ① 的守卫要写清"为什么这条断言存在"（否则接线的人会当它是碍事的旧约束）。

### D3 体检缺事件字段级门禁（**本组最该做的一项**）

**现象。** 体检脚本现在有 9 个产物侧检查，全部围绕**关系与实体**：
悬空边、枚举外取值、重复行、残缺年份、占位词当有效值、方向与时间矛盾、证据复用、关系量级、
标注结构。**没有一项检查事件字段的质量形态**——而阶段三（E 组）要改的恰恰是
`Result` / `Aggressor` / `Defender` 这些字段。

现有的 `check_placeholder_as_value` 报了占位词条数，但它**只是信息项、不进 `_GATE_PATHS`**，
也不看"填了但明显是错的"那类形态。

**当前基线（同一份旧产物，供改后对照）**：

| 指标 | 值 | 现状含义 |
| --- | ---: | --- |
| `TroopSize` / `Duration` / `Casualties` 写占位词 | 629 / 585 / 657 | 如实写"不详"是正确行为，**但比例要有数** |
| `Result` 值准确率 | 16.1% | 最差的一项；方向词比对口径下 |
| `Aggressor` / `Defender` 值准确率 | 34.3% / 42.8% | 攻守方与标注对不上 |
| 一字实体 | 地点 215 / 组织 58 / 人物 25 行 | 需逐类判定，尚无判定依据 |

**要改成什么。** 在 `tools/artifact_health_check.py` 新增 2~3 项**绝对数字**并纳入 `_GATE_PATHS`
（改完应当不增加）：

1. **字段占位词率**（把现有 `check_placeholder_as_value` 的计数升为门禁项，按字段分列）；
2. **攻守方里的"非组织值"**：用现成的 `EntityClassifier.is_valid_org_name` + 各字段词表，
   统计 `Aggressor`/`Defender` 里混进人名或地名的条数；
3. **`Result` 的弱值/空泛值**：复用 `config/publish_rules.json` 的 `weak_result_tokens`
   与 `Normalizer.is_placeholder_value`，统计"看起来有值、其实无法判定胜负"的条数。

**验收。** 体检报告多出这几项、`--baseline` 能比增减；新增用例放在 `tests/test_health_gate.py`：
构造一条"攻守方填人名"的事件，断言该项 +1。**不依赖参考集**，因此这就是阶段三的验收线。

**风险。** 门禁项要求"改完不增加"，所以**第 2、3 项的判定规则要先在旧产物上跑一遍**：
若旧产物本身就有大量命中（很可能），就把它们记为**基线值**而不是"应当为 0"，
否则门禁一建就是红的（上一批 A2 刚踩过"门禁恒非零"这个坑）。

### D4 包含关系的父子时间一致性检查

**现象。** 上一批放行了 `包含关系` 进 `published`（C1），门槛是"证据非空"。但 `包含关系` 的语义是
**父事件包含子事件**，因此有一条不依赖参考集的机械检查：**父事件的时间区间应包含子事件的**。
现在没有任何地方检查它——`check_direction_vs_time` 只检查 `顺承关系`（A 晚于 B 却标顺承）。

**要改成什么。** 在体检脚本里加一项：对每条 `包含关系`，若两侧起止年份都可解析，
统计"子事件区间未被父事件区间包含"的条数。**先只报数、不进门禁**（第一篇先摸清存量，
摸清后再决定是门禁还是候选区标记）。

**验收。** 体检报告新增该项并给出存量条数（旧产物上先跑一次得到基线）；不改变任何产物内容。

**风险。** 别把"父/子方向本身就是模型猜的"当成事实——这项检查只能发现"方向与时间字段矛盾"，
方向错了它可能反向报错。所以命名要写清是"**与时间字段矛盾**"而不是"错了"。

### D5 "过宽概括"事件的机械统计

**现象。** 事件粒度口径已定（过宽概括如"蒙金战争"不算事件、具体战役算；见总方案 10.1 第 1 项），
但落地只有两条零散的代码表：`main._is_summary_only_event` 的 4 个文本标记 + 2 个事件名，
`EventExtractor._is_summary_style_event` 的 10 个标记（4 个名称标记 + 6 个文本标记）。**两套表口径不同、也没有存量统计**——
而 C 组补标（人工）正需要"哪些条疑似过宽"这份清单。

**要改成什么。** 两步（都要做，顺序不能反）：

1. 把两处特征表合并进 **`config/publish_rules.json`**（新增 `overbroad_event_markers` 键），
   让 `main` 与抽取器读同一份——这是"改一处生效两处"的前提；
2. 体检脚本加一项统计：**疑似过宽概括的条数**并给出前 20 条样本（事件名 + 朝代 + source_text 片段），
   作为 C 组补标与 E4 的输入。

**验收。** 体检报告能列出疑似清单；`config` 改一处、`main` 与抽取器的行为同时变化（可用现有
`test_decision_filters.py` 的风格加一条断言）。

**风险。** 合并两处表会**改变抽取行为**（原两处口径不同：一处 4 标记、一处 7 标记）——
属于抽取侧改动，要随重跑生效；不要在同一批里既合并表又调阈值。

## 3. E 组：阶段三的主体（等 B/C 结论，先写判据不写改法）

这一组是路线图里"**按抽样与核验的结论改抽取规则**"本身。以下每项只给
**输入、判据、验收口径**——改法必须等结论出来再定。

### E1 字段准确率最差三项（`Result` / `Aggressor` / `Defender`）

- **输入**：B 组抽样判定里"事件字段"那一层的错误分布（是漏抽、错抽、还是口径不同）。
  当前值：`Result` 16.1%、`Aggressor` 34.3%、`Defender` 42.8%（同一份旧产物、231 对已配对事件）。
- **判据**：先把错误分成三类——① 原文没写（应当留空/不详）；② 抽到了但填错（换人/换方）；
  ③ 填对了但与标注口径不同（如标注写"周武王"、产物写"周军"）。**三类的改法完全不同**：
  ①只需在提示词里强化"不确定就写不详"；②要在提示词里加判别依据；③是**评估口径**问题，改抽取没用。
- **验收口径**：用 `evaluate_event_field_accuracy` 的值准确率 + D3 新建的字段级门禁，
  在**同一份产物**上前后对比；若改的是提示词，则必须等重跑后的产物。
- **明确不做**：不为了提准确率而让模型"猜"——数值/结果类字段**宁可留空**（总方案 2.6.4）。

### E2 派生关系继续收紧

- **输入**：抽样判定里关系层的错误形态（同句线索是否真的支持该关系）。
- **判据**：当前派生关系的证据已是同句，但仍可能有"同句出现 ≠ 语义成立"的情况
  （如句子里有"议和"二字、组织只是旁观者）。
- **验收口径**：体检的 `relation_volume`（当前平均 7.7 条/事件、极值 50）与 `evidence_reuse`
  （24.1%）作为绝对数字门禁；质量要看抽样。
- **约束**：不要退回"整段文本当证据"（那是上一轮修掉的）。

### E3 实体噪声治理

- **输入**：抽样判定里实体层的错误类型分布。
- **判据**：当前已知的噪声形态——一字实体（地点 215 / 组织 58 / 人物 25 行）、
  括号拆裂碎片（已在 `Normalizer` 加了两条半括号规则）、跨类型冲突（人名被判成组织等）。
- **验收口径**：`check_duplicates` + 实体计数（`identity` 块的行数/唯一名数）作绝对数字；
  质量看抽样。
- **明确不做**：不用"黑名单整条丢弃"（项目为此吃过一次亏，有用例钉着）。

### E4 事件粒度口径落地

- **输入**：C 组补标后的参考集 + D5 的疑似清单。
- **判据**：总方案 10.1 第 1、2 项已定口径；落地要**两侧同时**改（预测侧规则 + gold 补标），
  只放宽一侧的话 P 依然低。
- **验收口径**：`check` 层的疑似过宽条数（D5）应下降；事件 P/R 只能在该子集的参考集上读。

### E5 提示词真实语料 few-shot（上一批的 C2）

- **输入**：development 集（参考标注重建的产物）。
- **判据**：没有能验证"加了有没有用"的集合之前不做——否则是凭感觉改提示词。
- **验收口径**：development 上的抽样精确率前后对比 + 置信区间；**区间重叠就不声称变好**。

### E6 `EventType` 取值域与 RAG 27 类词典对齐（上一批的 C4）

- **输入**：重跑后产物的**实际** `EventType` 取值分布。
- **判据**：先定方向——以权威表（29 值）为准改 RAG 词典，还是以 RAG 词典（27 项）为准收窄权威表。
  `RAG/docs/data-contract.md` 写的是"27 类、无空值"，这条要一起改。
- **验收口径**：`dicts.json` 的类型数与权威表一致；RAG 侧 `check_docs.py --strict` 通过。

## 4. F 组：发布与重跑（C1 的上线打包）

**重跑前的提醒**（与本轮改动直接相关）：模型名已切到 `deepseek-flash` + 关思考，

## 7. 不要破坏什么

1. **评估的可复现性**：`match_relation_triples` 先按内容定序；不要用固定 `PYTHONHASHSEED` 掩盖顺序依赖。
2. **规范事件-事件关系类型要求精确相等**（`relation_types_match`）：退回纯模糊会让类型判错也拿满分。
3. **`gold` 按集合、`pred` 按条**这个不对称是有意设计，有断言钉着；动匹配逻辑不能改它。
4. **枚举权威表是唯一来源**（`war_extraction/utils/vocabulary.py`）：`test_enum_synchronization.py`
   直接读前端 `.vue`、RAG `field_map.py`、导入脚本比对，改一处漏一处就会红。
5. **派生关系的"同句证据"不变式**：传进规则函数的 `sentence` 由 `_entity_sentence` 保证含该实体名；
   线索词用连写形式或两字以上短语（单字命中率过高）。
6. **关系阶段降级不写缓存**（`RelationStageDegraded`）：数据不丢、失败可见、可重试三条同时成立。
7. **缓存键的因子只增不减**：`CACHE_CONFIG_FILES` 刻意不含 `eval_config.json`；
   D5 把特征表搬进 `config/publish_rules.json` 后，该文件**已在** `CACHE_CONFIG_FILES` 里，
   所以改它会自动让缓存失效——**这条要提前算清**（重跑是全额付费）。
8. **C1 未上线的状态标记要留到发布完成**：不要因为"代码里已经改了"就把它当成已生效。
