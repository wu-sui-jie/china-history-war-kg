## 0. 先记住三条路径（它决定每批怎么验）

| 路径 | 花钱 | 拿到什么 | 适用 |
| --- | --- | --- | --- |
| **干跑**（在旧产物上直接调函数） | 免费 | 只有数字，不改产物 | 规则类改动（派生关系、方向、发布过滤、字段后处理） |
| **缓存重放** | 免费 | 一份新产物，但**新旧规则的结果并存** | **别当生效用**（实测：`统帅` 与 `将领` 会同时出现） |
| **全额重跑** | 全额（整本 **211 段 × 3 阶段 = 633 次调用**；文档旧写的 196 是 2026-08-18 那次的分段数，分段器在 09-26 改过） | 唯一干净的产物 | 提示词 / `config/*.json` / `models/*.py` / 模型名 的改动 |

**进缓存键的只有这五类**：`prompt_version`（提示词目录）、`config_version`
（`aliases` / `relation_types` / `dynasty_ranges` / `publish_rules` 四份）、`schema_version`
（`models/*.py`）、`model_name`、分段参数。**改这五类之外的东西都不该付重跑的钱。**

### 3.0 dev 指标怎么算（照抄即可，2026-09-27 实测跑通）

参考集按朝代块切，而抽取是在**文本文件**上跑的：一个子集一份产物。dev = 唐 + 秦汉，
所以要两步——**先各跑一次子集抽取，再合并成一份与 dev 同范围的预测**：

```bash
cd entity-event-relation
python main.py data/dynasty_subsets/唐.txt            # 29 段 × 3 阶段 ≈ 87 次调用
python main.py data/dynasty_subsets/秦汉.txt          # 28 段 × 3 阶段 ≈ 84 次调用

# 合并（dev 横跨两个子集；不能拿整本产物切一刀代替——产物里没有字符坐标）
python tools/merge_extraction_outputs.py     --inputs output/唐/9_final_all.json output/秦汉/9_final_all.json     --output <仓库外>/dev_唐秦汉/9_final_all.json

python evaluate.py --pred <仓库外>/dev_唐秦汉/9_final_all.json     --annotations-dir data/annotations/v2_split/dev --output <仓库外>/eval_dev
```

test 侧（明）同理：`python main.py data/dynasty_subsets/明.txt`（13 段 / 39 次），
合并不需要（只有一份），`--annotations-dir data/annotations/v2_split/test`。**test 只用一次。**

**第一次跑出来的数（2026-09-27，唐 + 秦汉 = dev 221 事件）**——这是**第一份范围对齐、
且分母可信**的指标，之前的数（宏观 26.9% / 44.5%）都是"全书产物 vs 子集参考集"的错配产物，不能用：

| 层 | P | R | F1 |
| --- | ---: | ---: | ---: |
| 实体 | 64.69% | 78.75% | 71.03% |
| 事件 | 55.56% | 76.92% | 64.52% |
| 关系 | 52.91% | 86.53% | 65.66% |
| **宏观** | — | — | **67.07%** |

口径：`--annotations-dir data/annotations/v2_split/dev`，产物 = 唐 + 秦汉合并（事件 333 / 关系 4227，
`relation_degraded_stages` 均为 0），`model_served = deepseek-flash`、
`prompt_version = prompt-v2-20260420+1228b39b`、**`seed = null`（未固定随机种子）**。

**三层都是"召回高于精确"**（P 53~65% / R 77~87%）：模型抽出的比参考集里的多。注意参考集本身
只覆盖三个子集、且事件层是"人工判过"的——FP 里有多少是模型真错、有多少是**参考集仍然漏收**，
这份 gold-F1 分不出来。要分清得走人工抽样判定那条线（§3.1 里 E5 那条说的同一件事）。

**两个要盯的读数**：

- 产物的 `quality_report.diagnostics.relation_degraded_stages` **必须是 0**。
  它非 0 说明有关系阶段被降级成规则派生（模型把四类关系摊成扁平数组时会发生，见
  [`../../../docs/项目审查与修复历史.md`](../../../docs/项目审查与修复历史.md) §25）——
  那一段的模型关系全丢，指标会被它拖低，**先查这个数再谈指标**。
- 产物 metadata 的 `model_served` 要与 `model` 一致；`seed` 目前恒为 `null`
  （**流程没有固定随机种子**），所以同一配置跑两次的结果不完全可复现——
  比较 A/B 时要意识到这层噪声。

## 4. 不要破坏什么

1. **别为了"看效果"而重跑**：规则类改动一律先干跑（免费，见 §0 与指南 §3.3）。
2. **别单方面收紧预测侧**：E4 的表与 gold 补标要**两侧同时**动（只收紧一侧，P/R 朝不可解释的方向走）。
3. **别用缓存重放冒充生效**：新旧规则的结果会并存，实测会把同一人物挂上 `统帅` 与 `将领` 两条。
4. **别动那份冻结的抽样基准**：`evaluation/review/sample_20260926.csv/.json` 是跨版本对比的定位基准，
   判定结果只回填 `_with_source` 那份（规范 §1）。
5. **别在有可信集合之前声称变好**：置信区间重叠就不声称（这是整改方案定的口径）。
6. **别把"已修未上线"当成已生效**：§3 那张表是唯一依据。
