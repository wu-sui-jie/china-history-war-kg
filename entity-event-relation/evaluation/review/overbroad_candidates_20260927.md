# 「过宽概括」候选清单的判定材料（E4 预测侧扩表）

> **这份文件是什么**：`tools/artifact_health_check.py` 那份「过宽概括**形态式候选**」清单的逐条判定材料，
> 给 **C 组**（人工）决定"哪些特征该进 `publish_rules.json` 的 `overbroad_event_markers`"。
> 出这份材料的是机器（只报数、只分类、**不改表**），**判定归 C 组**。
>
> **生成的清单**：`python tools/artifact_health_check.py` 的
> 「过宽概括**形态式候选**」一节，29 条（占产物 1050 个事件的 2.8%），形态取自实测：
> 事件名含「战争」24 条、含「统一」6 条、结尾「之役」1 条（有重叠）。

## 0. 为什么现在才能改表（两侧同时改的那条纪律）

`overbroad_event_markers` **同时**被发布过滤与抽取器的识别过滤使用（D5 合并的），
所以改它等于**预测侧单方面收紧**。纪律要求**两侧同时改**：预测侧扩表 **＋** gold 补标。

**gold 侧现在已经满足了**：重建后的参考集 `data/annotations/v2/` 里，按同一形态筛过一遍
**一条都没有**（实测 0/296）——也就是说人工核验时已经把这些过宽概括判掉了。
所以"单方面收紧"的风险不再存在，扩表这件事**技术上已经解封**；剩下的纯粹是"哪些特征该进表"的判断。

## 1. 一条必须先看见的陷阱

**「战争」这个词不能直接当特征。** 29 条里有 **4 条**是这种形态：

```
清缅战争第一次战役 / 清缅战争第二次战役 / 清缅战争第三次战役 / 清缅战争第四次战役
```

它们名字里含「战争」，但**各自是一次具体战役**（清缅战争的四次用兵，时段不同、战果不同）。
把「战争」直接加进 `event_name_markers`，这 4 条会被一并过滤掉——那是**误杀**。

批一给这份清单时，同一类的教训已经写下来了：`霍邑战役`、`邙山会战`、`旅顺战役` 都是具体战役，
所以特征表**刻意不含「战役」「会战」**。这次要小心的是「战争」本身也不够格，
必须再加一个条件（例如"含「战争」**且不以「第N次…战役」结尾**"，或直接按下面的分类逐条列名）。

## 3. 建议的落地形态（给 C 组的两条路）

**路一（保守、推荐）**：只把 A 表的 19 条**按名字列进** `overbroad_event_markers.event_names`
（该表本来就支持逐名列举，`少康中兴`、`商代之远征` 就是这么进去的），
**不动** `event_name_markers` 的「战争」「统一」这类词级特征。
好处：零误杀、可逐条回溯、与"人工判定"这件事的性质一致（是判定，不是猜规律）。

**路二（激进）**：加词级特征「战争」「统一」，并补一条排除规则
（名字匹配 `第[一二三四五六七八九十]+次.*战役$` 的不算）。
好处：以后同类命名能自动兜住；代价：多一条需要维护的排除规则，且要先验证它在本书上不误伤。

**无论走哪条路，改 `publish_rules.json` 都会改 `config_version` → 抽取缓存全部失效（重跑是全额付费），
所以它必须并进批二那一次重跑**，不要单独跑。

## 4. 判定结果怎么回填

判定完成后，把结论写回本文件（把每个名字标成"进表 / 不进表"，并写下判据），
然后在当时的收尾执行单 §3 的待重跑清单里把 E4 那一行从"待 C 组判定"改成"已判定、待重跑"
（该清单已随收口删除；E4 的最终判定是**不做**，理由见模块 README 的「决策留档」）。
**没有这一步的话，下一个接手的人只会看到"清单里有 29 条"，不知道哪几条已经判过了。**
