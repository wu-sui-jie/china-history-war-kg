# feishu-bot 修复历史

本文件按主题归纳本模块历次修复的结论，只保留**仍影响当前代码的知识**：约束、不变量、
失败后果、验收口径、待决策项与未完成事项。逐条过程细节由 Git 历史承担（文末给出提交清单），
用例数与命令输出保留为证据。

相关文档：[需求与方案](需求与方案.md)（目标与分期）、[开发文档](开发文档.md)（设计与契约）。
实现与设计不一致时，以开发文档的「实现说明」小节为准。

## 一、卡片 2.0 迁移的收尾

**问题**：卡片整体迁到 2.0 规范（`schema: "2.0"` + `body.elements`）后，冒烟脚本
`scripts/local_smoke.py` 仍在按 1.0 形态取按钮（找 `tag == "action"` 容器与顶层 `value`）。
结果是按钮摘要恒为空、纠错反馈那一步打印"没有反馈按钮"就跳过——脚本不报错、退出码仍 0，
**验证环节静默失效**。

**现状与做法**：脚本的取值改为复用 `tests/card_helpers.py`（`buttons()` / `elements()` /
`feedback_msg_key()`），它是卡片取值的唯一实现；同时补上"非降级卡片缺反馈按钮时以
退出码 1 报错"（降级卡本来就不带按钮，不算异常）——把静默失效变成显式失败才是这条的要点。

2.0 的硬约束（写错会被飞书拒收整张卡片，实测 `code 200621`）：

- `collapsible_panel.border` 必须是对象且**只**接受 `color` 与 `corner_radius`；
- 按钮的回传参数必须放在 `behaviors[type=callback].value`，顶层 `value` 是 1.0 字段；
- 按钮是 `body.elements` 的**直接成员**（2.0 删掉了 `action` 容器）；
- 卡片要能 PATCH，`config.update_multi` 必须为 `true`。

**验证证据**：`data/smoke/*.json` 产物为 `schema: "2.0"` 且 `wide_screen_mode` 已消失；
`tests/test_cards.py` 有 2.0 合规守卫（组件 tag 白名单、`config`/`border` 键白名单，
占位卡也已纳入守卫）。

## 二、"成对写入"与死代码

**问题**：`dispatcher._record_assistant` 是全仓库无人调用的死代码，且与现行落库规则矛盾——
它只写 assistant 行，而现行规则是**能入历史的轮次才成对写 user + assistant 两行**。
留着它的风险是后来者误当可选路径调用，命令轮（如 `/help`）会重新混入历史。

**现状与做法**：该函数及其 docstring 已删除。`_record_turn` 是唯一落库入口，返回
`(user 行 id, assistant 行 id)`：第二个 id 是卡片按钮的 `msg_key`，第一个 id 只在发送失败
撤回本轮时用得到。

**为什么这条约束很硬**：历史参与 RAG 回答缓存的键。曾经的实测是同一个"介绍一下长平之战"
因为多了一条 `/help` 历史，从 34ms 的缓存命中变成 16–25s 的真生成，直接顶穿机器人 25s 预算。
降级/失败轮次同理：没有回答的孤立提问对模型没有价值，却照样污染上下文与缓存键。

**验证证据**：`grep -rn "_record_assistant" --include="*.py" .` 零命中；
`tests/test_dispatcher.py` 与 `tests/test_session.py` 覆盖成对写入、顺序与撤回。

## 三、示例题缓存：负缓存与窗口取档

**问题**：`DemoExamplesCache.refresh` 的守卫要求缓存**非空**（`fresh and self._questions`）。
接口失败或返回空列表时 `_questions` 保持为空，守卫永远不成立，于是**每次组卡都同步重打一次**
`GET /api/demo/examples`；端点不可用时最坏吃满 connect 5s + read 25s 的客户端超时，直接叠加在
用户等待时间上（单 worker 下还会排队放大）。

**现状与做法**：成功与失败两条路径都记刷新时刻，窗口按"上一次刷新是否失败"（`_last_fetch_failed`
标志，失败置位、成功清位）取不同值——成功后按 `DEMO_EXAMPLES_REFRESH_SECONDS`（默认 3600s）刷，
失败后按 `DEMO_EXAMPLES_FAILURE_RETRY_SECONDS`（默认 300s）再试。失败窗口必须为正数，且被
`min(failure_retry_seconds, refresh_seconds)` 夹住，不会比成功窗口更宽松。失败时旧题目照旧展示
（`_questions` 不动），只是下次刷新提前到 5 分钟后。

窗口按"上次是否失败"而不是"当前有没有题目"取档，是因为后者会让"留有旧题目、本次刷新失败"的
情形仍等满一小时——接口恢复了按钮区却迟迟不更新。

**顺带修掉一处同类隐患**：初始状态由 `_fetched_at = 0.0` 改为 `None`（"从未取过"显式化）。
原写法要靠"真实时钟远大于刷新窗口"才成立，注入假时钟就变成"启动后先假装缓存是新鲜的"。

**验证证据**：`tests/test_skills.py` 覆盖四条——失败进负缓存窗口、过窗口后再试、
失败窗口不超过成功窗口、留有旧题目时失败走短窗口。

## 四、发送链路：重试、幂等与"发送失败撤回本轮历史"

**问题**（线上实测）：RAG 5.9s 正常返回（`finish=normal`、10 条引用、4 个 panel 区），组卡后调
飞书 reply 时对 `open.feishu.cn:443` 的 TLS 连接被对端掐断（`SSLEOFError(8,
'UNEXPECTED_EOF_WHILE_READING')`），异常一路抛到 `worker_loop` 的兜底 catch，只留一条 ERROR 日志。
影响三层：用户侧纯沉默、历史被污染（这轮问答已入库）、无法自愈（同一 `event_id` 重投会被去重丢弃）。
根因：`lark_oapi/core/http/transport.py` 用 `requests.request(...)` 且无重试配置，
`HTTPAdapter` 默认 `max_retries=0`。

**现状与做法**（两层）：

- `bot/feishu_client.py` 的 `_call_with_retry`：reply / send_card / patch_card / upload_image 共用，
  只重试**传输层**异常（连接 / SSL / 超时）2 次，退避 0.5s / 1s；业务错误码（`resp.success() == False`）
  不重试。重试耗尽后**抛给调用方**——`dispatcher` 需要区分"这次真没发出去"与"发出去了但没拿到 id"，
  前者要撤回本轮历史，后者不该动数据。
- `bot/dispatcher.py` 的 `_send_reply` 捕获发送失败返回 `None`；最终失败时调 `_discard_unsent_turn`
  把刚落库的 user + assistant 两行**一起撤回**，答案全文打进 ERROR 日志供人工补偿，观测计数
  `send_failed` +1（不算任务失败）。

三条"必须"，都是踩过才知道的：

1. **reply / create 必须传 `uuid`，且必须在重试之间保持不变**（飞书按它做服务端幂等去重）。
   否则"请求实际到达但响应丢失"的重试会发出第二条消息，裸重试反而引入重复回答。
   图片上传与 PATCH 没有 uuid 语义：前者飞书不支持，后者 PATCH 本身幂等（同样的 content 再发一次结果相同）。
2. **每次尝试必须重建请求对象**：SDK 首次发送会把 `request.body` 换成 `MultipartEncoder`
   （`api/im/v1/resource/image.py` 里 `request.body = form_data`），复用同一个请求对象重试读到的是空流。
   因此 `_call_with_retry` 接收"可重复调用"的闭包，而不是现成的请求对象。
3. **上传图片必须把文件指针复位**：`prepare=lambda: handle.seek(0)` 在每次尝试前调用，
   否则第二次读到 EOF（发出去一张空图）。

**为什么发送失败要撤回历史**：这是"成对写入"原则的另一面——用户从未见过的回答不该留在历史里。
留着它有两个实害：下一轮上下文带着一条用户没看到的回答；**更实际的是历史参与 RAG 回答缓存的键**，
多一条这样的历史就让本该毫秒返回的问题退化成十几秒的真生成。代价是下一轮丢失这轮上下文，
这是可接受的取舍。

**决策点（已确认保留）**：审核意见为保留"发送失败撤回本轮历史"，理由：与成对写入是同一条原则的两面；
撤回动机（历史参与缓存键）是本模块真机踩过两次的坑；测试断言已随行为同步改写。
退回成本：删 `handle_message` 里 `else: self._discard_unsent_turn(...)` 三行并改回测试断言。

**环境侧缓解**：部署机挂系统代理（Clash 等）时这类 TLS 抖动更常见，给机器人进程设
`NO_PROXY=open.feishu.cn` 或关代理可消掉大半；worker 未死、`failed` 计数不增属设计内行为。

**验证证据**：`tests/test_feishu_client.py` 用记录式 HTTP 替身锁定"失败 2 次后成功 = 3 次尝试、
三次尝试 uuid 相同、耗尽后抛异常、业务错误码只试 1 次、上传重试两次的读位置都是 0"；
`tests/test_dispatcher.py` 与 `tests/test_integration.py` 锁定"两行被删、`history_for_rag` 为空、
`send_failed=1` 而 `failed=0`、worker 存活"。**真实飞书侧的重试 / 幂等表现至今未验证**（见第七节）。

## 五、低优先级项与并发边界

| 项 | 现状与做法 |
| --- | --- |
| 停机收尾 | `Dispatcher.stop(timeout)` 可传等待时长；`Application.close()` 传 RAG 预算（`RAG_QUERY_TIMEOUT + RAG_CONNECT_TIMEOUT + 5s`），避免在途查询被 `rag/db.close()` 打断后抛吓人堆栈；等太久仍可连按两次 Ctrl-C 走 `os._exit(0)` |
| 群聊 @ 剥离 | `strip_mentions` 只剥**本机器人**的 mention（按 `open_id` 比对）："介绍一下 @张三 提到的赤壁之战"里 @张三 必须留在问题里。拿不到 bot open_id 时退化为"只剥文本开头那一个 key"——宁可少剥，不要多剥 |
| 命令匹配 | `/help`、`/帮助`、`/?` 统一按"文本第一个词"命中（`base.matches_command`），`/帮助 长平之战` 与 `/help 长平之战` 同规则；也天然排除 `/helpx` 这类"以命令开头的新词" |
| ws 日志级别 | 跟随 `BOT_LOG_LEVEL`（不再硬编码 INFO），排查长连接问题时能降到 DEBUG |
| 孤儿扫描 | `scripts/cleanup_db.py` 把 `role` 并入首条 `SELECT`，删掉逐行回查与模块级缓存（顺带消掉缓存跨 `dry_run` 的脏读隐患） |
| `feedback` 表无 TTL | `SessionStore.cleanup()` 注释与开发文档 5.7 都写明：它是治理队列，**不在清理范围内**，需人工导出归档——别把"清理脚本每天跑"当成"反馈有人管" |
| pytest 输出 | 按消息精确过滤 SDK 的 `ExpiringCache._start_clear_cron was never awaited`（RuntimeWarning 在 `pytest.ini`，退出时的 asyncio ERROR 在 `tests/conftest.py`）。这是**压掉**而不是修掉的：SDK 自己起了清理协程却从不 await/取消，本端无法修；只丢这一条，其它 asyncio 日志照常输出 |
| 队列上限 | 队列有界（`QUEUE_MAX_SIZE`，默认 200），满时**快速拒绝**并回一条"当前繁忙"（按会话冷却，可关）。无界队列在消息突发时会一路吃内存直到进程被 OOM 杀掉 |
| 停机不死锁 | `stop()` 不靠往队列塞哨兵消息唤醒 worker（`put(None)` 在队列满时会阻塞，表现为"按了 Ctrl-C、日志说正在停止、进程却退不出来"），改为 `get(timeout=...)` 轮询 `_stop` |
| 认领可撤销 | 认领 → 入队 → 坐实三步，入队失败必须 `release()`：否则队列满时被拒的消息会被自己的去重记录永久挡在门外（`rejected_busy` 可被重投重新认领） |
| 卡住事件恢复 | `recover_stuck_events()` 在 worker 启动**之前**把超过 10 分钟仍是 `processing` / `received` 的行扫回可重认领状态。为什么需要：`processing` 在 `_CLAIMED_STATUSES` 里，进程被强杀（SIGKILL / OOM / `os._exit(0)`）会永久留下一行，飞书重投被当重复丢弃，那条提问连同用户界面上的占位卡一起永久卡死。阈值取 10 分钟是为了不抢"正在跑"的任务——抢回来会让同一条提问被回答两次 |
| 使用范围白名单 | `FEISHU_ALLOWED_CHAT_IDS` / `FEISHU_ALLOWED_OPEN_IDS` 已实现，命中任一即放行，两个都空 = 不限（内网默认）。判定放在服务端收到消息的那一刻；不在名单内**不回消息**，只记日志与计数 |
| 老库补列 | `CREATE TABLE IF NOT EXISTS` 不给已存在的表补列，`_COLUMN_MIGRATIONS` 让升级就地把老库带上（`processed_events.status` 默认 `accepted`，与"历史事件已记账"的语义一致） |

## 六、两段式回复与 `/new`

### 6.1 两段式回复（占位卡 → PATCH 整卡替换）

**问题**：知识问答同步等 RAG，介绍类长回答实测 12–25s，用户干等且会怀疑机器人没反应。

**现状与做法**：`Skill` 协议新增可选类属性 `wants_placeholder`（当前只有 `KnowledgeQaSkill`
声明为 `True`）；`dispatcher` 在执行技能**之前** reply 一张"正在检索…"占位卡，技能跑完后
`patch_card` 整卡替换**同一条消息**（不新增消息），最后回填 `bot_message_id`。

- `bot_message_id` 指向占位卡那条消息是**有意**的：PATCH 前后用户看到的始终是同一条消息，
  因此反馈工单的 `(open_id, message_id)` 去重口径与 `report_error` 的回退取值都自然成立。
- 为什么"要不要占位"由技能声明：慢的是"同步等 RAG"这件事本身，将来别的慢技能自己声明即可；
  `/help`、`/new` 这类命令与提示卡秒回，不声明就走单段式，不必在 dispatcher 里按技能名硬编码白名单。

三条失败路径的处置：

| 失败点 | 处置 |
| --- | --- |
| 占位卡没发出去（传输层抖动） | 退回单段式：技能跑完后按普通 reply 发一条新消息 |
| 最终卡 PATCH 失败 | 尽力再 PATCH 一次"发送失败"提示卡（不能让用户停在"正在检索…"）；本轮历史照旧撤回 |
| 占位卡发出的轮次最终降级/异常 | 降级卡同样 PATCH 到占位卡上（占位卡不能留在屏幕上转圈） |

**决策点（已按读法 B 实现）**：原话"占位卡已发但最终卡失败时，PATCH 占位卡为降级文案而不是
撤回了事"有两种读法——只做用户侧提示，或两者都做。本实现选**两者都做**：撤回的动机只与
"这条回答是否送达"有关，与"用户是否曾收到过别的东西"无关；占位卡是一次"正在处理"的交代，
不是回答。把没送达的回答留在历史里会让下一轮上下文与 RAG 回答缓存的键都带着它。
若改取"只做用户侧"的读法，改动是 `_deliver` 里成功/失败分支的一行，对应测试同步改。

**验证证据**：`scripts/local_smoke.py` 真调本机 RAG（版本 `20260915_v1`）跑通——主问题
「介绍一下涿鹿之战。」11.3s，占位卡 263 字符（仅 markdown）→ 最终卡 3983 字符（正文 + 4 个折叠区 +
关系图图片 + 3 个示例题按钮 + 反馈按钮），两个产物分别落在 `data/smoke/2_answer_placeholder.json`
与 `2_answer.json`；`--dead-rag` 时占位卡被替换为降级卡片。四条失败分支由 `tests/test_dispatcher.py`
与 `tests/test_integration.py` 覆盖（替身 + 真 worker 线程）。

**未验证**：占位卡在真实飞书客户端上是否会闪、PATCH 是否被客户端正常刷新——需要真实租户
（`README.md` 第 3 层验收清单第 13 条）。

### 6.2 `/new` 重置会话

**现状与做法**：新技能 `bot/skills/new_session.py`（命令词 `/new`、`/重置`），注册在 `help`
之后、`knowledge_qa` 之前（`knowledge_qa.match` 恒真，必须排最后）。命令匹配与 `/help` 共用
`base.matches_command`（按"第一个词"），不再各写一套。

`SessionStore.reset(key)` 在**一个事务**里删该 `session_key` 的 `messages` 与 `sessions` 行并返回计数。

删与不删的边界：

| 对象 | 处置 | 理由 |
| --- | --- | --- |
| `messages` | 删 | 历史组装的唯一来源，不删等于没重置 |
| `sessions` | 删 | 会话行只是 TTL 的载体，留着会让"重置"半途而废 |
| `feedback` | **不删** | 治理队列：用户重置自己的上下文，不该抹掉已提交的纠错记录 |
| 已发卡片上的反馈按钮 | 不动（其 `msg_key` 指向已删行） | 用户在新会话里再点旧卡片时，`report_error` 走既有的"消息不存在"静默分支（toast 已回执，只留日志） |

`/help` 说明书同步列出 `/new`，并补了一句两段式回复的预期（"长回答通常要等 5–25 秒：我会先回
一张「正在检索…」的卡片，查到后替换成正式回答"）——`/new` 是用户唯一的自助重置入口，不写进
说明书等于没有。

**验证证据**：`tests/test_skills.py`（命令词匹配、说明书含 `/new`）、`tests/test_session.py`
（历史清空、`sessions` 行删除、feedback 保留）、`tests/test_integration.py`（端到端：
重置后追问的 `history` 为空）；冒烟脚本第 5 步确认历史 4→0 条、feedback 1→1 行。

## 七、文档口径回写

实现与文档不同步的六处已逐条回写（开发文档 5.3 分流表补 `help` 行、`bot/skills/base.py`
的 Reply 注释改为实际落库顺序、`bot/session.py` 注释写明 `HISTORY_ASSISTANT_MAX_CHARS`
默认 800 而 400 是某次实测取值、开发文档第四节与 README 排查速查更正 ws 失败路径、
`render/render_subgraph.js` 头注释尺寸改为 1000×700 并注明"尺寸由 Python 侧下发"、
工作区存量单独提交）。另在 README 排查速查补了两条真实现象：

- **凭证写错的"假活"**：`auto_reconnect=True` 是**有意固定**的（长连接断线要自愈），代价是
  App ID/Secret 写错时 SDK 内部无限重试、线程不退出，服务"看起来活着"却永远收不到消息。
  两个判定动作：启动日志里**没有** `机器人 open_id：ou_xxx`（它只有凭证正确、能换到
  tenant_access_token 时才打）；开放平台「事件与回调」页的长连接状态**不显示"已连接"**。
- **发送失败撤回是设计内行为**：日志里的 `回复发送失败：已撤回本轮历史 N 行`（ERROR，带答案全文）
  说明回答没送达，历史已撤回，答案留给人工补偿；频繁出现时查系统代理。

## 十、踩坑教训与"改这里要同步改哪里"

**踩坑教训**（都是真机或 CI 上撞过的）：

- 历史参与 RAG 回答缓存的键：命令轮、未送达的回答、超时轮留下的提问行，都会让本该毫秒返回的
  问题退化成十几秒真生成（本模块踩过两次）；`scripts/cleanup_db.py --purge-orphans` 就是清这类残留行的。
- 卡片取值只能有一份实现。按 1.0 形态取值不会报错，只会**静默**少拿数据——所以冒烟脚本与
  测试必须共用 `tests/card_helpers.py`。
- 取卡片的"尺寸 / 编码"这类跨进程细节要显式声明：Node 子进程 stdout 必须 `encoding="utf-8"`
  （Windows 中文机器默认按 cp936 解读，JSON 解析失败且错误信息为空）；`render_subgraph.js`
  的出图尺寸由 Python 侧下发（1000×700），脚本头注释不是唯一事实来源。
- 时间窗类的守卫要按"上次结果"取档，不要按"当前有没有数据"取档——后者会让"有旧数据但刷新失败"
  的路径永远落在错误的窗口里。
- "本机绿、CI 红"：CI runner 自带 node 却没有 `render/node_modules`，只判 `shutil.which("node")`
  会漏判；现在 CI 装 `npm ci`，用例侧统一按 `renderer.is_available()`（node + 依赖 + 脚本）判断。
- SDK 副作用要按消息精确过滤，不要整类屏蔽：`pytest.ini` 只滤 `ExpiringCache._start_clear_cron`
  那一条 RuntimeWarning，`tests/conftest.py` 只从 asyncio 日志里丢同一孤儿任务的那条 ERROR。

**改这里要同步改哪里**：

- 卡片结构（组件 / 字段）→ `tests/card_helpers.py` 与 `tests/test_cards.py` 的 2.0 守卫、
  `scripts/local_smoke.py` 的摘要与退出码判断。
- 落库与历史规则 → `tests/test_session.py`（成对写入、撤回、TTL 过滤）、`tests/test_dispatcher.py`
  （顺序与撤回）、`scripts/cleanup_db.py` 的孤儿口径。
- 超时口径 → `config.py` 的校验规则（`RAG_QUERY_TIMEOUT` 必须小于 `RAG_JSON_BUDGET`）、
  RAG 侧 `QUERY_JSON_TIMEOUT_SECONDS`、README 排查速查表三处一起改。
- 配置项新增 → `config.py` + `.env.example` 双向对齐（`tests/test_config.py` 会双向检查）。
- 示例题窗口参数 → `tests/test_skills.py` 的四条窗口用例。
- 命令词表 → `bot/skills/*.py` 的命令别名与 `/help` 说明书文案（用户唯一的自助入口）。
