## 二、3.1 的四条（有实际影响的修复）

### 2.1 发送链路的重试与兜底（唯一改变线上行为的修复）

**现象（2026-09-24 23:09 线上日志）**：RAG 5.9s 正常返回，组卡后调飞书 reply 时对
`open.feishu.cn:443` 的 TLS 连接被对端掐断（`SSLEOFError(8, 'UNEXPECTED_EOF_WHILE_READING')`，
本机表现为常见的"挂系统代理"抖动）。异常一路抛到 `worker_loop` 的兜底 catch，只留一条
ERROR 日志——用户什么都没收到。根因已核对安装的 SDK 1.7.3：`lark_oapi/core/http/transport.py`
用 `requests.request(...)` 且没有重试配置，而 `HTTPAdapter` 默认 `max_retries=0`。

修复分两层：

| 层 | 改法 | 关键点 |
| --- | --- | --- |
| `bot/feishu_client.py` | 新增 `_call_with_retry`，reply / send_card / patch_card / upload_image 共用；对 `requests.exceptions.RequestException`（连接/SSL/超时）重试 2 次、退避 0.5s/1s | 见下三条"必须" |
| `bot/dispatcher.py` | `_send_reply` 捕获发送失败（返回 None 而不是抛异常）；最终失败时把刚落库的 user + assistant 两行**一起撤回**，答案全文打进 ERROR 日志供人工补偿 | 新增 `SessionStore.delete_messages`；`_record_turn` 改为返回 `(user 行 id, assistant 行 id)`；观测计数新增 `send_failed` |

三条"必须"，都是踩过才知道的：

1. **必须给 reply/create 传 `uuid`**（`ReplyMessageRequestBody` / `CreateMessageRequestBody`
   都支持）：飞书按它做服务端幂等去重。关键是它要在**重试之间保持不变**——否则
   "请求实际到达但响应丢失"的重试会发出第二条消息，裸重试反而引入重复回答。
   上传图片与 PATCH 没有 uuid 语义：前者飞书不支持，后者 PATCH 本身幂等（同样的 content 再发一次结果相同）。
2. **每次尝试必须重建请求对象**：SDK 首次发送会把 `request.body` 换成 `MultipartEncoder`
   （`api/im/v1/resource/image.py` 里 `request.body = form_data`），复用同一个请求对象重试
   读到的是空流。因此 `_call_with_retry` 接收一个"可重复调用"的闭包而不是现成的请求对象。
3. **上传图片必须把文件指针复位**：`prepare=lambda: handle.seek(0)` 在每次尝试前调用，
   否则第二次读到 EOF（发出去一张空图）。

为什么"重试仍失败要抛给调用方"而不是吞成 None：`dispatcher` 需要区分"这次真没发出去"
与"发出去了但没拿到 id"。前者要撤回本轮历史（见下），后者不该动数据。

**为什么发送失败要撤回历史**：本轮落地的是"成对写入"原则的另一面——
用户从未见过的回答不该留在历史里。留着它有两个实害：下一轮的上下文会带着一条用户
根本没看到的回答；**更实际的是历史参与 RAG 回答缓存的键**，多一条这样的历史就让本该
毫秒返回的问题退化成十几秒的真生成（与开发文档第十三节第 11、13 条同一个问题）。
代价是下一轮丢失这轮上下文，这是可接受的取舍。

### 2.2 示例题缓存补负缓存（3.1-3）

原先的刷新守卫是 `fresh and not force and self._questions`——要求缓存**非空**。接口失败或
返回空列表时 `_questions` 保持为空，守卫永远不成立，于是**每次组卡都同步重打一次
`GET /api/demo/examples`**；端点不可用时最坏吃满 connect 5s + read 25s 的客户端超时，
直接叠加在用户等待时间上（单 worker 下还会排队放大）。

改法：成功与失败两条路径都记刷新时刻，窗口按**上一次刷新是否失败**（`_last_fetch_failed`
标志，失败置位、成功清位）取不同值——成功后按 `refresh_seconds`（3600s）刷，失败后按新增的
`failure_retry_seconds`（新配置 `DEMO_EXAMPLES_FAILURE_RETRY_SECONDS`，默认 300s）再试。
失败窗口更短的理由：接口恢复后不该等一小时才有按钮；但它必须存在，否则退回"每张卡片一次 HTTP"。

> **审核后收口**：本条第一版实现把窗口取成"按当前有没有题目"（`refresh_seconds if
> _questions else failure_retry_seconds`），于是本记录这句"失败后按失败窗口再试"
> 对"留有旧题目、本次刷新失败"的情形并不成立——旧题目仍等满一小时。审核报告第三节
> 点出这处口径出入并推荐方案 A（保留旧题目不变化的前提下，改用失败标志取档），已按此
> 收口（提交 `8b68555`），并补了"留有旧题目时失败走短窗口"与"成功后窗口回退"两条用例。

### 2.3 冒烟脚本改按卡片 2.0 取值（3.1-1）

`scripts/local_smoke.py` 的两处解析（`_summarize` 的按钮统计、`_feedback_msg_key`）仍在找
1.0 的 `tag == "action"` 容器与顶层 `value`。现象是按钮摘要恒为空、冒烟第 4 步打印
"没有反馈按钮"并**跳过工单落库与投递的验证**——脚本不报错、退出码仍 0，验证环节静默失效。

改法：改为复用 `tests/card_helpers.py`（`buttons()` / `elements()` / `feedback_msg_key()`），
它是卡片取值的唯一实现。另外补一条：**非降级卡片缺反馈按钮时以退出码 1 报错**
（降级卡片本来就不带按钮，不算异常）——把"静默失效"变成"显式失败"才是这条的要点。

重跑结果（真调本机 RAG，版本 `20260915_v1`）：主问题 12.0s、出图 22 KB PNG、四个折叠区、
四个按钮（3 示例题 + 反馈有误）；追问历史 4 条 2595 字节；纠错反馈按钮 `msg_key=2`、
工单投递到运营群、`feedback` 表落 `status=open`；去重 1/1。`data/smoke/` 四个产物已重写，
字段为 `schema: "2.0"` + `width_mode`（旧的 `wide_screen_mode` 已消失）。

### 2.4 删除死代码（3.1-2）

删除 `bot/dispatcher.py` 的 `_record_assistant`（及其 docstring），全仓库无调用点。
它是上一轮"成对写入"改造（第十三条）之前的旧行为：只写 assistant 行、不写 user 行。
留着它的风险是后来者误当可选路径调用，直接破坏"成对写入"约束——命令轮会重新混入历史，
而历史参与缓存键（34ms 缓存命中退化成 16–25s 真生成）。
