## 二、#1 负缓存窗口口径（审核 P3）

**审核发现**：窗口取成"按当前有没有题目"（`refresh_seconds if _questions else failure_retry_seconds`），
于是"此前成功留有旧题目、本次刷新失败"仍等满 1 小时，`failure_retry_seconds` 只在题目为空时生效——
与本记录 2.2 节"失败后按失败窗口再试"的表述不符。审核推荐方案 A（改实现，让实现承接表述）。

**改法**：`DemoExamplesCache` 增加 `_last_fetch_failed`（失败置位、成功清位），窗口按它取档：

```python
window = failure_retry_seconds if self._last_fetch_failed else refresh_seconds
```

失败时 `_questions` 照旧不动（旧按钮继续可用），只是下次刷新提前到 5 分钟后。

**顺带修掉一处同类隐患**：初始状态由 `_fetched_at = 0.0` 改为 `None`（"从未取过"显式化）。
原写法要靠"真实时钟远大于刷新窗口"才成立，注入假时钟时会变成"启动后先假装缓存新鲜"——
本次新加的两条用例正好用假时钟写，改完才通过。这条与审核 P3 是两件事，一并记在这里。

**新增用例**：① 留有旧题目时刷新失败 → 短窗口内不重打 HTTP、过窗口后再试；
② 成功一次后窗口回到刷新间隔（不会被上一次失败拖成"每 5 分钟打一次"）。

**文档回写**：[修复实施记录-20260924.md](修复实施记录-20260924.md) 的 2.2 节改为"按
`_last_fetch_failed` 取档"并加"审核后收口"说明；README 文档表里审核报告一行的状态改为
"已按方案 A 收口"。

## 三、#2 两段式回复（批次③-1）

### 3.1 时序

```text
分流（resolve）
  → 技能声明了 wants_placeholder（当前只有 knowledge_qa）→ reply 占位卡，记消息 id
  → 技能执行（同步等 RAG，实测 12–25s）
  → 落库拿 messages.id → 补「反馈有误」按钮
  → patch_card(占位卡 id, 最终卡)：整卡替换**同一条消息**，不新增消息
  → 回填 bot_message_id（就是占位卡那条消息的 id，PATCH 前后不变）
```

`bot_message_id` 指向占位卡那条消息是**有意**的：PATCH 前后用户看到的始终是同一条消息，
因此反馈工单的 `(open_id, message_id)` 去重口径、`report_error` 的回退取值
（`message["bot_message_id"] or action.message_id`）都自然成立。

### 3.2 为什么"要不要占位"由技能声明

`Skill` 协议新增可选类属性 `wants_placeholder`（`bot/skills/base.py` 有注释，
`KnowledgeQaSkill` 声明为 `True`）。慢的是"同步等 RAG"这件事本身，将来若有别的慢技能，
它自己声明即可；而 `/help`、`/new` 这类命令与提示卡片本来秒回，不声明即走单段式——
不需要在 dispatcher 里按技能名硬编码白名单。

### 3.3 三条失败路径

| 失败点 | 处置 | 用例 |
| --- | --- | --- |
| 占位卡没发出去（传输层抖动） | 退回单段式：技能跑完后按普通 reply 发一条新消息 | `test_two_phase_falls_back_when_placeholder_fails` |
| 最终卡 PATCH 失败 | 尽力再 PATCH 一次"发送失败"提示卡（不能让用户停在"正在检索…"）；本轮历史照旧撤回 | `test_patch_failure_shows_failure_notice_and_rolls_back` |
| 占位卡发出的轮次最终降级/异常 | 降级卡同样 PATCH 到占位卡上（占位卡不能留在屏幕上转圈） | 冒烟 `--dead-rag` 与降级集成用例 |

PATCH 失败时**同时**撤历史，与单段式的"不保留未送达的回答"是同一条口径：用户看到的是
"没能发送成功"提示，回答本身确实没送达。

### 3.4 一处需要审核确认的读法

审核报告的原话是"占位卡已发但最终卡失败时，**PATCH 占位卡为降级文案而不是撤回了事**
（占位卡已送达，撤回语义不适用）"。这句话有两种读法：

| 读法 | 含义 |
| --- | --- |
| A. 只做用户侧 | 只 PATCH 提示，历史**不**撤（"撤回语义不适用"） |
| B. 两者都做（**本实现的读法**） | 用户侧 PATCH 提示（不沉默）+ 数据侧撤历史（回答没送达） |

选 B 的理由：撤回的动机与"用户是否曾经收到过**别的东西**"无关，只与"**这条回答**是否送达"
有关——占位卡是一次"正在处理"的交代，不是回答；把没送达的回答留在历史里，会让下一轮上下文
与 RAG 回答缓存的键都带着它（这是真机踩过两次的坑）。若你认为应取读法 A，改动是
`_deliver` 里成功/失败分支的一行（失败时改走 `set_bot_message_id` 的"发送失败也保留"分支），
对应测试同步改。

### 3.5 冒烟证据（真实 RAG）

主问题「介绍一下涿鹿之战。」11.3s：占位卡 263 字符（仅 markdown）→ 最终卡 3983 字符
（正文 + 四个折叠区 + 关系图图片 + 三个示例题按钮 + 反馈按钮），两次产物分别落在
`data/smoke/2_answer_placeholder.json` 与 `2_answer.json`；`--dead-rag` 时占位卡被替换为降级卡片。

## 四、#3 `/new` 重置会话（批次③-2）

### 4.1 实现

新技能 `bot/skills/new_session.py`（`/new`、`/重置`），注册在 `help` 之后、`knowledge_qa` 之前。
命令匹配与 `/help` 共用 `bot/skills/base.py::matches_command`（按"第一个词"）——
上一轮把 `/help` 的匹配口径统一过，这轮新增命令直接复用，不再各写一套。

`SessionStore.reset(key)`：一次事务里删该 `session_key` 的 `messages` 与 `sessions` 行，返回计数。

### 4.2 删与不删的边界

| 对象 | 处置 | 理由 |
| --- | --- | --- |
| `messages` | 删 | 历史组装的唯一来源，不删等于没重置 |
| `sessions` | 删 | 会话行只是 TTL 的载体，留着会让"重置"半途而废 |
| `feedback` | **不删** | 治理队列：用户重置自己的上下文，不该抹掉已经提交的纠错记录（开发文档 5.7） |
| 已发出卡片上的反馈按钮 | 不动（其 `msg_key` 指向已删行） | 用户在新会话里再点旧卡片时，`report_error` 走既有的"消息不存在"静默分支（toast 已回执，只留日志）——新增用例 `test_feedback_on_reset_row_is_ignored_silently` 锁住这条 |

### 4.3 说明书同步

`/help` 的 `HELP_TEXT` 增加了 `/new` 一行，并补了一句两段式回复的预期
（"长回答通常要等 5–25 秒：我会先回一张「正在检索…」的卡片，查到后替换成正式回答"）。
理由：`/new` 是用户唯一的自助重置入口，不写进说明书等于没有。
