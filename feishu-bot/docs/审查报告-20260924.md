## 三、代码问题

### 3.1 建议本轮修复（有实际影响）

**1. `scripts/local_smoke.py` 仍按卡片 1.0 形态解析按钮（功能性 bug）**

- 位置：`scripts/local_smoke.py:94-95`（`_summarize` 的按钮统计）、
  `scripts/local_smoke.py:147-155`（`_feedback_msg_key`）。
- 现象：两处都在找 `tag == "action"` 容器与顶层 `value`——那是 1.0 的写法。工作区代码
  已迁 2.0（按钮是 `body.elements` 直接成员、回传参数在 `behaviors[type=callback].value`），
  测试侧也已新建按 2.0 取值的 `tests/card_helpers.py`，唯独冒烟脚本没同步。
- 影响：`_summarize` 的按钮摘要永远为空；`_feedback_msg_key` 永远返回 `None`，冒烟第 4 步
  （纠错反馈）会打印"没有反馈按钮"并**跳过工单落库与投递的验证**——脚本不报错、退出码仍 0，
  验证环节静默失效。
- 修法：让 `local_smoke.py` 复用 `tests/card_helpers.py` 的 `buttons()` /
  `feedback_msg_key()`；修完重跑一次冒烟，刷新 `data/smoke/` 下的产物。

**2. `dispatcher._record_assistant` 是死代码，且与现行落库规则矛盾**

- 位置：`bot/dispatcher.py:486-502`（定义，全仓库无调用点）；现行实现是
  `bot/dispatcher.py:436-460` 的 `_record_turn`。
- 现象：两者高度相似但规则不一致——`_record_turn` 按"成对写入"同时写 user 行 +
  assistant 行（只有能入历史的轮次才写）；死代码只写 assistant 行（旧行为）。
- 影响：留着它，后来者很可能误当可选路径调用，直接破坏"成对写入"约束——命令轮
  （如 `/help`）会重新混入历史，而历史参与 RAG 回答缓存键，缓存命中（34ms）会退化成
  真生成（16–25s），顶穿预算（开发文档 5.2 实现期修正与第十三节第 11 条的真实教训）。
- 修法：直接删除该函数及其 docstring。

**3. `DemoExamplesCache` 缺"负缓存"，示例题接口故障时每张卡片多付一次 HTTP**

- 位置：`bot/rag_client.py:204-221`（`refresh`）。
- 现象：刷新守卫是 `fresh and not force and self._questions`——要求缓存**非空**。
  接口失败或返回空时 `_questions` 保持为空，守卫永远不成立，于是每次组卡都会
  同步重打一次 `GET /api/demo/examples`。
- 影响：RAG 的示例题端点不可用时，**每回答一个问题都额外付一次 HTTP**，最坏吃满
  connect 5s + read 25s 的客户端超时预算，直接叠加在用户等待时间上（且单 worker 模型下
  排队放大）。
- 修法：失败路径也把 `_fetched_at` 记为有效刷新时刻（或单独记失败时刻），让空结果
  同样能命中缓存窗口；需要区分"失败后多等一会儿再试"与"成功后按 refresh_seconds 刷"。

**4. 发送链路无重试、无兜底：一次瞬时 TLS 失败 = 用户收到沉默（线上实测）**

- 证据（2026-09-24 23:09 线上日志）：RAG 5.9s 正常返回（`finish=normal`、10 条引用、
  四个 panel 区），组卡后调飞书 reply 接口时对 `open.feishu.cn:443` 的 TLS 连接被对端
  掐断（`SSLEOFError(8, 'UNEXPECTED_EOF_WHILE_READING')`），异常一路抛到 `worker_loop`
  的兜底 catch，只留一条 ERROR 日志。
- 影响三层：
  1. **用户侧纯沉默**：回答已生成但什么都收不到，也无任何提示；
  2. **历史污染**：`_record_turn` 在发送**之前**落库（`bot/dispatcher.py:380`，反馈按钮
     要先拿 id 所致），发送失败后这轮问答已进历史——下一轮上下文与 RAG 回答缓存键
     都带着这条用户从未见过的回答；
  3. **无法自愈**：事件 ID 在回调入口已去重落库，飞书即使重投也会被当 duplicate 丢弃。
- 根因（已核对安装的 SDK 1.7.3）：`lark_oapi/core/http/transport.py` 无重试配置，
  requests 的 HTTPAdapter 默认 `max_retries=0`——单次瞬时抖动即抛异常；
  `bot/feishu_client.py` 的 `_reply` 只处理 `resp.success()==False`，不捕获传输层异常；
  worker 层只记日志。触发层是环境性的：requests 会读系统代理，Windows 上挂全局代理
  （Clash 等）时对 open.feishu.cn 的 TLS EOF 是常见现象。
- 修法（两层）：
  - **feishu_client 传输层重试**：reply / send_card / patch_card / upload_image 共用
    一个重试包装，对 `requests.exceptions.RequestException`（连接/SSL/超时）重试 2 次、
    退避 0.5s/1s。关键配套：给 reply/create 传 `uuid`（SDK 的两个请求体都支持，
    飞书按 uuid 做服务端幂等去重）——否则"请求实际到达但响应丢失"场景下重试会
    发出重复消息，裸重试反而引入新问题；
  - **dispatcher 发送兜底**：`_send_reply` 捕获发送异常，转为"发送失败"处理而不是
    任其炸到 `worker_loop`——最终失败时把刚落库的 user + assistant 两行删掉
    （历史不保留未送达的回答，与"成对写入"原则一致；需要把 `_record_turn` 目前
    丢弃的 user 行 id 一并返回），日志 ERROR 带答案全文供运营手工补偿。
- 环境排查：若部署机挂系统代理，给机器人进程设 `NO_PROXY=open.feishu.cn`
  或关代理，可消掉大半此类抖动；worker 未死、`failed` 计数 +1 属设计内行为。

## 五、优化与拓展方向

按"离现有代码的距离"排序，每条都注明已具备的基础。

### 5.1 体验类（直接缓解 12–25s 长答的干等）

1. **两段式回复**：worker 收到问题先回"正在检索…"占位卡，RAG 返回后用 `patch_card`
   整卡替换。基础已成立：同轮内 panel 数据在内存里，整卡重建不丢内容
   （`report_error` 不做 PATCH 的理由是**跨轮**不存 panel，同轮不受此限）。
   不动 RAG 协议，是长答体验性价比最高的一步。
2. **打字机流式输出**（需求文档待决项 3 的二期项）：`lark-oapi` 1.7.3 已内置
   streaming card 模块；机器人侧从 `/api/query/json` 换成消费现成 SSE 通道
   `/api/query` 即可拿增量，还能顺带展示 thinking/status 过程。根治方案，改动面大于上一条。
3. **上下文化的追问按钮**：示例题现在是全局轮换（1h 刷一次）；若 RAG 响应带
   `followup_suggestions`（或本地从 citations 的实体生成），追问按钮比示例题更贴合当前回答。
4. **`/new` 重置会话命令**：用户目前无法主动清空上下文，只能等 24h TTL。结合
   "历史参与缓存键"的已知特性，重置会话也是用户自救超时问题的手段。

### 5.2 架构与性能

5. **worker 池按 session_key 分片**：开发文档第四节已预留方案（同 key 固定同一 worker，
   会话内仍串行）。团队化之前做，多用户不再整体排队。
6. **子图渲染缓存**：按 subgraph 内容哈希缓存 image_key（飞书 image_key 可长期复用），
   热点实体二次提问零渲染成本，也省掉每次起 Node 进程的开销。
7. **运行期健康探测**：启动只探一次 RAG，中途 RAG 重启机器人无从感知，用户只会持续
   收到降级卡片。加周期性 health 探测，异常时打 WARNING。

### 5.3 运营闭环（feedback 表在攒数据，缺的是出口）

8. **工单状态流转**：feedback 表有 `status=open/done` 字段，但代码里没有任何地方把它
   置为 done。给运营群工单卡加"标记已处理"按钮（新 `card_action=resolve`，机制与
   report_error 完全同构），即可形成最小治理闭环。
9. **观测汇总**：dispatcher 已有 `stats` 计数、日志里有 `elapsed_ms/cache_hit/finish_reason`，
   加一条每日汇总日志（提问数、降级率、缓存命中率、平均耗时）就够运营判断预算。

### 5.4 安全与治理（团队化前必做）

10. **用户/群白名单**：当前租户内任何找到应用的人都能用，且与网页共享 RAG 每分钟 30 次
    的限流桶。加 `FEISHU_ALLOWED_CHAT_IDS`（空 = 不限制）是十几行代码的事。
11. **生产开启 `RAG_BOT_API_KEY`**：两边默认空（内网约定），RAG 换机或端口误暴露时
    这个口子就没了。

### 5.5 能力拓展（技能框架本来为此设计）

12. **主动推送**：`send_card` 已具备，"历史上的今天"类定时推送只差调度器；
    回链可复用"按钮即意图"模式。
13. **图谱直查命令**：`/图谱 长平之战` 复用 `SubgraphRenderer` 直接出大图，
    不走 LLM、秒回。
14. **纠错数据反哺引擎**：`bot/session.py` 的 `as_rag_history` 注释已预留
    `corrected_entities` 扩展位；feedback 表攒的"答错了"数据，是给 RAG F02 实体消解
    做种子或评测负样本的原料。
15. **多引擎路由**：机器人定位是"项目级 IM 入口"，Dispatcher 的注册顺序机制天然支持
    挂第二个引擎（如旧 backend 的规则问答）做降级双通道。
