## 四、运行架构与进程模型

```text
飞书服务端
   │ WebSocket 长连接（lark-oapi ws 客户端，SDK 自管重连）
┌──▼────────────────────────────────────────────┐
│ feishu-bot 进程（单实例）                        │
│                                                │
│  SDK 回调线程        worker 线程（1 个起步）      │
│  ┌────────────┐     ┌──────────────────────┐  │
│  │ dispatcher │ ──▶ │ 取任务 → 技能分流执行   │  │
│  │ 去重/入队   │队列  │ 调 RAG → 组卡片 → 回复 │  │
│  └────────────┘     └──────────────────────┘  │
│        SQLite（会话/消息/反馈/去重）              │
└───────┬────────────────────────────────────────┘
        │ HTTP（httpx，25s 预算）
   RAG 引擎（另一进程，8000 端口）
```

**并发模型决策：线程 + 队列，不引入 asyncio。** 理由：

- 消息量级是"个人自用 → 内部团队"，每分钟个位数消息，线程模型完全够用；
- SDK 的 ws 回调发生在 SDK 自有线程，回调里直接同步处理最简单，但会占用 SDK 线程
  导致飞书侧"秒级 ACK"超时——因此回调只入队，处理移到 worker 线程；
- RAG 调用是同步 HTTP（httpx），worker 线程阻塞等待即可，无需事件循环桥接。

**长连接线程归位（实现期修正）**：`ws.Client.start()` 会在自己的 asyncio 循环里永久阻塞
（`run_until_complete(_select())`，而 `_select()` 是 `while True: await asyncio.sleep(3600)`），
且 SDK **没有公开的 `stop()`/`close()`**。早期实现把主线程停在里面，结果是
"按 Ctrl-C、日志说正在停止、worker 也退了，进程却退不出来"（真机实测）。
现在 `run()` 把长连接放在**后台守护线程**，主线程只等一个 `threading.Event`：
收到 SIGINT/SIGTERM → 置位 → `app.close()` → 主线程返回、进程退出（守护线程随进程结束）。
连按两次 Ctrl-C 走 `os._exit(0)` 强制退出，作为"收尾卡住"时的逃生口。
停机时 `dispatcher.stop()` 的等待时长取 RAG 预算（`RAG_QUERY_TIMEOUT` + 连接超时 + 5s），
这样在途查询能收尾再关 httpx/SQLite——否则关闭动作会让在途任务抛异常（进程即将退出、
无实害，但日志有吓人堆栈）。
另：`bot/feishu_client.py` 的 ws 客户端**恒为 `auto_reconnect=True`**（长连接断线要能自愈）。
这条有个必须知道的副作用：**凭证写错（App ID/Secret 不对）时 SDK 内部无限重试、
线程不退出，服务"看起来活着"却永远收不到消息**——排查办法见 README「排查速查」的"假活"条
（判定方法：启动日志里没有 `机器人 open_id：ou_xxx`，且长连接状态不显示"已连接"）。

关键时序约束：

1. **ACK 与处理分离**：SDK 回调收到事件后，dispatcher 只做"去重检查 + 入队"，立即返回。
   飞书要求秒级应答，超时会重试投递——重试由幂等（按 `header.event_id` 去重）兜底，
   而不是靠回调里同步处理完；
2. **单 worker 起步**：会话内消息必须**串行处理**（保证历史顺序）。P0 单 worker 时
   **所有会话一起排队**——不只是同会话串行，不同用户之间也串行；个人自用无感，
   但团队并发时第二个提问者要等前一个跑完（最长 25s 超时 + 处理时间）。
   会话数上来后改成 worker 池：按 `session_key` 哈希分片（同 key 固定落到同一 worker，
   会话内仍串行），文档不展开实现；
3. **去重持久化**：`processed_events` 表落库（第七节），进程重启后飞书的重试窗口内
   依然不会重复回复。飞书的 WS 推送是**"至少一次"投递**（官方 SDK 也按此假设做去重），
   重试通常集中在 1 分钟内，表记录保留 24h 后由清理脚本删除。

## 五、模块详细设计

### 5.1 事件接入（dispatcher）

职责：接收 SDK 回调 → 解析 → 去重 → 入队；worker 消费 → 分流。

```python
# bot/dispatcher.py（签名示意）

def on_message(data: P2ImMessageReceiveV1) -> None:
    """SDK im.message.receive_v1 回调。只做三件事，必须毫秒级返回：
    1. 取 event.header.event_id，查 processed_events 表；
       已存在 → 直接 return（幂等，静默丢弃重试）；
    2. 写入 processed_events（INSERT OR IGNORE，以 event_id 为主键）；
    3. 解析出 MessageEvent 并入队。"""

def on_card_action(data) -> None:
    """卡片按钮回调（card.action.trigger，P1 示例问题 / P2 反馈按钮）。
    去重键优先取 event.header.event_id；实测若该字段缺失或不可靠，退化为
    稳定动作身份（message_id + operator.open_id + tag + value 摘要）+ 短时间窗——
    两者的语义都只是"抑制重投"，不做长期去重（用户对同一按钮的真实二次点击必须放行，
    例如连点两次同一个示例问题）。按钮参数通过 button 的 value 携带，
    value 是自由 JSON，约定结构见 5.5.3。
    本路径是 P1/P2 全部交互能力的前提，**P0 阶段就用最小 demo 实测**（第九节 P0-4），
    不要等 P1 开工才发现收不到回调。"""

def worker_loop() -> None:
    """取任务 → 按事件类型分发：
    - 消息事件 → 意图分流（5.3）→ 技能执行 → 发送回复；
    - 按钮事件 → 按 value.action 分发到对应处理函数。
    任何异常：记日志 + 给用户发"出错了请重试"兜底卡片，绝不让 worker 静默死掉。"""
```

`MessageEvent` 需要从 SDK 事件里提取的字段：

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `event_id` | `event.header.event_id` | 去重 |
| `message_id` | `event.message.message_id` | 回复消息（reply）；落库为 `messages.message_id`（按钮的 `msg_key` 用 `messages.id`，见 5.5.3） |
| `chat_id` | `event.message.chat_id` | 会话键、群聊场景回复 |
| `chat_type` | `event.message.chat_type`（`p2p` / `group`） | 单聊/群聊分支 |
| `open_id` | `event.sender.sender_id.open_id` | 会话键、反馈记录 |
| `text` | `event.message.content`（JSON 里的 `text`） | 问题正文 |
| `mentions` | `event.message.mentions` | 群聊剥离 @ 前缀（见下） |

**群聊处理规则**：`chat_type == "group"` 时，仅当 `mentions` 里包含本机器人
（对比 `mentions[].id.open_id` 与配置的 `FEISHU_APP_ID` 对应 bot open_id，
或按 `mentions[].key` 出现在文本开头判断）才处理；处理前把文本中的
`@机器人` 片段（mention key 替换）剥离，剩余文本作为问题。剥离后为空则忽略。
单聊不剥离，全部文本作为问题。

**群聊剥离只剥机器人自己**：文本里 @ 别人也是问题语义的一部分
（"介绍一下 @张三 提到的赤壁之战"），不能连它一起剥掉——只比对与 bot open_id 相符的
mention；拿不到 bot open_id 时退化为"只剥文本**开头**那一个 mention key"，
宁可少剥（问题里留个 `@_user_1`）也不要多剥（把问题内容吃掉）。

**两段式回复**：知识问答同步等 RAG，介绍类长回答实测 12–25s，
不给任何反馈用户只能干等。因此 worker 的时序是：

```text
分流（registry.resolve）
  → 技能声明了 wants_placeholder（当前只有 knowledge_qa）时先 reply 一张
    "正在检索…"占位卡，记下这条消息 id
  → 技能执行（这里是 12–25s 的 RAG 调用）
  → 落库拿 messages.id、补反馈按钮
  → patch_card(占位卡 id, 最终卡)：**整卡替换同一条消息**，不新增消息
  → 回填 bot_message_id（就是占位卡那条消息的 id，PATCH 前后不变）
```

只有"技能自己声明慢"才发占位卡：`/help`、`/new` 这类命令与提示卡片本来就秒回，
走普通单段式发送。占位卡/最终卡的失败路径各有明确处置（否则用户会停在"正在检索…"）：

| 失败点 | 处置 |
| --- | --- |
| 占位卡没发出去（传输层抖动） | 退回单段式：技能跑完后按普通 reply 发一条新消息 |
| 最终卡 PATCH 失败 | 再尽力 PATCH 一次"发送失败"提示卡；本轮历史照旧撤回（回答确实没送达） |
| 占位卡发出的轮次最终降级/异常 | 降级卡同样 PATCH 到占位卡上——占位卡不能留在屏幕上转圈 |

**不处理的消息类型**：`message_type != "text"` 时回复固定提示"暂只支持文字提问"
（图片、文件等），或静默忽略——P0 采用回复提示，避免用户以为机器人坏了。

### 5.2 会话管理（session / db）

**会话键**：`session_key = f"{open_id}:{chat_id}"`。
单聊场景 `chat_id` 也存在（p2p 会话有自己的 chat_id），直接拼接即可，
天然满足"会话按用户 × 群隔离"（G3）。

**传给 RAG 的 `session_id`**：直接用 `session_key`。
长度核对：open_id/chat_id 均以 `ou_`/`oc_` 开头、约 30+ 字符，拼接后约 70 字符，
低于 RAG 契约的 `session_id ≤ 128 字符` 上限，无需哈希。

**历史组装**：调用 RAG 前从 `messages` 表取该 session_key 最近 **24 小时内**
（会话 TTL）的记录，按时间正序转成 `history: [{role, content}]`：

- `role=user`：用户原始问题（群聊取剥离后的文本）；
- `role=assistant`：**RAG 返回的 `answer_md` 原文**（收敛器处理前的 Markdown——
  历史是给 LLM 的上下文，保真优先；卡片展示才做收敛）。
  但回答轮另有 `HISTORY_ASSISTANT_MAX_CHARS`（默认 800 字，0 = 不额外截断）这一道更严的上限：
  RAG 的指代消解只读历史里的**提问**（`server/query/understand.py::_resolve_coref`
  对 user 轮重新跑词典匹配），不读回答正文，所以截回答不影响"他后来怎么样了"这类追问；
  而不截的话，一个 4 轮会话的历史实测达 11.8KB，按 400 字截（**当时那次实测的取值**，
  默认值是 800）后只剩 3.7KB。
  **注意（实测）**：截断历史**没有**让生成变快（同题对比 11.1s vs 15.1s，差异在噪声内）——
  生成耗时由输出长度主导。这道上限的价值在请求体积、以及抑制"模型模仿上一轮的答案长度"，
  不要指望它解决超时；超时该调的是预算（见 5.4）；
- **总字节预算是真正的硬边界**：RAG 的 `REQUEST_MAX_BYTES = 65536`（64 KB，
  `RAG/config/defaults.py`）在参数校验**之前**就把请求拒掉（413），而契约里的
  "单条 4000 字符 × 40 条"在中文 UTF-8 下理论上限约 480 KB——**两者本身就可能打架**，
  照抄后两个上限必然踩坑。因此机器人侧按**总字节预算**反向组装：整份 history
  序列化后（`ensure_ascii=False`）**≤ 40 KB**，从最近的消息往前取，装满即停；
- 单条 `content` 截断到 4000 字符（契约 `history_content_max_chars`）作为次级保护，
  截断时保留开头、末尾加"……（已截断）"；
- 条数上限 40（契约 `history_max_items`）同样只作次级保护；RAG 服务端还会按
  `history_max_turns` 二次裁剪（默认 4 轮），机器人侧不做 turn 级裁剪；
- **`finish_reason` 为 `interrupted` 的回答不写入 messages**（回答可能不完整，
  RAG 契约明确其不得进入下一轮历史）；`failed` / `cancelled` 同样不写入；
- **写入时机（第十三节第 11 条）**：user 行与 assistant 行**一起写**，
  且只在"能入历史"的轮次写。若提问先落库、回答失败也留着，`/help`
  这类命令就会进入 RAG 历史——更严重的是历史参与回答缓存的键，多一条无意义历史就把
  同一问题从缓存命中（34ms）变成真生成（16–25s），直接顶穿 25s 预算（真机踩过）。

**TTL**：查询时按 24h 过滤是软口径；`scripts/cleanup_db.py` 每日物理删除过期
sessions/messages（硬口径）。两件事都做，表不会无限膨胀。

**`/new` 重置会话**：用户的上下文只能等 24h TTL 自然过期，而历史参与缓存键——
重置会话也是用户自救"答得不对 / 答得越来越慢"的手段。`/new` 删除该 `session_key` 的
`messages` 与 `sessions` 行（两张表一次事务），`feedback` **不删**（纠错记录是治理队列，
见 5.7）。被删行的 `messages.id` 就是已发出卡片上反馈按钮的 `msg_key`：用户在新会话里
再点旧卡片时，`report_error` 走既有的"消息不存在"静默分支（5.5.3），不给用户报错。

### 5.3 技能框架（skills）

```python
# bot/skills/base.py
@dataclass
class Reply:
    kind: str                  # "card" | "text"（P0 只有 card，text 留作兜底）
    card: dict | None = None   # 飞书卡片 JSON
    text: str | None = None

@dataclass
class SkillContext:
    event: MessageEvent        # 原始事件
    question: str              # 剥离 @ 后的问题文本
    session_key: str
    history: list[dict]        # 组装好的 RAG history

class Skill(Protocol):
    name: str
    def match(self, ctx: SkillContext) -> bool: ...
    def run(self, ctx: SkillContext) -> Reply: ...
```

**意图分流（规则）**，按注册顺序匹配，命中即执行；全不命中走 `knowledge_qa`
（兜底技能，`match` 恒真）：

| 顺序 | 技能 | 规则 | 说明 |
| --- | --- | --- | --- |
| 1 | `help`（P1） | 文本的**第一个词**是 `/help`、`/帮助` 或 `/?`（带不带参数都命中） | 命令前缀，零延迟；命中即返回使用说明卡片 |
| 2 | `new_session` | 第一个词是 `/new` 或 `/重置` | 清空本会话上下文（5.2）；命中即返回回执卡片 |
| 3 | `report_error`（P2） | 不走文本分流，仅由**卡片按钮回调**触发 | 按钮即意图，无需文本规则 |
| 4 | `knowledge_qa` | 兜底，恒真 | 所有普通文本消息；声明 `wants_placeholder`，走两段式回复（5.1） |

命令匹配的口径只有 `bot/skills/base.py::matches_command` 一处（按"第一个词"），
命令技能都用它——早先 `/help` 与 `/帮助` 各写一套前缀判断，`/帮助 带参数` 因此不命中。

技能还可以声明两个**可选类属性**，由 dispatcher 读取：

| 属性 | 作用 |
| --- | --- |
| `card_action` | 本技能处理哪个按钮动作（`report_error` / `ask`，见 5.5.3） |
| `wants_placeholder = True` | 本技能可能长时间阻塞 → dispatcher 在执行它之前先发占位卡，跑完 PATCH 成最终卡（5.1 的两段式回复） |

预留的规则位：暂无。技能增多后再评估模型分流（需求文档第三节）。

**knowledge_qa 执行流程**（P0-3）：

```text
取 history（session 模块）→ rag_client.query(question, history, session_key)
→ Reply(卡片)：
    finish_reason == normal/refused/degraded → 正文 + 引用折叠卡（5.5）
    finish_reason == refused                → 正文即拒答文案，无引用区
    其他 / 抛异常                            → 降级卡片
→ 发送（reply 到原消息）→ 写入 assistant 消息（按 5.2 规则）
```

**降级卡片**文案固定："抱歉，这条我暂时答不上来（原因：超时/服务暂不可用），请稍后重试，
或换个问法。" 触发条件：RAG 调用超时（`httpx.TimeoutException`）、HTTP 5xx、
`error_code in {timeout, server_busy, internal}`，以及 HTTP 413（`payload_too_large`，
属机器人侧历史组装出的内部问题，**绝不能对用户说"问题过长"**）。

只有 `error_code == invalid_request`（问题超 500 字等用户侧参数错误）才用
"问题过长或不支持，请精简后重试"；其余 4xx 一律走通用降级文案，并在日志里记录
`error_code` 与请求体字节数，便于定位是不是历史组装超了预算（5.2）。

### 5.4 RAG 客户端（rag_client）

```python
# bot/rag_client.py（签名示意）
def query(question: str, history: list[dict], session_key: str) -> dict:
    """POST {RAG_BASE_URL}/api/query/json
    请求体：{"session_id": session_key, "question": question, "history": history}
    （filters / corrected_entities 飞书通道暂不用，不传）
    头：X-Bot-Key（仅当配置了 RAG_BOT_API_KEY）
    超时：连接 5s / 读 RAG_QUERY_TIMEOUT（默认 25s）
    返回：响应 JSON（契约见第六节）
    HTTP 状态非 2xx → 抛 RagError(code, message)，由技能层转降级卡片。"""

# 超时口径（有意层层截断，不是"与 LLM 超时对齐"）：
# 机器人 25s（RAG_QUERY_TIMEOUT）< 非流式接口 30s（QUERY_JSON_TIMEOUT_SECONDS）
#   < RAG 的 LLM 单次超时 60s × 最多 3 次尝试。
# 即：模型真的跑满预算时，飞书通道**注定**拿到超时降级卡片，而不是慢慢等出长回答——
# 这是"对话体验优先"的取舍。实测参考（RAG/data/eval/20260915_v1/demo_examples.json，
# real_llm，12 题的 measured 字段）：首答 first_answer_ms 2.4–6.3s、中位 4.9s；
# 完整回答 total_ms 3.2–9.2s、中位 6.9s——对 25s 预算余量约 3.6 倍
# （机器人等的是完整回答，取 total_ms 口径；首答只用于说明"有增量出现得快"）。
# RAG 侧的 LLM 超时不需要为此调整；任何一方改这几个数值，都要重新审视这张关系表。
```

其他用途：

- `GET /api/health`：`main.py` 启动时探测一次，RAG 不可用只打警告**不阻塞启动**
  （机器人仍可收消息，回复"知识服务暂不可用"降级卡片）；health 里 `llm_available=false`
  时打显著警告（回答质量受限，需求文档第六节"上线阻塞项"）；
- `GET /api/demo/examples`（P1-3）：启动时与每 1h 刷新一次，缓存在内存，
  供示例问题按钮使用；接口失败时按钮区不渲染（不阻塞问答）。

**限流提示**：RAG 按 IP 每分钟 30 次。机器人是单来源（本机），与网页共享同一个桶。
个人自用无感；团队化后若频繁 429，处置是调高 RAG 侧 `RATE_LIMIT_PER_MINUTE`，
机器人侧不做本地限流队列（保持简单，日志里记录 429 即可）。

### 5.5 卡片组装（cards）

#### 5.5.1 Markdown 白名单收敛器（md_sanitizer）

飞书卡片 markdown 组件只支持 Markdown 子集，RAG（F06）输出的是通用 Markdown，
必须收敛，否则渲染错乱（需求文档风险 1）。卡片规范统一用 2.0（5.5.2），2.0 的
markdown 能力比 1.0 略强，但收敛器仍按**保守白名单**处理：拿不准的语法一律降级为
纯文本，宁可少样式，不可渲染错乱。

**白名单**（保留原样）：加粗 `**x**`、斜体 `*x*`、删除线 `~~x~~`、
行内代码 `` `x` ``、链接 `[text](url)`（仅 http/https）、无序列表 `- `、
有序列表 `1. `、引用 `> `、分割线 `---`、换行。

**转换与剥离规则**：

| 输入 | 处理 |
| --- | --- |
| `# 标题`（1–6 级） | 转为 `**标题**` 独立行（标题语义用加粗行承载） |
| 表格（`\|` 分隔行） | 每行转 `**单元格** · 单元格 · …` 文本；表头行加粗，分隔行（`---`）删除 |
| 代码块 ``` ` ``` 围栏 | 内容逐行加 `> ` 前缀（引用块承载），围栏行删除 |
| 图片 `![alt](url)` | 整行删除（卡片 md 不渲染外链图片；P0 无图片诉求） |
| HTML 标签 | 剥离标签保留内文（F06 正常输出不含 HTML，防御性规则） |
| 裸 URL | 不自动加链接语法，保持原样（避免误改 F06 输出） |
| 超长（> 4000 字符） | 截断并追加"……（内容过长已截断，完整内容请在网页版查看）" |

**实现要求**：逐行状态机实现（表格/代码块是多行结构），不做正则一把梭；
单测样例**必须包含评测题库（`RAG/data/eval/`）真实回答**中出现的全部 Markdown
结构，不允许只用人工构造样例（需求文档风险 1 的落地）。收敛必须是幂等的
（对已收敛文本再收敛结果不变），便于防御重复处理。

#### 5.5.2 知识问答卡片（knowledge_qa 输出）

**卡片规范统一按卡片 2.0**（`schema: "2.0"` + `body.elements`）：这是当前官方
SDK 与搭建工具生成的标准形态，`collapsible_panel` 等容器组件只存在于 2.0。
P0 就按 2.0 起手（与 1.0 的骨架成本几乎相同），避免 P1-1 时整体迁移。

骨架（P0 整包回复）。**以下骨架是 2.0 规范的正确写法**——
`config.wide_screen_mode`、`border: {"type": "default"}`、`{"tag": "action"}`
三处都是 **1.0 的写法**，照那样发出会被飞书**整卡拒收**
（`code 200621 unknown property ... -> border`），改法与依据见第十三节第 14 条：

```json
{
  "schema": "2.0",
  "config": {"update_multi": true, "width_mode": "fill"},
  "header": {"title": {"tag": "plain_text", "content": "战争史问答"}, "template": "blue"},
  "body": {
    "elements": [
      {"tag": "markdown", "content": "<answer_md 收敛后正文>"},
      {"tag": "hr"},
      {"tag": "collapsible_panel",
       "expanded": false,
       "header": {"title": {"tag": "plain_text", "content": "引用（3）"}},
       "border": {"color": "grey", "corner_radius": "5px"},
       "vertical_spacing": "8px",
       "elements": [
         {"tag": "markdown",
          "content": "**[1] 资治通鉴·卷 x（事件卡）**\n> 原文片段……\n**[2] ……**"}
       ]},
      {"tag": "button", "text": {"tag": "plain_text", "content": "反馈有误"},
       "type": "default",
       "behaviors": [{"type": "callback",
                      "value": {"action": "report_error", "msg_key": "<messages.id>"}}]}
    ]
  }
}
```

2.0 的三条硬规则（写卡片时必须遵守，违反即整卡被拒）：

1. **没有交互模块**：2.0 里没有 `{"tag": "action", "actions": [...]}`，按钮直接放进
   `body.elements`（代价是每个按钮独占一行；要横排用 `column_set` + `column`）；
2. **按钮回传参数写在 `behaviors`**：`[{"type": "callback", "value": {...}}]`，
   顶层 `value` 只在 1.0 的字段表里；回调事件里仍从 `event.action.value` 取值，
   所以解析代码与写法无关；`text.content` 上限 100 字符；
3. **config 没有 `wide_screen_mode`**：宽度用 `width_mode`（`default`/`compact`/`fill`）；
   `update_multi` 必须为 true（2.0 暂时只支持共享卡片）。
   另：`collapsible_panel.border` 只接受 `color` 与 `corner_radius`；`img` 的 `alt` 必填。

> 文档站每条 URL 后加 `.md` 可拿到纯 Markdown 版（页面里有
> `<link rel="alternate" type="text/markdown">`），比抓 HTML 可靠。飞书**没有**
> 离线校验卡片的接口（`cardkit.v1.card.create` 可作服务端 dry-run，但需要
> `cardkit:card:write` 权限），因此本地用 `tests/test_cards.py` 的「2.0 合规守卫」
> 把上述规则写成断言。

各区的数据来源与 P1 增量：

| 区 | 数据来源 | 分期 |
| --- | --- | --- |
| 正文 markdown | `answer_md` → 收敛器 | P0 |
| 引用区 | `citations[]`：`index/kind/title/snippet`；每条一行"**[index] title（kind）**"，片段以引用行展示。`kind` 原样透传（实际取值 `graph_triple`/`raw_text`/`event_card`/`evidence`，以 RAG data-contract 为准）。`conflicts[]` 存在时在引用区末尾追加"⚠ 信息存在冲突"行（不展开细节） | P0 出列表（2.0 骨架下直接放 `collapsible_panel`），P1 调优折叠与回调 |
| 实体卡文字化 | `panel.entity_cards[]`：每张卡一行"`name`（type｜dynasty｜start_date–end_date）"+ 描述/叙事字段（aggressor/defender/action/impact/place）逐行文字；放折叠组件"相关实体" | P1-2 |
| 时间线文字化 | `panel.timeline.groups[]` → "label：item1 → item2 → …"（取 name + start_date） | P1-2 |
| 地点列表 | `panel.map_points[]` → "name（modern_name）"列表；无坐标与有坐标同格式（飞书侧不做地图，复用降级格式） | P1-2 |
| 示例问题按钮 | `/api/demo/examples` 取 3 条 `question`，按钮 value 带 `{"action": "ask", "question": "..."}`，点击回调即作为新问题执行 | P1-3 |
| 子图图片 | `panel.subgraph` → 渲染 PNG → 上传得 image_key → `{"tag": "img", "img_key": "..."}`；渲染失败自动降级为分组文字列表 | P2-1 |
| 截断提示 | 响应 `truncated == true`（模型打满 `max_tokens`）时，正文末尾补一行"（回答可能被截断，完整内容请在网页版查看）" | P0 |

**裁剪纪律**（需求文档继承旧版 Q8）：panel/citations 一律**按字段取用**，
只取上表列出的字段；`panel.subgraph` 的 nodes/edges 在文字降级时限制输出条数
（nodes ≤ 30、edges ≤ 50，超出加"……等 N 项"），不得整表透传。

#### 5.5.3 按钮 value 约定

按钮回调 `value` 是自由 JSON，统一带 `action` 字段分发：

| action | value 字段 | 处理 |
| --- | --- | --- |
| `ask` | `question` | 按新问题走 knowledge_qa 流程（不依赖原消息） |
| `report_error` | `msg_key` = `messages.id`（十进制字符串） | 从 messages 表按键取 question/answer_md/citations → 组工单卡片发运营群；PATCH 原卡片用同一行的 `bot_message_id`（见第七节） |

### 5.6 子图出图（render/subgraph，P2）

推荐选型（需求文档待决项 1 的默认方案，P2 开工前确认）：
**Node + echarts SSR**——echarts 5.3+ 的 SSR 模式可在无浏览器环境渲染 SVG 字符串，
再用 `resvg-js`（纯二进制，无系统依赖）转 PNG，无需浏览器内核。

**布局约束（先落这条，否则出图必糊）**：前端 `SubGraphView` 用的是
`layout: 'force'`（力导向，配 `repulsion/edgeLength/gravity`），而 SSR 是一次性同步渲染，
力导向的异步迭代不会执行——直接拿同一份 option 出图会得到节点重叠的乱图。二选一：
① Node 侧先用 d3-force 预跑迭代（如 300 次）把 x/y 写进节点，再以 `layout: 'none'` 渲染；
② 改用 `circular`/分层等静态布局。配色、节点样式对齐前端，**布局只保证信息结构一致**，
不承诺与网页视觉一致。

流程：`panel.subgraph → 生成 ECharts option（graph 布局，node 按 type 着色）→
Node 脚本渲染 SVG → resvg 转 PNG → 临时文件 → feishu_client 上传图片
（POST /open-apis/im/v1/images）得 image_key → 卡片 img 元素`。

- 渲染子进程：`subprocess` 调 Node 脚本，超时 10s；失败（Node 缺失/超时/空图）
  返回 None，技能层自动降级为 5.5.2 的分组文字列表，**不允许空白**；
- 空图判定：`nodes` 为空 → 直接走文字降级，不起 Node 进程；
- 部署机需预装 Node ≥ 18（风险 2 的落地，写入部署清单）。

### 5.7 纠错流转（report_error，P2）

```text
用户点"反馈有误"按钮 → 回调（value.action=report_error）
→ 按 msg_key 从 messages 取 question / answer_md / citations
→ 落 feedback 表（status=open）
→ 组工单卡片发运营群（FEISHU_OPERATORS_CHAT_ID）：
   标题"纠错反馈 #<id>"，正文：提问人 open_id、问题、回答摘要（前 500 字收敛后）、
   引用标题列表、反馈时间
→ 用户侧回执：更新原卡片按钮为"已收到反馈"（PATCH 消息卡片，可选；失败不阻塞）
```

是否同时落 SQLite：**落**（表结构见第七节，成本低、为后续治理队列留数据）；
对接旧系统质检流程不做（需求文档 P2-2）。投递目标群用配置里的
`FEISHU_OPERATORS_CHAT_ID`（待决项 4：现有群还是新建群，运营侧定，配置项适配两者）。

**`feedback` 表没有 TTL**：它是治理队列（`status=open` → 运营处理后 done），
不随 `SESSION_TTL_HOURS` 过期，`scripts/cleanup_db.py` 也**不清理**它
（messages/sessions/processed_events 三张表才在清理范围内）。
需要腾空间时由人工导出归档——不要把"清理脚本每天跑"当成"反馈数据有人管"。

## 六、RAG 侧改动：POST /api/query/json

RAG 侧**唯一改动**，位置 `RAG/server/api.py` 新增一个路由（可配套一个响应
dataclass，放 `contracts/` 下），**不新增编排代码**。

### 6.1 实现方式：消费同一个生成器

```python
@app.post("/api/query/json")
async def query_json(req: Request):
    # 前置检查与 /api/query 完全一致：runtime → 限流 → 请求体尺寸 → QueryRequest 校验
    # （直接复用现有 _read_json_limited / QueryRequest.from_dict / 错误映射）
    ...
    result = await _collect(rt, q, deadline)
    # deadline = settings.query_json_timeout_seconds（新增配置，默认 30s）

async def _collect(rt, q: QueryRequest, deadline: float) -> dict:
    """逐帧消费 run_query（与 SSE 同一条编排路径），聚合为完整结果。

    run_query 产出的是 sse_format 后的 "data: {...}" 帧字符串，
    此处解析回 dict 后按事件类型聚合（解析成本可忽略，换取零分叉）。
    """
    deadline_at = time.monotonic() + deadline
    answer_parts: list[str] = []
    citations, conflicts, panel = [], [], None
    finish_reason, model_used, cache_hit, error = "", "", False, None
    agen = run_query(rt, q)
    try:
        while True:
            remaining = deadline_at - time.monotonic()
            if remaining <= 0:
                raise TimeoutError()
            frame = await asyncio.wait_for(agen.__anext__(), timeout=remaining)
            ev = json.loads(frame[len("data: "):].strip())
            # 按 ev["type"] 聚合，规则见 6.2
    except StopAsyncIteration:
        pass
    except asyncio.TimeoutError:
        # 区分整体超时与单帧等待超时：统一按超时处理
        error = {"error_code": "timeout", "message": f"超过 {deadline:.0f}s 上限"}
    finally:
        await agen.aclose()   # 触发 run_query 的 finally：取消 LLM 任务（P1-1 既有逻辑）
    ...
```

超时行为说明：`aclose()` 会走 `run_query` 的 `finally` 分支，取消未完成的
`gen_task`（LLM 生成），与 SSE 客户端断连时的回收路径完全一致，不泄漏任务；
超时轮不写缓存（`finish_reason` 不是 normal/refused，既有缓存卫生逻辑自动覆盖）。

### 6.2 逐事件聚合规则

| SSE 事件 | 聚合动作 |
| --- | --- |
| `session_start` / `status` / `entities` / `graph_results` / `text_results` / `fusion` / `thinking` | 忽略 |
| `answer` | `answer_parts.append(data.delta)` |
| `citations` | `citations = data.citations`；`conflicts = data.conflicts` |
| `panel` | `panel = data`（panel 事件 payload 即 PanelData 字典） |
| `done` | `finish_reason = data.finish_reason`；`model_used = data.model_used`；`cache_hit = data.get("cache_hit", False)`；`truncated = data.get("truncated", False)`（推理模型打满 `max_tokens` 时由 RAG 置位，卡片据此提示） |
| `error` | `error = {"error_code": ..., "message": ...}`（继续等 done 帧，done 里 `finish_reason=failed`） |

缓存命中（`cache_hit` 分支）产出 `answer`（整段 delta）+ `citations` + `panel` +
`done`，同一套规则天然覆盖（需求文档 5.1 的要求），无需分支处理。

### 6.3 响应契约

成功（HTTP 200）：

```json
{
  "status": "ok",
  "data": {
    "answer_md": "……完整 Markdown……",
    "citations": [ {"index": 1, "evidence_id": "…", "kind": "…", "title": "…", "snippet": "…"} ],
    "conflicts": [ ],
    "panel": {"entity_cards": [...], "subgraph": {...}, "timeline": {...}, "map_points": [...]},
    "finish_reason": "normal",
    "model_used": "…",
    "cache_hit": false,
    "truncated": false
  }
}
```

字段说明：`citations`/`panel` 结构与 SSE 事件 payload 完全一致（同一来源）；
`panel` 可能为 `{}`（无面板数据）；`finish_reason` 取值见 `contracts/sse.py::FinishReason`
（normal / refused / degraded / failed / interrupted …）；`truncated` 为 true 表示回答被
`LLM_MAX_TOKENS` 截断，机器人侧在正文末尾提示"可能不完整"（5.5.2 区表）。

失败（HTTP 非 200，复用 `_json_error` 结构）：

| 条件 | HTTP | error_code |
| --- | --- | --- |
| runtime 未加载 | 503 | internal |
| 限流 | 429 | rate_limited |
| 请求体/参数不合法 | 400/413 | invalid_request / payload_too_large |
| 聚合超时 | 504 | timeout |
| 编排内 error 事件 | 500 | 透传事件的 error_code（server_busy / internal 等） |

## 七、数据模型（SQLite）

数据库文件：`feishu-bot/data/bot.db`（目录不存在自动创建；`.gitignore` 排除）。
开启 `PRAGMA journal_mode=WAL`（读写并发表）与 `PRAGMA busy_timeout=5000`。

```sql
-- 会话（TTL 软口径用 updated_at 过滤）
CREATE TABLE IF NOT EXISTS sessions (
  session_key TEXT PRIMARY KEY,          -- "{open_id}:{chat_id}"
  open_id     TEXT NOT NULL,
  chat_id     TEXT NOT NULL,
  created_at  INTEGER NOT NULL,          -- unix 秒
  updated_at  INTEGER NOT NULL
);

-- 消息历史（history 组装与反馈取数共用）
CREATE TABLE IF NOT EXISTS messages (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,  -- 同时是按钮 value 的 msg_key
  session_key    TEXT NOT NULL,
  message_id     TEXT,                   -- 收到的用户消息 id（reply 用它）
  bot_message_id TEXT,                   -- 机器人回复卡片的消息 id（P2 PATCH 更新卡片用它）
  role           TEXT NOT NULL CHECK (role IN ('user','assistant')),
  content        TEXT NOT NULL,          -- user=原始问题；assistant=answer_md 原文
  finish_reason TEXT,                    -- assistant 轮记录；user 轮为 NULL
  citations      TEXT,                   -- assistant 轮 JSON 数组；P2 反馈取数用
  created_at     INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_messages_session
  ON messages (session_key, created_at);

-- 事件去重（幂等，含消息与卡片回调两类事件）
CREATE TABLE IF NOT EXISTS processed_events (
  event_id    TEXT PRIMARY KEY,          -- 飞书 event.header.event_id
  event_type  TEXT,
  received_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_processed_events_time
  ON processed_events (received_at);

-- 纠错反馈（P2）
CREATE TABLE IF NOT EXISTS feedback (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  open_id     TEXT NOT NULL,
  session_key TEXT NOT NULL,
  message_id  TEXT,
  question    TEXT NOT NULL,
  answer_md   TEXT NOT NULL,
  citations   TEXT,                      -- JSON 数组
  status      TEXT NOT NULL DEFAULT 'open',   -- open / done
  created_at  INTEGER NOT NULL
);
```

写入约定：`db.py` 提供单连接 + `threading.Lock`（单 worker 下竞争极低，
锁只为防御 dispatcher 线程与 worker 同时写 `processed_events`）。

- 数据版本不进机器人配置：机器人不感知 RAG 数据版本，跟随 RAG 的 health
  与启动参数（需求文档风险 5）；
- 飞书开放平台侧一次性配置：企业自建应用 + 机器人能力（只需这一个能力）；
  事件订阅选**长连接**模式，订阅 `im.message.receive_v1`；卡片回调走**新版**
  「卡片回传交互」（控制台回调订阅里添加，即 `card.action.trigger`）——
  **不要**加「卡片回传交互（旧版）」：旧版回调以 `CARD` 帧下发，而 `lark-oapi` 1.7.3
  的 ws 客户端对 `MessageType.CARD` 直接 return（丢弃），配了也收不到；
  长连接不需要 Encrypt Key / Verification Token（event 帧为明文 JSON，不做签名校验）；
  P2 起机器人须已加入运营群（`FEISHU_OPERATORS_CHAT_ID`），否则工单发不出去。
  逐页的"选什么/填什么"清单见 `README.md` 的「检测与验收 → 第 2 层」。

## 十二、实现注意点（风险落地清单）

编码时对照需求文档第九节逐条落地，此处补充实现层面的对应关系：

1. **Markdown 子集** → 5.5.1 收敛器 + 题库样例单测（10.1），禁止"先发了再修"；
2. **子图环境依赖与布局** → 5.6 的 Node 预装进部署清单；**SSR 不支持力导向布局**，
   须预计算坐标或改静态布局（5.6）；降级路径是**必经路径**，与成功路径同等测试
   （P2-1 验收含人为制造失败）;
3. **超时口径** → 机器人 25s（`RAG_QUERY_TIMEOUT`）< RAG 非流式 30s
   （`QUERY_JSON_TIMEOUT_SECONDS`）< LLM 单次 60s × 3 次尝试。这是**有意的层层截断**
   （对话体验优先），不是"与 LLM 超时对齐"——模型跑满预算时飞书通道就该出降级卡片；
   实测完整回答 3.2–9.2s、中位 6.9s（5.4），对 25s 预算余量约 3.6 倍；机器人侧绝不依赖 SSE 的 300s 口径；
4. **回调幂等** → `processed_events` 表 + INSERT OR IGNORE（5.1/第七节）；卡片按钮回调
   的去重键以 `event_id` 为准、缺失时退化为动作身份 + 时间窗，**由 P0-4 实测确认**；
   重复投递在日志中留痕（`duplicate` 标记）；`lark-oapi` 锁版本，升级须回归按钮回调；
5. **数据版本对齐** → 机器人不感知版本，只跟随 health（第十一节）；
6. **版权约束** → 引用片段直接用 RAG 返回的 `snippet`（RAG 侧已按片段返回），
   机器人侧不拼接、不放完整原文；收敛器不改变 snippet 内容；
7. **单实例** → 机器人与 RAG 都单实例起步；机器人侧 SQLite 单写锁设计（第七节）
   已按单实例假设，多实例部署前需改造（当前不做）；注意单 worker 下**所有会话串行**
   （第四节），并发体验的上限在这里；
8. **history 字节预算** → 按 5.2 的 ≤40KB 组装，条数与单条上限只作次级保护；
   413 属机器人侧内部问题，不得对用户显示"问题过长"（5.3）；
9. **卡片规范版本** → 全站按卡片 2.0（5.5.2）；折叠面板、流式卡片等能力都只在 2.0 上，
   不要混用 1.0 骨架。

## 十三、实现说明

本节集中记"设计与实现不一致的地方"，避免读者对着两份说法猜。
没有列出的部分（DLL、事件序列、卡片骨架、超时口径、幂等策略）都是按上文实现的。

1. **目录与文件**：
   - `bot/skills/help.py`：5.3 把 `/help` 列为"P1 随示例问题按钮一起加"的预留规则位，
     按同一风格独立成技能（注册在最前，命中即返回）；
   - Node 出图资产放 `feishu-bot/render/`（`package.json` + `render_subgraph.js`），
     Python 封装仍在 `bot/render/subgraph.py`（subprocess 调用）——把 `node_modules`
     放在 Python 包内部会让打包/清理都别扭；
   - `tests/` 另有 `test_cards.py`（10.1 要求 P0 起覆盖卡片）、
     `test_render_subgraph.py`、`test_config.py`、`test_main.py`（装配与启动自检），
     以及 `tests/conftest.py` 与 `tests/data/eval_answers.json`；
   - `tests/test_aggregate.py` 落在 RAG 侧（`RAG/tests/test_query_json.py`）：
     被聚合的代码在 `server/api.py`，测试跟着被测代码走；
   - RAG 侧新增 `contracts/query_json.py`（响应 dataclass）。

2. **技能接口扩展**：`Reply` 增加可选字段 `assistant_turn: AssistantTurn | None`
   （5.3 的 `Reply(kind, card, text)` 保持可用）。原因：assistant 轮要写进会话历史，
   而它需要的 `bot_message_id` 只有**发送之后**才知道——落库动作因此属于 dispatcher，
   技能只负责把"该记什么"交给它。

3. **卡片按钮与落库顺序**（P2-2 的实现关键）：按钮 value 要带 `messages.id`，
   而卡片必须在发送前组好，两者天然冲突。实际顺序是
   **技能归卡片（不带按钮）→ 落库拿 id → `attach_feedback_button(card, id)` → 发送 → 回填 bot_message_id**。
   代价是同一条链上有一次卡片原地修改，收益是"点了按钮指向的一定是真实落库的那一行"。

4. **纠错回执不做 PATCH 整卡**：5.7 把"更新原卡片按钮为「已收到反馈」"标为可选。
   飞书的 PATCH 是**整卡替换**，而 `messages` 表只存正文与引用、不存 panel，
   重建卡片会把用户正在看的实体卡/子图弄丢——宁可不动。用户侧回执由卡片回调的
   **即时 toast**（`on_card_action` 同步返回）承担；同一用户对同一条回答的重复反馈
   由 `feedback(open_id, message_id)` 去重，不再重复投递运营群。

5. **去重键实现**：消息事件的退化键用 `message_id`（长期，落 `processed_events`）——
   同一条消息的重投 `message_id` 必然相同，且用户不可能发出 `message_id` 相同的新消息，
   所以不需要时间窗；卡片回调的退化键（消息 + 操作人 + tag + value 摘要）**只存内存**
   并配一个极小窗口（默认 2s），因为它必须放行真实二次点击（P0-4 验收）。
   两种路径都把重复投递记为 `duplicate` 日志。

6. **历史组装的两个细节**（5.2 落地时明确）：
   - 终态过滤写在 SQL 里（`role='user' OR finish_reason IN (...)`），否则不可入历史的
     轮次会白占 40 条的名额；
   - 组装完成后若**头部是孤立的 assistant 轮**则丢弃（没有对应提问的回答不是上下文），
     并用真实序列化结果做一次兜底校验（估算可能偏乐观）。

7. **`/api/query/json` 的失败形态**（第六节的补充）：聚合期间出现 `error` 事件时，
   接口不返回 200 而是映射成 HTTP 错误（timeout → 504，其余 500 并透传 `error_code`；
   401 `unauthorized` 是新增的可选密钥错误码）。因此机器人侧看到的失败都是**HTTP 错误**，
   只有 200 响应里的 `finish_reason` 需要判断；`finish_reason` 不属于
   normal/refused/degraded 的 200 响应按契约外情况处理，直接降级且不写历史。

8. **一致性回归脚本的顺序设计**（10.2 的落地口径）：脚本固定"先 SSE、再非流式"，
   因为两次独立生成的结果本就可能因模型随机性而不同，**比对两个未命中没有意义**；
   固定顺序后，SSE 那次是真链路（未命中），紧随其后的非流式调用会命中刚写入的缓存，
   一轮同时覆盖"真实链路"与"回放路径"。要强制排除历史缓存干扰时用 `--bypass-cache`
   （给问题加一次性后缀，两通道用同一份问题文本，一致性仍然可比）。

9. **本地冒烟工具与接口存在性探测**（`scripts/local_smoke.py`、`RagClient.supports_json_query`）：
   这两件工具用来降低验收门槛，不必"有真实飞书客户端才能验收"：
   - `local_smoke.py` 用记录式替身顶掉"发给飞书"这一步，跑完整链路（真 config、真会话库、
     真调 RAG、真组卡片、真出图），把卡片 JSON 落盘供贴进**卡片搭建工具**预览——
     于是"卡片长相"这一类验收不需要飞书租户；
   - `supports_json_query()` 在启动时探一次非流式接口是否存在（空请求体的 POST，
     路由存在会被参数校验拒绝，返回 400/413/422/429）。原因是这类配置错误很难看出来：
     `RAG_BASE_URL` 指向没有该接口的旧实例时，health 正常、每次提问却只得到
     "服务暂不可用"，日志里看不出所以然。这种情况会在启动日志里被 ERROR 点名。

10. **真机首次运行暴露的三个问题及修法**（都已落成测试，见第十节）：
   - **`FeishuClient` 漏存 `app_secret`**：HTTP 客户端构造时用了它、但没留成实例属性，
     建长连接时才 `AttributeError`。教训：只测"鸭子类型替身"会让"构造真实 SDK 客户端"
     这条路完全没覆盖——所以 `tests/test_feishu_client.py` 用"记录式 HTTP 客户端"
     覆盖 reply/create/patch/上传图片的**真实 builder 组装**；
   - **子图渲染被误判失败**（编码）：Node 把含中文的绝对路径打在 stdout 上，
     而 Windows 上 Python 默认按本地编码（cp936）解读子进程输出——UTF-8 字节解错后
     JSON 解析失败，日志只剩一个空冒号。修法：协议改为 Node 只回 `{"ok":true,"bytes":N}`
     （路径由 Python 侧自己持有），并显式 `encoding="utf-8", errors="replace"`；
     失败且无 error 字段时把 stdout/stderr 片段打进日志；
   - **进程退不出来**：见第四节"长连接线程归位"。

11. **历史只记"有回答的轮次"**（真机超时问题的根因，见 5.2）：
    联调时发现同一个「介绍一下长平之战。」先问一次是 16–25s 的真生成，再问一次（含
    `/help` 那条历史）本该命中缓存却又是真生成、直接把 25s 预算顶穿。原因是命令轮
    （`/help`）也被记进了会话，而历史参与缓存键。写法是
    "user 行与 assistant 行一起写、只写能入历史的轮次"（`dispatcher._record_turn`），
    顺序上 user 先写以保证反馈工单取到正确的问题。副作用是"回答失败的提问不再留在历史里"
    ——这反而更合理：没有回答的孤立提问对模型没有价值。

12. **超时预算可调**（同一问题的另一半）：`RAG_QUERY_TIMEOUT` 与 RAG 侧
    `QUERY_JSON_TIMEOUT_SECONDS` 的"必须小于"关系不能把 30 写死在机器人侧校验里，
    否则想等更久也改不动。机器人侧因此有 `RAG_JSON_BUDGET`（默认 30，应等于 RAG 的
    非流式预算），校验比的就是这两者，两边一起调大即可（例：45 / 40）。
    实测参考（本机直连 RAG，非缓存）：短答题 5.5–7.6s；「介绍一下长平之战。」这类
    长回答 12–16.5s 且 `truncated=True`——**预算与回答长度直接相关**，
    想缩短等待还可以在 RAG 侧调小 `QUERY_FUSION_LIMIT` / `LLM_MAX_TOKENS`。

13. **历史收敛成"提问 → 回答"的成对结构**（`SessionStore._drop_orphans`）：
    写入规则（第 11 条）只能保证不再产生脏数据，**库里已有的旧数据不会自己变干净**——
    联调时实测到会话里残留着更早版本写下的 `/help` 行与"超时那轮留下的提问行"，它们既被当上下文
    发给模型，又让缓存键永远命中不了（本该毫秒返回的问题变成 12–16s 真生成）。
    于是查询侧加三道收敛：提问之前的孤立回答丢弃、连续提问只留最后一条、
    尾部没有回答的提问丢弃。存量数据用
    `python scripts/cleanup_db.py --purge-orphans` 清理（先 `--dry-run` 看条数）。
    这一条与第 11 条是同一个问题的两半：写入规则保证不再产生，收敛规则保证已存在的也不生效。

14. **卡片的三处 1.0 写法**（真机整卡拒收的原因）：
    首次真机发送时飞书报 `code 200621 parse card json err ... unknown property,
    property: type, path: ... -> body -> elements -> [1](tag: collapsible_panel) -> border`，
    排查后发现**五处骨架（5.5.2）里的三处字段都是 1.0 的写法**，对应写法见下表：

    | 位置 | 1.0 写法（错） | 2.0 正确写法 |
    | --- | --- | --- |
    | 折叠面板边框 | `border: {"type": "default"}` | `border: {color, corner_radius}` |
    | 全局配置 | `config.wide_screen_mode` | `config.width_mode`（default/compact/fill） |
    | 按钮容器 | `{"tag": "action", "actions": [...]}` | 按钮直接放 `body.elements` |
    | 按钮回传参数 | 顶层 `value` | `behaviors: [{"type": "callback", "value": {...}}]` |

    回调事件仍从 `event.action.value` 取参数，所以 dispatch/skill 层的解析**不用改**——
    变的只是卡片写法。另外确认合法：`markdown`、`hr`、`img`（`alt` 必填且只支持
    `plain_text`）、`collapsible_panel`；`button.text.content` 上限 100 字符。
    教训与对策：**飞书没有离线校验卡片的接口**（`cardkit.v1.card.create` 可做服务端
    dry-run，但需要 `cardkit:card:write`，本项目未开），所以把已知规则写成
    `tests/test_cards.py` 的「2.0 合规守卫」——违反就在测试里挂掉，而不是等用户点开卡片。
    附带一条实用技巧：飞书文档站每条 URL 后加 `.md` 可拿到纯 Markdown 版
    （页面含 `<link rel="alternate" type="text/markdown">`），比抓 JS 渲染的 HTML 可靠。

15. **串联排查：从"回复不出"到"超时"的三段式归因**（真机联调实录，供后续排查参照）：
    同一句「介绍一下长平之战。」在联调期先后以三种面目失败，每次的真因都不同，
    记录在此以免下次误判：

    | 现象 | 真因 | 处置 |
    | --- | --- | --- |
    | 机器人没反应 | 应用缺发消息权限（`99991672`） | 开放平台开 `im:message:send_as_bot` 并重新发布 |
    | 有回答但没发出 | 卡片混用 1.0 字段被整卡拒收（`200621`） | 见第 14 条 |
    | 降级卡片"超时" | ① 会话里的孤儿行污染缓存键 ② **RAG 进程未重启，仍是 30s 旧预算** ③ 长回答本身 11–25s，偶发抖动越线 | ①②见第 11–13 条；③调预算（45/40） |

    另一条实测结论值得记住：**同一个问题在同一会话里再问一次不会命中缓存**
    （历史参与缓存键），所以每次都是真生成；生成耗时由**输出长度**主导
    （1600 字答案约 11s，短答题 4–8s），历史长短的影响在噪声范围内（见 5.2 的说明）。
    因此判断"超时"时先看 `elapsed_ms` 与答案长度，再决定是调预算还是调输出长度。

16. **发送链路的重试与兜底**：
    线上出现一次"回答已生成、用户什么也没收到"——RAG 5.9s 正常返回，组卡后调飞书 reply
    时对 `open.feishu.cn:443` 的 TLS 连接被对端掐断（`SSLEOFError`），异常一路抛到
    `worker_loop` 的兜底 catch，只留一条 ERROR 日志。根因是 SDK 传输层用 `requests`
    且没配重试（`HTTPAdapter` 默认 `max_retries=0`）。两层修复：

    - **`feishu_client` 传输层重试**：reply/create/patch/上传图片共用一个重试包装，
      对 `requests.exceptions.RequestException`（连接/SSL/超时）重试 2 次、退避 0.5s/1s。
      配套两件事：① reply/create 传 **`uuid`**（飞书按它做服务端幂等去重，且必须在重试间
      保持不变——否则"请求实际到达但响应丢失"的重试会发出第二条消息）；
      ② 登录逻辑里每次尝试都**重建请求对象**（SDK 首次发送会把 `request.body` 换成
      `MultipartEncoder`，复用同一对象重试会读到空流），上传图片还要把文件指针复位。
      重试仍失败则**抛给调用方**（不再吞成 None）；
    - **`dispatcher` 发送兜底**：`_send_reply` 捕获发送异常→按"发送失败"处理；
      最终失败时把刚落库的 user + assistant 两行**一起撤回**（`SessionStore.delete_messages`，
      为此 `_record_turn` 改为返回 `(user 行 id, assistant 行 id)`），并把答案全文打进
      ERROR 日志供运营手工补偿。理由是"成对写入"原则的另一面：用户从未见过的回答
      不该留在历史里——它既污染下一轮上下文，又让历史参与的 RAG 缓存键永远命中不了。
      观测计数新增 `send_failed`（与"任务失败" `failed` 区分开）。

    环境侧提醒：requests 会读系统代理，Windows 上挂全局代理（Clash 等）时对
    `open.feishu.cn` 的 TLS EOF 属常见现象；给机器人进程设 `NO_PROXY=open.feishu.cn`
    或关代理可消掉大半此类抖动。

17. **三处易踩的坑（卡片迁移与死代码）**：

    - `scripts/local_smoke.py` 必须按卡片 **2.0** 形态解析按钮（1.0 的 `tag == "action"`
      容器与顶层 `value` 都不存在）：按 1.0 取值的后果是按钮摘要恒为空、纠错反馈环节
      **静默跳过**（脚本照样退出 0）。它复用测试侧的 `tests/card_helpers.py`
      （唯一一份 2.0 取值实现），非降级卡片缺反馈按钮会直接让脚本以退出码 1 报错；
    - `dispatcher._record_assistant` **已删，不要重新引入**：它只写 assistant 行，与
      "成对写入"的约束冲突，留着迟早被当成可选路径调用，直接破坏缓存键相关的约束；
    - `DemoExamplesCache` 必须有**负缓存**：刷新守卫只要求"缓存非空"时，接口失败这一条
      永远不成立 → 每次组卡都同步重打一次 `/api/demo/examples`，端点不可用时最坏吃满
      connect 5s + read 25s 的客户端超时。成功/失败两条路径都要记刷新时刻，
      失败后按 `DEMO_EXAMPLES_FAILURE_RETRY_SECONDS`（默认 300s）再试。

    另有三处口径：`strip_mentions` 只剥**本机器人**的 mention（群里 @ 别人是
    问题语义的一部分，一律剥掉会改问题语义）；`/help` 系列命令统一按"第一个词"匹配
    （否则 `/帮助 长平之战` 不命中）；ws 客户端日志级别跟随 `BOT_LOG_LEVEL`。
    运维侧两处：停机等待放宽到 RAG 预算、`cleanup_db --purge-orphans` 去掉逐行回查
    的 N+1（`role` 随第一次 SELECT 一起取）。反馈表无 TTL 的口径见 5.7。

18. **两段式回复与 `/new`**：

    - **两段式回复**：`handle_message` 在技能执行**之前**先 reply 一张占位卡，
      跑完用 `patch_card` 整卡替换同一条消息（消息 id 不变、不新增消息）。时序与
      三条失败路径见 5.1。三个实现要点：
      ① 是否发占位卡由**技能自己声明**（`wants_placeholder`）而不是按技能名硬编码——
      慢的是"同步等 RAG"这件事，将来有别的慢技能就同样能声明；
      ② 占位卡发失败退回单段式（一次传输层抖动不该让整轮没有回答）；
      ③ 最终卡 PATCH 失败时先尽力把占位卡换成"发送失败"提示（不能让用户一直看到
      "正在检索…"），同时按"不保留未送达的回答"撤回本轮历史——本实现的读法是
      **两者都做**：
      用户侧给提示（不沉默）、数据侧撤历史（回答确实没送达）；
    - **`/new` 重置会话**：新技能 `bot/skills/new_session.py`（`/new`、`/重置`），
      删本会话的 messages/sessions 行、保留 feedback；命令匹配与 `/help` 共用
      `base.matches_command`。`/help` 的说明书里同步列出了 `/new`——它是用户唯一的
      自助重置入口，不写进说明书等于没有。
      两段式对它不适用（命令轮秒回、没有 RAG 调用），因此它不声明 `wants_placeholder`。

    验证：冒烟脚本真调 RAG 跑通"占位卡 → 最终卡"（263 字符 → 3983 字符、四个折叠区、
    出图与四个按钮）与 `/new`（历史 4 → 0 条、feedback 1 → 1 行）；两段式的四条失败
    分支与 `/new` 的两条口径都有集成用例覆盖。
