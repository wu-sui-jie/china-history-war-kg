## 一、背景与定位

### 项目现状（一句版）

整个工程是「一条知识生产流水线 + 三个产品面」：

- `entity-event-relation/`：离线抽取流水线（LLM 三轮抽取 + 缓存 + P/R/F1 评测），产出图谱数据；
- `backend/` + `frontend/`：旧知识库管理台（Flask + SQLite/Neo4j 双库 + Vue3），图谱可视化、节点 CRUD、质检工作台、旧版问答；
- `RAG/`：新一代问答引擎（FastAPI，图谱 + 文本双通道 RAG），**运行时不依赖旧库**，只读自己的快照与索引制品，唯一耦合点是离线导出（F09）。

RAG 的"独立部署"（旧版 R1）已基本达成：代码同仓库、运行时独立，拷贝代码 + 数据制品即可在另一台机器启动问答。本需求不再处理分离问题，专注**给 RAG 加一个飞书入口**。

### 为什么是飞书

- 终端用户不会在电脑上开网页程序；飞书消息即交互，卡片、事件订阅都是现成的；
- **长连接模式**：企业自建应用可用 WebSocket 长连接收消息，**不需要公网回调地址、不需要备案域名**，个人电脑即可跑通——与"个人自用起步 → 内部团队自用"的场景完全匹配。

### 使用场景与边界

| 维度 | 结论 |
| --- | --- |
| 用户 | 先个人自用（自己的飞书验证闭环），再扩散到内部团队 |
| 明确不做 | 任何业务写操作（预约/改期/提醒等）；面向公众的渠道（小程序等）；知识库实时同步 |
| RAG 的角色 | 保持**只读、无状态**的纯知识引擎，不感知飞书的存在 |
| 机器人服务的定位 | **项目级** IM 入口（仓库根顶层目录，与 RAG 平级），当前只挂 RAG 一个引擎，未来能力以技能形式扩展 |

## 三、总体架构：两层 + 技能框架

旧版的三层边界（业务层/编排层/引擎层）随触发机制废弃，收敛为两层：

```text
飞书客户端（单聊 / 群聊 @机器人）
    │  WebSocket 长连接（飞书官方 SDK，无需公网回调）
┌───▼──────────────────────────────────────────────┐
│ 飞书机器人服务（新建，独立进程 feishu-bot/）          │
│  ① 事件接入：验签、去重、秒级 ACK，处理异步化        │
│  ② 会话管理：open_id × chat_id → 多轮历史（SQLite） │
│  ③ 技能框架：意图分流（规则）→ 技能执行 → 卡片组装   │
│     • knowledge_qa：调 RAG → 翻译为飞书卡片         │
│     • report_error：收集纠错 → 转发运营群（起步）    │
│  ④ 子图服务端出图（P2）：渲染为图片随卡片发送        │
└───────┬──────────────────────────────────────────┘
        │ HTTP（同机内网；可选共享密钥）
┌───────▼──────────────────────────────────────────┐
│ RAG 引擎（现状 + 1 个新接口）                       │
│  POST /api/query/json（新增：聚合 run_query 生成器）│
│  F02 理解 / F03 图谱 / F04 文本 / F05 融合 / F06 生成：零改动 │
└──────────────────────────────────────────────────┘
```

**技能框架原则**（继承旧版 Q7/Q10 的修正结论）：

- 机器人服务是所有"动作"（反馈收集、通知、未来扩展）的唯一归属地；RAG 只回答知识问题；
- 意图分流起步用**规则**（按钮回调 / 命令前缀），不引入 LLM 意图识别——技能只有 2 个，规则零延迟且可测试；技能增多后再升级为模型分流；
- RAG 是**工具**而非 agent（旧版 Q10）：机器人服务调用的是"数据/接口"，不是"页面"。

**模块位置与边界（2026-09-21 确认）**：

- 机器人服务是**项目级**的 IM 入口，不属于 RAG 子系统：目录放在**仓库根 `feishu-bot/`**，
  与 `backend/`、`frontend/`、`RAG/`、`entity-event-relation/` 平级——它未来可挂载 RAG 之外的
  引擎与技能，放 `RAG/` 内部会造成归属错位；
- 隔离要求：独立依赖清单（`feishu-bot/requirements.txt`，不写入 `RAG/requirements.txt`，
  可与 RAG 共用 Python 3.11 环境；核心依赖 `lark-oapi` **锁定版本**，升级前须回归按钮回调）；
  自有 SQLite（会话与反馈），运行时不读写 RAG 目录；
- **删除边界**：若后续判断方向不对，删除 `feishu-bot/` 整个目录即完全下线，其他模块零影响；
  RAG 侧唯一改动（非流式接口）是纯增量能力，保留不回滚——任何非浏览器调用方都可复用。

## 五、改造点清单

### 5.1 RAG 侧：唯一改动是一个只读接口（小改动）

`POST /api/query` 是给浏览器流式消费的，机器人服务需要"一次调用取完整结果"。新增 `POST /api/query/json`（非流式），**消费同一个生成器**——`server/sse.py::run_query` 是纯异步生成器，按固定事件序列产出（见第十节事实表）。非流式接口把 `answer` 增量拼成完整 Markdown、其余事件直接取 payload，聚成一个 JSON 返回：

```json
{
  "answer_md": "……",
  "citations": [ /* 引用列表 */ ],
  "panel": { /* 实体卡/子图/时间线/地图点 */ },
  "finish_reason": "normal",
  "model_used": "……"
}
```

- 缓存命中（`cache_hit` 分支）时 answer/citations/panel 一并回放，聚合路径同样可用；
- SSE 通道的心跳 15s 与总时长 300s 护栏只约束流式通道；非流式同步等待另设自己的超时预算（机器人 25s、接口 30s），与 LLM 超时（单次 60s × 重试）构成**有意的层层截断**——对话体验优先，超出预算发降级卡片，不做"等模型慢慢答"；
- 可选共享密钥：`RAG_BOT_API_KEY` 环境变量，设置后该接口要求请求头 `X-Bot-Key`（默认关闭，内网场景可不开）；
- 不改 F02–F06 任何链路。

### 5.2 机器人服务侧（全部新建）

| 模块 | 职责 | 要点 |
| --- | --- | --- |
| 事件接入 | 收消息/按钮回调 | 长连接 SDK；回调只做 ACK 与入队，处理异步化（飞书要求秒级应答，超时会重试，须幂等） |
| 会话管理 | 多轮历史 | 键 `open_id × chat_id`；SQLite 持久化防重启丢失；TTL 清理 |
| 技能框架 | 意图分流与执行 | 接口示意：`Skill(name, match(ctx), run(ctx) -> Reply)`；起步两个技能 |
| 卡片组装 | RAG 输出 → 飞书卡片 | **统一按卡片 2.0 规范**（折叠面板等组件只在 2.0 上）；**Markdown 白名单收敛器**（飞书卡片只支持 md 子集）；引用折叠与按钮回调注册 |
| 子图出图 | panel.subgraph → 图片 | 服务端渲染（选型见待决项 1）；失败降级文字列表 |
| 纠错流转 | 反馈收集与投递 | 起步转发运营群；后续可落 SQLite 对接旧系统质检流程 |

### 5.3 输出翻译对照表

| RAG 输出 | Web（现状） | 飞书卡片对应 |
| --- | --- | --- |
| `answer` Markdown | MarkdownContent 渲染 | 卡片文本（飞书 md 子集，白名单收敛） |
| `citations` | 右侧证据卡，可展开原文 | 回答末尾引用列表 + 折叠片段 |
| `panel` 实体卡 | EntityCardsView 标签页 | 文字化实体卡区 |
| `panel` 子图 | SubGraphView（ECharts） | **服务端渲染图片**，失败降级分组文字 |
| `panel` 时间线 | TimelineView | 文字化时间轴 |
| `panel` 地图点 | MapView（ECharts + 内置地图） | 复用"无坐标→地点列表"降级，输出文字列表 |

panel 的前端现状（翻译时的字段参照）：五类数据由 RAG 前端 `PanelPane.vue` 的五个标签页消费——
引用证据（`EvidenceView`）、实体卡（`EntityCardsView`）、子图（`SubGraphView`，ECharts）、
时间线（`TimelineView`）、地点（`PlacesView`/`MapView`，ECharts + 内置 `china-map.json`，无坐标自动降级为地点列表）。
飞书侧翻译对齐这些视图实际消费的字段即可，panel 结构本身（`contracts/panel.py`）无需改动。

### 5.4 不改动与回归护栏

F02 实体识别/消歧、F03 图谱检索、F04 文本检索、F05 融合/冲突/panel 装配、F06 生成与缓存、
F09/F11 离线链路、F10 评测闭环均无需改动。

回归口径：接口适配完成后，用 F10 评测闭环跑回归（入口 `RAG/scripts/run_evaluation.py`，题库 + 进程内复跑 F02–F06 链、绕缓存，产物在 `RAG/data/eval/<版本>/runs/`）。
**新增一条 P0 回归口径：同一问题分别走 SSE 与非流式接口，`answer`/`citations`/`panel` 三者必须一致**，防止聚合实现与流式实现分叉。

## 六、关键技术决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 飞书接入方式 | 企业自建应用 + WebSocket 长连接 | 无需公网回调/备案/审核；个人本机可跑 |
| 意图分流 | 规则（按钮回调/命令前缀） | 技能仅 2 个；零延迟、可测试；后期可升级 LLM 分流 |
| 会话持久化 | SQLite（机器人服务自持） | 重启不丢；单机场景够用，不引入外部依赖 |
| RAG 调用超时 | 机器人 25s / 非流式接口 30s，超时发降级卡片 | 对话体验优先；实测 12 道演示题完整回答 3.2–9.2s、首答 2.4–6.3s，对 25s 预算余量约 3.6 倍，慢问降级属预期行为 |
| 鉴权 | 同机内网 + 可选 `RAG_BOT_API_KEY` | 内部场景不做完整鉴权体系；公网暴露不在范围内 |
| 限流 | 维持 RAG 现状（按 IP 滑窗） | 内部人数少；按用户配额（原 A13）暂缓 |
| 机器人服务位置 | 仓库根顶层 `feishu-bot/`，与 RAG 平级 | 项目级 IM 入口，不放 RAG 内部；整目录删除即可下线，互不影响 |
| LLM 密钥 | 上线前必须配好 | 否则 F06 走离线摘要回答器，飞书回复质量受限（原 A2，真正的上线阻塞项） |

## 七、旧版结论的继承与废弃清单

**继承（仍有效的关键结论）**：

- 旧版 Q1：RAG 与旧系统的分离是**要固化的边界**，不合并代码——本文 5.4 延续；
- 旧版 Q8：图谱接口的 `LIMIT 200` 是"看图护栏"不是"工具上限"——机器人服务不得整表透传，翻译时按字段裁剪；
- 旧版 Q10：飞书出现的是"**数据**"而非"页面"；RAG 是**工具**而非 agent——本文技能框架的立论；
- 旧版 Q11：旧库是源头与治理面，快照 + 索引是离线构建产物，答问是"构建一次、服务多次"的在线服务；
- 旧版 5.4：知识库更新 = 离线重建 + 换版本重启（`export_snapshot.py` → `build_index.py` → 固定版本重启），是**运维任务**，与机器人无关；
- 旧版 Q5/A7：旧问答页维持现状（保留作对照基线），不在本需求范围内处置。

**废弃（不再出现在本方案中）**：

| 废弃项 | 原位置 | 废弃原因 |
| --- | --- | --- |
| 预约改期触发机制 | 原 R4、第七节、P3、A5/A12 | 本项目不存在预约业务；写操作违背 RAG 只读边界 |
| 微信小程序通道 | 原第六节对比、P4 | 用户群体已定内部场景；未来若需公众渠道再议 |
| "Hermes" 概念 | 全文 | 只是代号，从未是现成软件；改称"飞书机器人服务" |
| Agent 工具收编旧后端 | 原 A6/A9/A10/A14 | 机器人场景只需知识问答 + 反馈，无需 tool calling 体系；留待未来 |

1. 子图服务端出图选型：echarts SSR（Node 侧渲染，配色/结构对齐前端，推荐）vs pyecharts + 浏览器快照（依赖浏览器内核，环境更重）——P2 前拍板即可。**已知约束**：前端子图用的是 ECharts 力导向布局，而 SSR 是一次性同步渲染、力导向迭代不会执行——必须在 Node 侧预计算坐标（d3-force 迭代后走 `layout: 'none'`）或改静态布局；出图只承诺信息结构一致（开发文档 5.6）；

4. 纠错投递目标：用现有群还是新建专用运营群。

## 九、风险与注意事项

1. **飞书 Markdown 子集**：卡片不支持完整 Markdown，F06 输出必须经白名单收敛器，否则渲染错乱——翻译层要带单测，用评测题库的真实回答做样例；卡片规范**统一按卡片 2.0**（折叠组件等能力只在 2.0 上，见开发文档 5.5.2），不要混用 1.0 骨架；
2. **子图出图的环境依赖**：SSR 需 Node 环境（快照方案需浏览器内核），部署机要预装；渲染失败必须自动降级文字列表，不能空白；
3. **非流式超时口径**：SSE 的心跳 15s/上限 300s 只约束流式通道；非流式接口 30s、机器人 25s，且都远小于 LLM 的单次 60s × 重试——慢问必然走降级卡片，这是有意取舍而非缺陷；
4. **回调幂等**：飞书的 WS 推送是"至少一次"投递，机器人侧需按事件 ID 去重，否则一次提问可能回复多条；卡片回调（`card.action.trigger`）能否稳定走长连接、`event_id` 是否可用，**P0 就要用最小 demo 实测**（开发文档 P0-4），不要等 P1 才发现；
5. **数据制品与代码版本对齐**：快照/索引与代码同版本发布（manifest 版本校验已有）；机器人服务不感知数据版本，跟随 RAG 的 health 即可；
6. **版权约束**：卡片中引用原文片段保持短摘录（引用组件本就按片段返回），不暴露原文全量；
7. **单实例并发**：机器人服务与 RAG 各自单实例起步；RAG 的内存图谱 + FTS5/Chroma 在内部场景够用，多 worker 会各加载一份数据，暂不开启；机器人侧单 worker 时**所有会话串行**（不同用户也要排队），并发上限在此，会话数上来后按 session_key 分片；
8. **历史组装边界**：RAG 的请求体上限（64KB）先于参数校验生效，机器人侧必须按**总字节预算**组装历史（开发文档 5.2），否则长会话会拿到 413，且这种错误不得对用户显示为"问题过长"。
