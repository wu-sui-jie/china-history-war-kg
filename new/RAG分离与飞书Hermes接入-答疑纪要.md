# RAG 分离与「飞书 + Hermes」接入 — 答疑纪要

- 文档类型：评审答疑 / 结论记录
- 记录时间：2026-09-13
- 来源：围绕 [RAG分离与飞书Hermes渠道化-需求分析.md](RAG分离与飞书Hermes渠道化-需求分析.md) 的两轮评审疑问及答复
- 答疑轮次：第一轮 Q1–Q4（分离与启动路径、功能丰富度、向量与存储扩展性、Agent 与飞书接入）；第二轮 Q5–Q7（旧问答页去留、旧系统定位与运行环境、"收编工具"的复用边界）；第三轮 Q8–Q9（图谱 200 节点限制与工具收敛策略、页面功能在飞书的体现范围与旧系统价值）；第四轮 Q10（整体理解确认：旧库留在 Web、RAG 在飞书、agent 取数路径）；第五轮 Q11（链路理解确认：离线构建与在线服务的分工）
- 状态：已答复；其中「待决项」需业务侧拍板

## 一、总体结论

1. **RAG 与旧前后端的分离不是缺陷，而是要固化的边界**。需要解决的是它带来的三个副作用：双问答并存、入口分散、数据靠人工同步；**不建议合并代码**。
2. **只把 RAG 接入飞书，功能确实单一**（RAG 对外只有 3 个接口，能力边界就是知识问答）。但补齐能力所需的接口**大部分旧后端已经具备**，收编为 Agent 工具即可。
3. **当前不是"没用向量库"，而是向量索引还是占位空文件**，F04 实为纯 FTS5 关键词检索。当前 1 万级 chunk 规模本地存储完全够用；风险在于「全量重建 + 单文件矩阵 + 暴力检索」的实现方式，而非"本地 vs 向量库"。
4. **"RAG + 大模型 API"做问答机器人够用，做"能改预约时间的助手"不够用**；且飞书接入与 Agent 成熟度**不构成串行依赖**，可并行推进。真正的上线阻塞项是 LLM 密钥配置与会话/任务持久化。
5. **旧问答页不必立刻删除**：先取消它的用户入口身份（摘路由/菜单），保留作答案质量对照基线，新入口稳定后再删除；删除范围仅限"问答页 + 问答入口"，不含实体识别/规则推理模块。
6. **"旧系统降级为管理后台"改的是服务对象，不是系统形态**：旧前端建议保留（管理动作需要图谱可视化与表单交互）；两套运行时靠「进程隔离 + HTTP 通信 + 数据单向离线流动」共存，在线只跑 RAG，旧系统连同 Neo4j 按需启动。
7. **"收编旧后端接口为工具"复用接口与数据、不复用页面**：页面间的关联性由 Agent 会话上下文接替；真正的工作量是把"页面友好"的响应适配成"模型友好"的工具签名，前提是所选模型支持 tool calling。
8. **图谱接口的 200 条上限是"看图护栏"，不是"工具上限"**：200 条关系三元组对 ECharts 刚好，对模型是灾难级体量；工具必须单独设计收敛策略（聚合摘要 + top-K + 字段裁剪 + 可追问），不能把 200 直接搬过去。
9. **"页面功能是否在飞书体现"不该是目标**：飞书要的是"结论 + 依据 + 可追问"，不是复刻页面。读类可对话化、图谱/地图降级体现、写与批量类留在旧系统；旧系统从台前退到幕后，它的价值是 RAG 的数据源头与质量保障。
10. **整体理解确认**：旧库页面留在 Web、飞书侧由 Hermes 接待用户、数据来自旧库，这三条成立；但需修正三点——飞书出现的是"数据"而非"页面"，agent 调用的是"数据/接口"而非"页面模块"，RAG 是工具而非 agent。
11. **链路分工确认**：旧知识库是**源头与治理面**（不是"离线构建产物"），RAG 的快照 + 索引才是**离线构建产物**，agent 答问走的是**在线服务（检索 + 生成）**而非"在线构建"——构建一次、服务多次。

## 三、Q1：RAG 与旧前后端分离、启动路径不同，如何解决？

### 结论

分离本身应当保留。需要处理的是三个副作用：双问答并存、入口分散、数据人工同步。**不要合并代码**。

### 现状

三个独立启动路径：

| 系统 | 后端 | 前端 |
| --- | --- | --- |
| 旧知识库系统 | Flask `backend/app.py`（5000） | Vue3（3001，代理 5000），含旧问答页 |
| RAG | FastAPI `scripts/run_server.py`（8000） | Vue3（5173，代理 8000） |

### 三个副作用

1. **双问答并存**：旧 `/api/ai/inference` 与 RAG `/api/query` 口径不同（引用规则、拒答策略都不一样），同题不同答，且需维护两套。
2. **入口分散**：前端是两个独立工程（旧系统 3001、RAG 5173），后端各自为政，没有统一网关。
3. **数据靠人工同步**：RAG 数据经离线 F09/F11 导出，不自动跟随旧库更新。

### 建议：三收敛（不改代码即可完成前两项）

1. **角色收敛**：旧系统降级为知识管理后台（图谱 CRUD、质量工作台、审核）；旧问答 `/api/ai/inference` 明确下线或标记旧版；RAG 成为唯一面向用户的问答引擎。
2. **入口收敛**：用户侧统一从 Hermes/飞书进入；Web 前端保留给运营与演示。若仍需 Web 一站式访问，用 Nginx 按路径分流（`/api/rag/*` → 8000，其余 → 5000），前端只连一个域名。
3. **运维收敛**：两套服务各自提供启动/停止脚本或 Dockerfile，端口写死配置；RAG 换数据版本固化为「离线构建 → 拷贝数据制品 → 重启」流程。

### 为什么不合并进旧系统

RAG 是 Python 3.11 + FastAPI + pydantic，旧后端是 Python 3.8 + Flask + SQLAlchemy + py2neo。把 RAG 做成 Flask 蓝图会同时引入依赖冲突、启动耦合与部署耦合，收益为零。分开部署、以 HTTP 为边界才是正确形态。

## 四、Q2：只把 RAG 接入飞书，功能是否过于单一？

### 结论

会退化为「只会背历史书的问答机器人」。RAG 对外仅 `POST /api/query`、`GET /api/health`、`GET /api/dicts` 三个接口，能力边界就是知识问答。

### 但补齐能力的接口大多已存在

旧后端已有的只读接口可直接收编为 Agent 工具：

| 工具用途 | 现成接口 |
| --- | --- |
| 知识问答 | RAG `POST /api/query` |
| 实体详情 | `/api/node/detail`、`/api/entity/detail` |
| 事件关系 | `/api/graph/event_event`、`/api/node/relations` |
| 按类型/关系查询 | `/api/node/by_type`、`/api/node/by_relationship` |
| 时间线 | `/api/timeline/events`、`/api/timeline/overview` |
| 地图/地点 | `/api/map/events` |
| 全局搜索 | `/api/search/global` |
| 预约改期/提醒 | 业务层（Hermes 技能，需新建） |

### 建议的最小工具集

只读类（5–6 个）：`search_war_knowledge`（RAG）、`get_entity_detail`、`get_event_relations`、`list_events_by_dynasty_or_type`、`get_timeline`、`get_place`；写操作类（改期/提醒）单独一类并控权限。

补充：RAG 的 `panel` 数据已含实体卡、子图、时间线、地图点（`contracts/panel.py`、`docs/data-contract.md`），翻译成飞书卡片或服务端出图后，能明显改善"功能单一"的观感。

## 五、Q3：当前无向量库、本地存储，大规模文本处理会不会出问题？

### 结论（先纠正事实）

**现在不是"没用向量库"，而是向量索引还没建——是占位空文件**，F04 实为纯 FTS5 关键词检索。

### 现状证据

- `data/index/20260904_v2/build_report.json`：`"vectors": {"mode": "placeholder", "dim": 0}`
- `vectors/embeddings.npy` 仅 128 字节（0×0 矩阵）
- `server/text/searcher.py` 注释：向量检索不可用，自动降级关键词
- `data/index/vectors.py`：`build_vectors(embed_fn=...)` 接口已留，`embed_texts` 未实现

当前规模 9544 chunk，`chunks.jsonl` 11MB、FTS 库 44MB、快照 27MB、原文 1.9MB。**该量级本地存储完全没问题**，SQLite FTS5 是正式全文索引。

### 分规模判断

| chunk 规模 | 本地文件方案 | 风险 |
| --- | --- | --- |
| 1 万级（当前） | FTS5 + 空向量 | 无 |
| 10 万级 | FTS5 可用；若上向量，单文件矩阵 + 暴力算距离开始吃内存 | 可用，需改增量构建 |
| 100 万级 | 单文件矩阵达数十 GB、查询 O(N) 扫描、全量重嵌耗时长 | **必须换 ANN 索引/向量库** |
| 100 万以上 | 全量重建不可行 | 向量库 + 增量 upsert + 分片 |

### 三条演进原则

1. **抽象检索接口**：保持 `chunk_id`、metadata 与 evidence 契约不变，仅替换 F04 内部实现为「FTS5 + 向量库」混合检索。因 F05 融合层已在等 F04 向量模式，换 Qdrant/Milvus/pgvector 属 **F04 内部改动**，不波及 F02/F05/F06。
2. **切分方案一次做对**：每改一次切法 = 全量重嵌 + 重建索引 + 重跑评测，代价最高。大规模前先定：结构化切分（按事件卡/章节）、元数据标注（朝代、事件类型、实体）、去重。现状为 800 字符 / 80 重叠 / 按句子边界（`data/index/chunking.py`）。
3. **评测兜底**：RAGv4 已暴露检索质量问题（F04 长改写 AND 失效、`event_type` 筛选原文损耗、F02 朝代子串误判拒答），规模放大会加剧。换向量/加重排前先跑基线，否则无法区分"规模退化"与"方案本身问题"。

### 一句话

先抽象 F04 检索接口、定死切分与元数据方案，**不必急着上向量库**；到 10 万级再平滑替换，风险可控。

## 六、Q4：接入飞书要等 Agent 建好，而 Agent 只是「RAG + 大模型 API」，会有影响吗？

### 结论

做「问答机器人」够用；做「能改预约时间的助手」不够用。且飞书接入与 Agent 成熟度**没有强依赖，不必串行等待**。

### 够用的部分

RAG 的 F02→F06 本质已是「RAG + LLM」的 Agent 雏形（实体识别 → 检索 → 融合 → 生成），多轮问答（`QueryRequest.history` 上限 4 轮）已可运行。飞书 P0/P1 只需薄适配层：收消息 → 调 RAG → 回卡片，不必等 Agent 完善。

### 不够用的三个坑

1. **没有工具调用就没有"动作"**：纯文本进出的「RAG + LLM」无法执行"改预约时间"。触发机制需要工具注册、持久化任务、幂等与审计，RAG 里没有也不应有，必须由 Agent 侧实现。
2. **会重复实现两套意图层**：RAG 内部 F02 已做意图判定/实体识别/查询改写；若 Agent 再用 prompt 自行判断检索，会出现两套意图逻辑。应明确：Agent 负责对话路由与动作，**知识问题一律转发 RAG**，由 F02–F06 生成带引用的答案。
3. **双 LLM 调用翻倍成本与延迟**：Agent 若自行生成回答，而 RAG 的 F06 也生成一次，单问两次 LLM。要么由 RAG 生成、Agent 仅转达（推荐，保留引用/面板/拒答），要么 RAG 只做检索、Agent 生成（需为 RAG 新增"仅检索"模式，属额外开发）。

### 两个现实前提

- **LLM 密钥尚未配置**：`LLM_BASE_URL`/`LLM_API_KEY` 未配时 F06 使用离线摘要回答器（`scripts/run_server.py` 启动提示），向量亦为占位。接入飞书前必须先接通真实模型，否则用户拿到的是摘要拼接而非真回答。
- **会话状态必须由 Agent 持有**：RAG 只按客户端传入的 `history` 裁剪，自身不存储会话。飞书多轮、群聊多用户隔离、跨天改期任务的重启恢复，都需 Agent 侧落库。

### 建议推进方式

飞书通道（应用凭证、事件订阅、卡片渲染、身份映射）与 Agent 能力并行推进：先做 P0/P1 问答闭环，同时建设 Agent 工具层（5–6 个只读工具 + 预约/提醒写操作）。真正阻塞上线的是 LLM 密钥与会话/任务持久化，而非"Agent 是否构建完成"。

## 七、Q5：既然角色收敛，旧知识库系统里的智能问答页面是不是要删掉？

### 结论

**需要取消它作为用户入口的身份，但不必马上物理删除。** 删除是最后一步，不是第一步。

### 事实依据（影响面很小）

- 页面名为「历史问答助手」，注册于 `frontend/src/router/module/base-routes.ts:44`（路径 `/knowledge/inference`，`requireAuth: true`）。
- 全仓库**只有它自身**调用旧问答接口：`frontend/src/views/inference/index.vue`（第 836 行调 `/api/ai/inference/stream`，另有 `/api/ai/inference`）。
- 因此删除该页不会牵连其他页面。

### 为什么不立刻删

1. **旧问答是唯一的答案质量对照基线**。RAGv4 评测已暴露问题（F02 朝代子串误判导致拒答、F04 长改写 AND 失效、应拒答缺口）。新问答上线初期需要"同题双答对比"来验证 RAG 是否真的更好，删掉就没有参照物。
2. **需限定删除范围**。旧链路的实体识别与规则推理（`backend/inference/`、`backend/rules/`）可能被其他功能共用，删前须确认调用方，**只删"问答页 + 问答入口"，不要连推理模块一起删**。

### 推荐执行顺序

```text
先上线新入口（飞书/Hermes）→ 再摘掉旧入口（菜单/路由）→ 观察一段时间 → 最后删页面与后端接口
```

顺序不可颠倒：飞书未上线就删页面，会造成"用户没有任何问答入口"的功能真空。

### 三种处理方案

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| A 直接删 | 删页面 + 路由 + `/api/ai/inference` | 新入口已稳定运行较久，不再需要对照 |
| B 摘入口、保留代码（推荐） | 从菜单/路由移除或移入"已归档"，后端接口保留 | 过渡期，保留对照能力 |
| C 换数据源 | 保留页面外壳，接口从旧推理切到 RAG `/api/query` | 仍想要一个 Web 备用入口 |

## 八、Q6：「旧系统降级为管理后台」是什么意思？是变成纯后端吗？运行环境不同怎么办？

### 「管理后台」的含义

**"降级"改的是"服务对象"，不是"系统形态"。** 旧系统仍是完整的前端页面 + 后端服务，只是从"面向普通用户的问答与图谱展示"变为"面向管理员的数据维护工具"（节点增删改查、质量工作台、审核、触发抽取）。

**不是**只保留后端 API。是否保留旧前端取决于管理动作的轻重：

| 形态 | 内容 | 适用判断 |
| --- | --- | --- |
| A（推荐）保留旧前端 + 旧后端 | 完整管理台 | 图谱可视化、表单编辑、批量审核等重交互功能重写成本高 |
| B 只保留旧后端 API | 管理动作交给新平台或纯接口调用 | 仅当管理动作很简单（如仅做数据修补、无需看图） |

判断标准：**管理功能是否需要"人看图、点节点、填表单"**。需要则保留前端（形态 A）；纯批量数据修补才考虑形态 B。

### 运行环境不同如何解决

核心原则：**不统一运行环境，只统一"数据边界"与"通信方式"。**

1. **进程隔离**：两套各自独立环境（旧：Python 3.8 + Flask + Neo4j；RAG：Python 3.11 + FastAPI），各自 venv/conda 或 Docker 镜像、各自端口，**互不 import 代码**，版本差异因此不冲突。
2. **通信只走 HTTP/JSON**：不共享进程，不共享 ORM 与模型代码。
3. **数据单向流动（关键）**：旧库（SQLite/Neo4j）是权威数据源；RAG 的 `data/snapshot`、`data/index` 是离线派生的只读制品（F09/F11 构建）。RAG 在线运行时不连旧库，环境差异被这条单向数据流消解。
4. **优化常驻成本**：旧系统需常驻 Neo4j + SQLite，仅为问答或 Agent 工具而 7×24 运行并不划算。建议**在线只跑 RAG**，旧系统（含 Neo4j）仅在人工维护时启动；Agent 所需只读查询由 RAG 直接在快照上提供（`entities.json`、`relations.json`、`event_cards.json` 已在用）。
5. **入口统一**：用 Nginx 按路径分流（管理台 → 旧服务，问答/Agent → RAG/Hermes），对外只暴露一个域名。

### 安全提示

旧后端只读接口**目前无后端鉴权**（`backend/app.py` 未发现 `login_required`/JWT 校验，仅前端路由 `requireAuth` 守卫）。这使"给 Agent 调用"技术上省事，但**必须依赖内网隔离**，不可暴露公网。

## 九、Q7：「把旧后端只读接口收编成工具」是指直接拿旧页面模块来用吗？

### 结论

**收编的是"接口与数据能力"，不是"页面"。** 对话形态里没有"页面"这一概念。

### 三个层次的复用边界

```text
数据  →  接口(API)  →  页面(UI)
可复用      可复用        不复用
```

旧页面为"鼠标点击、路由跳转、组件状态"而设计，搬到飞书对话里无处安放，也不应搬运。

### "页面之间的关联性"如何解决

**不需要"解决"，而是被 Agent 的会话上下文天然替代。**

| 旧系统（页面形态） | 新形态（对话形态） |
| --- | --- |
| 点击图谱节点 → 路由跳转到实体详情页 | Agent 记住当前话题，直接调 `get_entity_detail` 回答 |
| 页面间共享的筛选条件（朝代、类型） | 用户对话中说"唐朝的"，或存入 Agent 的 session state |
| 页面 A 选中实体 → 页面 B 展示其关系 | 同一会话连续追问，上下文连续 |

原来靠"页面跳转 + 全局状态"承载的关联性，改由 **Agent 会话状态**承载——这正是需要新增会话持久化的原因（行动项 A6）。

### "页面和模型如何匹配"：工具的"函数签名"要与大模型的调用能力对齐

1. **工具 schema 化，数量克制**：每个工具有名称、描述、参数、返回值；参数尽量枚举化（朝代、事件类型取自 `dicts.json` 词典）。工具总数控制在 5–6 个，过多会降低模型选择准确率。
2. **返回值要"模型友好"而非"页面友好"**：旧接口返回的是给页面渲染的信封，如 `/api/node/detail` 返回 `{"code":200,"msg":"success","data":...}`（含布局、坐标等字段）。直接喂给大模型既费 token 又难理解，**必须加适配层**裁剪为规范化摘要（实体概要、三元组列表、事件要点）。这才是"收编工具"真正的工作量，而非"换个 URL 调用"。
3. **前提是模型支持 function calling / tool use**：不支持就只能退化为"prompt 描述工具 + 解析输出"，不稳定，属选型必查项。
4. **工具返回要带来源/引用**：沿用 RAG 的 evidence/citation 机制，飞书卡片才能展示依据。

### 工具设计样例

| 工具 | 入参 | 出参（模型友好） | 可复用来源 |
| --- | --- | --- | --- |
| `search_war_knowledge` | question, dynasty?, event_type? | answer_md + citations | RAG `/api/query` |
| `get_entity_detail` | name 或 entity_id, type? | 实体概要文本 + 关键属性 | 快照 `entities.json` ／ 旧 `/api/node/detail` |
| `get_event_relations` | event_name, relation_type? | 关系三元组文字列表 | 快照 `relations.json` ／ 旧 `/api/graph/*` |
| `list_events` | dynasty?, event_type?, limit? | 事件列表（名称 + 时间 + 类型） | 快照 `event_cards.json` ／ 旧 `/api/node/by_type` |
| `get_timeline` | 实体名或朝代 | 按时间排序的事件序列 | 快照 ／ 旧 `/api/timeline/events` |
| `get_place` | place_name | 古今地名 + 坐标或文字位置 | 快照 ／ 旧 `/api/map/events` |

每个工具有两条实现路径：

- **路径一（推荐）**：只读工具**直接建在 RAG 快照上**——快照已含实体、关系、事件卡，加一层薄查询即可，**不依赖旧服务常驻**，相当于把旧后端的读能力在 RAG 内重建。
- **路径二**：**在线调旧后端 HTTP 接口**——开发最省，但要求旧后端与 Neo4j 常驻、接口无鉴权需内网隔离，且需额外做"页面响应 → 模型响应"的适配层。

两者可混用：先用路径一覆盖高频工具，个别冷门查询再走路径二。

## 十、Q8：页面数据已从全量收敛为只返回 200 个节点，模块化后如何保证飞书回答的"模型思考时间"？

### 前提纠正：200 是"看图护栏"，不是"工具上限"

| 对比项 | 旧页面（ECharts） | 模型 / 工具 |
| --- | --- | --- |
| 约束来源 | 渲染性能与网络体积 | token 预算与注意力 |
| 200 条关系三元组 | 刚好够画一张不卡的图 | **灾难级体量**：序列化后数千至上万 token，首 token 延迟、成本、准确率一起恶化 |
| 收敛方式 | 全量截断（`LIMIT 200`） | 需要"聚合 + top-K + 可追问" |

结论：**不能把"200 条"直接搬成工具的返回上限**，否则"页面卡顿"会变成"回答又慢又贵又答不准"。

### 工具侧收敛策略

1. **聚合摘要优先于原始列表**：默认返回"共 N 条 + 分布（按朝代/类型）+ 最相关 5 条"，给模型"全局画像 + 样例"。
2. **参数化分页**：`limit`/`offset` 由模型按需请求，默认取小（5–10），需要更多再追问一轮。
3. **字段裁剪**：只回名称、类型、时间、关系类型；剥掉坐标、布局、样式字段（页面信封 `{"code","msg","data"}` 不可直接喂模型）。
4. **长列表转"可继续追问"**：卡片给按钮/提示（"按朝代筛选""只看人物"），把体量分摊到后续轮次。

### 延迟构成与分层对策

一次飞书问答延迟 ≈ 飞书消息往返 + 意图路由（1 次 LLM）+ 工具执行 + 生成（1 次 LLM）。工具执行在 RAG 里是毫秒级（内存图谱 + 本地 FTS5），**大头在 LLM 生成**。

| 对策 | 具体做法 | 效果 |
| --- | --- | --- |
| 减少 LLM 往返轮次 | 知识问题**整包交给 RAG 一次完成**（F02→F06 内部串行、对外一次调用一次生成），不让 Agent 走"想→调工具→再想→再生成"多轮链 | 直接砍 1–2 次 LLM 往返，最有效 |
| 并行工具调用 | 多维度查询并发发出，不串行等待 | 压缩多工具场景总时长 |
| 命中缓存 | 回答缓存（改写问题 + 历史，TTL 3600s）命中走 `cache_hit`，**不调用 LLM** | 热点问题延迟接近零 |
| 收紧超时与重试 | 当前超时 60s、重试 2 次，最坏约 3×60 秒，聊天场景不可接受；对话通道建议 15–25s、重试 0–1，超时即降级（F06 已有离线摘要回答器） | 封住长尾 |
| 感知延迟可视化 | 飞书卡片"先发送、后更新"：先回"正在查询…"，完成后更新同一张卡片 | 等待可感知，体感改善 |
| 回调必须秒级应答 | 收到消息立即 ACK，异步处理完再主动发消息/更新卡片；**绝不把 LLM 调用同步阻塞在回调里** | 避免重试、重复触发与重复计费 |
| 模型分工 | 小模型做意图路由与工具选择，大模型只做最终生成；或让 RAG 生成、Agent 不生成 | 省一次 LLM 调用 |
| 限流改维度 | 由按 IP（30 次/分）改为按用户配额 | 防单用户刷爆并发拖慢所有人 |

**一句话**：保证"思考时间"的办法不是让模型想得更快，而是让它少想几轮、能缓存的先缓存、把等待变得可见。

## 十一、Q9：这些页面功能会在飞书上体现吗？如果不能，旧系统的价值体现在哪里？

### 三类功能，结论不同

| 类别 | 代表功能 | 飞书能否体现 |
| --- | --- | --- |
| 可直接对话化（读） | 实体详情、关系查询、时间线、地点、全局搜索 | **能**：工具 + 卡片 |
| 需降级体现 | 图谱可视化（ECharts 子图）、历史地图 | **部分**：服务端出静态图 / 地图卡片 / 文字列表（RAG panel 已有该降级逻辑） |
| 不适合 IM（写与批量） | 节点增删改、表单编辑、批量审核、质量工作台、数据修复与节点合并、抽取任务触发、可视化编辑 | **不能，也不该**：属"鼠标 + 大屏 + 表单"的操作形态 |

### 旧系统的价值

因果前提：**RAG 的全部数据都来自旧库**（经 F09 导出快照、F11 建索引）。

- **飞书体现"知识的消费面"**：问答、查询、展示，面向用户。
- **旧系统体现"知识的生产与治理面"**：数据从哪来、质量谁保证、错了在哪改，面向管理员。

具体价值有三：

1. **数据源头**：旧库（SQLite/Neo4j）是权威数据源，RAG 只是其只读派生。旧系统停摆，RAG 没有新数据可更新。
2. **质量保障**：数据错误、重复、关系缺失，只能在旧系统的审核/修复/质量工作台处理；IM 无法承载批量审核与节点合并。
3. **演示与讲解场景**：大屏看图、图谱可视化汇报是 IM 替代不了的，这也是建议保留旧前端（形态 A）而非退成纯 API 的理由。

### 关于"不能在飞书体现"的隐含担忧

**"页面功能是否在飞书体现"本身不该是目标。** 飞书的目标是"回答问题"，不是"复刻页面"。200 节点的图谱在飞书上既画不出也不该画——用户要的是"长平之战和哪几场仗有关"，答案是一句话加三五个依据，而非一张 200 节点的图。图谱可视化留在旧系统供管理员与演示使用，正好各归其位。

**一句话**：旧系统从台前退到幕后——用户侧价值下降，生产侧价值反而是 RAG 的前提；飞书侧要的不是页面，而是"结论 + 依据 + 可追问"。

## 十二、Q10：整体理解确认——旧库留在 Web、RAG 在飞书、agent 去旧知识库找答案，对吗？

### 结论

基本正确，有三处需修正。

### 成立的部分

- **旧系统保留在 Web**：承担知识生产与治理，兼作演示看图。
- **RAG 主要面向飞书**：飞书是用户侧主要入口。
- **用户在飞书提问、agent 去知识库取数**：成立。

### 需修正的三处

1. **"旧知识库不在飞书呈现" → 准确说是"旧知识库的*页面*不在飞书呈现"**。实体信息、关系、时间线、地点等数据会以"工具结果 + 卡片"形式出现；不出现的是页面形态（表单、图谱画布、批量审核表）。飞书答案的数据来源正是旧知识库。
2. **agent 调用的是"数据/接口"，不是"页面模块"**。页面（Vue 组件、ECharts、路由）为鼠标操作而设计，agent 既无法也不应调用。可被调用的是三类，返回的全是数据：

| 被调用的东西 | 例子 | 返回 |
| --- | --- | --- |
| RAG 问答接口 | `POST /api/query` | 回答正文 + 引用 + panel 数据 |
| 建在 RAG 快照上的只读工具 | 实体详情、关系、时间线、地点 | 结构化数据 |
| （可选）旧后端只读 HTTP 接口 | `/api/node/detail`、`/api/graph/*` | 结构化数据 |

组装成卡片的是 Hermes；页面渲染永远只发生在 Web 端。

3. **"RAG(agent)" 混淆了两个概念**。RAG 是**一个工具**，不是 agent。正确关系：Hermes = agent（意图路由、会话、触发器、动作），RAG = agent 手中的"知识问答"工具。

### 修正后的表述

> 旧知识库继续在 Web 端作为生产/治理后台；飞书侧由 Hermes（agent）接待用户，它把知识问题交给 RAG 引擎、把结构化查询交给只读数据工具，再把返回的数据组装成卡片；所有"页面"只留在 Web，飞书里出现的只是**回答和数据**。

### 交互映射

| 用户在飞书问 | 谁处理 | 返回什么 |
| --- | --- | --- |
| "赤壁之战主帅是谁" | Hermes → RAG `/api/query` | 回答 + 引用 + 面板数据 |
| "长平之战和哪几场仗有关" | Hermes → 只读工具（快照 relations） | 关系列表卡片 |
| "看看唐朝战争图谱" | 不做交互式图；服务端出静态图或文字列表 | 图片卡片 / 列表 |
| "改一下这条记录时间 / 批量审核" | 不在飞书做，引导到 Web 管理台 | 提示 + 链接 |

### 设计后果（需提前知晓）

若"调用旧知识库"指**在线调旧后端接口**，则旧后端 + Neo4j 必须 7×24 常驻，与"在线只跑 RAG、旧系统按需启动"的建议冲突。推荐取舍：**高频只读工具建在 RAG 快照上**（快照已含实体、关系、事件卡，不依赖旧服务常驻），旧后端接口仅作补充。

**一句话总结（第四轮）**：旧库页面留在 Web、飞书侧由 Hermes 接待、数据来自旧库——方向正确；关键修正是把"调页面"改成"调数据接口"，并认清 RAG 是工具、Hermes 才是 agent。

## 十三、Q11：整体链路理解确认——旧知识库是 agent 的"离线构建"、agent 使用时是"在线构建"，对吗？

### 结论

方向正确，但有两处用词会误导后续实现，应改为：

> 旧知识库是 agent 知识的**源头与治理面**；RAG 的快照 + 索引才是 agent 的**离线构建产物**；agent 答问时走的是**在线服务（检索 + 生成）**，不是在线构建。

### 两处需要拧一下

1. **"旧知识库 = 离线构建" → 它是离线构建的*输入*，不是产物**。被构建出来的是 `data/snapshot/<版本>` + `data/index/<版本>`（只读、带版本号）。旧知识库自身也是在线系统——管理后台需要有人在线维护数据，它承担的角色是"生产 + 治理"，不是"构建产物"。
2. **"使用时 = 在线构建" → 在线是*检索 + 生成*，不是构建**。构建一次、服务多次。若每次提问都重建索引或实时跑 LLM 抽取，会又慢又贵；F09/F11 做成离线脚本正是为避免这一点。数据更新时才重新构建，然后做一次版本切换（服务指向新快照/索引），不是每次问答重建。

### 完整链路

```text
【生产/治理层｜在线运行，有人参与】
   管理后台(Web) ◄──► 旧库 SQLite/Neo4j ── 权威数据源，可增删改查
                          │
                          │  离线构建（数据更新时按需触发，不是每次问答）
                          │  F09 导出治理快照 → F11 切分建索引
                          ▼
【RAG 只读知识制品｜离线产物，带版本】
   data/snapshot/<v>  +  data/index/<v>
                          │
                          │  在线服务（每次问答都读它，不重建）
                          ▼
【服务层｜在线】
   RAG 引擎 F02–F06  →  Hermes(agent)  →  飞书
```

### 三个角色的分工

| 角色 | 谁承担 | 做什么 | 频率 |
| --- | --- | --- | --- |
| 生产与治理 | 旧库 + 管理后台 | 数据增删改查、审核、修复 | 人工随时 |
| 离线构建 | 旧库 + F09/F11 | 导出治理快照、切分建索引 | 数据变更时按需 |
| 在线服务 | RAG 引擎 | 检索 + 生成回答 | 每次用户提问 |

### 为什么这个区分不是抠字眼

- **性能**：在线不重建，响应是"毫秒级检索 + LLM 生成"；若误解为"在线构建"，延迟模型就完全错了。
- **成本**：LLM 只用于**生成**；构建阶段的抽取（`entity-event-relation`）是另算的一次性成本。混淆会导致成本估算错误。
- **部署**：数据制品可按版本发布与回滚（`manifest.json` 的 `source_snapshot` 一致性校验，`server/runtime.py` 启动时校验）。

### 一个例外

若选"agent 在线调旧后端接口"（路线 B），旧库就**同时**是离线构建的输入**和**在线数据源，且必须 7×24 常驻——"旧库只是离线输入"不再成立。这也是推荐路线 A（只读工具建在 RAG 快照上）的原因：在线只有 RAG 一条链路，上述"离线构建 / 在线服务"的分工才完整成立。

**一句话总结（第五轮）**：旧知识库 = 源头与治理面；RAG 的快照 + 索引 = 离线构建产物；agent 答问 = 在线服务。把"在线构建"改成"在线服务"，模型即准确。

### 待决项（需拍板）

1. **Hermes 的定义与能力边界**：是否已有飞书自建应用？消息收发、定时、日程、卡片是现成还是需自建？
2. **最终用户是谁**：公众消费者（终态为微信小程序，重：备案/审核/合规）还是企业内部/场馆/团体（飞书即可）。
3. **"预约"业务的落点**：改期事件来自用户对话还是业务系统 webhook。
4. **部署网络**：Hermes 与 RAG 是否同内网即可；RAG 是否允许 Hermes 之外访问。
5. **Web 问答页保留策略**（建议保留，作为运营/演示通道）。
6. **是否需要卡片流式"打字机"体验**（相对整包回复属二期优化）。
7. **管理台形态选择**：保留旧前端（形态 A，推荐）还是只保留后端 API（形态 B）。
8. **模型能力确认**：拟接入 Hermes 的模型是否支持 tool calling，决定工具层的实现方式。
9. **对话通道延迟目标**：整链路的 SLO（如 P95 ≤ N 秒），据此确定 LLM 超时/重试取值与降级阈值。
10. **是否采用"先发卡片后更新"的进度交互**：影响飞书侧的首响体验与实现复杂度。
11. **只读工具的数据来源**：建在 RAG 快照上（推荐，旧服务不必常驻）还是在线调旧后端接口（要求 Neo4j 常驻）。

### 三句话总结（第二轮）

1. **旧问答页**：先摘入口、后删页面，中间保留作对照基线；只删问答页，不连推理模块一起删。
2. **"降级为管理后台"**：改的是服务对象而非系统形态，旧前端建议保留；两套运行时靠「进程隔离 + HTTP 通信 + 数据单向离线流动」共存，在线只跑 RAG、旧系统按需启动。
3. **收编工具**：复用接口与数据、不复用页面；页面间关联性由 Agent 会话上下文接替；真正工作量是把"页面友好"响应适配成"模型友好"的工具签名。

### 三句话总结（第三轮）

1. **200 是看图护栏**：图谱接口的 `LIMIT 200` 服务于渲染性能，对模型是灾难级体量；工具必须另设"聚合摘要 + top-K + 字段裁剪"的收敛策略。
2. **延迟靠少调 LLM 与可见进度**：知识问题整包交给 RAG 一次完成、命中缓存、收紧超时重试、回调秒级 ACK 后异步处理、卡片先发后更新——而不是指望模型想得更快。
3. **旧系统退到幕后而非被淘汰**：飞书承载"知识的消费面"，旧系统承载"数据源头 + 质量治理 + 演示看图"；页面功能能否在飞书体现不该是目标。
