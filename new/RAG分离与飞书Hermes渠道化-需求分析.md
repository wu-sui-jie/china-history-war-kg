## 一、需求背景与目标

### 1.1 原始想法

1. 把 `RAG/` 从整个项目中**分离**出来，作为可独立部署的问答能力。
2. 普通用户不会在电脑上打开网页程序，而是用**手机 / 微信小程序 / IM** 这类入口，希望改成
   **Hermes + 飞书**的方式，降低使用门槛。
3. 需要一套**触发机制**：例如用户预约时间发生变更后，由 Hermes 修改时间（提醒/日程）等。

### 1.2 要达成的目标（可验收表述）

| 编号 | 目标 | 验收口径 |
| --- | --- | --- |
| R1 | RAG 可独立部署，不再依赖旧项目目录结构 | 拷贝 RAG 代码 + 数据制品到独立机器即可启动问答 |
| R2 | 用户通过飞书对话即可提问并获得带引用的回答 | 单聊/群聊 @机器人 提问，收到回答卡片 |
| R3 | 回答中的引用与知识面板在飞书内可用 | 引用可查看、实体/时间线有呈现、图谱有图片或文字降级，无空白 |
| R4 | 具备触发机制：预约时间变更后自动改期/重排提醒 | 改期事件（对话或 webhook）触发后，提醒按新时间生效 |
| R5 | 现有 Web 问答页保留，作为运营/演示通道 | Web 通道功能不回退 |

## 二、现状盘点

整个工程实际是「一条知识生产流水线 + 面向不同人群的三个产品面」：

| 模块 | 角色 | 使用者 | 形态 |
| --- | --- | --- | --- |
| `../entity-event-relation/` | 数据生产：LLM 三轮抽取，从战争史原文抽实体/事件/关系，产出图谱数据 | 开发者（离线） | Python 批处理 + 缓存 + P/R/F1 评测 |
| `../backend/`、`../frontend/` | 旧知识库系统：SQLite + Neo4j 双库，图谱可视化、节点 CRUD、质量工作台、旧问答 `/api/ai/inference` | 管理员/编辑 | Flask + Vue3 Web 后台 |
| `RAG/` | 新一代智能问答引擎：图谱 + 文本双通道 RAG，自包含 | 最终用户 | FastAPI + SSE + Vue3 SPA |

数据流：`entity-event-relation` 产出原文数据 → 旧库 →（F09 导出）→ `RAG/data/snapshot/` + `RAG/data/index/` → 在线问答。

### 2.1 RAG 的分离度评估（结论：天生可拆）

- `README.md` 明确：RAG 为**独立仓库**，运行时不依赖旧后端、旧前端、Neo4j 是否启动，只读取自身目录下的治理快照与索引。
- 唯一耦合点是**离线导出**：`scripts/export_snapshot.py` 通过 `.env` 的 `LEGACY_SQLITE_PATH` / `LEGACY_RAW_TEXTS`
  一次性只读旧 SQLite 与原文（默认值见 `config/defaults.py`）。导出完成后，在线服务不再访问旧项目。
- 因此本需求不需要"解耦重构"，主要是**接口形态、鉴权会话、输出适配、部署打包**四件事。

### 2.2 在线面现状（决定改造范围）

**对外 API（`server/api.py`）**

| 接口 | 说明 |
| --- | --- |
| `POST /api/query` | SSE 流式问答（F02→F03/F04→F05→F06） |
| `GET /api/health` | 健康检查（版本、向量/LLM 可用性） |
| `GET /api/dicts` | 朝代/战争类型筛选词典（F01 下拉数据源） |

**SSE 事件顺序（`server/sse.py`）**

```text
session_start → status → entities → status(graph_search) → graph_results
→ status(text_search) → text_results → status(fusion) → fusion
→ status(generating) → answer(增量) → citations → panel → done
```

**单次回答产出三类数据（统一定义见 `contracts/` 与 `docs/data-contract.md`）**

1. `answer`：Markdown 正文（带引用编号）
2. `citations`：引用列表（来源、原文片段、冲突标记）
3. `panel`：结构化知识面板 JSON —— 实体卡、图谱子图、时间线、地图点（无坐标自动降级为地点列表）

**前端（RAGv3）**只是上述数据的渲染器：`ChatPane`、`SubGraphView`（echarts）、`TimelineView`、
`PlacesView`、`EntityCardsView`、`EvidenceView`，并已做窄屏抽屉降级。

**数据规模**：快照 JSON 约 27MB、索引约 54MB（FTS5 库）；内存图谱 + FTS5 一次加载即可服务。
回答有磁盘缓存（按改写后问题做 key，TTL 3600s），高频问题不重复消耗 LLM token。

> 关键判断：**回答本质是「Markdown 文本 + 结构化 panel 数据」，没有任何浏览器独占能力**，
> 天生适合平移为 IM 卡片消息。改造难点不在算法链路，而在把 SSE 流与 panel 富展示翻译成聊天消息。

## 三、目标形态：拆成三层边界

原始想法里混在一起的三件事（拆 RAG、用户走手机、Hermes+飞书+触发）实际是三个不同边界，拆开即可落地：

```text
┌─────────────────────────────────────────────────────────────┐
│ 业务层（预约/提醒/日历等结构化业务数据）                        │
│ 预约系统 ──改期事件──▶ Hermes 触发器（webhook / 定时 / 意图）    │
└───────────────┬─────────────────────────────────────────────┘
                │ 按意图分流
┌───────────────▼─────────────────────────────────────────────┐
│ 渠道编排层 = Hermes（飞书机器人网关 + 会话 + 技能路由）          │
│  • 接收飞书消息（im.message.receive_v1 / @机器人）             │
│  • 触发机制：定时任务 / 业务变更 webhook / 消息事件             │
│  • 调用技能：改期、发提醒、写日历、查知识                        │
└───────┬───────────────────────────────┬─────────────────────┘
        │ 知识类问题走 RAG                │ 结构化动作直接调业务系统
┌───────▼───────────────────────────────┘
│ 引擎层 = RAG（保持现状，HTTP 化）                               │
│ 纯知识问答：Markdown 回答 + 引用 + panel                        │
└────────────────────────────────────────────────────────────────┘
```

边界原则：

- **引擎层（RAG）**：只回答知识问题，无状态、不接触预约等写操作。
- **编排层（Hermes）**：用户（飞书）与引擎之间的翻译官，也是所有"动作"和"触发"的归属地。
- **业务层（预约系统）**：数据归谁管谁负责，通过事件把"已改期"通知 Hermes。

> 「用户预约时间改变后 Hermes 修改时间」——改的是**结构化预约/提醒数据，不是知识库**，
> 因此天然属于编排层 + 业务层。把它做进 RAG 是职责错位；让 RAG 专注只读知识问答，
> Hermes 专注动作与触发，这个边界本身就是最好的架构。

## 四、待确认问题（会改变结论，需先拍板）

1. **Hermes 的定义**：本方案按「飞书机器人 + 意图识别 + 技能/定时/卡片能力的编排网关」假设。
   它是否已有飞书自建应用？消息收发、定时、日程能力是现成还是需从零搭建？
2. **最终用户是谁**：面向**公众消费者** → 微信小程序是终态（重：备案/审核/内容安全）；
   面向**企业内部/场馆工作人员/受邀团体** → 飞书即可，不必上小程序。
3. **"预约"业务落点**：改期事件从哪发出——用户在飞书对话里说，还是独立预约系统的 webhook？
   这决定 R4 的事件源与实现归属。
4. **部署网络**：Hermes 与 RAG 是否同内网即可？RAG 是否允许 Hermes 之外直接访问？
5. **是否保留 Web 问答页**（建议保留，成本为零，作为运营/演示通道）。
6. **是否需要"打字机"流式体验**：影响是否要做飞书卡片流式更新（相对整包回复是二期优化）。

## 五、改造点清单（映射到代码）

### 5.1 引擎层：只新增一个非流式接口（小改动）

`POST /api/query` 是给浏览器流式消费的。Hermes/飞书需要"一次调用取完整结果"。建议新增
非流式 JSON 接口（如 `POST /api/query/json`，或给现有接口加 `stream=false` 参数），
内部复用 `server/sse.py` 的 `run_query` 生成器在服务端聚合，**不改 F02–F06 任何链路**：

```json
{
  "answer_md": "……",
  "citations": [ /* 引用列表 */ ],
  "panel": { /* 实体卡/子图/时间线/地图点 */ },
  "finish_reason": "normal",
  "model_used": "……"
}
```

飞书侧先做整包回复；需要流式体验再走卡片增量更新（当前 F06 增量是模拟切句，真流式需 LLM token 流，另议）。

### 5.2 会话与身份（必须补，工作量中等）

现状：`session_id` 为调用方任意字符串、无鉴权、限流按 IP、`CORS` 全开。对外服务需要：

| 项 | 现状 | 目标 |
| --- | --- | --- |
| 会话标识 | 调用方任意传 | 由 Hermes 生成 = `open_id` + 群/单聊维度 |
| 多轮上下文 | 服务端按 `history_max_turns=4` 裁剪 | 群聊多用户共存时注意上下文隔离 |
| 鉴权 | 无 | RAG 与 Hermes 之间共享密钥/内网；飞书消息验签在 Hermes 层 |
| 限流 | 按 IP（进程内滑窗） | 按用户/会话维度，可通过请求头透传 |

### 5.3 输出翻译（把 Web 渲染换成消息可承载的形态）

| RAG 输出 | Web（现状） | 飞书对话对应 |
| --- | --- | --- |
| `answer` Markdown | MarkdownContent 渲染 | 卡片文本（飞书 md 子集，需白名单收敛） |
| `citations` | 右侧证据卡，可展开原文/跳转 | 回答末尾引用列表；片段放折叠卡片 |
| `panel` 实体卡/证据 | 标签页 + 折叠区 | 折叠卡片 / 交互按钮（"查看详情"再推一条） |
| `panel` 子图（echarts） | 前端绘图、节点可点击追问 | **服务端渲染成图片**（echarts SSR/静态渲染）或降级为分组文字列表 |
| `panel` 时间线 | TimelineView | 文字化时间轴（已有"战国 / 时间不详"分组） |
| `panel` 地图点 | PlacesView 地图/列表降级 | 飞书地图卡片，或复用"无坐标→文字列表"降级 |

要点：子图/地图是 Web 独占最多的部分，**服务端出图为通用解法**；Web 版不删，与飞书通道共存，引擎只有一份。

### 5.4 部署与数据更新（决定"分离"是否彻底）

- `RAG/` 目前是父目录下的**嵌套独立 git 仓库**（`RAG/.git`），建议独立成仓库并作为独立服务部署。
- 部署的关键不是代码而是**数据**：`data/snapshot`、`data/index` 被 `.gitignore` 忽略，原文有版权不进仓。
  正确姿势：内部机跑离线链路（F09 导出治理 + F11 建索引，版本自动对齐）→ 打包数据制品（约 80MB）
  → 拷贝/上传到服务器 → 服务启动加载最新一致版本（版本校验 `server/runtime.py` 已具备）。
- 知识库更新 = 离线重建 + 换版本重启；这是**运维任务**，与用户触发的业务触发器无关，不可混淆。
- 历史战争知识基本不变，无需实时数据同步。

### 5.5 不需要改动

F02 实体识别/消歧、F03 图谱检索、F04 文本检索、F05 融合/冲突/panel 装配、F06 生成与缓存、
F09/F11 离线链路、RAGv4 评测闭环均无需改动。接口适配完成后，可用 `evaluation/` 与
`data/eval/` 题库跑回归，防止适配过程破坏链路。

## 六、渠道选型：飞书 vs 微信小程序

| | 微信小程序 | 飞书（企业自建应用） |
| --- | --- | --- |
| 适合用户 | 外部**公众消费者** | 企业内员工、场馆工作人员、合作方/教育团体 |
| 资质与审核 | 需企业主体认证、服务类目、**每次发版走微信审核** | 企业内部应用免应用市场审核，迭代快 |
| 网络要求 | 服务器**必须公网 HTTPS + 备案域名** | 机器人支持**长连接模式，可不需要公网回调地址**，内网可跑 |
| 聊天式问答 | 需自建聊天 UI，并接内容安全合规 | **消息即交互**：卡片、@机器人、事件订阅、日程都是现成的 |
| 与预约/提醒结合 | 需自建推送（订阅消息） | 飞书自带日程、提醒、卡片回调 |

工程结论：

- 用户是**普通公众** → 微信小程序是终态，但重（备案、审核、合规）。
- 用户是**场馆导览/内部运营/受邀团体** → 飞书几乎零成本。
- 推荐路径：**先飞书 + Hermes 打通"问答 + 触发"闭环，未来若要面向公众，同一 RAG 引擎再挂小程序通道**
  （届时补 HTTPS/域名/审核），引擎层无需二次改动——这正是"引擎层 + 渠道层"分层的价值。

## 七、触发机制设计（以"预约改期"为例）

触发器只有三类，统一落到 Hermes 层的"触发服务"：

| 触发类型 | 例子 | 事件来源 |
| --- | --- | --- |
| 消息事件 | 用户说"把周三的讲解改到周六 10 点" | 飞书 `im.message.receive_v1`，Hermes 意图识别 |
| 定时任务 | 预约前 1 天 / 2 小时发提醒 | Hermes 定时器，提醒任务持久化（SQLite）防重启丢失 |
| 业务变更 webhook | 后台/小程序改了预约，系统主动推"改期事件" | 业务系统回调 → Hermes 接收、验签 |

"预约改期"完整链路（Hermes 主导，RAG 不参与）：

```text
① 用户对话改期 / 业务系统改期 webhook
        ↓
② Hermes 触发服务收到事件（预约单号 + 旧时间 + 新时间）
        ↓
③ Hermes 调用预约系统确认改期（幂等：同一事件重复投递只生效一次）
        ↓
④ Hermes 重算后续提醒任务：
     旧提醒删除或改期 + 新提醒按新时间重排（落库、统一时区、失败重试）
        ↓
⑤ 飞书卡片回执用户："已改到周六 10 点，提前 2 小时提醒你"
        ↓
⑥（可选）用户接着问"周六这场战争是哪一场？"
     → Hermes 按意图把问题路由给 RAG → RAG 回答 → Hermes 转卡片
```

实现要点：

- 提醒/预约任务**持久化**（不能只放内存，服务重启即丢）；
- 改期回调**幂等**（回调可能重试）；
- **审计日志**（谁在何时改了什么）；
- 以上均属 Hermes 侧独立模块，与 RAG 无关。

## 八、分期落地建议

| 阶段 | 内容 | 验收 | 工作量 |
| --- | --- | --- | --- |
| P0 | RAG 增加非流式 JSON 接口；独立部署包（代码 + 数据制品），移出对父目录的只读依赖 | Hermes 一次调用可拿到 answer/citations/panel | 小（约 1 天） |
| P1 | 飞书机器人收文本 → Hermes 调 RAG → 卡片整包回复；@机器人、`open_id` 会话隔离 | 单聊/群聊均可问答 | 小-中 |
| P2 | 输出翻译：引用折叠卡、panel 文字降级、子图服务端出图 | 演示问题卡片不丑、不空白 | 中 |
| P3 | 触发服务：定时提醒 + 预约改期 webhook 处理 + 回执卡片 | 改期后提醒自动重排 | 中 |
| P4 | 选型确认后接入微信小程序通道（复用 P0 接口） | 小程序可问答 | 取决于选型 |

P0–P1 是"把 RAG 换成飞书/Hermes 入口"的最小闭环，完成后即可给用户使用；P3（触发机制）与 P1 不冲突，可并行。

## 九、风险与注意事项

1. **Hermes 定义未定**：若 Hermes 不具备消息收发/定时/卡片能力，P2、P3 的工作量会显著上升（需自建网关与调度）。
2. **飞书 Markdown 子集**：飞书卡片不支持完整 Markdown，F06 输出需做白名单收敛，避免渲染错乱。
3. **图谱/地图可达性**：IM 内无法交互式画图，必须走"服务端出图 + 文字降级"双路径，不能直接搬运 panel。
4. **多用户并发**：内存图谱 + FTS5 单实例可服务；多 worker 会各自加载一份数据，需评估内存，建议限流 + 单实例起步。
5. **数据制品与代码版本对齐**：快照/索引与代码必须同版本发布，`manifest.json` 版本校验已有，发布流程要固定。
6. **版权约束**：原文文本受版权限制，公开渠道仅发布治理后的知识快照，不可暴露原文全量（沿用现有约定）。
7. **写操作边界**：预约/提醒等写操作不要混入 RAG，避免知识引擎被业务状态污染。
